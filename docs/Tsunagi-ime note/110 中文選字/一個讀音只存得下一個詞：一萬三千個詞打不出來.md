# 一個讀音只存得下一個詞：一萬三千個詞打不出來

從 §2.42.1 的第四件（「候選清單列詞，不只單字」）查下去，發現**根因
不在介面層，在資料層**。

### 2.45.1 症狀

打「這段**程式**」出來的是「這段**城市**」。去第 3 格選「程」：

```text
選「程」 → 程市      ← 「市」沒有跟著變「式」
選「式」 → 城式
```

CLAUDE.md 記的「選了『你』，『郝』跟著變『好』」在這裡**沒有發生**。

### 2.45.2 根因：詞表一個鍵只放一個詞

```text
城市 ㄔㄥˊ ㄕˋ
程式 ㄔㄥˊ ㄕˋ      ← 讀音完全相同
```

`build_zh_layout` 的詞表是 `HashMap<按鍵串, 一個詞>`，分數高的勝出
——**「程式」在建表時就被丟掉了**。`word_for()` 的回傳型別也是
`Option<單一個詞>`。所以連動不是壞掉，是**詞層裡根本沒有「程式」
可以連動過去**。

規模：

| | |
|---|---|
| 不同的按鍵串 | 132,050 |
| 有兩個以上的詞 | **10,859（8%）** |
| **被丟掉的詞** | **13,175** |
| 最擠的一個鍵 | `u4g4`（ㄧˋㄕˋ）**14 個詞**：意識／意思／一世／儀式／議事… |

**詞庫裡有一萬三千個詞，使用者永遠打不出來。**

### 2.45.3 做法：版面不動，同段裡塞多個詞

版面上詞的酬載是「blob 裡的一段位元組」，**沒有存長度**——所以同讀音
的詞可以用 `SEP`（``，Unit Separator）接在同一段裡，**二進位格式
完全不用改**，只有 `VERSION` 從 2 跳到 3。

- `ZhDict::word()` 仍回第一個 → **既有呼叫端一個都沒動**
- 新增 `ZhDict::words()` 與 `dict::words_for()` 回全部，best 在前
- `apply_word_context` 改成**挑跟使用者選過的字相容的那一個**，挑不到
  就用第一個（行為等同修前）

選字連動因此只是「多一個過濾條件」，不是新機制：

```rust
// 「城市」與「程式」讀音相同，選了「程」就該挑到「程式」
words_for(keys).find(|w| 字數對得上 && 每個 picked 的格子都吻合)
```

**「別名只填空位」那道保險不再需要**（§2.41.3）：一鍵多詞之後，別名
給最低分排在真詞後面就好。`gp6ai6`（ㄕㄣˊㄇㄛˊ）仍然預設「神魔」，
但「什麼」現在也選得到——比原本「只填空位」更好。

### 2.45.4 代價：量到的全部是零或更好

| | 改前 | 改後 |
|---|---:|---:|
| 切點涵蓋／前 3／第 1 | 570／561／553 | **完全一樣** |
| 文字命中 | 679/720、2.3% | **完全一樣** |
| 測資稽核 | 0 | 0 |
| **改寫「倒數第 3 格以上」** | 0 | **0**（硬指標） |
| `dict_zh.bin` | 3,864,355 B | 3,964,676 B（+98 KB） |
| 私有工作集／行程 | 6.669 MB | 6.467 MB |
| 詞庫載入 | 0 ms | 0 ms |
| 按鍵 p99 | 10.1～10.6 ms | 10.4 ms |

`.bin` 多的 98 KB 是 **mmap 的共用頁**，不是每個行程各付一份。

**`check_rewrite` 這次一定要跑**——`apply_word_context` 是「前面的字
突然改了」那條路的核心（§2.28），改它必須確認「倒數第 3 格以上」還是 0。

### 2.45.5 §2.42.1 第四件的 B 決定不做

原本的第四件包含介面層：候選清單直接列出「程式」讓使用者一次選中。
**A 做完之後不需要了**——只要選對第一個字，整個詞就跟著對，而選第一個
字本來就是既有的逐格選字。B 要動「框能跨格」的模型，工程量大得多，
換來的只是少按一次方向鍵。

使用者裁決：「如果 A 夠準，B 應該就不用了」。

### 2.45.6 已知限制：反向不連動

選第 2 格的「式」不會讓第 1 格變「程」——`pick` 只往後修
（`apply_word_context(&mut slots[idx..])`），那是 §2.28 的既有原則。
要改的話會動到「改寫觸及範圍」那個量過的性質，另案處理。

### 2.45.7 候選清單的第一個要是「現在顯示的字」

A 做完之後使用者馬上發現的下一件事：被修正過的那一格，候選清單順序
不對。

```text
選了「程」之後   #0 text=程（手動選的）  候選 成 程 城 承 …
                 #1 text=式（詞層修的）  候選 是 事 市 世 士 示 式 …
                                                              ↑ 排第 7
```

候選本身是依**字頻**排的，但那一格顯示的未必是字頻第一名。而反白進
選字時停在第 0 個（`select.rs` 的 `cand_idx = 0`），於是**方向鍵一移
就把剛修好的字弄丟**。

規則統一成「**清單的第一個永遠是這一格現在顯示的字**」——把它從原位
搬到最前面，其餘維持字頻順序。這跟 §2.24 給英文段定的「第一個放英文
原文，讓使用者永遠回得來」是同一條，只是推廣到所有語言。

**純顯示層**：預設輸出走的是 `best_char` 與 `apply_word_context`，
不經過 `candidates_for`，所以三支計分器一個數字都沒動（實測確認）。

### 2.45.8 教訓

**先問「資料在不在」，再問「介面出不出得來」。**§2.42 把這件事歸類成
介面問題（候選只列單字），照那個方向做的話會去改選字的框模型，而
「程式」在詞層根本不存在，改完仍然選不到。
