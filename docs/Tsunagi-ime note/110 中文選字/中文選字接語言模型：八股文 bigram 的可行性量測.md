# 中文選字接語言模型：八股文 bigram 的可行性量測

> **狀態**：可行性量測完成，實作見 2.56

**起因**：使用者回報「中文自動選出來的字準確率還不滿意」。這一節是
spike 的結果，**還沒有動任何程式**。

### 2.53.1 缺的是哪一塊

現在的選字是「以字為單位、用詞去修正」——同音字靠字頻（已按讀音打折，
§2.16），詞層再回頭修（`apply_word_context`）。**沒有任何一步看前後文**。

「他在／他再」「這份／這分」「要跟／要根」這一類，光看字本身永遠分不開，
因為兩邊的字頻差不多。準確率高的輸入法（微軟新注音、RIME、搜狗）核心都是
n-gram：統計「這個字後面接那個字」出現多少次，選字時算整條路的總分。

§2.15 曾經否決「維特比 DP ＋ 長度先驗」，那是拿**詞頻**猜分詞——單一詞
出現幾次，不含「誰接誰」。n-gram 補的正是後者，**是不同的資料，不是同一
件事再試一次**。

### 2.53.2 資料盤點：兩個候選

| 來源 | 內容 | 授權 | 有沒有 n-gram |
|---|---|---|---|
| libchewing `tsi.csv` | 16 萬條詞＋詞頻＋注音 | LGPL-2.1-or-later | **沒有** |
| RIME 八股文 `zh-hant-t-essay-bgc.gram` | 字級 bigram，10.5 萬條，9.8MB | LGPL-3 | 有 |
| RIME 八股文 `zh-hant-t-essay-bgw.gram` | 詞級 bigram，99.2 萬條，39.5MB | LGPL-3 | 有 |

新酷音**完全沒有「誰接誰」的統計**，它靠詞頻加分詞規則，所以解不了前後文
那一類。它的詞頻是為輸入法調過的（單字沒被語料頻率灌水），那是另一條線，
這次沒量。

八股文的來源作者只說「開放的互聯網語料精煉而成，全程自動處理」，
**沒有交代語料出處**——這是最大的風險，下面量了。

### 2.53.3 `.gram` 檔案格式（實作要照這個做）

自己寫了讀取器驗證，格式完全解出來了。spike 的 Python 版在
`scratchpad/octagram/gram.py`。

**檔案版面**（偏移從 0 起算，小端）：

| 偏移 | 大小 | 內容 |
|---|---|---|
| 0 | 32 | `"Rime::Grammar/1.0"`＋補零 |
| 32 | 4 | checksum（實測是 0，可以不管） |
| 36 | 4 | double array 的**單元數**（不是位元組數） |
| 40 | 4 | 相對指標，指到 double array（相對於偏移 40 本身，實測值 4） |
| 44 | 單元數 × 4 | darts-clone 的 double array 影像 |

**darts-clone 單元解碼**（每個單元 4 位元組的 `u32`）：

```text
has_leaf = (unit >> 8) & 1
label    = unit & 0x800000FF          （葉節點 bit31 = 1，所以跟純位元組比不會誤中）
offset   = (unit >> 10) << ((unit & 0x200) >> 6)
value    = unit & 0x7FFFFFFF
```

查表：`node = 0`，每個位元組做 `node ^= offset(unit) ^ byte`，比對
`label == byte`；走完之後若 `has_leaf` 就到 `node ^ offset(unit)` 取 `value`。

**鍵的編碼不是 UTF-8**，是八股文自己的一套（`gram_encoding.cc`）：

- 碼位 < 0x80：直接一個位元組（0 例外，寫成 `0xE0`）
- **0x4000 ≤ 碼位 < 0xA000**：兩個位元組 `[(u>>8)+0x40, u&0xFF]`；低位元組
  剛好是 0 時寫成 `[0xE1, (u>>8)+0x40]`。**CJK 常用區整段落在這裡**，
  所以絕大多數鍵是「每字兩個位元組」
- 其餘：`[0xE0|n]` 加 n 個 `0x80|七位元` 的續接位元組

**值是 `int(ln(次數) × 10000)`**，還原時除以 10000 得到 `ln(次數)`。
**注意那是次數不是機率**，所以高頻字天生佔便宜，見 §2.53.5。

**兩個實測到的限制**：

1. **沒有單字（unigram），也沒有三字（trigram）**。字級模型裡查 `在`、
   `的`、`將來再` 全部查不到——它就是純粹的兩字組表。所以**沒辦法從檔案
   自己算條件機率**，要正規化只能用我們自己的 `char_freq.txt` 當分母。
2. **鍵沒有詞邊界**。`Lookup(context, word)` 是「先走完 context，再從那個
   節點做前綴搜尋」，所以存的就是字元序列。**這反而是好事**——不必知道
   斷詞位置，拿任意字串去查就行。

### 2.53.4 量測一：同音字挑不挑得對

測法：從 `core/testdata/` 撈出所有連續中文段（1049 段），每個位置取正解
那個字，跟**同讀音的所有競爭者**比排序，看第一名對不對。只算單音字
（避開多音字的讀音歧義）且有競爭者的位置，共 1218 個。

| 排序方式 | 第一名正確 |
|---|---|
| 字頻 × 讀音佔比（現行基準） | 846（69.5%） |
| 純 bigram（字級） | 1028（84.4%） |
| **混合：ln(字頻) + 1.5 × bigram** | **1102（90.5%）** |
| 混合（詞級模型） | 853（70.0%） |

權重掃過 0～5，1.5 最好，0.75～3.0 之間都在 88% 以上，**不敏感**。

**詞級模型（39.5MB）對這件事沒有用**——它的鍵是詞對詞，拿字對字去查
大多落空（涵蓋正解只有 55.9%）。**只要字級那份 9.8MB。**

修好 272 個、弄壞 16 個。弄壞的 16 個裡有 12 個是 `友達`（測資裡的日文
被我的擷取器誤當中文），1 個是 `這裡→這裏`（見 §2.53.6），真正的迴歸
只有 3 個。

**但這個 69.5% 不是引擎的真實準確率**——引擎有詞層，`問題`、`需求`、
`客戶` 這些它本來就對。所以這個數字證明「bigram 有訊號」，不代表「能拿
20 個百分點」。真實的收益看下一項。

### 2.53.5 量測二：拿引擎真正答錯的來測

`check_compose` 現況 **738/790（93%）、錯字率 2.5%**，選字錯 35 句。
把那些句子的期望與實際逐字對齊，取出 40 個真正錯掉的中文位置，問
bigram 分不分得開正解與引擎給的字。

| 算法 | 分得開 |
|---|---|
| 只看左鄰 | 27/35（77%） |
| 只看右鄰 | 25/35（71%） |
| 左右相加（原始次數對數） | 31/39（79%） |
| 左右相加＋扣掉自身字頻 | 32/39（82%） |
| **上面再加異體字正規化** | **33/39（85%）** |

三個結論：

1. **必須看兩邊**。只看左鄰時 `將來再說` 分不開——線索在右邊（`再說`）。
   真正的解碼要在整句上找最佳路徑（維特比），不是逐格挑。
2. **要扣掉自身字頻**。存的是 `ln(次數)` 不是條件機率，`在` 比 `再` 常見
   兩個數量級，所以 `看在` 的次數天生大於 `看再`。改成
   `ln(次數) − ln(該字字頻)`（關聯強度）之後 79% → 82%。
3. **剩下的硬案例集中在「再／在」**（4 個裡有 3 個仍分不開）。那是資料
   稀疏，不是算法問題。

### 2.53.6 最大的坑：異體字，簡繁轉換留下的疤

**`這裡` 在模型裡完全不存在，只有 `這裏`；`因為` 不存在，只有 `因爲`。**
拿 300 個高頻字當左鄰數命中數：

| 我們的寫法 | 命中 | 模型的寫法 | 命中 |
|---|---|---|---|
| 為 | **0** | 爲 | 299 |
| 線 | **0** | 綫 | 250 |
| 裡 | 145 | 裏 | 262 |
| 著 | 232 | 着 | 279 |
| 台 | 210 | 臺 | 258 |

這是簡體語料用 OpenCC 的 `s2t`（不是 `s2twp`）轉過來的痕跡。反過來
`麼`、`說`、`溫`、`顏`、`污` 模型用的是我們這一套，**所以不是整份都要翻，
是一張小表**。

**解法是查表前正規化，輸出的字不動。**只收真正的異體字（同一個詞、不同
字形）七個：`裡→裏、為→爲、著→着、台→臺、線→綫、痴→癡、麽→麼`。
上線／上限那個案例就是 `線` 零命中造成的，加了表就修好。

**用語偏向另外量了 42 組台灣／中國說法**（軟體／軟件、網路／網絡、
影片／視頻……）：字級模型**中國說法贏 25、台灣說法贏 8**。但這件事的
傷害比數字看起來小——輸入法只在**同讀音**的候選之間比較，`軟體` 和
`軟件` 讀音不同，永遠不會競爭。真正會咬到的是異體字那一類，而那張表
修得掉。

**這仍然是要記住的限制**：模型對台灣用語的覆蓋偏弱，不是會給出錯的
台灣用語。

### 2.53.7 效能

| 項目 | 數字 |
|---|---|
| 檔案大小（字級） | 9.8 MB |
| 每次查表（Python 版） | 0.9 μs |

資料結構是唯讀的 mmap 友善版面，跟 `dict_bin` 同性質，**可以直接照
§2.10.5 那條路走**（mmap ＋ 多行程共用頁）。Rust 實作預期快一到兩個
數量級，按鍵延遲那邊應該量不出來，但**要照規矩用 `bench_typing` 驗**。

### 2.53.8 待決事項（要使用者裁決才動手）

1. **要不要走這條路**。收益是「引擎真正的錯有 85% 分得開」，成本是
   多一份 9.8MB 的資料檔、一個 darts-clone 讀取器、選字層改成整句
   維特比。
2. **語料的來歷不明能不能接受**。授權是 LGPL-3 沒問題，但作者沒交代
   語料出處，而且明顯是簡體語料轉過來的。要不要因此改成自己從中文
   維基（CC BY-SA）統計一份？那是另一個量級的工作。
3. **異體字對照表要不要進版控**。它是「為了配合這份語料」而存在的
   補丁，語料換掉就要重做。
4. **選字層要不要改成整句維特比**。日文那邊已經有整套（§2.23），
   中文現在是逐格挑。改了才吃得到「看兩邊」那 6 個百分點。
   **只接選字層就好，切法那半實測沒有用**，見 §2.53.9。
5. **要不要一起試新酷音的詞頻**。它是為輸入法調過的，可能讓 §2.15
   否決掉的「維特比＋長度先驗」復活。這次沒量。

spike 的腳本都在暫存區（`gram.py`、`audit_vocab.py`、`audit_pick.py`、
`audit_real2.py`、`audit_pmi.py`、`audit_variant.py`、`audit_final.py`），
**還沒有收進專案**——要留的話再決定放哪。
