# 中文詞層貪心搶字：尾端重切＋詞完整性閘門

**起因是使用者實測回報**：打「建立」跳出「件立」。這一節記錄病因、
三輪量測，以及使用者提出的兩個判準（收尾偵測、詞完整性）如何把
§2.60 否決掉的方向重新救回可行範圍。

> **已實作**（`compose::recut_tail`）。下面 2.74.1～2.74.10 是實作前的
> 量測紀錄，保留原貌；原設計四道閘門裡的**收尾偵測與固定窗口接進產品碼
> 之後拆掉**（理由見 2.74.11），最後只留「切得更完整才套用」與
> 「只碰最後兩段中文（`RECUT_SPANS`）」兩道，見 2.74.14 結論。

### 2.74.1 病因：跟 §2.60 是同一個，不是新東西

單獨打「建立」完全正確，**加了前文才壞**：

```text
建立        ✓
想建立      ✗ 「想見立」
前建立      ✗ 「前件立」
```

`apply_word_context` 是「由左往右、最長先、命中就跳、不回溯」。
詞庫裡 `想見`、`前件` 都是真詞，左邊那個詞先把「建」搶去當「見」／
「件」，剩下「立」落單只好單獨猜。

**不是引擎不認識「建立」**——詞庫第 50105 行就有。這一點很重要，
它決定了修法不是補詞庫。

### 2.74.2 先確認詞性系統不是答案（使用者問的第一個問題）

使用者問「是不是要導入詞性系統」。**不是**，三個理由由硬到軟：

1. **中文詞庫沒有詞性欄位**。`BPMFMappings.txt` 只有「詞＋注音」兩欄，
   詞性是日文詞典才有的。§2.61.2 已經卡在這裡一次
2. **詞性處理不到現在的錯**。漏斗當時錯的中文句子（`目標試題生`、
   `這段城市的`、`改道下午`）全是同音詞誰常見的問題——「城市」與
   「程式」詞性一樣，分不出來
3. **標註本身會錯**。中文沒有形態變化，詞性要靠上下文猜，等於引進
   第二個猜錯就壞掉的環節去修第一個

### 2.74.3 三輪量測：新工具 `spike_word_lattice`

新增 `core/src/bin/spike_word_lattice.rs`，**逐鍵餵入**（不是一次
餵完整句），同時量正確句數與遠處改寫次數，才比得出打字過程的性質。
基準是 1022 句含中文的測資。

| 做法 | 對的句數 | 遠處改寫 |
|---|---|---|
| 現行（貪心，只看左鄰） | 907 | **238** |
| 全面詞格維特比＋位置凍結 | 909 | 259 |
| ＋收尾偵測（使用者提案一） | 909 | 259 |
| ＋詞完整性閘門（使用者提案二） | **909** | **247** |

**淨收益 +2 句**，跟 §2.60 當初量到的 +3 一致——**獨立複驗了第二次，
不要再拿「換成 lattice」當新點子提**。

參數敏感度：`SINGLE_COST` 從 2 掃到 12 完全不動（+2），`WRANK` 在 3
是峰值、兩側都掉（1→-1、5→-3）。**窄峰不是穩健的收益**，這一點要
記住。

### 2.74.4 使用者提案一：用「音節收尾」判斷打完了沒

使用者的觀察：

> `今天wu` 這就很明顯還沒打完，`今天天` 這種就是有明顯結束的訊號。

**引擎其實已經知道**——打一半的按鍵走英文 passthrough 原樣顯示，
成字了才變成可選字的中文格：

```text
今天      → 「今天」
今天w     → 「今天w」      ← 原封不動，沒猜字
今天wu8   → 「今天wu8」
今天wu84  → 「今天天」     ← 成字了
```

判準因此是「最後一格是不是可選字的中文／日文格」。實測：

| 指標 | 數字 |
|---|---|
| 真正打完時判為收尾 | **902 / 1022（88.3%）** |
| 打字過程中觸發重算的按鍵比例 | **31.3%** |

**兩個數字都是好消息**：訊號真的存在，而且夠嚴——2/3 的時間完全不動，
前文不會閃。漏判的 12% 全是**中文後面接英文詞**（「討論 build」），
英文沒有「音節打完」的概念，判不出來。

這一刻重算的視覺理由很強：畫面本來就要從 `wu84` 變成「天」，
**那一刻本來就在動**，順便修正前文是連貫的。

### 2.74.5 使用者提案二：詞完整性閘門，與第一版判準寫錯

使用者的話：「判斷到使用者打完了重算時，也要檢查詞的完整性才可以做
修正」。

**第一版判準寫錯了**，記下來因為錯得有教育意義：比「落單字數」與
「最長詞長度」，結果**把目標案例也擋掉**——

| 切法 | 形狀 |
|---|---|
| `想見`＋`立` | 一個雙字詞＋一個落單字 |
| `想`＋`建立` | 一個雙字詞＋一個落單字 |

**形狀完全一樣。** 差別在**哪一個字落單**：「想」單獨成詞很常見，
「立」單獨出現在句尾很罕見。改用**落單字的字頻總和**當判準才通過。

教訓：**「更完整」不能只看結構統計量**，要看落單的那個東西合不合理。

閘門的效果：改寫 259 → 247，弄壞的句子 3 → 2，收益維持 +2。

### 2.74.6 使用者提案三：四字窗口——方向對，實測是 5

使用者：「中文的自動重算應該可以控制在四個字之內，超過就凍結，
因為大部分詞不超過四字」。

**詞庫的詞長分布支持這個直覺**：

| 詞長 | 條目數 | 累積 |
|---|---|---|
| 2 字 | 75,727 | 52.1% |
| 3 字 | 34,817 | 76.1% |
| **4 字** | 31,098 | **97.5%** |
| 5 字以上 | 3,581 | 100% |

實測窗口 3～4 是 +1、**5～6 是 +2**，收斂。取 5 —— 四字詞要看得到
左右鄰各一格才判得準。

### 2.74.7 日文不需要這一套

使用者問日文適不適用。**不需要**：日文選字層已經是整句 Viterbi
（§2.23），它本來就在看兩邊。

而且**中文詞層去碰日文格會弄壞它**——spike 中途一度量到「改寫降到
200」，追下去發現是前綴沿用把日文格也一起沿用了，`ございます` 被洗成
`go`、`お願い` 洗成 `one`。修掉之後數字回到 247。

**那個假數字差點被當成結論寫進來**，這是「量到好消息先懷疑自己」的
又一例。

### 2.74.8 遠處改寫的方向：大部分不是中文

把每一次遠處改寫的方向查出來（`DETAIL=1`）：

| 方向 | 次數 |
|---|---|
| 錯 → 對 | 22 |
| 對 → 錯 | 7 |
| **錯 → 還是錯** | **285** |

**大宗是「改了但兩邊都不對」**，而且看內容大部分根本不是中文：
`音楽`→`音`、`何度`→`何`、`落とさ`→`を`——那是日文自己的 Viterbi
在重新理解句子，**基準 238 裡本來就含這些**。

所以中文詞層實際造成的改寫增量比表面的 9 次更小。**跟一個含雜訊的
基準比較，會高估自己的代價**。

還觀察到**同一格來回跳**：`延`→`一`→`延`、`慾`→`預`→`慾`、
`適`→`是`→`適`。最終收斂到對的，但過程中閃爍。這是 lattice 的固有
性質（§2.60.3 已記），閘門壓掉一部分但不是全部。

### 2.74.9 新酷音怎麼做的（使用者要求查證）

> `auto_snapshot_selections`（Windows 版 26.4.1 起預設開）：游標一離開

兩個值得注意的旁證：

### 2.74.10 實作時才發現的第四道閘門：防抖

**三道閘門不夠。** 照 §2.74.3～2.74.6 的設計實作完，漏斗 +1，
但**改寫硬指標 `⚠` 從 1 衝到 9**——那是必須是 0 的指標。

用 `FINDFAR` 把多出來的改寫逐一列出來，病灶一眼就看得出來：

```text
昨天的會議記錄    第30鍵 紀→記   第32鍵 記→紀   第33鍵 紀→記
mail 寄出去了     第42鍵 寄→祭   第43鍵 祭→寄
我會在明天之前    第18鍵 載→在   第19鍵 在→載
```

**同一格來回跳。** 其餘的其實都是變對的（`各`→`個`、`一`→`議`、
`名`→`明`、`器`→`氣`），問題全出在擺盪。

病因是**重切的起點會隨著打字往前移**：尾端那一段連續注音格越來越長，
所以早就定案的格子每一鍵都被重新決定一次，而分數在兩個都合理的候選
之間擺盪（`紀`／`記` 都是真詞、都接得上「會議」）。

修法是**只改最後一個詞涵蓋的那幾格**，前面的詞既然已經成詞就不再翻案：

```rust
let tail = new.last().map(|w| w.chars().count()).unwrap_or(0);
let start = n - tail;   // 只填這裡到尾端
```

這一步是把貪心的優點拿回來一部分——**「命中就跳」天然不回頭**
（§2.60.3），重切放棄整段最佳解，換取不翻案。

| | 漏斗 | `⚠` |
|---|---|---|
| 實作前 | 1279 | 1 |
| 三道閘門 | 1280 | **9** |
| ＋防抖（最終） | **1280** | **1** |

**教訓：離線 spike 量不到這件事。** spike 跑的是自己那份實作，
「起點隨打字前移」是產品碼裡 `compose` 每次從頭算的性質——
**要等接進真正的呼叫路徑才會現形**。

### 2.74.11 接進產品碼之後三個判準全部翻案（同日，使用者實測）

commit 之後使用者馬上打出新的案例：**「我想要**件立**一套標準」**。
追下去發現前一輪的設計有三個地方是錯的，而且**離線 spike 全部量不到**
——它跑的是自己那份實作，這些病因都只在真正的呼叫路徑上才現形。

**① 只填最後一個詞 → 修好的字保不住。**
打完「我想要建立」是對的，再打「一」就變回「件立」。因為重切每次都
從貪心的結果重算，而貪心每一鍵都會把「建立」重新算成「件立」，
只填最後一個詞等於把修正丟掉。**改成整段填回去。**

**② 固定窗口 → 比對的基準不是畫面上的東西。**
6 格時窗口把「我」擠出去，重切只看得到 `想要建立一`——那一段貪心
本來就是對的，閘門判定「不需要修」。可是畫面上的「件立」是**整句**
貪心（`我想`／`要件`／`立`）造成的。**病灶是拿窗口內的貪心當基準，
比對的卻不是實際顯示的結果。** 改成整段重切，範圍改用「最後兩段」
（`RECUT_SPANS`）限制——空格會把句子切成兩段，只做尾端那段碰不到
壞掉的字。

**③ 「只在剛收完一個字時跑」本身就是擺盪的來源。**
這一條最反直覺。判準（§2.74.4）本身很準，但接進產品碼之後：
多打一個還沒成字的按鍵時重切整個不跑，畫面掉回貪心的結果，
下一鍵成字又跑一次——

```text
我會在明天…  打 f（未成字）→ 我會載明天…  再成字 → 我會在明天…
```

`在`↔`載` 每一鍵來回，**一句貢獻 20 次遠處改寫**。

**擺盪的來源是「跑／不跑」交替，不是重算本身。** 拿掉這道閘門、
一律跑之後，`⚠` 從 26 降到 5。**穩定的規則比聰明的規則重要。**

`just_settled` 因此整個移除。§2.74.4 量到的 88.3% 沒有錯，錯的是
「拿它當開關」——那個判準要用的話，該用在**別的地方**（例如決定
要不要送出、要不要學習），不是用來決定重算跑不跑。

**④ 還發現一個閘門太寬鬆。** `寄出去`＋`了`（落單 1、最長 3）被換成
`祭出`＋`去了`（落單 0、最長 2）——落單數確實少了一個，判定「更完整」
就套用，但「祭出去了」是錯的。**長詞是強證據**：詞典收了三字詞
「寄出去」，把它拆成兩個雙字詞需要比「落單少一個」更強的理由。
加上 `nl < ol → false`（不准把長詞拆短）之後 `⚠` 從 5 降到 2。

剩下的 2 次：1 次是日文的（`は`→`ha`，改動前就有，就是基準那個 1），
1 次是 `是`→`適`（變對的）。

### 2.74.12 閘門的最後一關判準用錯了（2026-09-10 實測回報）

使用者實測 §2.60.1 的原始案例——「請務必在期限內完成」仍然打成
**「請勿必再騎現內完成」**，重切沒救到它。

埋 log 一看，**維特比其實算對了**：

```text
貪心  ＝ ["請勿", "必", "再騎", "現", "內", "完成"]
維特比＝ ["請", "務必", "再", "期限", "內", "完成"]   ← 正解
更完整 ＝ false                                     ← 被閘門擋掉
```

兩邊形狀完全一樣（落單 3、最長 2），所以走到最後一關「比落單字的
字頻總和」：

| | 落單字 | 字頻和 |
|---|---|---|
| 貪心 | 必＋現＋內 | **23.57** ← 贏 |
| 維特比 | 請＋再＋內 | 21.72 |

**貪心的落單字剛好都是高頻字**，錯的那個勝出。

**病灶是判準用錯地方。** 「比落單字的字頻」是為「同一個位置該讓誰
落單」設計的（§2.74.5），但這裡兩邊的落單字**根本不是同一批**，
比總和沒有意義。

改成**整條路的 bigram 總分**——同一句話每一對相鄰字都算進去，
衡量「這樣讀通不通」而不是「誰落單比較常見」：

```text
請勿必再騎現內完成 = 34.27
請務必再期限內完成 = 43.66   ← 差 9.4 分
```

修好之後只差 `再`／`在` 一個字，而那是 §2.61.2 補量判定的雙義問題
（靠學習層）。

**代價：改寫硬指標從 2 漲到 10，接受了。** 查過那 10 次的來源：

- **6 次來自同一句**（`這批貨物預計明天到達`），而那句**最終是修對
  的**——打字中途從「慾記名天道」一次跳到正解，修好 3 個字就記 3 次
- 1 次是日文的（改動前就有）
- 其餘零星，多數也是變對

所以**不是擺盪，是一次性的修正**。掃過「要贏 N 分才換」的門檻
（0～8）換不到東西：0 → ⚠10、3 → ⚠11、8 → ⚠6 但漏斗掉 4 分
——門檻只會連正確的修正一起擋掉，所以不加。

**使用者裁決（2026-09-10）：接受這個取捨。**

### 2.74.13 這一節順手回答了 §2.21（反白刪除）的一個待決事項

§2.21.10 記了完整的經過，
這裡只留指路。兩件事：

- **位置式的凍結是病因，不是解法。** §2.21 原本在問「刪除後要凍多遠」
  （只凍前面／前後都凍），而 `RECUT_WINDOW` 被拿掉正是因為那種思路
  「比對的基準不是畫面上的東西」。反白刪除該凍的是**格**，不是位置
- **`recut_span` 裡的 `if !slots[i].picked` 就是現成的機制。** 它的語意是
  「使用者表態過的字不覆蓋」——反白刪除**沒有**另外加旗標，而是靠
  `Pick` 改記位置（§2.21.11 ②）保證修正不會貼到別的格上。段刪除另外
  用了凍結區（`adopt_frozen`），格刪除刻意不凍（§2.21.12）

**反之亦然：日後動 `recut_tail`／`RECUT_SPANS`／`picked` 這一帶，
要順手看一下 §2.21 的結論還站不站得住。** 尤其 `RECUT_SPANS`——
刪除會讓注音段合併（§2.21.11 ①），那是它的正常輸入之一。

### 2.74.14 結論

**已實作**（`compose::recut_tail`），最後只剩**兩道**閘門：

1. **只在切得更完整時才套用**（`more_complete`）——落單字變少或詞變長；
   **不准把長詞拆短**；形狀一樣時比**整句 bigram 總分**（§2.74.12
   把這一關從「落單字的字頻」換掉了）
2. **只碰最後兩段連續中文**（`RECUT_SPANS`）——掃全部段落會讓 `⚠`
   衝到 41，只做尾端一段又漏掉「空格把句子切成兩段」的情況

原設計的另外兩道（收尾偵測、固定窗口）**接進產品碼之後全部拆掉**，
理由見 §2.74.11。

驗收：

| 項目 | 結果 |
