# 同音字排序：字頻沒有「讀音」這個維度

### 症狀

打「第一集」，把游標移到最後一格叫出候選清單，第一名是**「吃」**：

```
吃 及 集 即 極 級 急 擊 疾 吉
```

「吃」有 ㄐㄧˊ 這個讀音（「口吃」），出現在清單裡不算錯，錯的是排第一。

### 根因

那串順序完全等於字頻由高到低，一個不差：

```
吃1329 > 及1089 > 集1010 > 即896 > 極830 > 級779 > 急686 > 擊524 > 疾316 > 吉278
```

`char_freq.txt` 記的是「這個字在語料裡出現幾次」，**沒有讀音這個維度**。
「吃」那 1329 次幾乎全部來自 ㄔ（吃飯），可是排 ㄐㄧˊ 這一格時程式把
整個字的總頻率直接拿來用。

**這不是零星個案**：詞庫裡有 3580 個字是多音字，而字頻最高的那批
（的、不、一、了、來、會、行、長、為）全是多音字，每一個都在污染
它其他讀音的候選清單。`priority.txt` 裡 `ㄉㄧˋ 第 地 的 …` 特地把
「的」壓到第三，其實就是在手工補同一個病。

### 解法：讀音別字頻

`BPMFMappings.txt` 的每個詞條都附了**逐字對齊**的注音，把 `word_freq`
依這個對齊分攤下去，就得到「這個字念這個音時貢獻了多少詞頻」：

```
吃  ㄔ 997‰   ㄐㄧˊ 2‰
行  ㄒㄧㄥˊ 874‰  ㄏㄤˊ 112‰  ㄒㄧㄥˋ 13‰
長  ㄓㄤˇ 733‰  ㄔㄤˊ 264‰
的  ㄉㄜ˙ 890‰  ㄉㄧˋ 88‰  ㄉㄧˊ 21‰
```

**輸出佔比而不是絕對值**，這一點是關鍵。排序是在同一個讀音底下比大小，
若直接用絕對詞頻，同一格裡「有詞條覆蓋的字」（動輒數十萬）會壓死
「沒被覆蓋的罕見字」（退回字頻，只有幾百）——兩種尺度混在一起會製造
新的排序錯誤。用佔比則是**在原本的字頻上打折**：沒被覆蓋的字視為
1000‰，行為完全不變。

實作：`gen_reading_freq` 離線產生 `data/bopomofo/char_freq_by_reading.txt`
（5315 個字、6190 條，109KB），`dict.rs` 載入後把單字候選的分數從
`char_freq` 改成 `char_freq × 佔比`。

**產生的檔不進版控**——它跟 `char_freq.txt`、`word_freq.txt` 一樣是
衍生資料，`data/download.ps1` 的最後一步會產生它。進版控的只有
`priority.txt` 那種「重新下載也生不出來」的人工判斷。

**選離線產生而不是啟動時即時算**：即時算要多掃 14 萬筆詞條，跟「切換
輸入法 0 ms」（§2.10）
和記憶體目標相衝；離線檔還有個好處是人可以直接打開檢視。

### 結果

ㄐㄧˊ 這一格變成 **及 集 即 極 級 急 擊 疾 吉 寂**，「吃」沉到後面。

`check_compose` 沒有任何一項退步：總計 649/720 → 650/720，錯字率
4.7% → 4.6%，注音 95% → 96%，holdout 96% → 100%。

**提升幅度小是預期的**——那份計分器量的是「不動選字鍵直接送出」的
第一名，而那條路多半由詞層級查表決定，本來就繞過了單字排序。這次修的
是**使用者主動叫出候選清單時看到的東西**，計分器照不到那一面。這也是
一個提醒：分數沒動不等於沒有問題，有些缺陷得靠眼睛看。
