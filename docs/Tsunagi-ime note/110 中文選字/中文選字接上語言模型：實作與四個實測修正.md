# 中文選字接上語言模型：實作與四個實測修正

§2.53 是可行性量測，這一節是**實作**。收益、代價、以及過程中被實測
推翻的三個設計，全部記在這裡。

### 2.56.1 結果

| | 改前 | 改後 |
|---|---|---|
| 文字命中（790 句） | 738 | **748** |
| 選字錯 | 35 | **25** |
| 錯字率 | 2.5% | **2.2%** |
| 注音錯字率 | 1.5% | **1.1%** |
| 切點三個數字 | 640／631／623 | **完全不動** |
| 按鍵 p99 | 11.2ms | **10.6ms** |
| 常駐記憶體 | 23MB | **23MB** |

**切點一個數字都沒動**——這是預期內的，語言模型只接在選字層，
不參與切法競爭（§2.53.9 已經量過它對切法是 +0）。

**延遲反而變好**是量測雜訊，不是語言模型讓它變快；重點是**沒有變差**。
記憶體不動則是 mmap 生效的證據：9.8MB 的檔案沒有進私有工作集。

### 2.56.2 資料與版面

`data/bopomofo/zh_bigram.gram`（RIME 八股文 `zh-hant-t-essay-bgc.gram`，
LGPL-3，9.8MB）。**原樣使用、不轉檔**——它本來就是 darts-clone 的唯讀
double array，跟 `dict_bin` 同性質，mmap 直接吃。

讀取器在 `core/src/lm.rs`，版面與鍵編碼的細節見該檔的模組註解（§2.53.3
解出來的那份）。`check_lm` 這支工具**釘住五個 spike 量過的實際數值**
——手寫的位元運算算錯不會當機、只會靜靜給出錯的分數，那種缺陷在計分器
上看起來只是「收益比預期少一點」，極難聯想到讀取器。

### 2.56.3 四個實測修正（三個推翻了原本的設計）

**(a) 異體字：單向轉換改成共存。**

原規劃是「查表前把 `為` 換成 `爲`」。掃描之後發現那張人腦列的表
**有四條方向是反的**——`說`(972 命中) 換成 `説`(0) 會把好好的資料換沒，
`顏`／`溫`／`污` 同理。改成**兩種寫法都查、取最大值**之後，方向錯誤
最壞只是白查一次。

另一個理由是**有些字兩邊都有資料**（`裡` 530／`裏` 870，語料裡混用），
單向換會丟掉另一邊那幾百筆證據。

**表不能靠人腦列候選。** 資料驅動的掃法是：拿詞庫前 3000 個高頻字，
各用 500 個高頻字當左右鄰去數命中，撈出「幾乎查不到」的，再對每個
候選字形雙向驗證。人腦版漏掉了 `眾`(字頻 1100)、`群`(586)、`床`、`啟`
四個常用字。

**(b) 扣字頻要扣「命中字形」的，不是原字的——這個坑很陰。**

共存 ＋ 扣自身字頻兩條規則**相乘會產生反效果**。實測症狀是
「謝謝你」被改成「謝謝妳」、「剛才」變「剛纔」。

原因：共存讓 `妳` 借用 `你` 的次數，`謝→你` 與 `謝→妳` 拿到**完全
一樣的原始次數**（15.01）；但扣自身字頻時 `妳` 只有 54、`你` 有 4224
——分母小的分數反而更高（11.0 對 6.7）。`纔` 字頻是 1，扣完直接飆到
14.3。

改成扣**實際借到資料的那個字形**的字頻之後，借來的次數也還回對應的
分母，四句 `妳` 全部修好，弄壞從 6 降到 3。

**(c) 「我們的常用字優先」要有實質權重，不能只當 tie-break。**

第一版寫成 `1e-6 * log_freq`，**完全沒有作用**——被 bigram 分數壓過去。
`妳` 不是同分而是真的贏了。改成有實質權重的先驗（`LM_W_OWN = 0.1`）
之後才擋得住。

教育部字頻表正好代表台灣的用字習慣，所以這一條同時是「台灣化」與
「資料稀疏時安全退回自己的排序」。

**(d) 中國用語要主動擋，字頻先驗擋不完。**

`介面→界面`、`剛才→剛纔` 需要一份小黑名單，查到就當作沒資料。
**只需要收「同讀音會競爭」的**——`軟體`／`軟件` 讀音不同，在候選清單裡
本來就不會撞，收了也沒用。這一條讓命中從 752 到 754（spike 階段）。

### 2.56.4 詞層保護：拿 6 句換 1 句，還是換了

**這是全節唯一「用分數換正確性」的決定。**

接上語言模型之後 `cargo test` 掛了一個：`各位` 被改成 `個為`。
根因是詞層明明給了對的詞，統計把它覆蓋掉了。

加上「詞層碰過的格語言模型不動」之後測試綠了，但命中從 754 掉到 748。
掃過四種放行策略：

| 策略 | 文字命中 | `各位` |
|---|---|---|
| **全保護（採用）** | **748** | **✓** |
| 有競爭者就放行 | 751 | ✗ |
| 長詞且有競爭者才放行 | 749 | ✓ |
| 完全不保護 | 754 | ✗ |

**選 748 的理由**：那 6 句幾乎都是 §2.45 那個「同讀音存得下多個詞、
詞層取第一個」的延伸（`救回來`／`就回來` 同鍵，詞層永遠取前者），
**那是詞層自己該修的問題**。讓統計去繞過詞層，會連 `各位` 這種詞層
明明給對的也一起賠掉。

**`個為` 的 bigram 是 12.6、`各位` 只有 7.7，而那不是資料錯誤**
——「一個為了…」在語料裡真的比「各位」常見。單字 bigram 分不出
「這兩個字是一個詞」與「這兩個字常常相鄰」，**那正是詞層存在的理由**。

所以剩下那 6 句的正解是回頭修詞層的同讀音挑選（§2.45 的延伸），
不是調鬆這道保護。

### 2.56.5 效能：寬度限制是必需品，不是可選的優化

第一次量成本時是紅燈：最壞一句（`昨天的會議記錄已經寄給大家`）要
**49,275 次字對查詢**，Rust 就算比 Python 快 30 倍也要 14ms，而按鍵
預算只有 16ms、現況已經用掉 11.2ms。

解法是**每格只考慮前 5 個候選**（`LM_WIDTH`）：

| 每格候選數 | 最壞查詢數 | 命中 |
|---|---|---|
| 不限制 | 49,275 | 754 |
| **5 個** | **320** | **754** |
| 3 個 | 126 | 754 |

**成本降到 1/154，命中一句都沒少。** 很合理——正解幾乎都在前幾名，
第 20 個同音字不可能是答案。

### 2.56.6 這次學到的

- **保守不等於安全。** 原規劃「只收七個真正的異體字」聽起來很謹慎，
  實際上漏了四個常用字又收了四條反向的錯誤。**這種表要掃，不要想。**
- **兩條各自正確的規則相乘可能出錯。** 共存對、扣字頻也對，合在一起
  卻讓罕見字形分數暴衝。改動涉及兩個機制時，要專門量它們的交互。
- **spike 的數字要在實作後複驗。** 754 是 spike 預測、實作後也拿到 754，
  但加上詞層保護之後是 748——**spike 沒有模擬到詞層**，那是它的盲區。
