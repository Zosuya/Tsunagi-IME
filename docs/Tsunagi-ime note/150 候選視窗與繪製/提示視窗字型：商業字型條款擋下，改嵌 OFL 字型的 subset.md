# 提示視窗字型：商業字型條款擋下，改嵌 OFL 字型的 subset

全半形提示視窗（`platform/windows/src/width_window.rs`）的標籤
「自／半／全」用**寫死的字型**，目前是 `lithue-1.0 Regular`。

### 現在沒有打包，也不需要

程式裡只有一個字型**名字**：

```rust
const SYMBOL_FONT: &str = "lithue-1.0 Regular";
```

`CreateFontW` 拿這個名字去問系統要，字型檔完全不進 DLL——
所以 DLL 大小不受影響。開發機裝了那套字，就是那個字形。

### 但發佈給別人時會出問題

對方電腦沒裝 lithue 的話，GDI 會**靜默退回系統預設字型**——
不會報錯，只是字形不一樣。功能不受影響，但視覺跟設計的不同。

這件事同樣適用於候選視窗：使用者在設定頁指定的字型，換一台
電腦可能不存在。差別在那是**使用者自己選的**，退回預設是合理的；
而提示視窗是我們寫死的，退回就違反了「寫死」的用意。

### 發佈時的三個選項

| 做法 | 大小 | 授權 |
|---|---|---|
| **只嵌那三個字的字形** | 約 2～5 KB | 要確認字型授權允許 subset 嵌入 |
| 嵌整套字型 | 3～10 MB | 多數中文字型不允許 |
| 不嵌，接受退回系統字型 | 0 | 無 |

**建議第一種**。三個字用 subset 工具（`pyftsubset`、`fonttools`）
裁出來只有幾 KB，再用 `AddFontMemResourceEx` 在執行期載入——
那個 API 載入的字型只有本行程看得到，不會污染系統字型清單。

實作大概是：把裁好的 `.ttf` 用 `include_bytes!` 嵌進 DLL，
啟用時 `AddFontMemResourceEx` 註冊，`CreateFontW` 就找得到了。

### 做了（2026-09-03），但不是原本打算的那套字型

**原本的計畫被授權擋下來。** 那套商業字型的條款寫著「限兩台裝置、
不得轉讓給任何人」——subset 只取六個字也不行，那仍然是散布字型資料，
而「不得給任何人」沒有數量豁免。

`fsType=0`（技術上標示可自由嵌入）**不能拿來反駁條款**。那個位元只是
字型檔裡的一個旗標，廠商常常沒設對；白紙黑字的合約才是依據。

改用 SIL Open Font License 的來源（Noto Sans TC，Windows 11 內建），
那個授權明確允許 subset 與散布。

#### 三個實作細節

| 事情 | 為什麼 |
|---|---|
| 改名成 `Tsunagi Symbols` | **OFL 的義務**——來源的保留字型名稱是 `Source`，修改版不得使用。順帶避開跟系統同名字型搶 `CreateFontW` |
| 字重定格在 400 | 來源是可變字型，**預設值是 100（Thin）**，那麼細的筆畫在 28px 的視窗裡會糊掉 |
| 不呼叫 `RemoveFontMemResourceEx` | 字型要活到行程結束，而 DLL 卸載時機由宿主決定；提早移除會讓還開著的提示視窗畫不出字。4KB 的常駐成本可以接受 |

`AddFontMemResourceEx` 載入的字型**只有本行程看得到**，不污染使用者的
系統字型清單，也不必寫檔到磁碟。載入失敗不是致命的——`CreateFontW`
找不到那個名字就退回系統字型，字形不同但功能不受影響。

產物 `res/symbols.ttf` 只有 **3,972 bytes**，產生腳本
`res/make_symbol_font.py`。**改了標籤文字要重跑**，不然新字沒有字形。

### 什麼時候該做

Phase 5 發佈前。現在是個人專案、開發機有那套字，不必提前處理。
