# 版面高度只能有一個算法

**症狀**：候選清單第一列的字頂端被預覽列的黃底蓋掉一截。

### 原因：兩處各算各的

版面的垂直座標被算了兩次，而且算法不一樣：

| 誰 | 算什麼 | 用的式子 |
|---|---|---|
| `paint` 畫預覽列 | 它的**底**在哪 | `pad*2 + line_h` |
| `paint` 畫候選列 | 第 n 列的**頂**在哪 | `pad + (n+1) * line_h` |

預覽列上下各有一份內距（`pad*2`），候選列卻只算了一份——
兩邊差了一個 `pad`（預設 8 邏輯像素），第一列候選就往上侵入
預覽列的範圍。

`show` 算視窗高度時用的是第三套式子（`pad*2 + line_h*列數`），
跟前兩者都不一致。三個地方各自「看起來合理」，湊在一起就錯。

### 修法：抽成純函式

`layout(pad, line_h, has_preview, rows, has_hint) -> (list_top, height)`

繪製與量高度都呼叫它，**版面只有一個算法**。這比「把三處的數字
各自修對」可靠——後者下次改版面時還會再錯一次。

抽出來的另一個好處是**測得到**。這種座標錯位本來只能靠肉眼看，
現在有六條測試鎖住：候選清單不侵入預覽列、提示列正好接在清單
下面、高度容得下所有內容、沒有預覽列／沒有候選時不扁掉。

### 一般化的教訓

**同一個幾何量在兩個地方各算一次，遲早會對不上。**
座標、尺寸、索引這類東西，要嘛只算一次傳下去，要嘛抽成一個
兩邊都呼叫的函式。這跟 §2.7「算段數 vs 算字元數的坑踩了五次」
是同一類問題——判準散落在多處就會發散。
