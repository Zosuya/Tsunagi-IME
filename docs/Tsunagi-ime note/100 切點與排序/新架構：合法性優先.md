# 新架構：合法性優先

### 舊架構怎麼失敗的

原本的 Phase 1/2 是這樣設計的：

```
每個引擎回傳「候選 + 信心分數」→ 辨識層依分數合併排序 → 詞格 DP 選最佳路徑
```

實作出來、跑 426 句測資的結果：**切點正確率 40.8%**（第一名），
前 10 名涵蓋 58.2%。

失敗的根源是**把兩件事混在一起**：

1. 「這段按鍵在這個語言下**合不合法**」——結構問題，答案是 yes/no
2. 「這段按鍵**該顯示什麼字**」——詞庫問題，答案是一串排序過的候選

舊架構讓引擎同時回答這兩件事，於是「合法性」被壓成了分數的一部分，
再跟詞頻、語言先驗混在一起加權。結果是**分不出「這不可能是日文」與
「這是罕見的日文詞」**——兩者都表現為低分。

實際的後果：

```
生誕|live       →  seitannlive     整串沒切
明日|meeting    →  ashitameeting   整串沒切
check|_|一下     →  check|u vu84    空白判斷錯
```

### 新架構

```
Phase 1  合法性判斷（yes/no，不碰詞庫）
Phase 2  切點引擎（依合法性瀑布切段）
後續     選詞模組（查詞庫、決定顯示什麼）← 獨立於前兩者
```

同一份測資，**95.3%**（第一名）。

### 為什麼差這麼多

**第一，合法性是硬約束，不該被分數稀釋。**
`ngr`、`bldk` 不可能是日文——這是結構事實，不是「信心度低」。
把它變成 0.1 分之後，遇到另一個 0.05 分的注音解讀就輸了。

**第二，注音與日文的按鍵集合天然不相交。**
注音必須以聲調鍵收尾（`3467` 或空白），日文只用字母和 `-`。
實測「注音與日文都判合法」的按鍵組合是 **0 個**。
舊架構用分數比大小，等於白白製造了不存在的競爭。

**第三，切點與選字是不同粒度。**
`sushi` 要顯示成 すし 還是 sushi，那是選詞模組的事；
切點引擎只需要知道「這裡是一段」。混在一起會讓切點被選字的偏好帶偏。

### 這次量測本身的教訓

第一次量出來的舊架構成績是 **99.3%**，那是錯的。錯在比對範圍——
只看「空白造成的切點」，而沒有空白的句子（`seitannlive`）期望切點集合
是空的，**任何答案都算通過**，包括整串不切。

修正方式是給測資加第二欄「按鍵層級的切點期望」：

```
文字期望          按鍵期望             按鍵序列
check|_|一下      check| |u vu84      check u vu84
```

第二欄不需要任何推導，逐字元比對即可。加了這一欄之後，舊架構的真實
成績才浮現（40.8%）。

**教訓**：評分器測不到的地方，等於沒有測。設計測資時要先問
「這把尺量得到全部嗎」，而不是先看分數好不好看。
