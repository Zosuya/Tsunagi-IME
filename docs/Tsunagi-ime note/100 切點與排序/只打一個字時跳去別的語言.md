# 只打一個字時跳去別的語言

使用者回報「注音只打一個字時會優先跳別的語言」。量化：**150 個高頻
單音節裡 7 個中招（4.7%）**。

```text
ㄌㄧㄠˇ 了 → ぅ襖    ㄐㄧㄚ 家 → る啊    ㄋㄧㄢˊ 年 → す雸
ㄐㄧㄥ 經 → る鞥     ㄐㄧㄡˋ 就 → る噢   ㄍㄨㄥ˙ 公 → ej/5    ㄧㄣ 因 → up
```

型態很一致：**5 個被日文假名咬掉開頭**（`ru`→る、`su`→す，剩下的再
當注音）。

### 2.20.1 根因：`covered` 對注音只算多音節詞

`bopomofo_claimed_chars` 的迴圈是 `for len in (2..=MAX_WORD)`——**單音節
不算**。註解寫得很清楚，理由也對：單音節一律查得到，算進去 `covered`
就等於段長、失去鑑別力。

但副作用是單音節注音的 `covered` 是 0，而切成「日文假名＋殘渣」反而
有分（`ru`、`su` 都是合法假名）。任何一個兩字母假名都能贏過一個中文字。

連帶還有第二個症狀：`promote_language_reps` 挑代表的條件是
`covered > 0`，所以**單音節時中文代表根本不會被選出來**——打一個字時
選單裡連一個保證的中文選項都沒有。

### 2.20.2 兩刀，都很窄

**一、整串是一個音節就不要切開。** `Score` 加一欄 `fewer_split_syllable`，
擺在優先序最前面。**可以擺最前面是因為它只在「整串剛好是一個合法注音
音節」時才有值**，其他輸入一律是 0。而且只罰「切開」——整串當英文
（`up`）也是一段、不受影響，那種真歧義留給後面的欄位決定。

熱路徑要小心：判斷需要把各段接回原字串，那是一次配置。用**長度先擋**
（一個注音音節最多四個鍵）——`concat` 在這條路上曾讓 p99 從 12.4ms 衝到
17.9ms。實測加了之後 p99 沒有變化（11.0／11.6／11.2ms）。

**二、代表的後備。** 沒有任何切法的 `covered > 0` 時，退而求其次挑
「整串都是這個語言」的那一種。單音節就有 `（中）` 標記了。

### 2.20.3 結果

| | 改之前 | 改之後 |
|---|---|---|
| 150 個高頻單音節第一名錯的 | 7 | **1** |
| `check_incremental` 第 1 名 | 551/570 | 551/570 |
| `check_compose` 文字命中 | 650/720 | 650/720 |
| 按鍵延遲 p99 | 11.3ms | 11.2ms |

**三支計分器一個數字都沒動**——720 句測資裡沒有單音節輸入，所以量不到
差別是合理的。這正是「窄規則」的意義：只在它該作用的地方作用。

### 2.20.4 同一天冒出來的近親：單母音沒有日文可選

使用者回報「自動打日文母音，切法裡面沒得選（日）」。實測五個單母音
`a i u e o` **連日文切法都沒生成**（只有英文與符號兩列），而 `ka`、`ai`
都正常。

兩層原因：

1. **`lang_of` 把單母音判給英文**。那條「很常用的英文詞不讓給日文」的
   規則本來是為了擋 `you`→よう、`the`→てぇ（英文前 5000 名裡有 145 個
   中招），但 `a`、`i` 這種單母音也是最常用的英文詞，一起被收走了。
   而 `lang_of` **一段只回一個語言**，判成英文之後日文段就不存在。
2. **日文代表是「挑」出來的，英文代表是「造」出來的**。所以生成階段
   沒給出日文段時，英文照樣有選項，日文就沒有。

改第 2 點：**日文代表也造一個**（整串當日文，前提是 `romaji::validity`
說合法而且日文引擎有開）。**不改第 1 點**——那會動到切點排序，而
`a␣banana`、`I␣am` 這些英文正解都靠那條規則。三支計分器一個數字沒動。

### 2.20.5 剩下那一個不是引擎的問題

`ej/5`（ㄍㄨㄥ˙ 公）修不掉，因為那是**上游詞庫的一列打錯**：輕聲在本專案
的配置上是 `7`，`5` 是 ㄓ。查過整份 `BPMFBase.txt`，106 條輕聲裡**只有
這一條**寫成 `5`。影響僅限於「輕聲的公」打不出來，一般的一聲「公」正常。

> **✅ 2026-09-12 修掉了，而且不只一條——是兩條。** 當時漏掉「夫」
> （`ㄈㄨ˙`），它的壞法不同：按鍵欄 `zj` **整個缺了聲調鍵**，跟一聲
> 撞在一起。完整經過見下面的 2.20.6。

### 2.20.6 兩條都修好了，連同把 BPMFBase 釘進版控（2026-09-12）

2.20.5 說「修不掉」，真正的原因不是技術上修不掉，而是**那個檔不進
版控**——改了下次 `download.ps1` 重跑就被蓋掉，別台開發機也拿不到。
所以這次先解決版控，再解決資料。

**一、掃出來是兩條，不是一條**

重掃 106 條輕聲，有兩條不合規，而且**壞法不同**：

| 列 | 原本 | 改成 | 怎麼壞的 |
|---|---|---|---|
| 8052 | `公 ㄍㄨㄥ˙ gong5 ej/5` | `ej/7` | 尾巴多一個 `5`（在大千是 ㄓ） |
| 26460 | `夫 ㄈㄨ˙ fu5 zj` | `zj7` | **聲調鍵整個掉了**，跟一聲撞在一起 |

同一個根因：第三欄的漢語拼音**用 `5` 表示輕聲**（`gong5`／`fu5`），
上游轉成大千按鍵時沒換成 `7`。一個把 `5` 直接抄進去，另一個把它當成
「沒有聲調」丟掉。

**錯在上游，不是我們轉壞的**——當場抓了 McBopomofo 最新版（26535 列，
比本地的 26652 少，代表上游有更新過）比對，兩列一模一樣。也反證過
欄位語意沒誤解：全檔第四欄結尾 `4` 有 8805、`6` 有 7157、`3` 有 4340、
`7` 有 104 筆，完全符合大千配置；104 + 2 = 106。

修正前後（`chars_for`）：

```text
ej/7  []     → ["公"]     輕聲的公本來打不出來
ej/5  ["公"] → []         ㄍㄨㄥㄓ 這個無意義組合本來會打出「公」
zj7   []     → ["夫"]
ej/ 、zj （一聲，尾端空白）不受影響
```

**二、四份上游原料進版控（1.9MB）**

`BPMFBase.txt` 707KB、`en_50k.txt` 609KB、`zh_tw_50k.txt` 521KB、
`char_freq.txt` 46KB。判準是**體積小、而且踩過坑**：

- **上游會錯**——就是上面這兩列
- **上游會飄**——`en_50k` 飄過一次，害
  `cutpoint::prune::tests::英文段_是詞的保留` 在全新下載的資料上掛掉

其餘不進：日文辭典 58MB、國教院 xlsx 17MB 太大；`*.bin` 與
`word_freq.txt` 是 `gen_*` 產的**成品**，重跑就有。

兩個實作上的坑：

1. **`data/english/` 要改寫成 `data/english/*`**，否則 `!` 例外不生效
   （`.gitignore` 開頭那段早就記過這個坑，這次換一個目錄又踩一次）
2. **`char_freq.txt` 不是下載的，是 `Convert-MoeCharFreq` 就地轉檔產生**，
   而 `Set-Content` 無條件覆寫——它進版控之後，重跑一次 `download.ps1`
   就會把版控那份蓋掉。內容雖然一樣，但 `Set-Content` 產 CRLF，
   git 會看到 5701 列全變。那支函式補上了「已存在就略過」。
   （另外三份走 `Get-File`，它本來就有這道檢查。）

`.gitattributes` 把這四份釘成 `eol=lf`。理由跟腳本那幾條不同：這些是
從上游原封不動抓下來的，**釘住行尾才能跟上游逐位元組比對**——「上游
是不是又飄了」要實際 diff，行尾差異會把真正的改動蓋掉。

**三、`char_freq.txt` 是 ND，只能原樣保存**

§2.31 查證過教育部
字頻是 **CC BY-ND 3.0 TW**：可以散布（義務是標示出處），而 Big5 表格轉
成兩欄屬於**格式轉換，不算改作**。但由此而來的限制要寫在資料旁邊——
**那個檔進了版控之後不得修改內容**，將來發現它有錯要另做覆寫表。
另外三份是 MIT，可以直接修。`download.ps1` 的檔頭授權清單原本漏標
教育部與國教院兩份，一併補上。

**四、鎖它的是單元測試，不是測資**

測資鎖不住這個修正——`mkkeys` 產不出輕聲的鍵，因為**輕聲讀法在詞庫的
詞層裡不存在**，只存在單字層（「老公」「丈夫」收的都是一聲）。測資是
「打這串鍵應該出這些字」，而沒有任何詞會用到那兩個輕聲鍵串。

改用 `dict::tests::輕聲的按鍵一律以7結尾`：**直接讀 `BPMFBase.txt` 這個
文字檔**，掃過每一條輕聲、要求第四欄以 `7` 結尾。這條測試能成立正是
因為那個檔現在進版控了；它不載入 `dict_zh.bin`（成品、不進版控，依賴它
的測試在全新機器上會掛）。反向驗證過：把資料改回 `ej/5`，測試立刻紅，
訊息直接指出行號與整列內容。

上游哪天把這兩列修好、或又弄壞別的列，這裡都會紅。
