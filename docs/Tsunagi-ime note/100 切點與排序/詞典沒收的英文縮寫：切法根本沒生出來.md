# 詞典沒收的英文縮寫：切法根本沒生出來

使用者回報 `yt舊有問題了` 打不出來——**而且按 Tab 也救不回來**，
切法選單裡只有「整串當英文」與「注音符號直出」兩列。

### 2.39.1 根因：規則二把它殺在生成階段

`cutpoint/prune.rs` 的規則二要求「只有英文引擎吃得下、又不是最後一段」
的段落必須是英文詞典裡的詞。`yt` 三個條件全中——注音不合法（ㄗㄔ 兩個
聲母）、日文不合法、而且**不在 `en_50k.txt` 裡**。

於是「`yt` | `ru.4` | …」這種切法在**生成階段**就被丟掉了，後面的中文
永遠獨立不出來。這違反 Phase 2 的硬指標「切點涵蓋 100%，正解一定要在
候選裡」，也違反 `prune` 自己寫的原則「寧可留錯、不可殺對」。

對照組很乾淨——差別純粹是語料的偶然，跟語言學無關：

| 前綴 | 在 en_50k？ | 結果 |
|---|---|---|
| `ig` / `gg` / `tv` / `pc` / `at` | 在 | 正常切得出中文 |
| `yt` / `fb` / `ytb` / `vtuber` | 不在 | 完全打不出來 |

兩個延伸事實：

- **打空白也沒用**。規則二只看「是不是詞」，不看左右是不是邊界
  （只有規則一才看）。
- **學習層救不了，這是雞生蛋**。`english::is_word` 確實會問切詞學習
  那一層，但切詞學習是靠使用者按 Tab 選過的切法學的——切法從來沒
  出現在選單裡，就永遠學不到。

### 2.39.2 為什麼「看下一段是什麼語言」那條路不可行

第一個想到的解法是「英文段後面若接著注音／日文段就放行」。
**在時序上來不及，不要再試一次。**

累加式切法是「分支一旦死掉就不會復活」（見 [[Phase 2 完成：累加式切法與排序]]）。`yt` 這條分支在
打到第 3 鍵（`ytr`）時就必須活下來，而那時候「下一段」只有一個還在
打的字元 `r`，看不出任何東西。同理，任何需要往右看的判準都無效。

還有一個實作上的硬限制：`incremental.rs` 的段落驗證快取用
`(起點, 終點)` 當鍵，前提是「丟棄規則最多看到 `chars[end]`」。
往右多看一格以上，快取就會給出過期的答案。

所以能救的只有**不看後面**的規則。

### 2.39.3 做法：把規則一從長度 1 推廣到長度 3

規則一（單字母）本質上就是「邊界上的短段放行」，只是上限訂在 1
（`a`、`I`）。這次把上限拉到 3，並多要求整段都是字母：

```text
長度 ≤ 3 ＋ 左邊是邊界（開頭／空白／標點）＋ 整段都是字母 → 放行
```

`ACRONYM_MAX = 3` 是掃出來的——2、3、4 對三支計分器**一個數字都沒動**，
差別只在候選數中位：

| | 基線 | N=2 | N=3 | N=4 |
|---|---|---|---|---|
| 切點涵蓋 | 570/570 | 一樣 | 一樣 | 一樣 |
| 前 3 名 | 560/570 | 一樣 | 一樣 | 一樣 |
| 第 1 名 | 551/570 | 一樣 | 一樣 | 一樣 |
| 文字命中 | 677/720（2.5%） | 一樣 | 一樣 | 一樣 |
| **候選數中位** | **36** | 38 | **39** | 43 |
| 按鍵 p99 | 11.2ms | 11.0ms | — | 10.9ms |

常見縮寫幾乎都在三個字母以內（yt、fb、ig、tw、ytb、nba），4 多付
7 個候選卻只多收 asap 那類，所以停在 3。上限 `ALIVE_LIMIT = 400`
沒有被碰到。

**只看左邊界、不看右邊界**，這點跟規則一不同，理由就是 2.39.2。

### 2.39.4 順帶救到的：短前綴 ＋ 已知詞

`merge` 會把相鄰的英文段黏回去，所以詞典沒收的長詞也跟著通了：

```text
vtuber = vt（這條規則放行）＋ uber（本來就是詞）
```

`vtuberru.4` 的選單因此多出「vtuber就」「vtuberる噢」，原本一種都沒有。

### 2.39.4.1 左邊界的第一版寫錯了（2026-09-04 當天修）

上線後用 20 句自編的三語混打句子回歸，抓到一個**很大的漏洞**：

```text
ytru.4u.3jp4wu6      yt 在開頭         → 過
5k4ek7 ytu.3jp4wu6   yt 在空白後       → 過
5k4ek7ytu.3jp4wu6    yt 接在「這個」後  → 整段中文都不轉
```

第一版的左邊界寫成「開頭／空白／標點」，而**縮寫夾在中文句子中間才是
最常見的情況**。原因是注音音節一定以聲調鍵結尾（一聲是空白，其餘是
`3`／`4`／`6`／`7`），所以「中文後面」看到的是**數字**，既不是空白也不是
標點。

判準改成**「左邊那個字元不是英文字母」**——這句話直接表達了規則的本意
（我沒有把一個英文字砍成兩半），三種情況一起涵蓋，而 `configg6ru0` 的
`onf`（左邊是 `c`）仍然擋得住。

三支計分器再次一個數字都沒動，候選數中位 39→40，p99 10.6ms。

被這個漏洞蓋住的實例：`那個vtuber昨天直播` 原本**連候選都沒有**
（`vtuber` 單獨打卻是對的），修完是第一名。

**教訓**：判準寫成「列舉允許的情況」（開頭／空白／標點）很容易漏，
寫成「否定不允許的那一種」（左邊不是字母）才涵蓋得完整。而漏掉的
那種，剛好是真實使用中最常見的。

### 2.39.5 代價：沒解決的案例，第一名會變醜

`vtuberru.4` 原本第一名是乾淨的英文原樣 `vtuberru.4`，現在是
「vt宇部っる噢」，正解掉到第 3、第 6。

**打得出來了，但要按 Tab。** 這是排序層的事——放行只負責讓切法存在，
排名是 `rank.rs` 的職責，兩件事分開看。使用者裁決過接受這個交換。

### 2.39.6 這件事跟「youtube 排第 17 名」不是同一個病

同一天回報的 `youtube沒事`（打成「ようつべ沒事」）**看起來像，其實不是**：

```text
yt        切法根本沒生出來    → 生成問題（本節）
youtube   切法排第 17／26     → 排序問題（youtube 在 en_50k，排 10160）
```

`ようつべ` 是日文詞典（mozc）真的收了的詞，所以它拿得到 `covered` 與
`dict_chars` 的分，又躲過 `fewer_kana_bits` 的短碎片懲罰（那條只罰
「合法但不在詞典裡」的）。單獨打 `youtube` 第一名就已經是「ようつべ」。

這跟 §2.24（`ii` 打不出いい）是同一族——語言判斷一票定生死，只是
方向相反。修法完全不同，另開一輪。

**教訓**：回報「打不出來」時，第一件事是分辨**切法有沒有生出來**。
沒生出來要改 `prune`，生出來但排後面要改 `rank`——改錯地方的話，
分數會動而問題不會好。`show_ime` 的 `-m` 參數就是為了看清楚這件事
而加的（預設只列 6 種，看不到第 17 名）。
