### `windows` crate 版本與 `#[implement]` 巨集的一個關鍵陷阱

用 `windows = "0.62"` 搭配 `#[implement(...)]` 巨集實作 COM 介面時，光是
在 `Cargo.toml` 加 `windows` 依賴**不夠**——巨集展開後的程式碼裡有裸露的
`windows_core::...` 路徑（不是 `::windows_core` 絕對路徑，也不是
`windows::core`），這要求 `windows_core` 這個 crate 名稱本身能被目前 crate
直接解析。但 `windows_core`只是 `windows`的**間接依賴**，Cargo 預設不會把
間接依賴塞進目前 crate 的 extern prelude，所以會出現：

```
error: cannot find `windows_core` in the list of imported crates
```

**修法**：額外直接加一行 `windows-core = "0.62"`（與 `windows` 同版號）到
`Cargo.toml`，讓它變成直接依賴、進入 extern prelude。這是本專案唯一一個
純粹的建置環境陷阱，值得記下來避免下次重踩。

### `#[implement]` 巨集生成型別的心智模型

`#[implement(ITfFoo, ITfBar)]` 套在 `struct TextService { ... }` 上時：

- 巨集會另外生成一個 `TextService_Impl` 型別，它才是真正實作
  `ITfFoo_Impl` / `ITfBar_Impl` trait 的地方（`impl ITfFoo_Impl for TextService_Impl`）。
- `TextService_Impl` 對 `TextService` 有 `Deref`，所以在 trait 方法內寫
  `self.some_field`（`TextService` 的欄位）可以直接用，不需要额外解包。
- 若需要「拿一個指向自己、實作某介面的 COM 參照」（例如把自己當
  `ITfCompositionSink` 傳給 `StartComposition`），在 `&TextService_Impl`
  上可以用 `ComObjectInterface::<ITfXxx>::as_interface_ref(self)` 拿到
  `InterfaceRef`，`.clone()` 出一個 owned 的介面參照——**但只有在
  `self` 的型別是 `&TextService_Impl`（也就是身處某個 `_Impl` trait 方法
  內）才拿得到**；如果把邏輯抽成 `impl TextService { fn helper(&self) }`
  的一般方法，`self` 會退化成 `&TextService`，就再也拿不到這個「同一個
  COM 身分」的參照了。本專案的作法是把需要這種操作的函式寫成自由函式、
  顯式傳入 `&TextService_Impl`（例如 `text_service.rs` 裡的
  `update_composition(service: &TextService_Impl, ...)`），而不是包成
  `impl TextService` 的方法。

### `DllRegisterServer` 裡一定要注意的 `GetModuleHandleW(None)` 陷阱

一開始很直覺地用 `GetModuleHandleW(None)` 去問「我自己這顆 DLL 在哪」，
但這個 API 在**任何情境下都回傳呼叫端主執行檔的 handle**（例如
`regsvr32.exe`、或 `cargo test` 產生的測試執行檔），而不是目前這顆 DLL
自己。寫進 `InProcServer32` 的路徑因此完全錯誤（會指到 regsvr32.exe 本身）。

正確作法：`GetModuleHandleExW(GET_MODULE_HANDLE_EX_FLAG_FROM_ADDRESS, <這個函式本身的位址>, &mut handle)`——
用「目前正在執行的程式碼的位址」反查它所屬的模組，才能保證是本 DLL 的
`HMODULE`。細節見 `registration.rs::dll_path()`。

這也解釋了為什麼 `cargo test` 沒辦法完整驗證註冊流程：測試執行時
`ime-tip-windows` 是以 `rlib` 形式靜態連結進測試執行檔，`dll_path()`
反查回來的地址就在測試執行檔裡，而不是真正的 `ime_tip_windows.dll`。
`crate-type = ["cdylib", "rlib"]` 兩者並存正是為了讓 `cargo test` 能跑
（測試邏輯本身），但要驗證「真正註冊到系統」還是得對著編出來的 `.dll`
本身操作——這就是為什麼另外寫了 `register_tool` bin（見下）。

### 候選視窗為什麼要 `WS_EX_NOACTIVATE`

候選視窗如果搶走了 Windows 焦點，TSF 會把目前 focus document 換成候選視窗
自己的 context，後續打字的目標就從原本的 App 換成候選視窗，組字狀態全部對
不上。用 `WS_EX_NOACTIVATE` 建立、`ShowWindow(hwnd, SW_SHOWNOACTIVATE)`
顯示，讓它純粹是「畫面」，不參與 focus/TSF context 的任何切換。定位用
`GetGUIThreadInfo(0, ...)` 拿前景執行緒的 caret 矩形再 `ClientToScreen`，
拿不到就退回滑鼠游標位置。

### 組字（composition）生命週期

1. 第一個按鍵：`ITfInsertAtSelection::InsertTextAtSelection` 在目前選取
   位置插入初始字元並拿回 `ITfRange`，用這個 range 呼叫
   `ITfContextComposition::StartComposition` 開始組字，同時把自己（cast
   成 `ITfCompositionSink`）掛上去接收強制終止通知。
2. 後續按鍵：直接對 `composition.GetRange()` 拿到的 range 呼叫
   `SetText`，不用重新 `StartComposition`。
3. 送出（Enter/選字）：對 range `SetText` 換成最終文字後
   `composition.EndComposition(ec)`。
4. 取消（Esc/刪到空）：**先對 range `SetText` 寫入空字串**，再
   `EndComposition`。

> ⚠️ **這裡有個實際踩過的坑**（2026-08-23 在記事本實測時發現）：
> 早期實作的第 4 點是「直接 `EndComposition`，不改文字內容」，認為那等於取消。
> **不對。`EndComposition` 的語意是「結束組字狀態」，不是「丟棄組字內容」。**
> 可以把組字中的文字想成用鉛筆寫在紙上的草稿，`EndComposition` 只是
> 「把鉛筆放下、不再標示這是草稿」，紙上的字還在。實測現象就是：
> 按 Esc 後底線消失了，但文字以一般文字的身分留在文件裡。
>
> Backspace 刪到空時也走同一條路徑，但那時 range 已經是空的，剛好看不出
> 問題——這是這個 bug 拖到實測才浮現的原因。
>
> 修正方式：`text_service.rs` 將原本的 `Option<&str>` 參數換成具名的
> `EndKind::Commit(&str)` / `EndKind::Cancel`。`Option` 的 `None` 很容易被讀成
> 「取消」，但實際語意是「不寫入任何文字」，兩者不同；改成具名列舉後，
> 兩種意圖在型別上就分得開，且都會確實執行 `SetText`。

所有讀寫都必須包在 `ITfEditSession`（`edit_session.rs` 把「一個
`FnMut(ec) -> Result<()>` closure」包成 TSF 要求的 COM 物件）裡，透過
`ITfContext::RequestEditSession(tid, session, TF_ES_READWRITE | TF_ES_SYNC)`
執行——本專案一律用 `TF_ES_SYNC`，故意不處理非同步 edit session，換取邏輯
單純；代價是如果宿主程式的 context 正忙（回傳 async 需要排隊），目前的
實作會直接吃到錯誤而不是重排——這是有意識的 Phase 0 簡化，之後如果在真實
App 裡測出「常常拿不到 session」的狀況，才需要處理 async 分支。

### 底線不是宿主畫的，是輸入法自己要求的

組字時看不到底線，**不是 bug，是漏了一整套實作**。TSF 的分工是：組字文字
要長什麼樣（底線樣式、顏色、粗細）由**輸入法提供**，宿主只負責照著畫。
三件事缺一不可：

1. **註冊 `GUID_TFCAT_DISPLAYATTRIBUTEPROVIDER` category**（`registration.rs`）
   ——沒這一行，就算實作了下面兩項，宿主也不會來問。
2. **實作 `ITfDisplayAttributeProvider` / `ITfDisplayAttributeInfo` /
   `IEnumTfDisplayAttributeInfo`**（`display_attribute.rs`）——宣告「我提供哪些樣式」。
3. **組字時把樣式套到 range 上**（`text_service.rs` 的 `apply_display_attribute`）。

第 3 點有個轉折：TSF 的屬性值是 VARIANT，GUID 不能直接塞進去，要先用
`ITfCategoryMgr::RegisterGUID` 換成一個 `TfGuidAtom`（u32 代碼），再寫進
`GUID_PROP_ATTRIBUTE` 屬性。像是「不能把整份文件塞進表格欄位，得先去櫃檯換一個編號」。

> 樣式刻意不指定文字與背景顏色（`TF_CT_NONE`），只畫底線——讓宿主沿用自己的
> 配色，深色／淺色主題下都不會出現看不見的字。

需要的 `windows` crate features：`Win32_System_Variant` 與 `Win32_System_Ole`
（`VARIANT` 同時被這兩個 gate 擋著，只開一個會看到
「found an item that was configured out」這種不直覺的錯誤）。

### 插入點（caret）同步：`Collapse` 不會通知宿主，`GetRange` 要重拿

兩個坐標合起來才能讓游標跟著打字跑：

**一、`SetText` / `InsertTextAtSelection` 不會順便移動插入點。**
這兩件事在 TSF 裡是分開的。`range.Collapse()` 也不能代替——它只調整 range
物件本身，**不會通知宿主**，所以宿主那支會閃的游標不會動。要用
`ITfContext::SetSelection`。

**二、`composition.GetRange()` 的端點在 `SetText` 之後不會跟著新文字延展。**
它還記著舊的邊界。拿這種過時座標去 `SetSelection`，**每個呼叫都回 `S_OK`**，
游標卻停在文字前面。正確做法是 `SetText` 之後**重新** `GetRange()`。

> **這個 bug 花了很久才找到，因為 HRESULT 完全正常。** 最後是靠寫一個臨時的
> 檔案 log，實際量「收合後的端點在文件第幾個字元」才看出來。
> **教訓：HRESULT 回 S_OK 只代表「呼叫合法」，不代表「參數是你以為的那個值」。**
> 遇到「每個呼叫都成功但行為不對」時，直接量數值比繼續推論快得多。

三條路徑（開始組字、每次按鍵、送出）都必須同步游標，所以抽成共用的
`sync_caret_to_composition_end`。這一連串問題的共同模式就是「某條路徑漏做了某件事」
（Esc 漏了清空、起始路徑漏了游標），集中在一個函式里才不會再漏。

### 候選視窗定位要向 TSF 問，不能靠 Win32 API 猜

早期實作用 `GetGUIThreadInfo(0, ...)` 取 caret 位置，拿不到就退回 `GetCursorPos`。
**兩者都是錯的**：

- `GetGUIThreadInfo` 的第一個參數傳 `0` 代表「目前執行線」。單行程 App（記事本）
  剛好蒙對，但多行程架構（瀏覽器）的文字區在別的行程，根本查不到。
- `GetCursorPos` 拿的是**滑鼠指標**位置，跟文字插入點完全無關。

正確做法是 `ITfContextView::GetTextExt`，直接向宿主問「這段組字文字畫在螢幕
哪裡」。文字區可能在子視窗、另一個行程、甚至是自繪的畫布（Electron）——
只有宿主自己知道答案。

實作細節：
- `GetTextExt` 需要 edit cookie，必須包在 edit session 裡。用 `TF_ES_READ`
  （唯讀）即可，不要要求 `TF_ES_READWRITE`——權限要得越低，宿主越不容易拒絕。
- 回傳的已經是螢幕座標，不要再 `ClientToScreen`。
- 有些 App 會回 `S_OK` 但給全零矩形，要當成失敗走退路。

### 候選視窗不能只靠 `WS_EX_NOACTIVATE`：點擊還會抳走宿主焦點

`WS_EX_NOACTIVATE` 只能防止視窗**被啟用**，擋不住滑鼠點擊的副作用。
若 `wndproc` 沒處理滑鼠訊息、全交給 `DefWindowProcW`，點下去時宿主 App 會
認為自己失去輸入焦點而把插入點藏起來，而候選視窗又不接受啟用——
**結果兩邊都沒有插入點**。

修法：回應 `WM_MOUSEACTIVATE` 並回傳 `MA_NOACTIVATEANDEAT`，明確告訴 Windows
「不要啟用我，這次點擊也不用傳給我」，宿主就完全不會被驚動。

> 目前點候選字**不會真的選字**（`wndproc` 沒有 `WM_LBUTTONDOWN` 處理）。
> Phase 0 的候選視窗是純顯示，選字靠數字鍵。滑鼠選字屬 Phase 3 UX 範圍。

### `ITfCompositionSink::OnCompositionTerminated` 目前只是最保守的清空

當宿主/使用者的操作導致組字被強制中止（例如切換視窗），目前只是清掉本地的
`composition` / `input_buffer` / 候選視窗狀態，不會嘗試把已經打一半的文字
轉成什麼特殊呈現。這是刻意的 Phase 0 簡化，先確保不會殘留一個指向已經失效
的 `ITfComposition` 造成後續呼叫全部出錯。
