# 遊戲內卡頓：九次量測排除輸入法，順手補齊載入路徑的量測點

> **狀態**：輸入法已排除（九次量測，全程 5ms）。**剩下的對照測試在
> 使用者手上**——下一局開始時完全不碰輸入法，看凍結還在不在。

## 症狀

使用者回報：**LOL 一局開始會卡一次，凍住 10～20 秒，後面就不會了**。
只有 LOL 有，記事本／瀏覽器／VS Code 都正常。

## 結論：不是輸入法

九次遊戲內載入（含全新對戰的第一次），**從 DLL 進入行程到完全就緒
一律是 5～6ms**：

| 量測點 | 記事本 | LOL |
|---|---|---|
| `DllMain` → `DllGetClassObject` | 0ms | **0～1ms** |
| `refresh_config`（含擴充包） | 4ms | **4ms** |
| `set_keyboard_open` | 0ms | **0ms** |
| `lang_bar::install` | 0ms | **0ms** |
| `Activate` 全程 | 6ms | **5～6ms** |
| 詞庫背景載入 | 19ms | **17ms** |
| 按鍵時的同步等待 | 未觸發 | **未觸發** |

**遊戲裡的數字跟記事本一模一樣。** 一個只跑 5ms 的東西不可能讓行程
凍住 15 秒。

關鍵的一筆是 2026-09-21 16:49:16（UTC）那次——**新對戰、全新的
`League of Legends.exe` 行程、第一次載入**，正是使用者描述的觸發場景：

```
16:49:16.255  [載入] DllMain PROCESS_ATTACH
16:49:16.256  [載入] DllGetClassObject      ← 間隔 1ms
16:49:16.262  [啟用] Activate 結束 @5ms
16:49:17.000  [key] LCtrl → 接手            ← 0.7 秒後按鍵正常回應
```

## 被排除的六個嫌疑

每一個都是先推論、再量測、再推翻。**留著是因為「量過」本身就是結論**
——下次再有人懷疑同一條路，不必重做。

| 嫌疑 | 推論的理由 | 量測結果 |
|---|---|---|
| 詞庫載入慢 | 資料檔共 72MB，Vanguard 可能逐一掃描 | 17ms，與記事本相同 |
| 擴充包載入慢 | 台語包 4.4MB，`refresh_config` 是同步的 | 4ms |
| 按鍵時同步等待 | `ensure_dict_loaded` 在按鍵執行緒上、握著狀態鎖 | 從未觸發（門檻 50ms） |
| 碰工作列卡住 | 全螢幕獨佔把工作列蓋掉，`AddItem` 仍要求加按鈕 | 0ms ×9 |
| TSF 全域狀態卡住 | compartment 是跨行程通知 | 0ms ×9 |
| 模組載入被攔 | Vanguard 驗證剛映射進來的未簽章 DLL | 0～1ms ×9 |

最後一項原本是最強的嫌疑——它能解釋「量不到」（我們的第一行 log 要等
COM 來了才寫得出來）。加了 `DllMain` 之後這個死角補上了，嫌疑也隨之
排除。

## 最可能的真相

LOL 進新對戰本來就會卡一下（載入地圖資源、編譯著色器、Vanguard 進場
檢查）。使用者習慣在進場時切輸入法準備打字，**兩件事在時間上重疊**，
於是被歸因到輸入法身上。

**未完成的一步**：下一局開始時完全不碰輸入法，看那 10～20 秒還在不在。
還在就百分之百確定與我們無關。這個測試不花額外時間，正常玩就做得到。

## 量測方法：三次都量錯了方向，log 的欄位不夠是主因

### 第一次：以為是詞庫，量了才知道熱快取只要 20ms

先寫了一支暫時工具（`dbg_loadtime`，已刪）量整條載入路徑，跑在使用者
真實的設定與包上：`learn` 1ms／`english` 11ms／詞庫 0ms（mmap）／
`pack::load` 3ms，**總計 20ms**。詞庫當場就不成立了。

**`english::load` 是唯一真的讀檔案進 `HashSet` 的**（11ms），其餘都是
mmap，成本攤在查詢時的缺頁。

### 第二次：log 沒有宿主名與時間，量到的東西無法歸屬

初版 log 每行只有訊息本身。兩個後果：

- **分不出是誰寫的**——輸入法同時活在好幾個宿主行程裡，它們寫**同一個
  檔案**。這正是 2026-09-07 把 VS Code 的 `ActivateEx` 誤認成遊戲的
  原因（見 [[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]]）
- **看不出卡在哪一段**——沒有時間就只有順序

補上「宿主程式名 ＋ 牆上時鐘 ＋ 相對毫秒」三個欄位之後才開始量得動。

### 第三次：卡頓不落在任何兩行之間 → 補 `DllMain`

補完欄位再量，發現**整份 log 每一步都是毫秒級，而使用者實際等了十幾
秒**。那代表空白落在第一行 log **之前**。

`DllGetClassObject` 是 COM 來要物件的時刻，在那之前還有一整段「載入器
映射模組、跑相依項、反作弊掃描剛進來的程式碼」——那段量不到。

所以加了 `DllMain`，只做一件事：在 `PROCESS_ATTACH` 記一行。它跟
`DllGetClassObject` 的差就是那段空白。

> **`DllMain` 裡幾乎什麼都不能做**——載入器握著一把全域鎖，在裡面碰
> COM、開執行緒、載別的 DLL 都可能死鎖。所以那支**只寫一行 log**
> （開檔、寫入、關檔），而且只在 `PROCESS_ATTACH` 那一次。

## 留下來的量測點

這次的副產品，以後任何「宿主卡住」的問題都用得到：

- **log 每行帶宿主名與牆上時鐘**（`debug_log.rs`）
- **`DllMain`**：量「DLL 進入行程 → COM 要物件」那段空白
- **`Activate` 逐段計時**：`refresh_config`／`set_keyboard_open`／
  `lang_bar::install`，以及真正的結尾 `Activate 結束`
- **`preload_traced`**（`core/src/lib.rs`）：逐本詞庫回報耗時。
  `core` 不能自己寫 log（平台無關），所以收一個回呼——**載入順序只有
  一份**，在平台層另抄會漂掉，而漂掉的症狀是「量到的跟真正跑的不是同
  一條路」，不會有任何編譯錯誤
- **`[卡頓]` 警告**：按鍵入口的同步等待超過 50ms 才記。**不無條件記**
  ——那條路每次開始組字都會走，記的話 log 會被 `0ms` 淹掉

### 兩個修掉的誤導

- **`[啟用] 完成 @5ms` 印在 `Activate` 中段**，後面還有 compartment
  與語言列兩件同步工作。讀 log 會以為啟用只花 5ms 就結束了。
  改名成「詞庫已派工」，另加一行真正的 `Activate 結束`
- **`ensure_dict_loaded` 的兩個呼叫端後果天差地遠**：背景執行緒讀是
  免費的，**按鍵執行緒讀是凍住宿主**（TSF 的按鍵回呼跑在宿主 UI 執行
  緒上，而且那時狀態鎖還握著）。log 不分開標就量不出「使用者有沒有
  真的等到」，所以加了 `who` 參數

## 教訓

**「只有某個環境會卡」不等於「那個環境讓我們變慢」。** 這次六個嫌疑
全部指向「環境拖慢了我們」，量完發現我們在那個環境裡跟平常一樣快——
慢的是環境自己，我們只是剛好同時在場。

**量測點要覆蓋到「我們還沒開始跑」的那一段**，否則「log 裡什麼都沒有」
會被誤讀成「沒有問題」，實際上是「問題在量測範圍之外」。
