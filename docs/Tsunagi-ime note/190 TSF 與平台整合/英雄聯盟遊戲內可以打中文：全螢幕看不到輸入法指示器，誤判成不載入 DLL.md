### 2.58.0 更正（2026-09-15）：遊戲內可以打中文，上一次量錯了

**一句話：LOL 遊戲內聊天框打得出中文，所有功能正常。2026-09-07 量到的
「只出英文字母、log 零筆」不是遊戲擋掉我們，是那次根本沒切到我們的
輸入法。**

**根因是量測環境本身**：**全螢幕遊戲把工作列整個蓋掉，輸入法指示器
看不到**，所以「現在是哪個輸入法」在遊戲裡**沒有任何辦法確認**。
上一次是從視窗模式的工作列讀來的，那個讀數不能代表全螢幕當下的狀態
——結果整條推論鏈建立在一個看錯的前提上。

**這次怎麼切對的**：**盲按 `Win+空白`**（看不見指示器，靠按的次數盲切
輪替），切到之後遊戲內聊天框組字、候選、送出全部正常。

**作廢的結論**（原文保留在下方的表與段落裡，供對照，但**都不成立**）：

| 2026-09-07 寫的 | 2026-09-15 的實際情況 |
|---|---|
| 遊戲內打字只出英文字母 | **打得出中文**，切對輸入法就正常 |
| 遊戲行程從未載入我們的 DLL（log 零筆） | 沒切到我們當然零筆——**那是結果不是原因** |
| 是遊戲那一層排除我們（Scaleform 白名單） | **沒有證據**。白名單這條推論回到「查不到證據」的狀態 |
| 以後 H11 填「－ 未涵蓋」不必再測 | H11 **是一般宿主**，照其他宿主的短版測 |
| 使用者只能切成微軟注音才能在遊戲內打中文 | **不必**，我們自己就能用。README 不要寫那句話 |

**唯一留下來的實測事實**：大廳（`LeagueClientUx.exe`）正常（CEF，跟
Chrome 同一條路）、沒開聊天框時技能鍵正常不組字。後者現在才知道**是
`GUID_COMPARTMENT_EMPTYCONTEXT` 真的生效**，不是「我們不在遊戲行程裡」。

**這一次的教訓**（比 §2.58.10 那條更硬）：**「證據是零」有兩種解釋
——東西不在，或是你的量測沒接上。** log 零筆同時符合「遊戲不載入我們」
與「沒切到我們」，而上一次只考慮了前者，因為工作列的讀數看起來排除了
後者。**排除用的那個觀察本身要先確認可靠**：全螢幕下工作列看不到，
那個讀數從頭到尾就不存在。

**下次測遊戲的第 0 步**：遊戲**全螢幕時沒有辦法確認當前輸入法**，所以
要嘛先在視窗／無邊框模式切好再轉全螢幕，要嘛**盲按 `Win+空白` 輪替**、
用「打得出中文」本身當作切對了的證據。**不要拿工作列的讀數當證據。**

### （以下為 2026-09-07 的原始記錄，結論已作廢，保留供對照）

**一句話：遊戲行程根本不載入我們的 DLL，所以底下所有「會壞在哪」的
推論都不會發生——也修不好。**

| 觀察 | 證據 |
|---|---|
| 遊戲內聊天框打字**直接出英文字母** | 實測 |
| 遊戲行程**從未載入我們的 DLL** | `%TEMP%\ime_debug.log` 全檔零筆遊戲的 `[啟用]` 與 `[key]` 記錄；那幾筆 `ActivateEx` 經比對都是 VS Code（`[key] Code Down`） |
| Windows 認得我們，是**遊戲那一層**排除的 | 視窗模式下工作列顯示的正是通譯輸入法 |
| 大廳（`LeagueClientUx.exe`）**完全正常** | 實測，跟 Chrome 同一條路 |
| 沒開聊天框時**技能鍵全部正常**、不組字 | 實測 |

**這證實了 §2.58.2 那條原本標「查不到證據」的推論**：LOL 遊戲內的
輸入法行為，跟 2017 年前 Scaleform 白名單機制的描述完全一致——
不在支援清單上的輸入法**連訊息都不送**（官方文件說回 `GFxIME_NotSupported`），
症狀與 PIME 2016 年那兩則回報（issue #90／#115，「只能打出英文字母」）
一字不差。原本擔心 Riot 近年重寫過 UI 所以推論可能不適用，實測看來
那個機制還在。

**兩條推論被推翻**：

1. **§2.58.1 原本列為「最要命」的第 1 條風險不存在。** 原本擔心
   `Mode::Idle` 對所有字母鍵都有綁定、進遊戲會吃掉技能鍵，要靠
   `GUID_COMPARTMENT_EMPTYCONTEXT` 擋住。實測技能全部正常——但**不是**
   因為空 context 生效，而是更徹底的原因：**我們不在遊戲行程裡，
   不可能吃掉任何鍵**。原本設計的第 1 步量測（`ImmAssociateContext(NULL)`
   會不會被翻成空 context）在 LOL 上量不到，那條問題仍然未驗證，
   要換一個真的會載入我們的 IMM32 宿主才量得到。
2. **做 UI-less（方案 A）對 LOL 沒有用。** §2.58.7 原本要靠量測第 4 步
   （遊戲的候選清單有沒有東西）決定要不要做 A。實測給出的答案比那更前面：
   遊戲**連我們的訊息都不收**，不是「收了但候選給不出來」。A 案唯一的
   收益前提（遊戲會來拿 `ITfCandidateListUIElement`）不成立。

**九步量測表的實際結果**：第 1 步過（但理由與預期不同，見上）、
第 7 步（大廳）過、第 2～5 步**前提不成立所以不適用**——那些都建立在
「輸入法有進到遊戲裡」之上。第 6 步（Ctrl 鎖英文逃生口）在 LOL 上
**用不著了**，因為遊戲本來就只給英文。第 8、9 步同理。

**附帶收穫（跟 LOL 無關但更重要）**：新加的 `[啟用]` log 顯示，這台
機器上**所有宿主的 `ActivateEx` 旗標都是 `0x0`**，沒有任何一個用
`TF_TMAE_UIELEMENTENABLEDONLY` 啟用我們。所以 §2.58.3 講的那個
「宣告不實」問題目前還沒真的害到任何宿主——**但它仍然是錯的宣告**，
方案 B 照做。

**旁證：新酷音走完了整條路，一樣沒解決 LOL。** 這是很強的佐證，因為
他們與我們處境相同（第三方 TSF 輸入法）而且真的實作了 UI-less：

- PIME 時代的 issue #90／#115（2016）**至今 open、零則留言**；#185 有
  maintainer 正式診斷「須要 PIME 支援 UILess Mode」，追蹤用的 #199
  也還開著——**PIME 從未補上**
- 換架構後的 `windows-chewing-tsf` **2025-07 實作了 UILess mode**
  （commit `0723ca5`），2026-03 還有一個 commit 標著 **in-game**
  （`b98db5c`），CHANGELOG 提到改善 **Minecraft** 相容性，官方公告寫
  「UILess 模式……**與全螢幕遊戲相容**」
- **但從未點名 LOL，也查不到任何 LOL 成功的使用者回報**

**這正是白名單機制的預期結果**：Autodesk 官方文件的支援清單是**寫死的
具名清單**（日文 MSIME、微軟拼音、繁中倉頡／注音／新注音／大易／速成／
行列，第三方只有 ATOK、Google 拼音、搜狗拼音），**沒有任何開源輸入法**。
社群那份 `IMEConfig.xml` 教學列的 tag 也全是微軟系＋自然輸入法——
**沒有新酷音的**。PIME #115 的發問者當年卡住的原因就是「找不到新酷音的
displayName 與 tag」，因為**根本不存在**。

**結論**（⛔ **2026-09-15 作廢**，見本篇開頭的更正）：LOL 遊戲內打中文
這件事，**不是我們能修的**——決定權在 Riot 那份支援清單，不在輸入法。
做 UI-less 也沒用（白名單比對在協商之前）。使用者要在遊戲內打中文，
只能用清單上認得的輸入法（微軟注音）。README 的遊戲段就寫這句話。
相容性測試清單的 H11 記「－ 未涵蓋（遊戲不載入本輸入法）」。

**給使用者的三條路**（⛔ **作廢**，我們自己就能用，README 不要寫）：

1. **進遊戲前切成微軟注音**（Win+空白），打完切回來——唯一可靠的方式
2. **在大廳打字**，大廳是 CEF、完全正常；受影響的只有遊戲進行中那個聊天框
3. 改遊戲的 `IMEConfig.xml`——**不建議**，見 §2.58.8

### 2.58.0.1 對照組：Minecraft（Java 版）——同樣打不進去，但**有解**

順手量的另一個遊戲，結論與 LOL **相反**，正好把「遊戲打不出中文」
拆成兩種完全不同的病。

**實測（2026-09-07）**：使用者在 Minecraft Java 版**可以正常打中文**
——但**不是直接在遊戲聊天框打**，而是叫出 Windows 的輸入面板
（畫面上那個「灰色、旁邊有綠色箭頭」的小框），在那裡面組完字再插入
遊戲。**那個小框是一般的系統文字欄位**，我們在裡面能用，跟在記事本裡
能用是同一回事——**跟 Minecraft 支不支援輸入法無關**。

也就是說：**Minecraft 本身仍然打不了中文，使用者用的是系統提供的繞道。**
這與 RIME／小狼毫多筆「Minecraft 只能打英文」的回報（rime/home
#744、#959、#973、#1237）並不衝突——那些講的是直接在遊戲聊天框打字。

**但 Minecraft 的病因跟 LOL 完全不同，而且有解**：

| | LOL | Minecraft（Java 版） |
|---|---|---|
| 輸入層 | Scaleform GFxIME | **GLFW**（LWJGL 3） |
| 病因 | **白名單**：不在具名清單上就回 `GFxIME_NotSupported`、忽略所有 IME 訊息 | GLFW **完全不解析 IME 訊息**——查證實際抓原始碼搜過，`WM_IME_*` 一個都沒處理、IMM32 API 一次都沒呼叫；但 `WM_CHAR` 正常收 |
| 有沒有白名單 | **有** | **沒有**——機制上不可能有：`WM_CHAR` 是輸入法送出後由系統轉發的，收的那端認不出是誰送的，**沒有東西可以拿來比對清單** |
| 做 UI-less 有沒有用 | **沒用**，白名單比對在協商之前 | **有用**——輸入法自己畫候選、commit 時把結果丟進 `WM_CHAR`，遊戲就收得到 |
| 實證 | 新酷音做了 UI-less 仍未解決 LOL | **新酷音 26.4.1.0 就是這樣修好的** |

**決定性的一條**：新酷音 26.4.1.0（2026-04）的發佈公告寫
「**遊戲模式**：確保 UILess 模式下候選字游標單步移動，**改善 Minecraft
相容性**」。**若 Minecraft 真有白名單，再怎麼改 UILess 都不可能有效**
——這反過來證明了它沒有。

**附帶查證到的兩件事**（先前的假設是錯的）：

- **GLFW 3.4 沒有加入任何 IME API。** 官方 release notes 的 15 項新功能
  裡沒有 preedit 相關的東西。IME 支援的 issue（glfw#41，2013 年開）
  **至今 open**，實作 PR（glfw#2130）也還 open，都掛在 milestone 3.6。
  LWJGL 那邊的「合併 IME 修正」issue 已 closed——他們等上游。
- **基岩版原生支援 IME**（跟 Java 版不同技術棧），所以這個問題只在
  Java 版。

**這對本專案的意義**：Minecraft 是「A 案值得做」的**唯一已證實**案例
——但收益只是「少開一個灰色小框」。決定見 §2.58.7。


### 2.58.7 三條路與取捨

| | A. 做 UI-less 模式 | B. 拿掉 `UIELEMENTENABLED` 宣告 | C. 什麼都不改 |
|---|---|---|---|
| 做什麼 | 實作 `ITfUIElement`＋`ITfCandidateListUIElement`（＋讀音用的 `ITfReadingInformationUIElement`），候選視窗改成「先問宿主要不要畫」，宿主說不要就只餵資料 | `TSF_CATEGORIES` 少一項，其餘不動 | — |
| LOL 遊戲內 | 候選由遊戲畫，全螢幕與定位問題一起消失（**前提是遊戲內 UI 真的還是 Scaleform，且它的清單認得我們**，見 §2.58.2、§2.58.8） | 遊戲把我們當「不支援」，跟 PIME 2016 的回報一樣：只能打英文 | 現況：宿主以為我們支援，實際彈自己的視窗 |
| 其他 UI-less 宿主 | 全部受益 | 全部誠實地不啟用 | 全部被騙 |
| 工程量 | 中～大：候選視窗的狀態機要多一個「不畫」分支，`ui.rs`／`candidate_window.rs` 都要動；候選要改**翻頁**不能捲動；`EndUIElement` 兩種情況都要呼叫；`BeginUIElement` 的呼叫時序跟 CLAUDE.md 已知陷阱「COM 通知的入口不可以拿狀態鎖」要對齊（宿主在 `BeginUIElement` 裡回呼我們的機率不低） | 一行，**但要提權重新註冊**（改了類別，見 CLAUDE.md「改程式碼不需要重新註冊」的例外） | 零 |
| 何時做 | 量完（§2.58.6 第 4 步證實候選拿不到）之後決定 | **量完就做**，不管結果——現況是錯的宣告 | 不接受 |

**量完的結論（2026-09-07，見 §2.58.0）：B 現在做；A 仍然值得做，
但理由不是 LOL。**

**A 對 LOL 確實沒用**，而且原因比「第 4 步量到候選拿不到」更前面：
遊戲連我們的 DLL 都不載入。**Scaleform 的白名單比對發生在 UI-less
協商之前**——不在清單上就回 `GFxIME_NotSupported` 並忽略全部 IME 訊息，
再完美的 `ITfCandidateListUIElement` 也沒有機會被問到。

**但「A 救不了 LOL」不等於「A 沒價值」**（初稿一度這樣寫，是錯的推論
——見 §2.58.10 的第二條教訓）。新酷音的歷程正好是反證：

| 時間 | 事件 |
|---|---|
| 2016 | PIME issue #90／#115 回報 LOL 只能打英文，**至今 open、零則留言** |
| 2016-08 | PIME #185，maintainer KenLuoTW 正式診斷：「有些遊戲可能採用了自己的方式去繪製輸入法 UI，**這須要 PIME 支援 UILess Mode 才能支援**」 |
| 2016-09 | PIME #199「需要讓輸入法可以辨識自己是否為 uiless mode」，**至今 open**——PIME 從未補上 |
| 2025-07 | 換架構後的 `windows-chewing-tsf` commit `0723ca5` **實作 UILess mode**；**25.8.1.0** 發佈公告寫「UILess 模式：支援無介面模式運作，**與全螢幕遊戲相容**」 |
| 2026-04 | **26.4.1.0** 發佈公告的「重要修復」：「**遊戲模式**：確保 UILess 模式下候選字游標單步移動，**改善 Minecraft 相容性**」（commit `b98db5c`） |

**新酷音做了 UI-less，而且明確是為了遊戲——但沒有任何一則證據顯示
LOL 因此能打中文。** 官方公告講的是泛稱「全螢幕遊戲」，從未點名 LOL，
也查不到使用者實測回報。這與白名單機制的推論完全一致：UI-less 是
**必要條件，不是充分條件**。

所以 A 的真正收益是**自繪 UI 但沒有白名單**的那一類遊戲——
**Minecraft 是已證實的代表**（見 §2.58.0.1），LOL 不是。

**決定（2026-09-07）：A 與 B 都先不做，維持現狀。**

> **2026-09-15 補**：這個決定**結果仍然成立，但理由要換**。原本的理由
> 是「A 救不了 LOL，唯一收益只有 Minecraft」；現在 LOL 本來就能用，
> A 對 LOL 更沒有必要。**A 依然擱置、B 依然跟著不做**，下方「代價要
> 記著」那條（錯的 `UIELEMENTENABLED` 宣告）也依然有效。

- **A 擱置**：唯一確定的收益是「Minecraft 能直接在遊戲聊天框打字」，
  而使用者現在靠 Windows 的輸入面板（那個灰色小框）已經打得出來，
  只是多一個步驟。工程量中～大，收益是「少按一個鍵」。
  **之後有人提再做。**
- **B 跟著不做**：B 與 A **互斥**——拿掉 `UIELEMENTENABLED` 之後，
  日後要做 A 得把它加回來，又一次提權註冊。既然保留了做 A 的可能，
  先做 B 反而多跑一次。
- **代價要記著**：現況是**錯的宣告**（宿主以為我們支援 UI-less，
  實際不支援）。log 顯示這台機器上目前沒有任何宿主用 UI-less 啟用
  我們（旗標都是 `0x0`），所以還沒真的害到誰——**但這是「還沒遇到」
  不是「沒問題」**。哪天有宿主真的用 `TF_TMAE_UIELEMENTENABLEDONLY`
  啟用我們，症狀會是「候選視窗該讓宿主畫卻自己彈出來」。
  `registration.rs` 的類別表旁邊已經加了警語註解指到本節。

A 若日後要做，兩份參考實作：微軟 DXUT 的 `Optional/ImeUi.cpp`
（**宿主端**，`CTsfUiLessMode` 第 345 行起，看遊戲期待 TIP 怎麼表現）、
以及新酷音的 `tip/src/text_service/ui_elements/candidate_list.rs`
（**輸入法端**，`#[implement(ITfUIElement, ITfCandidateListUIElement)]`，
跟我們同樣是 Rust ＋ `windows` crate，最直接可比）。

**新酷音踩過、我們一定會遇到的坑**：UI-less 下方向鍵語意不同。一般
模式是 3×3 九宮格，UI-less 由宿主畫、多為直式單列，**上下左右都必須
一次只移動一格**（commit `b98db5c` 修的就是這個，PIME #199 提的也是
同一個坑）。這跟 §2.58.3 講的「要翻頁不要捲動」是同一類問題：
UI-less 下候選的**互動語意**由宿主決定，不是我們。

初稿把 A 排在「簽章之後」，理由是怕 Vanguard 白做——**那個理由早就
撤銷**（§2.58.4）。

**量測前先做的那件小事已經做了**：接住 `ActivateEx` 的 `dwFlags` 並
寫進 log（commit `fbb39d0`）。它在這次量測裡的實際貢獻是**排除法**
——log 裡那幾筆 `ActivateEx` 一比對就知道是 VS Code 不是遊戲，
否則「技能正常」這個結果會被誤讀成「空 context 機制生效了」。

A 若日後要做，先讀微軟 DXUT 的 `Optional/ImeUi.cpp`（宿主端的完整參考
實作，`CTsfUiLessMode` 那個類別，第 345 行起）——那是遊戲端**期待 TIP
怎麼表現**的最權威範本，比讀規格快。

### 2.58.8 不做的兩條路

**改遊戲的 `IMEConfig` 把自己加進去。**那是社群懶人包的做法，Garena
時代可行；除了「改遊戲資料夾的檔案在 kernel 級反作弊時代是自找麻煩」
之外，還有兩個查證出來的理由：那篇懶人包的作者在 **2023-01-06 台服轉
Riot 伺服器後明言停止更新**，而留言區從 **2018 年起就有人回報「更新後
IMEConfig 檔直接消失」「方法失效」**。而且那是使用者端的 hack，不是
輸入法能發布的東西。就算 A 做好了，遊戲認不認我們是 Riot 那份清單決定
的，不是我們決定的——這是 A 收益不確定的根本原因。

**另寫一個 IMM32 的 IME DLL。**Win11 還裝得了 IMM32 IME（懶人包的
舊微軟注音就是），但那是**第二套平台層**，跟 Phase 6 跨平台的成本同一
量級，換來的只有「Scaleform 那類 2017 年前的遊戲 UI」。不值得。
