# 英雄聯盟：評估階段的推論與查證

> **狀態**：評估階段的推論，實測後多條被推翻

> 推錯的地方一樣有參考價值。**實測結果與最後的決定見 [[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]]。**

> 踢出遊戲、Riot 官方叫人切回微軟輸入法），已在文中逐條標明。留著那些

### 2.58.1 結論先講（評估階段的預期，部分已被 [[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]] 推翻）

**LOL 是兩個宿主，不是一個。**大廳（`LeagueClientUx.exe`）是 CEF，
跟 Chrome 同一條路，H4 通過它就通過（已查證：Riot 官方技術部落格與
CEF 升級公告都確認大廳用 Chromium Embedded Framework；**實測也過**）。
**真正的問題只在遊戲內（`League of Legends.exe`）的聊天框**，那裡的
UI 歷史上是 Scaleform GFx，輸入法走的是 **IMM32**，而且**遊戲自己畫
組字與候選**——不是我們的候選視窗看不看得到的問題，是遊戲根本不會去
看我們的視窗。（**實測更極端**：遊戲連載都不載入我們，見 [[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]]。）

三件原本預期會壞的事，依嚴重度排：

| # | 症狀（預期） | 根因 | 實測結果 |
|---|---|---|---|
| 1 | **沒開聊天框時按 Q 放技能變成組字** | 遊戲關掉聊天框時是否用 `ImmAssociateContext(NULL)` 收回 IME，橋接層會不會把它翻成 `GUID_COMPARTMENT_EMPTYCONTEXT` | **沒發生**，但不是靠這個機制——我們不在遊戲行程裡。這條在 LOL 上量不到 |
| 2 | 組字看得到、**候選看不到或空的** | 遊戲用 `ImmGetCandidateList` 拿候選，橋接層只在 TIP 真的走 **UI-less 模式**時填得出來——我們沒做，**卻宣告了自己會做** | **連組字都沒有**——遊戲直接出英文。宣告不實的問題本身仍然成立 |
| 3 | 候選視窗跟著滑鼠跑／被遊戲蓋住 | 遊戲沒有 caret，定位退路一路掉到 `GetCursorPos`；真獨佔全螢幕時 topmost 視窗未必畫得出來 | **不適用**——沒有候選視窗會出現 |

**做法的順序**（已依實測更新）：LOL 這條路走不通，**方案 A 不做**；
**方案 B 照做**（拿掉沒有實作支撐的宣告，理由與 LOL 無關）。
**不要做的**：改遊戲的 `IMEConfig`（§2.58.8）。

### 2.58.2 LOL 的輸入路徑：Scaleform GFxIME ＋ IMM32

台灣 LOL 圈有一篇從 2014 年一路更新到 2023 年 Riot 接手伺服器的
懶人包（巴哈姆特，作者顯示名 Smokeycat）——「解決 Win8、Win10 在 LOL
中無法選字問題」。症狀是**大廳能打、進遊戲就選不了字或打出來是空白**，
解法是把 TSF 架構的「微軟新注音」換成 IMM32 架構的舊「微軟注音」，
或者去改遊戲資料夾裡的 `IMEConfig.xml`，給輸入法補一組
`imeName`／`displayName`／`Tag`（**已查證，原文逐字**）：

```xml
<imeName>微軟注音</imeName>
<displayName>New Phonetic</displayName>
<Tag>GFxIME_Ch_Trad_NewPhonetic</Tag>
```

新酷音（PIME）2016 年就有同樣的回報：issue #90「在遊戲進行中時新酷音
輸入法是完全無法使用的狀態」，只出得來英文字母；issue #115 問的正是
「需要在 win 10 下的標籤」（**已查證，兩則都在，#115 至今 open**）。

這幾條線索拼起來就是 Scaleform 的 IME 機制（Autodesk 文件叫
**Data Driven IME Registration System**）。官方文件寫得比社群推測還白
（**已查證，原文**）：

> During IME initialization, we first obtain a list of IMEs installed on
> the user's system and compare this list to the list of supported IMEs.
> **Only IMEs that are common between the two lists would appear in the
> Scaleform language bar.** For non-supported IMEs, we simply ignore all
> IME related messages and **return GFxIME_NotSupported** from the
> HandleEvent call.

> The new data driven system will expose the list of supported IMEs in an
> **XML format** and allow customers to modify this list ... **without
> needing to rebuild Scaleform Player or GFxIME.**

也就是說：**取交集、不在清單上的當作不存在**——這就是「只能打出英文
字母」的來源；而清單是 XML、可以加條目不重編遊戲，那正是社群懶人包在
改的東西。它列舉的方式是讀 `SYSTEM\CurrentControlSet\Control\Keyboard Layouts`
登錄機碼。組字字串與候選清單則由 `libgfx_ime` 的 C++ 用 IMM32 拿
（`ImmGetCompositionString`／`ImmGetCandidateList`），再**用 Flash 自己畫**。

**⚠ 但「LOL 現在還在用 Scaleform」查不到證據。** 只查得到歷史 patch
notes 提過 Scaleform 在畫遊戲內聊天，而 **Autodesk 已於 2017-07-12
停售並停止支援 Scaleform**，Riot 近年也重寫過遊戲內 UI。那份 Autodesk
文件寫的是 Windows XP／Vista／7 年代。所以本節的 Scaleform 推論要當成
**「2017 年前確定如此，現況未經證實」**——§2.58.6 第 4 步量到的結果
才是真的。

**這跟全螢幕沒有關係。**社群回報「Win10 下全螢幕或視窗模式都能選字」
（在 IMEConfig 補好之後），因為候選是遊戲畫在自己的畫面裡的。
我們的候選視窗在這個宿主裡**本來就不該出現**。

### 2.58.3 一個 TSF TIP 在 IMM32 宿主裡是怎麼跑的

Windows 對「不認識 TSF 的程式」有一層橋，把 IMM32 的呼叫翻成 TSF、
再把 TIP 的動作翻回 `WM_IME_*` 訊息。微軟官方文件描述了這個機制但
**沒給它名字**（`ImmDisableTextFrameService` 頁說 TSF 的功能也提供給
那些不是為 TSF 寫的程式，條件是 `Msctf.dll` 與 `Msimtf.dll` 都載入）；
業界慣稱的 **CUAS（Cicero Unaware Application Support）**只在非官方
來源查得到，Cicero 是 TSF 的舊代號。三個環節各有各的坑：

**組字字串（預期會通）。**`InsertTextAtSelection`＋`StartComposition`
在橋接層會變成 `WM_IME_COMPOSITION`＋`GCS_COMPSTR`，送出走
`GCS_RESULTSTR`——這兩個旗標的語意有微軟官方文件（前者是「使用者正在
組的、也是組字視窗顯示的那串」，後者是「使用者即將完成組字」）。
**但要誠實說**：官方沒有保證橋接層一定會把 TSF TIP 的組字狀態完整
合成為這兩則訊息，而下一段的候選清單正好證明**這層轉譯是有缺口的**。
所以「組字會通」是有根據的推測，不是保證。另**待量一件**：自動模式的
組字區顯示的是原始按鍵（`su3cl3`），遊戲會把那串畫在聊天框裡，看起來
會像打錯了——那是既有設計，不是 bug，但要知道。

**候選清單（預期會壞）。**`ImmGetCandidateList` 對 TSF 輸入法拿不到
候選，是遊戲圈的已知問題。微軟國際化工程師 Michael Kaplan 2008 年講得
最準：**這個失效是選擇性的**——不是所有 IME 都壞，只有一部分，因為
Vista 起 IME 全面從 IMM-based 轉成 TSF-based，而相容層覆蓋不完全；
他的結論是應用程式應該改用 TSF。微軟自家 DXUT 的
`Optional/ImeUi.cpp` 就有這句（**已查證，逐字**）：

```cpp
// In Vista, we have to use TSF since few IMM functions don't work as expected.
```

它為此另外實作了一整個 `CTsfUiLessMode`（第 345 行），用
`ActivateEx(&cid, TF_TMAE_UIELEMENTENABLEDONLY)` 啟用、`AdviseSink` 掛
`ITfUIElementSink`，在 `BeginUIElement`／`UpdateUIElement`／`EndUIElement`
三個回呼裡用 QI 分流 `ITfReadingInformationUIElement` 與
`ITfCandidateListUIElement`；同時保留 IMM32 的 `ImmGetCandidateList`
包裝當退路，用 `g_bUILessMode` 切換——**兩條路並存**，正是「只有部分
IME 壞掉」的工程回應。

規格上，橋接層能填給 IMM32 程式的候選**只能來自 TIP 主動交出來的
`ITfCandidateListUIElement`**——也就是 UI-less 模式：TIP 顯示任何 UI
之前先呼叫 `ITfUIElementMgr::BeginUIElement`，宿主回 `pbShow=FALSE`
就代表「我自己畫，你把內容給我」（**已查證**：官方寫的是宿主回 TRUE
代表「我不想畫，你自己畫」，回 FALSE 代表「不准你畫，我從 `pElement`
拿資料自己畫」）。之後每次候選變動呼叫 `UpdateUIElement`，收掉時
`EndUIElement`。

規格還有三條初稿沒提、但實作時會咬人的**不對稱規則**：

- `UpdateUIElement` **只在 `pbShow=FALSE` 時才是必須的**；`EndUIElement`
  則**兩種情況都要呼叫**，宿主靠它追蹤元素生命週期
- 內容不必在 `BeginUIElement` 當下就備妥——第一次 `UpdateUIElement`
  的 update flag 會是全位元
- 候選清單在 UI-less 下**要用翻頁不要用捲動**（官方明說候選還在的時候
  改 page index 不是好主意），因為宿主會對不上

**進入 UI-less 有兩個閘門，我們兩個都過了——這才是問題所在。**

| 閘門 | 官方要求 | 我們 |
|---|---|---|
| 註冊 `GUID_TFCAT_TIPCAP_UIELEMENTENABLED` | `ActivateEx` 的 `TF_TMAE_UIELEMENTENABLEDONLY` 只啟用有這個類別的 TIP | ✅ 有（`registration.rs` 的 `TSF_CATEGORIES`） |
| 實作 `ITfTextInputProcessorEx` | 官方明寫：沒實作這個介面的 TIP 不會在 UI-less 執行緒被啟用 | ✅ 有（`text_service/mod.rs`） |
| 實際走 `ITfUIElementMgr` 呈現所有 UI | 官方明寫：屬於這個類別的 TIP **必須**用 `ITfUIElementMgr` 顯示任何 UI | ❌ **沒有** |

也就是說，**我們對外的資格完全合格，宿主會真的把我們啟用起來，然後我們
照樣自己彈視窗，而它等的 `BeginUIElement` 永遠不會來。**這不是漏做一半，
是宣告與行為不符。這也不只是 LOL 的事：任何用
`TF_TMAE_UIELEMENTENABLEDONLY` 啟用執行緒的程式（全螢幕遊戲、自繪 UI
的軟體）都被騙了。**兩條路擇一**（[[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]] 的 A 或 B），不能維持現狀。

還有一個**現在就看得到的線索沒接**：`ActivateEx` 的 `dwFlags` 正是宿主
用來說「這是 UI-less 執行緒」的旗標，而我們的實作直接把它丟掉
（`_dwflags`，轉呼叫 `Activate`）。接住它並寫進 debug log，量測時就能
直接看到宿主有沒有以 UI-less 啟用我們——這是 A 案最小的第一步，
改動極小。

**候選視窗定位（預期會退到滑鼠）。**`caret_anchor` 的鏈是
`GetTextExt` → `GetScreenExt` → `GetGUIThreadInfo` → `GetCursorPos`。
遊戲視窗沒有 Win32 caret，橋接層對 `GetTextExt` 多半回
`TS_E_NOLAYOUT`（[[候選視窗跑到滑鼠旁邊：網頁欄位的 TS_E_NOLAYOUT]] 的網頁欄位就是這樣），`GetScreenExt` 若能答
會給整個遊戲視窗的矩形——那視窗本身就是整個螢幕。所以要嘛貼在螢幕
左下、要嘛跟著滑鼠。**但這件事在 UI-less 做好之後就不存在**——遊戲
自己畫，我們不用定位。

**全螢幕可見性（次要，且初稿把風險低估了）。**初稿寫「Windows 11 已經
沒有真正的獨佔全螢幕」——**這是錯的**。微軟 DirectX 部落格的說法是
Fullscreen Optimizations **攔截**全螢幕獨佔、改用 DWM 的最佳化無邊框
視窗（原文的說法是「你的遊戲以為自己在獨佔全螢幕，實際上 Windows 讓它
跑在無邊框視窗模式」），但**真獨佔並沒有被移除**——使用者在 exe
相容性頁勾「停用全螢幕最佳化」就退回去，那個選項存在的意義就是這個。
正確的說法是**「預設被接管，不是不存在」**，所以 topmost 視窗畫不出來
的風險比初稿估的高。Godot 編輯器在 Win10 全螢幕下「IME 能打但候選視窗
看不到」的 issue #48714 至今仍 open（**已查證**），代表這條路**還是會
踩到**。同上——UI-less 做好之後不需要我們的視窗，這條自然消失；沒做好
之前，逃生口是遊戲的「無邊框」模式。

**另一條要劃掉的**：微軟建議遊戲在 `WM_IME_SETCONTEXT` 把 `lParam`
清成 0 來抑制系統 IME 視窗——這是真的（官方文件與 DXUT 原始碼都有），
**但它只對 IMM32 IME 有效**，`WM_IME_SETCONTEXT` 是 imm32.dll 的 API
不是 msctf.dll 的。微軟 Q&A 上有實測回報確認這點，而微軟員工在同一串
的建議正是「改走 UI-less mode」。所以**遊戲清 lParam 這招管不到我們**，
遊戲全螢幕的候選視窗問題只有 UI-less 契約一條路。

### 2.58.4 Vanguard：初稿的兩條主張都查不到

這一段初稿寫得最篤定，查證後**最站不住**。分開講：

**站得住的**（已查證）：

- 2024-04-11 起 LOL 強制 Vanguard，kernel 級
- 「VAN: Incompatible Software」這個錯誤真的存在，Riot 官方支援頁有此標題
- FanControl（issue #2481，2024-05-01）與 OpenRGB（GitLab issue #316）
  確實因為 `inpoutx64.sys` 被擋——理由是那支驅動有權限提升漏洞，
  OpenRGB 已改用 WinRing0

**⚠ 查不到的（初稿當成前提在用）**：

- **「Vanguard 走訪模組清單比對簽章、所以沒簽章的 DLL 有風險」——沒有
  可靠證據。** Riot 官方材料（Vanguard On-Demand 公告）談的全是**驅動
  層**：Runtime Driver Attestation、進入遊戲的裝置驅動清單、易受攻擊
  驅動黑名單、Secure Boot ＋ DSE 擋未簽章的作弊驅動。「使用者模式 DLL
  的簽章檢查」只在第三方外掛分析站看到，而且那裡講的 signatures
  是**外掛特徵碼比對**，不是 Authenticode 數位簽章驗證——兩件事不能
  混為一談。**沒有證據說沒簽章的 DLL 會因此被擋。**
- **「PIME 進 LOL 被 Vanguard 判不相容、換 windows-chewing-tsf 就正常」
  ——零證據。** 搜尋引擎摘要會生成這句話，但逐一打開它引用的來源，
  沒有一篇真的有這段內容。實際找到的 PTT 串：「被強上 Vanguard 後進不去
  遊戲」通篇**沒提輸入法**；「無蝦米輸入法無法打中文」是 **2018 年**
  的事，早於 Vanguard 六年，起因是遊戲更新後舊版無蝦米與遊戲不相容。
  而且**無蝦米不是 PIME**，把兩者當同一件事讓這條更站不住。
- **「Riot 官方叫人進遊戲前切回微軟輸入法」——查不到**，而且那句話的
  措辭幾乎與**微軟** Compatibility Cookbook 的「Third-party input method
  editors」一文雷同。疑似是搜尋引擎把微軟的話安到 Riot 頭上。
  （Riot 支援站是純前端渲染，抓不到內文，所以只能說「無法證實」，
  不是「確定沒有」。）

**修正後對我們的意義**：DLL 是 Windows 依註冊表載進遊戲行程的，跟被擋
的核心驅動不是同一類；**「沒簽章所以會被 Vanguard 擋」這個擔憂目前沒有
根據**。相容性測試清單 H11 早就為此標成可跳過，那個保守選擇仍然合理
（kernel 級反作弊 ＋ 沒實測過 ＝ 未知風險），但**理由要從「已知會被擋」
降級成「未知」**。

連帶要改的還有一件事：初稿據此推出「**UI-less 那種工程量在簽章前不值得
投入**，做完可能還是被 Vanguard 擋」——**這個時程理由不成立**。要不要
做 A 應該由 §2.58.6 第 4 步量到的結果決定，不是由簽章決定。

**測的時候的底線**（不管上面怎麼修，這幾條照舊）：

1. 用**自訂／練習模式**測，不進積分——被踢出遊戲在對戰裡是害到隊友
2. 出現「VAN: Incompatible Software」就**停**，記下完整錯誤碼，不要
   反覆重試
3. 未知風險仍然是風險：H11 不是發布阻擋條件，不想冒險就照原決定跳過

### 2.58.5 「按 Q 放技能變成組字」——最要命、也最容易漏掉的一條

`keymap` 在 `Mode::Idle`（沒組字）對**所有字母鍵都有綁定**——
測試裡就寫著 `assert!(lookup(Mode::Idle, 0x41).is_some())`，這是自動
模式的本意：第一個字母就開始組字。在文書程式沒問題，在遊戲裡等於每一個
技能鍵都會被我們接走。

擋住它的機制**理論上已經在**：遊戲關掉聊天框時會
`ImmAssociateContext(hwnd, NULL)`（Scaleform 只在 IME 文字欄有焦點時
開 IME），橋接層把它翻成 TSF 的空 context，而 `document::keyboard_disabled`
**已經看** `GUID_COMPARTMENT_EMPTYCONTEXT`——那是 [[密碼欄位與帳號欄位]] 為密碼欄做的，
語意就是「宿主要求輸入法退場」。`refresh_password` 在每一段組字的
第一鍵重問一次，所以焦點從聊天框回到遊戲後的第一個技能鍵就會重判。

**但沒有量過**：橋接層對 `ImmAssociateContext(NULL)` 的翻法（空 context
vs 換成另一個 document manager vs 根本不通知）沒有文件保證。這是
§2.58.6 的第 1 步，它不過關的話**後面全部不用測**——一個會吃掉技能鍵
的輸入法，在遊戲裡的正確行為只有「完全不介入」。

退路永遠在：**Ctrl 鎖英文＋半形**是「等同關掉輸入法」的狀態
（見第四章「鎖定英文半形完全不組字」），按鍵原樣進宿主。這是要寫進
README 遊戲段的一句話，不管量出什麼結果。

### 2.58.6 量測計畫（照順序，前一步是後一步的前提）

> **✅ 這張表已經跑過（2026-09-07），結果見 [[英雄聯盟遊戲內可以打中文：全螢幕看不到輸入法指示器，誤判成不載入 DLL]]。**摘要：第 1 步過
> （但理由與預期不同）、第 7 步過、第 2～5 步**前提不成立**——遊戲不
> 載入我們的 DLL，所以「輸入法在遊戲裡的行為」無從量起。表留著是因為
> 它對**別的** IMM32 宿主仍然適用，換個宿主照樣能跑。

前置：`.\build-ime.ps1`、`.\check-dll.ps1`、`data\debug.on`、
**LOL 整個關掉重開**（Riot Client 在系統匣有背景行程，那也要關）。
遊戲設「無邊框」開始，全螢幕留到最後。

### 2.58.10 這一節本身的教訓：推論鏈很長時，錯的是最舒服的那一環

這一節初稿寫得條理分明、每段都有來源，查證之後**三條主張塌掉、兩條
方向錯了**：

| 初稿說 | 實際 |
|---|---|
| Vanguard 走訪模組清單比對簽章，我們沒簽章所以有風險 | 官方材料只談驅動層；「模組簽章檢查」查不到，非權威來源講的是外掛特徵碼 |
| PIME 進 LOL 被 Vanguard 踢，換 windows-chewing-tsf 就好 | 零證據。找到的 PTT 串一則沒提輸入法，另一則是 2018 年的無蝦米，早六年；而且無蝦米不是 PIME |
| Riot 官方叫人進遊戲前切回微軟輸入法 | 查不到。措辭幾乎與**微軟** Compatibility Cookbook 同一篇文章雷同 |
| Win11 已經沒有真正的獨佔全螢幕 | 真獨佔還在，只是預設被 FSO 接管；停用最佳化就退回去——**風險比初稿估的高** |
| 遊戲清 `WM_IME_SETCONTEXT` 的 lParam 抑制我們的視窗 | 那是 imm32 的 API，**對 TSF TIP 無效** |

錯的裡面有三條**都是搜尋引擎摘要的產物**——摘要把數個來源揉成一段
通順的話，打開來源卻沒有那句。這比「找不到資料」更危險，因為它讀起來
就像已經查證過了。

**實測之後又多兩條**（這次錯的是「量測結論」而不是「查證」）：

| 量完當下說 | 實際 |
|---|---|
| 第 1 步過關 ＝ 空 context 機制擋住了技能鍵 | **不是**。技能正常是因為我們不在遊戲行程裡。原本要驗的那條（`ImmAssociateContext(NULL)` 會不會被翻成空 context）**在 LOL 上根本量不到**，仍然未驗證 |
| 遊戲不載入我們 → 所以 UI-less（A 案）沒價值，不做 | **推論跳太快**。「A 救不了 LOL」為真，「A 沒價值」為假——A 決定的是魔獸世界、Minecraft 那類**沒有白名單、只是自繪 UI** 的遊戲。新酷音 2025 年就是為此做的 |

第一條是**把「結果對」誤讀成「機制對」**：預期的保護機制與實際的原因
完全不同，而症狀一模一樣。要不是新加的 `[啟用]` log 讓我發現那幾筆
`ActivateEx` 是 VS Code 不是遊戲，這個誤讀會直接寫進文件當成「已驗證」。
**加一行 log 的價值在這裡——它讓「沒發生」與「沒被觸發」分得開。**

第二條是**否定了前提就順手否定結論**：LOL 這個案例確實不需要 A，
但 A 從來就不只服務 LOL。查了新酷音才發現他們早就走完這條路——
做了 UI-less、明確為了遊戲、而且**一樣沒解決 LOL**。同一件事的兩面
（該做、但救不了這個特定遊戲）如果只看一面，會得出相反的行動。

**2026-09-15 又多一條，而且比前兩條更根本：整個實測結論都是錯的。**

| 2026-09-07 量到 | 2026-09-15 實際 |
|---|---|
| 遊戲只出英文字母、log 零筆 → 遊戲不載入我們 | **那次根本沒切到我們的輸入法**。切過去之後遊戲內中文全部正常 |

**錯在哪**：`log 零筆` 同時符合兩種解釋——「遊戲不載入我們」與
「沒切到我們」。當時之所以只考慮前者，是因為「視窗模式下工作列顯示的
正是通譯輸入法」看起來排除了後者。**但那個排除用的觀察本身不可靠**：
**全螢幕遊戲把工作列整個蓋掉，當下根本沒有辦法確認輸入法是哪一個**，
視窗模式讀到的值不能代表全螢幕當下的狀態。

於是一個看錯的前提，往上長出了「Scaleform 白名單」「不是我們能修的」
「H11 以後不必測」「README 要叫使用者切微軟注音」一整串結論——而且
每一步的推理都沒有毛病，錯的只有最底下那一格。**這正是本節標題那句話
的又一次實例，只是這次錯的不是查證，是量測環境。**

判準：**「證據是零」有兩種解釋——東西不在，或你的量測沒接上。**
排除後者所用的那個觀察，要先確認它在當下真的觀察得到。

四個可以帶走的判準：

- **打開來源再引用。**摘要層級的「某某回報說」不算數。這次每一條假訊息
  在點進去之後都當場垮掉。
- **越舒服的推論越要查。**「沒簽章 → 反作弊會擋」聽起來天經地義，所以
  初稿拿它當前提推出了「A 案要等簽章之後再做」的時程決定。一個沒查證
  的前提，撐起了一個真的會影響排程的結論。

  文件裡的完成宣告要跟程式碼對得起來，不然下一個人（包括三個月後的
