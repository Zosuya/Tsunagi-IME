# 候選視窗跑到滑鼠旁邊：網頁欄位的 `TS_E_NOLAYOUT`

> **狀態**：主修法已驗收；ITfTextLayoutSink 那條正解仍未做（spike 把宿主弄死後整段移除）

使用者回報「某些網站的搜尋欄，候選視窗不會貼在游標附近」，實例是
YouTube 的搜尋欄（宿主 Firefox）。

### 2.38.1 量出來的原因

埋 log 量一輪就清楚了——**12 次定位，12 次全部失敗**，錯誤碼都是
`0x80040206`（`TS_E_NOLAYOUT`）：

```text
[定位] GetTextExt 失敗 hr=0x80040206 (TS_E_NOLAYOUT 版面還沒算好) → 退路
[定位] 退路：只剩滑鼠位置 (-1546,165)
[定位] 退路：只剩滑鼠位置 (-1356,181)      ← 座標一路變，那是滑鼠軌跡
```

`TS_E_NOLAYOUT` **不是錯誤，是「等一下再問」**：宿主說這段文字的版面
還沒算好，現在答不出座標。網頁欄位特別容易踩到——YouTube 搜尋欄一打字
就彈建議清單、整塊重排。Firefox 與 Chromium 都會這樣，這是它們 TSF
實作的正常行為。

問題出在**我們把它當一般失敗**：第一層失手就直接掉到最後的保底
（滑鼠位置），於是候選視窗跟著滑鼠跑。中間那層 `GetGUIThreadInfo`
在瀏覽器本來就查不到（多行程，§已記在 `candidate_window` 的註解），
等於沒有緩衝。

### 2.38.2 解法：`GetScreenExt` 當中間退路

`ITfContextView::GetScreenExt` 問的是「這塊文字區整體在螢幕的哪裡」，
**不需要逐字版面**，所以版面沒算好的當下仍答得出來。

實測 YouTube 搜尋欄回的是矮扁矩形，而且右緣會隨輸入變動——那就是
搜尋框本身，不是整個網頁內容區：

```text
[定位] 退路：GetScreenExt rc=(-1594,148,-1011,174) 寬583 高26
[定位] 退路：GetScreenExt rc=(-1594,148,-1038,174) 寬556 高26
```

修好之後同一個場景重測：**29 次 `NOLAYOUT` 全部被這層接住，滑鼠退路
0 次**。

退路的順序現在是：

| 層 | 問什麼 | 何時用得上 |
|---|---|---|
| 1 | `GetTextExt` | 正常情況，精確到游標 |
| 2 | `GetScreenExt` | 版面沒算好（網頁欄位），精確到「哪個框」 |
| 3 | `GetGUIThreadInfo` | 單行程 App 的保險（瀏覽器查不到） |
| 4 | 滑鼠位置 | 最後保底 |

**這是「貼對框」不是「貼對字」**：單行搜尋框剛好等於精確，多行編輯區
（留言框、Word 內文）拿到的是整塊區域，落點會是那塊的左下角。要精確到
游標那一格得靠下一節那條路。

### 2.38.3 正解還沒做：`ITfTextLayoutSink` 的通知，而且 spike 把宿主弄死了

`TS_E_NOLAYOUT` 官方配套的處理是登記 `ITfTextLayoutSink`，宿主算完版面
會呼叫 `OnLayoutChange`，那時重新問一次並移動候選視窗。

spike 寫了，**一測就把宿主卡死**。原因是 `OnLayoutChange` 裡去拿了
狀態鎖——那個鎖不可重入，宿主在我們已持鎖時送通知，同一條執行緒鎖
第二次就死鎖。**這正是 [[架構決策與程式碼導覽]] 記過的「一打字瀏覽器就卡死」同一個坑**，
上次發生在 `OnKeyDown`，這次換個入口又踩一次。

診斷靠的是 log 的形狀：**通知那行 log 一次都沒印出來**，而印它之前
唯一做的事就是拿鎖。

因為那條路還沒驗證成功，**spike 的程式碼整段移除、不留死碼**。日後
要接續，兩個要求先寫在這裡：

- `OnLayoutChange` **完全不碰狀態鎖**（要讀狀態只能用「拿不到就放棄」
  的方式）
- 登記與取消登記要成對，`Deactivate` 時一定要 `UnadviseSink`——不拆的話
  context 會一直握著我們的參考

順帶一提，這輪也確認了 `TS_E_NOLAYOUT` 的實際數值是 `0x80040206`
（`TF_E_NOLAYOUT` 是它的別名）。程式裡的錯誤碼對照表一度寫成
`0x80040300`，那是憑印象寫的，log 量出來才發現不對——又一次
「不要靠推論，埋 log 量數值」。
