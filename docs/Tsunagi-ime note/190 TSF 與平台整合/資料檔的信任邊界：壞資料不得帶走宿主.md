# 資料檔的信任邊界：壞資料不得帶走宿主

發布前把「讀取使用者可寫入資料」的每一條路徑盤過一遍。動機是一個
結構性事實：這個 DLL 載在**每一個宿主行程**裡，而且註冊了
`GUID_TFCAT_TIPCAP_SECUREMODE`，UAC 提示框、鎖定畫面這些高權限行程也會
載入它、讀同一批資料檔。**讀資料的那一方權限比寫資料的那一方高**，
所以資料檔要當敵意輸入看。

### 2.37.1 誰能寫、誰會讀

| 位置 | 誰能寫 | 內容 |
|---|---|---|
| `data/`（DLL 旁） | 開發期是使用者資料夾底下；裝進 Program Files 之後只有管理員 | 二進位詞庫、接續矩陣、`priority.txt` |
| `%APPDATA%\tsunagi-ime\` | 同一位使用者的任何程式 | `config.toml`、`packs\*.txt`、`themes\*.toml`、`learned.txt` |

`data/` 那條邊界成不成立，**完全取決於安裝程式把 DLL 與資料放在哪**
（§2.35 已經是 Program Files）。開發期本來就沒有這條邊界——能改 `data/`
的人也能直接換掉 DLL。

### 2.37.2 找到的問題與修法

**一、壞的 `dict_ja.bin`／`dict_zh.bin` 會讓查詢無限迴圈，宿主整個凍結。
實測確認。**

`find` 用線性探測、遇到空槽才停。檔頭驗證原本只看 magic、版本、
位移遞增、槽數是二的冪，沒有防「每一槽都填了東西」。造一個檔頭全過、
每槽填非零的檔，`find` 三秒後還在跑。**這不是 panic，`guard.rs` 的
`catch_unwind` 攔不到**——症狀是每個宿主（含檔案總管）按一鍵就永久
凍結，比崩潰更糟。

修法兩刀：
- `find` 的探測次數封頂在槽數（`for _ in 0..slots` 取代 `loop`），
  順便擋掉槽裡指到不存在索引的情況
- 檔頭多驗「每一區宣告的元素數量塞不塞得進它到下一區的空間」
  （槽數區 ≤ `off_blk`、區塊表 ≤ `off_kana`、候選起點 ≤ `off_cand`、
  候選陣列 ≤ `off_surf`）——原本 `slots`／`n_read` 灌大會在查詢時
  切片越界，那是 panic、會被攔下降級成丟掉那一鍵，但仍是每一鍵都丟

**二、`connection_single_column.txt` 第一行寫個天文數字，宿主直接
abort。實測確認。**

`vec![0u16; n]` 配置失敗走的是 `handle_alloc_error`，那是 abort 不是
unwind，`catch_unwind` 攔不住、行程以 134 結束。只在 `dict_ja.bin` 不
存在、退回從文字重建時才會跑，而且在背景執行緒，但任何執行緒 abort
都會帶走整個宿主。修法：品詞 id 是 `u16`，邊長超過 65535 直接當作沒有
這個檔（mozc 是 2672）。

**三、領域包與學習檔的輸出文字沒有任何過濾。這是「包會流通」之後最
實際的風險。**

`pack::parse` 只切 TAB 與換行，第三欄原樣進索引、原樣送進文件。一個
惡意包可以把常見讀音對到含 U+202E（雙向覆寫）或零寬字元的字串——
使用者以為打的是 `github.com`，送出的在網址列與終端機裡看不出差別。
`incremental.rs` 那條 `is_control` 檢查的是**按鍵串**不是輸出。

修法：新模組 `core/src/sanitize.rs`，`is_safe_output()` 擋三類——
控制字元、Unicode 雙向控制字元、零寬與其他不可見的格式字元。包的
輸入欄與輸出欄、學習檔的文字欄載入時都過這關，整條丟掉、其餘不受
影響。**同形字（西里爾 а 冒充拉丁 a）不在這裡處理**——那是看得見的，
要靠混合字集偵測，先不做。

**四、`packs_dir` 與 `background.image` 可以是 UNC 路徑。**

`resolved_dir` 對自訂路徑照單全收，`background.rs` 週期性對它 stat，
候選視窗開啟時對圖片路徑做 `is_file`。指到 `\惡意主機\share` 的話，
每個宿主行程（含高權限的）會週期性發 SMB 連線，等於 NTLM 認證外洩，
而且 SMB 逾時會卡在按鍵那條執行緒上。輸入法用不到網路路徑，
`config::is_remote_path` 一律拒收（`\` 與 `//` 開頭）。前提是
`config.toml` 已被同使用者的程式改寫，嚴重度中等。

### 2.37.3 確認沒有問題的部分

- TOML 解析：一百萬層巢狀陣列不炸堆疊，壞檔退回預設
- 包名的路徑穿越：`pack::read` 有擋 `/`、`\`、`:`、`..`
- 主題檔只有顏色與描邊濃度，沒有路徑類欄位
- 字型只用名稱向 DirectWrite 查，不從使用者路徑載字型檔
- 圖片走 Windows 內建 WIC 解碼
- 設定頁三處「開啟資料夾」都先確認是資料夾或走固定路徑
- `panic.on` 只在 `panic-test` feature 才編進去
- mmap 的就地覆寫是 UB，靠「產生端先寫暫存檔再改名」守著（§2.10.5），
  安全性同樣落在 `data/` 的目錄權限上

### 2.37.4 驗證

- 六個回歸測試：每槽填滿的檔不卡死（日／中各一）、數量灌大被認出來、
  矩陣邊長灌大拒收、網路路徑拒收（設定與包各一）、藏不可見字元的
  包條目不收；加上 `sanitize` 自己的三個
- `cargo test` 441 通過；三支計分器一個數字沒動
  （570/570・560/570、677/720・2.5%、測資稽核 0）
- `bench_dict` 三本詞庫 9ms，代表真正的 `.bin` 沒有被新的檔頭檢查誤判
  成壞檔（誤判會退回文字重建，要 700ms）

### 2.37.5 教訓

**「不會 panic」不等於「不會帶走宿主」。** 崩潰隔離（[[崩潰隔離：panic 不得帶垮宿主]]）擋的是
unwind，這次找到的兩個洞一個是無限迴圈、一個是配置失敗的 abort，都
從 `catch_unwind` 旁邊繞過去。讀外部資料的迴圈要有上限，配置的大小
要有上限，這兩條跟 `catch_unwind` 是三件不同的事。
