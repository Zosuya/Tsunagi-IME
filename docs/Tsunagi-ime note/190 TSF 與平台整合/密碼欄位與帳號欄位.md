# 密碼欄位與帳號欄位

原本在密碼框打字時，**密碼會原封不動顯示在候選視窗上**——欄位遮成
`••••••`，旁邊卻飄著一個把密碼寫得清清楚楚的框。螢幕分享和截圖也會
錄進去。這一節記的是怎麼修的，以及**兩個被實測判死的想法**。

### 2.12.1 兩條訊號，應用程式各用各的

TSF 底下「這裡別用輸入法」有兩種表達方式：

| 訊號 | 誰在用 |
|---|---|
| 輸入範圍標成 `IS_PASSWORD` | 原生程式 |
| `GUID_COMPARTMENT_KEYBOARD_DISABLED` 旗標 | **Chromium 系瀏覽器** |

第一版只做了輸入範圍，結果在瀏覽器裡完全無效。補上旗標之後才對。

旗標**在文件與執行緒兩個層級都要查**——宿主用哪一個沒有規定。

判到就完全不接手：`OnTestKeyDown` 與 `OnKeyDown` 都直接回 0，按鍵原樣
交給宿主，順便收掉可能殘留的候選視窗。

**問不到就當作不是密碼**：寧可漏判也不要誤判——誤判的話一般欄位突然
打不了中文，使用者會以為輸入法整個壞了。

### 2.12.2 實測：Brave 的輸入範圍分不出任何東西

做了一個七欄位的測試頁，在 Brave 裡逐格打字，量每一格回報的輸入範圍：

| 欄位 | 輸入範圍 | 停用旗標 |
|---|---|---|
| 網址列 | `IS_SEARCH` | false |
| 一般文字 | `IS_PRIVATE` | false |
| **密碼** | `IS_PRIVATE` | **true** |
| `type=email` | `IS_PRIVATE` | false |
| `autocomplete=username` | `IS_PRIVATE` | false |
| `autocomplete=email` | `IS_PRIVATE` | false |
| `type=url` | `IS_PRIVATE` | false |
| 一般文字＋`autocomplete=off` | `IS_PRIVATE` | false |

**除了網址列，全部都是 `IS_PRIVATE`。** 密碼欄跟一般欄位在輸入範圍上
完全無法區分——只有那個旗標分得出來，而且**只在密碼欄亮**，
`autocomplete=off` 與搜尋欄都沒有誤判（那正是最怕的情況）。

### 2.12.3 被判死的想法：帳號欄位自動切英文

**帳號一定是英文，被判成日文很煩**——實測的結果（原本用的是真實帳號，
公開前換成結構相同的例子，判斷行為一樣）：

```
wasabinet  → 「わさびnet」     ✗   wa/sa/bi 全是合法羅馬字
kokoromap  → 「こころmap」     ✗   同上
alpha7891  → alpha7891        ✓   有數字
john.doe   → john.doe         ✓   有符號
user2024   → user2024         ✓   有數字
```

規律是：**帶數字或符號的都對，純字母又長得像羅馬拼音的會被判成日文**。
根本原因是 §2.7 的已知限制
——詞庫沒有的英文詞排不上去。

本來想靠輸入範圍判斷「這是帳號欄」然後自動切英文。上面那張表證明
**辦不到**：`type=email`、`autocomplete=username` 跟一般欄位長得一模
一樣。

所以這件事的解法不是欄位偵測，而是：

- **現在**：按 `Ctrl` 鎖定英文（一個鍵）
- **Phase 4**：個人化——打過一次就記住

> 這條路已經量到底了，**不要再繞回來查一次**。

### 2.12.4 `IS_PRIVATE` 真正的用途留給 Phase 4

雖然它分不出密碼欄，但它的語意是「這裡打的東西不要學起來」。

Phase 4 的個人化是「使用者打過的詞自動加權」，到時候**不理這個標記的
話，帳號、身分證字號、信用卡號、私訊內容都會被學進個人詞庫**——那才
是真正該擔心的洩漏，而且是持久的（存在硬碟上）。

正確的分工：

| 訊號 | 用途 |
|---|---|
| 停用旗標 | 不要介入（已完成） |
| `IS_PRIVATE` | **不要學習**（Phase 4 要做） |

### 2.12.5 驗證過程：兩次「以為修好了」

這一段的教訓比結論值錢。

**第一次**用 WinForms 的 `UseSystemPasswordChar` 測，畫面完美：密碼顯示
成點、沒有候選視窗。埋 log 才發現**判斷函式根本沒被呼叫**——那種控制項
會讓 Windows 整個關掉 TSF，按鍵壓根不會送到輸入法。保護是 Windows 給
的，自己寫的程式碼一行都沒跑到。

改用 `SetInputScopes` 把一般文字框標成密碼（瀏覽器做的就是這件事），
才真的走到那條路。

**第二次**使用者回報「瀏覽器裡還是有候選框」，查下去是**瀏覽器行程載的
是舊 DLL**。這裡有個比想像中更廣的陷阱：

> **開新分頁不夠，要整個程式關掉重開。** 輸入法的 DLL 載在瀏覽器的主
> 行程裡，分頁是子行程。同理適用於任何長時間開著的程式——編輯器、
> 聊天軟體、Claude 自己。`check-dll.ps1` 就是為了這種情況做的：覺得
> 「明明改了怎麼沒變」，先跑它。

兩次都是「看起來對」但證據不成立。**畫面會騙人，log 不會。**
