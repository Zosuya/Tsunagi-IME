# 日文整句轉換：分詞＋選字

使用者實測回報：打 `gohannwotabemasu` 得到「ごはんをたべます」全假名。
單詞轉換是有效的（`gohann` → **ご飯**），整句沒有。

### 2.23.1 症狀與根因

整句被當成**一格**，引擎拿整串假名去查詞典——查不到就退回假名。
那一格的候選只有三個（平假名／片假名／半形），**根本沒有漢字可選**。

順帶澄清一個常見誤會：打 `gohan`（單 n）連日文都排不到第一。撥音在
本專案**一律打 `nn`**（見 `romaji`）。

### 2.23.2 分詞與選字不能分開，必須同時

分法決定字，字又反過來決定分法：

```text
ごはん   → 一個詞「ご飯」
ご|はん  → 兩個詞「五|半」
```

所以要在**所有「分詞 × 選字」的組合**裡一次找出總成本最低的路——
那就是 Viterbi。成本來自 mozc 的資料，格式是
`讀音 ⟨左id⟩ ⟨右id⟩ ⟨詞成本⟩ 表記`：

```text
ああると	1851	1851	7129	アアルト
```

那三個數字**就是文法結構**：id 是詞類，接續矩陣記「右 id 接左 id」
要付多少成本——「名詞→を→動詞」便宜，「助詞→助詞」貴。

### 2.23.3 這不是被否決過的那個維特比

§2.15 寫著「維特比 DP ＋ 長度
先驗被實測否決——不要再試一次」。**那是中文的實驗**，用 `word_freq`
（語料詞頻）當成本，而那份資料單字累積量太大、算出來沒有分詞壓力。

日文完全不同：mozc 給的是**訓練好的成本模型**（詞成本＋2672×2672
接續矩陣）。不是同一個實驗，不該被那條結論擋住。

### 2.23.4 語言切點與日文分詞是兩個維度（使用者指出）

| 維度 | 誰決定 | 產出 |
|---|---|---|
| 語言切點 | 切點引擎（Phase 2） | 「這一段是日文」 |
| 日文內部分詞 | 日文轉換（Viterbi） | 「這段日文裡有幾個詞」 |

**切點引擎不該去做日文分詞**——搜尋空間會爆，而且兩件事混在一起之後
出問題分不出是哪一層。反過來 Viterbi 也不該移動語言邊界。

架構上早就對稱，只是日文還沒有分詞能力：

```text
Segment（語言段） → compose → Slot[]（選字單位）
  注音段 → 切成音節     → 每音節一格   ← 已經是這樣
  日文段 → Viterbi 分詞 → 每個詞一格   ← 要加的
  英文段 → 不切         → 一格
```

所以改動很集中：**切點引擎完全不動**（`Score` 與排序不變，570 句的
切點分數理論上零變化，可以直接用 `check_incremental` 驗證），只動
`compose.rs` 的 `Language::Romaji` 分支。

### 2.23.5 附帶解鎖：日文的逐詞選字與學習

現在整句一格、沒有漢字候選可選，所以
§2.22 的學習對日文整句**幫不上忙**
——使用者選不了，也就沒東西可記。

分詞之後每個詞各自有候選，使用者可以逐詞選字，學習就有訊號了。
**這讓「先整句、後學習」的順序更站得住**。

### 2.23.5.1 互動不必改：兩個維度早就對應兩組按鍵

| 按鍵 | 維度 | 在問什麼 |
|---|---|---|
| `Tab` | 語言切點 | 這串按鍵怎麼分語言段（中／日／英） |
| `←` `→` | 選字 | 這一格要哪個字／詞 |

日文分詞之後方向鍵在**詞**之間移動，跟注音在**字**之間移動是同一件事，
只是單位不同。**不必新增任何按鍵**——架構分對了，介面自然不用改
（使用者 2026-09-01 指出這個對應）。

### 2.23.5.2 第三個維度：詞界調整，先不做

Viterbi **分詞也可能切錯**（把 `ごはん` 切成 `ご|はん`）。那時方向鍵
只能在錯的格子之間移動——**選不出正確的詞，因為它根本沒被切出來**。

日文 IME 的標準解法是「文節伸縮」（`Shift+←/→`）。那是第三個維度：

| 維度 | 按鍵 | 調整什麼 |
|---|---|---|
| 語言切點 | `Tab` | 中／日／英 的邊界 |
| **日文詞界** | **未定** | `ご飯` vs `ご\|はん` |
| 選字 | `←` `→` | 這一格要哪個字／詞 |

**先不做**：一次只動一個維度才驗得出是哪一層出問題。先讓 Viterbi 上線、
量它切錯的頻率——**如果切錯很少，這個維度可能根本不需要介面**。
先量再決定要不要加按鍵，不要預先設計一堆互動。

### 2.23.6 順序：先整句，再二進位詞庫

§2.10.5 自己寫著：二進位的
雛形**把 mozc 的成本值丟掉了**，而「要不要存成本值」這題要等後續功能
才有答案。整句轉換的 Viterbi 正是需要成本值的那個功能——

- 先整句 → 再二進位：格式一次設計對
- 先二進位 → 再整句：文件自己預期「格式很可能要改一次」

記憶體不是現在的阻礙：50MB 是 **Phase 5 的驗收項**，現況 222MB 已超標
四倍，多 13.6MB 不改變任何結論。

### 2.23.7 矩陣自帶一個小型的二進位需求

`connection_single_column.txt` 是 **36MB 的文字檔**，2672×2672 = 714 萬格。
現在只讀 BOS/EOS 兩條線（10.4KB）；要載完整矩陣得解析 714 萬行，那正是
「文字版詞庫 705ms」問題的翻版，會破壞切換輸入法 0ms。

所以要先把矩陣離線轉成二進位（`u16` 存 **13.6MB**，像
`char_freq_by_reading.txt` 那樣由 `download.ps1` 產生）。**那是小範圍
的工作，不必連詞庫本體一起做**，而且會先摸清二進位那條路的實作細節。

### 2.23.7.1 spike 結果：矩陣不是障礙（2026-09-01）

| 項目 | 文字版 | 二進位版 |
|---|---|---|
| 載入 | 90.1 ms | **6.9 ms**（快 13 倍） |
| 查一次 | — | **2.6 ns**（100 萬次 2.6 ms） |
| 檔案 | 36 MB | 13.6 MB |
| 記憶體 | — | +13.6 MB |

**查詢速度是最關鍵的那個數字**：Viterbi 一句話要查幾千次接續成本，
2.6 奈秒等於免費。載入 6.9ms 也遠低於背景載入的預算。

記憶體是**淨增 13 MB**（乾淨量法：`bench_connection --bin-only`，
4 MB → 17 MB）。跟檔案大小幾乎一比一——「載入時零解析」就是把檔案
原封不動放進記憶體。放進整體來看：

| 階段 | 常駐 |
|---|---|
| 現在 | 222 MB |
| 加上完整矩陣 | 約 236 MB |
| 之後做二進位詞庫 | 43 + 13.6 ≈ **57 MB** |
| Phase 5 目標 | < 50 MB |

**要注意的是最後兩列**：二進位詞庫做完之後大約 57MB，**仍然略高於
50MB 目標**。那時的選項是接受、或把矩陣改成 mmap——多個宿主行程就能
共用同一份實體記憶體（見 §2.10.5），
13.6MB × 每個行程 vs 共用一份，多開幾個程式時差很多。

現在記下來，免得 Phase 5 才發現差那 7MB。

文字版的 90ms 其實沒有原本擔心的那麼糟（705ms 那個是更大更複雜的
解析），但二進位還是明顯較好，而且**省掉 714 萬個暫時字串的配置**。

實作要點：**存成一整塊位元組、載入時零解析**——轉成 `Vec<u16>` 要再
走一次 714 萬格、多配置一份 13.6MB；查表時才取那兩個位元組便宜得多。

工具：`gen_connection`（離線產生，`download.ps1` 最後一步會跑）、
`bench_connection`（量這三個數字）。`connection.bin` 是衍生資料，
不進版控。

### 2.23.9 結果與三個被實測打臉的假設

```text
gohannwotabemasu      → ご飯を食べます
sushiwotabemasu       → 寿司を食べます
watashihagakuseidesu  → 私は学生です
```

| 項目 | 之前 | 之後 |
|---|---|---|
| 文字命中 | 650/720 | 650/720 |
| 錯字率 | 4.6% | **4.2%** |
| 日文錯字率 | 10.7% | **8.7%** |
| 切點（涵蓋／前3／第1） | 570／560／551 | **完全沒動**（如預測） |
| p99 延遲 | 11.2ms | 11.1～11.6ms |
| 記憶體 | 218 MB | 231 MB |
| 改寫率 | 2.05 次/百鍵 | 2.26 次/百鍵 |

**切點一個數字沒動**，正是「兩個維度分開」那個判斷的驗證。

三個假設被實測打臉，都寫進了對應的註解：

**一、「載不到矩陣就退化成只看詞成本，仍然比整段不轉好」——錯得離譜。**
mozc 讓高頻詞的詞成本趨近零（`目` 是 **12**、`に` 是 **0**），**全靠矩陣
擋住亂接**。沒有矩陣時 DP 會把 `あにめ` 切成 `あに`＋`目`。改成**沒有
矩陣就不分詞**——寧可不轉也不要轉錯。

**二、矩陣不能讓呼叫端自己記得載。** `check_compose` 與 `show_ime` 各自
載詞典卻沒載矩陣，量出來的行為跟使用者看到的不一樣，**一度誤判成大退步
（577/720）**。現在 `load_japanese` 一併載。

**三、按鍵不能照假名長度比例分。** 羅馬字跟假名不等比（`すし` 兩個假名
五個字母），實測 `sushi|wo|tabe|masu` 被切成 `sush|iw|otab|emasu`。
改用 `kana::mora_spans` 拿真正的對應——格子的按鍵**必須接得回原字串**，
`check_rewrite`、整格刪除、學習都靠這個性質。

### 2.23.10 順帶修掉的 bug：候選拿錯東西去查

`candidates_for` 對日文格傳的是 `slot.text`（**已經轉換過的表記**）而不是
讀音。那一格是漢字時（`ご飯`）就查不到任何候選，只剩三種假名寫法。

分詞之前整句常常停在假名所以不明顯，**分詞之後每格都是漢字，問題就整個
浮出來**——而那正好擋住「逐詞選字」，也就等於擋住日文的學習訊號。
改成拿 `slot.keys` 轉出讀音再查，`ご飯` 的候選從 3 個變 7 個。

### 2.23.8 量測時要注意的坑

日文段切成多格之後，`check_compose` 報的「日文段數 278」會變大
（一段變好幾格）。**比較基準要對齊**，不然會誤以為錯字率變了。
