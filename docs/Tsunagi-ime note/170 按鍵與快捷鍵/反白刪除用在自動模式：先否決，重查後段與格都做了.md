# 反白刪除用在自動模式：先否決，重查後段與格都做了

> **狀態**：2026-09-01 否決、2026-09-10 重查後實作完成；否決期的記錄刻意保留在內文

「反白的單位整個刪掉」原本只在鎖定模式生效。2026-09-01 使用者問能不能
也用在自動模式，當時**否決**；**2026-09-10 重查，否決的理由已經不成立，
當天實作完成**（段刪除、格刪除各一個 commit，見 §2.21.12）。

2026-09-01 的原始記錄（§2.21.1～§2.21.4）**保留不動**，那是判斷怎麼變的
證據；§2.21.5 起是重查與實作的經過。

## 2.21.1 一格在自動模式未必是一個字

| 語言 | 一格是什麼 |
|---|---|
| 注音 | **永遠一個字**（`su3`→你、`g4`→世）——compose 把注音再切成音節 |
| 日文 | **可能是整句**（`sushiwotabemasu` → すしをたべます 只有一格） |
| 英文 | 整個詞（`hello` 一格） |

所以真要做的話，得加一道「這一格是一個字」的守門。

## 2.21.2 但真正的問題不是那個，是重算

實測刪掉中間那一格之後：

```text
新世紀   刪掉「世」 → 心悸        ← 「新」也跟著變「心」
check 一下  刪掉「一」 → ちぇ喝下  ← check 整個崩掉變成日文
```

**根本差異：鎖定模式沒有切法重算，自動模式有。** 而且一般倒退鍵只刪
最後一個鍵、影響小；整格刪除是從**中間**挖掉一塊，那才是重算失控的
原因。

這正是 CLAUDE.md 記過的那類抱怨（§2.15）
——新酷音使用者說「連續打出一句話以後，前面的字突然改了」。在自動模式
做整格刪除等於主動製造那個情況。

## 2.21.3 日後真要做，該解的是別的問題

不是「怎麼刪整格」，而是**「刪完不要重切」**。專案裡已經有
`chosen_cut`／`find_chosen` 那套「記住使用者挑過的切法、重算後找回來」
的機制可以延伸——刪除後把原本的分段結構釘住，不讓引擎重切。

要處理的難點是「刪完之後原本的分段對不上了」：`find_chosen` 比對的是
前綴，而中間挖掉一塊之後前綴就變了。

## 2.21.4 現況下正確的做法

自動模式要改中間某個字，正確工具是**選字**（方向鍵移過去換字），
不是刪掉重打——選字不會動到其他格。

## 2.21.5 重查（2026-09-10）：§2.21.3 指的那條路已經被別的功能鋪好了

§2.21.3 說「該解的是刪完不要重切，可以延伸 `chosen_cut`／`find_chosen`」。
**那個方向在 2026-09-01 是對的，但它已經不是最好的解，而且 `chosen_cut`
本身力道不夠：**

| | `chosen_cut` | 段選單的逐段定案 |
|---|---|---|
| 性質 | **提示**——重算後去新清單找，找不到就算了 | **定案**——引擎不准再有意見 |
| 比對範圍 | **只認第一刀**（後面幾刀刻意不比，見 `find_chosen`） | 每一段都算 |
| 中間挖空之後 | 切點位置全部位移，拿舊位置去比就對不上 | 不受影響（凍的是前綴本身） |

`find_chosen` 只認第一刀不是疏漏，是為了修「挑過的切法多打一個字就
跳回第一名」那個 bug。也就是說它天生不適合用來釘住整句的分段。

**該借的是 §2.70 段選單
的凍結機制**（`Incremental::freeze_user_prefix`）——2026-09-01 時它還不存在。
它的效果正是 §2.21.2 要的：**前面定案、後面重算**。

## 2.21.6 前區凍結沒有技術瓶頸（重查的主要結論）

`freeze_user_prefix` 已經是成熟的一支，三種情況都處理了：

| 情況 | 做什麼 | 成本 |
|---|---|---|
| 落在引擎已凍好的前區內（最常見） | 換掉前面幾段，後區一個字都不動 | 幾乎零 |
| 落在引擎某段的中間 | 拆開那一段，**只有尾巴那幾個鍵**重算（93 鍵長句約一半走這裡） | 幾個鍵 |
| 完全對不上 | 回 `false`，呼叫端走**慢路**：拿剩下的按鍵重開引擎，`adopt_frozen` 把前區補回去 | 一次重建 |

**慢路是關鍵：它保證不會失敗。** 就算使用者的切點跟引擎衝突到底也走得通
——那正是使用者要的，他就是不同意引擎的切法。效能量過：快路 93 鍵長句
47ms → 0.46ms。刪除比定案更輕（不必挑候選）。

**唯一不能走這條路的是鎖定注音**：它走 `BopomofoInput`（四格音節緩衝），
`freeze_user_prefix` 只支援 `Cascade`，會退回慢路重建成 `Cascade`，整串按鍵
就沒了（實測：定案之後段變成空的、送出空字串）。見 `seg_confirm_with` 裡的
`lock.is_some()` 分支。但鎖定模式本來就沒有後區要重算，這條路對它沒有用。

## 2.21.7 使用者的分辨：兩個崩掉的例子只有一個是問題

使用者看 §2.21.2 那兩個例子時指出（2026-09-10）：**第一個沒問題，第二個才是**。

| | 新世紀 → 心悸 | check 一下 → ちぇ喝下 |
|---|---|---|
| 變的是什麼 | 同一段注音裡換了字 | **語言整個翻盤** |
| 是不是合理結果 | **是**——直接打「ㄒㄧㄣㄐㄧˋ」也會得到「心悸」，而「新紀」不是詞 | 不是，`check` 是使用者明確打的英文 |
| 使用者的感受 | 「喔，變成心悸，合理」 | 「我的 check 去哪了」 |

**判斷結果一致的重算不算失控。** 這個分辨曾經帶出一個更輕的解法方向
（只釘語言、不釘切點——同語言的切點對輸出沒影響，`normalize` 會黏回去，
所以只有跨語言翻盤才有後果）。**但那個方向沒有被採用**，因為它需要
先驗證「語言可以單獨釘住嗎」（切點與語言在 `cutpoint` 裡是綁在一起算的），
而前區凍結**根本不必拆解這兩者**，把那個未驗證的問題整個繞開了。

代價要記著：**前區凍結會連「心悸」一起擋掉，得到「新紀」。** 使用者傾向
接受——「新」是已經看在眼裡的字，沒碰它就不該變；那兩個音其實該是「心悸」
是選字或重打要處理的事，不該由一次刪除代勞。

## 2.21.8 自動模式有三種反白，不是一種

使用者指出（2026-09-10）「反白刪除」其實是兩件事。查完是三種，第三種可以排除：

| 反白 | 單位 | 誰在管 | 刪除的難度 |
|---|---|---|---|
| **選字框** | 一**格**（方向鍵移動） | `select_idx` / `last_select` | 要接凍結機制 |
| **段選單反白**（TAB） | 一**段** | `segmenu` | **小**——「前定案後重算」已經在了 |
| 切法選單反白 | 一整**列**（整句的某一種切法） | `cutting_index` | 不適用：反白的不是組字區的一塊 |

**段刪除比格刪除便宜一個等級**，理由有三：凍結機制長在它身上；語意上
「這一段要當成什麼」多一個選項「不要這一段」是同一個心智模型；而且它天生
躲過 §2.21.1 的守門問題（段的邊界是引擎切出來的、帶語言標記，日文長句在
段選單裡本來就會被推邊界處理）。

## 2.21.9 使用者的三個裁決（2026-09-10）

| 問題 | 裁決 |
|---|---|
| 格與段都做，還是段先走 | **段先做，格接著做**（分兩個 commit） |
| 段選單裡倒退鍵原本是刪單鍵，誰佔那顆鍵 | **做成設定，A／B 不二選一**——並存時刪整段用 `Shift+`倒退鍵 |
| 開關要幾個 | **各自一個**（格一個、段一個），理由同 `enter_in_segmenu` |

「凍到哪裡（只凍前面／前後都凍）」這一項**被 §2.74 的實作回答掉了**——
那個問法本身是錯的，見下一節。

## 2.21.10 §2.74 實作之後的修正：凍「格」不凍「位置」（2026-09-10）

§2.74.11 把中文詞層重切接進產品碼，
順手回答了 §2.21.9 原本的第 2 項，也推翻了本節前面用的問法。

**原本的問法錯了。** §2.21.6～2.21.9 一路在問「凍多遠」——只凍前面、
前後都凍、`freeze_user_prefix` 只支援前綴。那是**位置式**的思路。而 §2.74
翻案之後的產品碼證明位置式的凍結**本身就是病因**：

> 第一版限制「只看離尾端 N 格」，結果修好的字會在下一鍵掉回去……
> 病灶是**拿窗口內的貪心當基準，比對的卻不是實際顯示的東西**。

`RECUT_WINDOW` 因此整個拿掉了。現在的範圍是 `RECUT_SPANS = 2`
（最後兩個**連續注音段**）——邊界是空白、別的語言、標點自然形成的，
**結構性的界線，不是數字**。

**而該借的機制已經在了**：`recut_span` 填回去時有一道

```rust
if !slots[i].picked {          // 手動選過的字不覆蓋
```

`picked` 的語意是「使用者選過這個字」。反白刪除要的是「使用者看過這一格」
——**同一種東西，只是門檻寬窄不同**，而且剛好對上 §2.74.9
查到的新酷音判準（凍結看的是「使用者的游標動作」，不是「距離尾端幾格」）。

當時由此推論：反白刪除該「把使用者看過的那些格各自標成不准動」，
`recut_span` 那個 `if` 多認一個旗標即可。

**但實作最後沒走那條路**（記在這裡因為推論的方向是對的、只是不必走到那麼遠）：

| 當時的推論 | 實際做法 |
|---|---|
| 逐格標記「看過了」，重算時不准動 | **段刪除**：整段前區交給凍結區（`adopt_frozen`）；**格刪除**：不凍 |
| 靠新增的旗標擋重算 | 靠既有的 `picked`（沒有新旗標） |

原因有兩層。**段**的粒度剛好對上凍結區的既有介面，直接交給輸入層保管
比自己記旗標乾淨（§2.21.6 那三種情況都處理好了，還有慢路兜底）。而**格**
的粒度太細，凍下去會誤傷 §2.21.7 那種「判斷結果一致的重算」——使用者
認為「新世紀刪掉世 → 心悸」是對的，逐格凍會把它擋掉。

`picked` 那道 `if` 仍然是關鍵，但用途不是「凍住」而是「**不覆蓋**」：
重算照跑，只是不動使用者已經表態的字。真正讓刪除安全的是 `Pick` 改記
位置（§2.21.11 ②），那才是「修正不會貼到別的格上」的保證。

## 2.21.11 那兩個新問題實測了：一個無害、一個是現存的 bug

§2.74 落地後浮出兩個問題，實測（用真正的操作路徑，不是離線 spike）：

**① 段會合併／消失——會發生，但無害。**

```text
注:su3 | 英:hello | 注:cl3    刪掉 hello → 注:su3cl3   （三段變一段）
注:su3 | 英:␣     | 注:cl3    刪掉空白   → 注:su3cl3
```

合併本身**正是使用者要的**（`你hello好` 刪掉 hello 就該得到「你好」）。
`RECUT_SPANS` 指的範圍跟著變，但那是重算的正常輸入，不是錯。

**② `picked` 錯位——不只會發生，而且是刪除以外也踩得到的現存 bug。**

原本 `picks` 只記 `(按鍵, 選的字)`，靠「由左往右、按鍵相同、用過就不再用」
對回去。三個症狀都重現了：

```text
你好擬*好  再打 su3   → 擬*好你好你      修正跳到第 0 格
你好擬*好  刪 3 鍵    → 擬*好你          同上
擬*好妳*好 重建一次   → 妳*好你好        兩個修正混掉，還丟了一個
```

**第三個最嚴重**：使用者選了兩個字，重建後只剩一個、而且貼在錯的格上。
這跟刪除無關，是打字時就踩得到的——所以它先被獨立修掉（§2.21.12 的
第二個 commit）。

## 2.21.12 實作：三個 commit（2026-09-10）

| commit | 做什麼 |
|---|---|
| `12b3dd1`＋`a0d79b1`＋`adaa68e` | **段刪除**（段選單 TAB 反白一段，刪掉它） |
| `0d12018` | **`picks` 改記位置**（修 §2.21.11 那三個 bug） |
| `c463f32` | **格刪除**（選字模式反白一格，刪掉它） |

**段刪除有前區凍結，格刪除沒有。** 這不是漏掉，是 §2.21.7 的裁決：
格的粒度太細，凍下去會把「新世紀刪掉世 → 心悸」這種**判斷結果一致的
重算**也擋掉，而使用者認為那個結果是對的。段的粒度剛好——一段是一個
語言單位，凍住它不會誤傷同語言內的重新選字。

**`Pick` 記位置是格刪除的前提。** 對位不可靠的話，刪掉前面一格會讓後面
的修正貼到別的格上（實測回報「修正過的字會跳走」）。所以順序是：先修
對位，再做格刪除。

### 2.21.12.1 鍵位與設定

三態，格與段**各自一組**（`DeleteUnitKey`）：

| 設定值 | 倒退鍵 | `Shift+`倒退鍵 |
|---|---|---|
| `Backspace` | 刪整個單位 | 也刪整個單位 |
| `ShiftBackspace` | 刪一個鍵 | 刪整個單位（**兩者並存**） |
| `Off` | 刪一個鍵 | 刪一個鍵 |

預設**段開（`Backspace`）、格關（`Off`）**——自動模式的一格未必是一個字
（日文一格可能是整句），讓要的人自己開比較誠實。

三態而不是開／關，是因為倒退鍵在選單裡已經有用途（刪一個鍵），而
「誰佔那顆鍵」兩派都有道理（使用者裁定：做成可選，不替他決定）。

### 2.21.12.2 實作時踩到的三個坑

**① 空白段本來被擋掉，實測證明那道守門是錯的。**
原本推論「刪掉空白會把兩邊的段黏起來，那是改變斷詞不是刪掉一段」，
實測 `注:su3 | 英:␣ | 注:cl3` 刪掉空白之後**仍然是兩段**——段的邊界是
引擎依音節切的，不靠空白撐著。而使用者打了空格又想拿掉本來就是最自然
的需求。**那道守門擋掉的是合理操作**（`a0d79b1`）。

**② `seg_locked` 一個欄位背了兩個職責。**
實測回報「選到 hello 段刪除反白不會跳到你好」。反白其實跳對了，壞的是
**選單早就不在了**：刪除時把 `seg_locked` 設成前區長度，而 `seg_done()`
的判斷是 `seg_locked >= seg_count()`——刪掉最後一段之後前區長度剛好等於
剩下的段數，`seg_done()` 回 true，TSF 層就把選單整個關掉。

修法是認清**刪除不是定案**：使用者說的是「不要這一段」，不是「前面那些
我都確認過了」（`adaa68e`）。

那次的測試也漏了——原本只驗 `seg_index()`，反白跳對了就通過，抓不到
選單不在。**斷言要驗使用者看得到的東西**，不只驗內部狀態。

**③ 位元組與字元兩套座標混用。**
`delete_marked_slot` 原本用 `keys.len()`（位元組）算位置，而 `Pick::at`
用字元。按鍵串實測全是 ASCII（使用者按的每一鍵都是鍵盤字元，全形轉換
發生在**顯示**那一層，不進 `keys`），所以兩者現在等價、沒有真的錯位
——但統一成字元才是同一套座標，哪天有非 ASCII 進來不會默默出錯。

### 2.21.12.3 驗收

| 項目 | 結果 |
|---|---|
| 測試 | 635 → **650**（段 5＋對位 3＋格 6，另修 2 筆過期斷言） |
| 漏斗 | **1286 持平**（新增的操作路徑，不影響既有測資） |
| 改寫硬指標 `⚠` | **10 持平**（改動前 stash 量過同一個數字） |
| 按鍵延遲 p99 | **9.1ms**（預算 16ms） |
| 常駐記憶體 | 25 MB |

`picks` 改記位置**順帶變快**：兩邊都按 `at` 遞增，排序後同步掃一次，
從 O(格數 × picks) 降到 O(格數 + picks)。實測 60 格 30 pick 從 688ns
降到 161ns（−77%），20 格 3 pick 也快 27%。這條路在熱路徑上——
`rebuild_slots` 每按一鍵跑一次，而**切法選單的預覽每一列都跑一次**。
記憶體每個 pick 多 8 bytes（一句話個位數，送出就清）。
