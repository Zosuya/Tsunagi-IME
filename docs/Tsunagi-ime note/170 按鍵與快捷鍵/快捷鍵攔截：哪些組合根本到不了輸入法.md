# 快捷鍵攔截：哪些組合根本到不了輸入法

Phase 3 清單上的最後一項——§1.6 問「TSF 下攔截
快捷鍵的正確做法」。這件事**推論不出來**：同一個 `Ctrl+W` 在記事本沒人
要、在瀏覽器是關分頁。只能量。

## 2.14.1 量測方法

按鍵從鍵盤到輸入法要過三關——系統、宿主 App、輸入法，任何一關都可能
先吃掉它。所以量測點放在 TSF **一定會問**的那一步，
「有沒有出現在 log 裡」就等於「輸入法看不看得到」。

工具留在專案裡（`platform/windows/src/keyprobe.rs` 埋點、
`tools/keyprobe.py` 分析），**之後要加新鍵位時再跑一次就好**：

```powershell
# 1. 開啟：在 data/ 建一個空的 debug.on
# 2. 宿主程式整個關掉重開（開新分頁不夠）
# 3. 切到本輸入法，把要測的組合按過去
python tools/keyprobe.py     # 讀 %TEMP%\ime_debug.log
```

**探針只記組合鍵，不記一般打字**。理由不是省空間，是密碼欄的判斷發生
在探針之後，等判斷完再記就會漏掉要量的東西——而要量的正好就是組合鍵，
不記字母就不會把使用者打的內容寫進檔案。

## 2.14.2 結果

四個宿主（記事本、Word、Brave、Firefox）一致的部分：

| 組合 | 到得了嗎 |
|---|---|
| `Win+空白`、`Win+D`、`Alt+Tab`、`Ctrl+Shift+Esc` | **永遠到不了**——系統在 TSF 之前就攔走 |
| `Alt+Q`、`Ctrl+Alt+J`、`Ctrl+Alt+K` | **永遠到不了**——Alt 系組合四個宿主全沒到 |

記事本與 Word 的完整結果：`Ctrl+C V X Z A S F P N` **全都到得了**
（Word 連 `Ctrl+T`、`Ctrl+W` 都到）。也就是說**宿主自己的快捷鍵不會
擋住輸入法看到它們**——是我們主動回「不要」才交還給宿主的。

> **Brave 與 Firefox 的數據不採信**：分布不合理（`F9` 到得了、方向鍵
> 反而沒到），比較像量的時候不在組字狀態。瀏覽器要重測的話得分
> 「有組字」與「沒組字」兩種狀態各跑一次——留給之後真的要加鍵位時做。

## 2.14.3 最有價值的發現：宿主分兩派

| 宿主 | 行為 |
|---|---|
| Word | 幾乎都先問 `OnTestKeyDown`（19/20） |
| 記事本 | 幾乎都直接送 `OnKeyDown`（19 次裡只問 1 次） |

這正是 §1.6 想問的「preserved key vs 一般 key event」的實務答案，而且
有直接後果：

> **我們對 TSF 說「這個鍵我不要」，在「直接送」的宿主上根本不會被問到。**
> 所以任何依賴那個回答的邏輯，**兩個入口都要各做一次**。

`ctrl_tap` 的標記就是這樣寫的——`OnKeyDown` 那邊有一段防衛性的重複標記，
註解寫「有些宿主不見得會先問」。**那原本只是猜測，現在量到了。**
