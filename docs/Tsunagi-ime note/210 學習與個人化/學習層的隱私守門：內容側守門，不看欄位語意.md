# 學習層的隱私守門：內容側守門，不看欄位語意

> **這一段獨立成一篇**：模糊音容錯那半見 [[注音模糊音容錯：四組音、預覽列直接改掉]]。

> **功能一（隱私守門）已完成**（2026-09-15，`learn::privacy`，
> **三宿主實打通過**）。三個待決的答案：門檻 **5**（量出來的）、
> `cut:` 用**選項①**、**不做雜湊**。實作經過見 2.81.38，
> 第一版誤擋整句中文的完整經過見 2.81.39。
>
> 同一節的另一半（功能二，模糊音容錯）**已經實作完成**（2026-09-12，
> 漏斗 1291 → 1320），見 [[注音模糊音容錯：四組音、預覽列直接改掉]]。

起點是兩個功能構想：

1. 學習的時候要不要儲存帳號類資料
2. 注音容易打錯的音（`ㄣ`／`ㄥ` 那種）能不能用查詞庫的方式修正

### 2.81.1 功能一的現況盤點：密碼欄早就擋住了，缺的是帳號欄

不是從零開始，兩個平台各有一道已經做好的防線：

| 平台 | 判準 | 擋到什麼程度 |
|---|---|---|
| Windows | `IS_PASSWORD` 或 Chromium 的停用旗標（`document.rs` 的 `refresh_password`） | **整個不介入**，密碼不可能被學走 |
| macOS | `IsSecureEventInputEnabled()`（`echo_ime.rs` 的 `learn_and_save`） | 送出時不記 |

缺的是**非密碼但敏感**的那一類：帳號、email、身分證字號、信用卡號、
私訊內容。§2.12.4 當初把它
列成 Phase 4 待辦，解法寫的是「`IS_PRIVATE` 的欄位不要學」。

### 2.81.2 §2.12.4 的原案不能照做：Chromium 把一般欄位也標成 `IS_PRIVATE`

這個衝突當初沒被點出來——證據就在同一節的
§2.12.2 實測表裡：

> **除了網址列，全部都是 `IS_PRIVATE`。**

也就是說「`IS_PRIVATE` 就不學」等於**在瀏覽器裡全面停止學習**，而瀏覽器
是使用者打最多字的地方。原案的代價遠比它防到的東西大。

**使用者裁決（2026-09-12）：改走內容側守門，做在 `core` 層。**
不看欄位語意，看「要被寫進檔案的字串長什麼樣子」——平台無關、
瀏覽器裡一樣有效，而且誤擋的代價只是「這條沒學到」。

原生欄位語意白名單（`IS_EMAIL_*`／`IS_TELEPHONE_*`／`IS_DIGITS`…）
沒有被否決，只是**瀏覽器不標這些**，單獨做等於在最需要的地方沒有保護。
要做也是內容側之後的補強，不是替代品。

### 2.81.3 文件沒寫到的洩漏路徑：`lang:`／`cut:` 存的按鍵串就是明文

盤點時翻出來的，比原本擔心的東西更具體：

- 帳號是英文段、`selectable = false`，所以**不會**進選字學習（`record`
  只記可選字的格）——這條原本的擔心其實不成立
- 但只要按過 TAB 改切法，`record_cutting`（`learn.rs:845`）就會把
  `lang:<整串按鍵>` 寫進 `learned.txt`。**英文段的按鍵串就是它的字面**
  ——帳號以明文躺在硬碟上

這條不管守門怎麼設計都要補。

**2026-09-14 複查**，三件事跟原本寫的不太一樣：

| 查了什麼 | 結果 |
|---|---|
| 洩漏範圍 | **比原本寫的廣**——`cutting_records` 最後一行記的是 `cut:{整串按鍵}`，**不分語言**。不只「英文段的字面」，混語言句子的整串按鍵都在裡面 |
| 實際觸發頻率 | **低**。使用者的 `learned.txt` 2862 行裡 `lang:` 與 `cut:` **各 0 條**——要按過 TAB 換切法或用段選單定案才會寫 |
| 掛守門的位置 | **現成的**。`cutting_records` 是純函式（`learn.rs:869`），兩個呼叫點都經過它 |

**這改變了優先順序的判斷**：洩漏是真的、範圍比想像大，但**不是每天都在發生**
——它只在「使用者主動改切法」時寫入。所以這件事該做，但不必當成緊急修補。

### 2.81.35 使用者的質疑與實測：兩個族群，結論相反

**使用者問（2026-09-14）**：帳號要「符合中日文才會有轉換錯誤」才需要
調切法吧，這種情況是不是比較少？

**問得對，但只對了一半。** `spike_acct` 拿 16 串量第一名切法
（**第一名就是整段 ＝ 使用者沒有理由按 Tab ＝ 不會寫進 `learned.txt`**）：

| 族群 | 第一名就是整段 | 意思 |
|---|---|---|
| **帳號／密碼（英數混合）** | **8 / 10** | 使用者的直覺**成立**——`sampleuser`、`mypassword2024`、`s3cr3tp4ss` 都一次到位 |
| **純數字／證號** | **0 / 6** | **完全相反**——每一串都切歪 |

純數字那組全軍覆沒的原因是 CLAUDE.md 早就記著的那條：
**主鍵盤數字鍵全是注音鍵**。所以：

```text
0912345678  →  英:091234｜注音:56｜英:78      （56 被當成注音）
123456      →  英:1234｜注音:56
987654321   →  英:9｜注音:87｜英:6｜注音:54｜英:321
```

**這正是最敏感的那一類**：手機號碼、身分證、信用卡號、驗證碼。它們
**每一次都會切歪，使用者每一次都得按 Tab 修**——於是每一次都寫進
`learned.txt`，而 `cut:` 的鍵就是整串號碼的明文。

> **結論**：守門不但要做，而且**真正的風險集中在純數字**，不是原本
> 假設的「英數帳號」。英數帳號反而多半安全（引擎一次就給對）。
>
> 這也解釋了為什麼 `number` 那一節的通過率只有 79.2%——同一個病因，
> 只是那裡量的是「打得對不對」，這裡量的是「會不會被記下來」。

### 2.81.4 守門規則，與一個會讓切詞學習全滅的陷阱

規則（命中任一條就不記）：

| 規則 | 擋什麼 | 2.81.35 的量測 |
|---|---|---|
| **連續數字 ≥ 5** | 電話、身分證、卡號、驗證碼 | ★ **最重要的一條**。門檻**從 6 改成 5**（2.81.36 量的：誤擋 0 句，再往下一位就開始擋年份） |
| 含 `@` 且兩側有字元 | email | |
| 英數混合且長度 ≥ 8 | 帳號、token、隨機密碼 | 實際風險比想像低（8/10 一次切對，不會被按 Tab），但留著沒壞處 |
| `[A-Z][12]\d{8}` | 台灣身分證 | ★ 同上，`A123456789` 實測必切歪 |
| 13～19 位數字且 Luhn 通過 | 信用卡 | ★ 同上 |
| 含 `://` 或 `www.` 開頭 | 網址 | |

★ 那三條是**真正在擋事情**的；其餘幾條是防禦深度。**實作時先做數字那幾條**。

**陷阱：規則不能無差別套在「按鍵串」上。** 注音段的按鍵串是 QWERTY
亂碼（`ru/ 6wu84` 那種），第三條「英數混合 ≥ 8」會把它整片吃掉——
**切詞學習直接失效，而且不會有編譯錯誤、也不會有測試失敗**。這正是
CLAUDE.md 那條「一個設定套用到兩層實作，漏掉一邊只會在使用者手上壞掉」
的典型死法。

所以守門要分辨「鍵即明文」與「鍵只是按鍵」：

| 記錄點 | 套用對象 | 理由 |
|---|---|---|
| `learn::record`（選字） | **文字** | 注音鍵串不是明文，不看 |
| `learn::record_cutting`（`lang:`／`cut:`） | 其中的**英文段字面** | 英文段的按鍵串就是它的文字；注音／日文段不套 |

驗收要有一條測試直接守住這件事：**一串正常的中文按鍵不可以被守門擋掉**。

### 2.81.36 門檻要訂幾位？拿測資量，答案是 5

使用者問（2026-09-14）：**連續數字大於 4 是不是就不該存了？**

`spike_privacy` 拿**真的測資**（1421 筆）量誤擋——誤擋的判準是
「正常測資的文字被擋掉」，那句話本來該學卻學不到。

| 門檻 | 誤擋句數 | 誤擋率 | 擋住的敏感樣本 |
|---|---|---|---|
| 3 | 7 | 0.5% | 8/8 |
| **4** | **4** | 0.3% | **8/8** |
| **5** | **0** | **0.0%** | 7/8 |
| 6 | 0 | 0.0% | 6/8 |

**門檻 4 誤擋的四句，全部是年份**：

```text
[number] 2026年        [number] 1000円
[number] 2026 report   [number] 2026 年度 report
```

**這正是「四位數」最常見的無害用法**——年份、價格。而門檻 5
**誤擋歸零**，還是擋得住手機、市話、身分證、信用卡、六位驗證碼、
生日、郵遞區號＋門牌。

#### 「誤擋」到底會怎樣？是學不到，不是變錯

使用者問（2026-09-14）：那四句是**學不到**還是**會變成錯的**？

**是學不到，而且那四句根本不需要學。** 兩層證據：

**一、查不到就原封不動。** `rank::promote_learned_cut` 查不到學習記錄
就 `return cands`（`rank.rs:1035`）——**不改動任何排序**，不是退回某個
更差的選擇。學習層在這裡是「加分」不是「決定」。

**二、那四句不靠學習本來就對。** 實際跑一遍：

```text
2026 report   第一名 → 2026 report    ✅
2026          第一名 → （英）2026      ✅
1000          第一名 → （英）1000      ✅
```

所以守門在這裡擋掉的是「**強化一個本來就對的結果**」——使用者完全
感覺不到差別。

> **這讓門檻的取捨更輕鬆了**：門檻 4 的「代價」其實比帳面上更小。
> 但既然門檻 5 連這點代價都不必付、又只漏掉一次性的四位數驗證碼，
> **仍然取 5**。
>
> 更廣的一條：**學習層的誤擋是「少一個加分」，不是「多一個錯誤」**。
> 這是隱私守門敢用寬鬆規則的底氣——跟選字層那種「改掉使用者選過的字」
> 完全不同量級。

| 門檻 5 漏掉的 | 為什麼可以接受 |
|---|---|
| **四位數驗證碼**（`8274`） | 它是**一次性**的，記進學習檔沒有長期價值也難以回推用途；而為了它要付「每個年份都學不到」的代價 |

> **使用者的直覺方向對**（4 位就開始敏感），但**量完是 5**——差的那一位
> 正好卡在年份上。這跟 §2.81.35 是同一種收穫：**憑感覺會訂太嚴，
> 而太嚴的代價是無聲的**（那幾句只是默默學不到，不會有人回報）。

### 2.81.37 雜湊那條路：技術上可行，但解決的問題比想像小

使用者要評估（2026-09-14）。先確認**技術上做不做得到**：

| 查詢端 | 怎麼用鍵 | 雜湊後還能用嗎 |
|---|---|---|
| `Cutting::lang`（`learn.rs:721`） | `self.lang.get(keys)` 整串精確查 | ✅ 可以——鍵只要能對上就好 |
| `Cutting::cut`（`learn.rs:726`） | `self.cut.get(keys)` 整串精確查 | ✅ 同上 |

**兩邊都是精確查表，沒有前綴比對或範圍掃描**，所以把鍵換成雜湊
功能完全不受影響。

**但它解決的問題比想像小：**

| | 雜湊擋得住 | 雜湊擋不住 |
|---|---|---|
| 檔案被別人看到 | ✅ 看不出原文 | |
| **值欄位** | | ❌ `lang:` 的**值**是語言代碼沒問題，但**選字學習那條路**（`record`）記的鍵是按鍵、值是**文字本身**——那才是最像明文的地方，雜湊鍵救不到 |
| 字典攻擊 | | ❌ 手機號碼只有 10 位、身分證有格式，**窮舉得完**。要擋得加 salt，而 salt 要存哪又是新問題 |

**代價是明確的**：學習檔**不再是人看得懂的**，而「可以手動刪行」
是寫在檔案開頭第一行的設計（`# 智慧學習記錄——引擎自動累積，可以手動刪行`）。
使用者想刪掉某一條時再也找不到它。

> **結論：不做雜湊，做守門。** 守門是「**根本不寫進去**」，雜湊是
> 「寫進去但難看懂」——前者才是隱私問題的正解，而且不必付掉可讀性。
> 雜湊該留在「萬一守門規則有漏網之魚」的備案位置，不是第一道防線。

### 2.81.9 還沒定的（回來先看這裡）

**功能一**

| 待決 | 傾向 |
|---|---|
| 誤擋要不要留 log | `dlog!` 記一筆「因隱私規則跳過」，只有 debug 開時看得到 |
| 要不要給「連帳號類也一起學」的進階開關 | **不給**——隱私守門給開關等於多一個會被誤關的面，而誤擋只是**少一個加分**（2.81.36 查證：查不到就原封不動，不是變錯） |
| **`cut:{整串按鍵}` 怎麼處理**（2026-09-14 新增） | 見下——原設計只講「英文段的字面」，漏了這一條 |

**第三件的三個選項**（複查時發現原設計沒涵蓋）：

`cutting_records` 最後一行記的是 `cut:{整串按鍵}`，鍵裡含**整句**的按鍵，
不分語言。守門規則不能直接套（注音鍵串是 QWERTY 亂碼，會被「英數混合
≥8」整片吃掉，就是 2.81.4 那個陷阱）。

| | 做法 | 代價 |
|---|---|---|
| ① | **整串裡只要有任一英文段命中守門，這條 `cut:` 就不記** | 最安全。代價是含帳號的句子連「切點位置」也學不到——但那本來就是該忘掉的句子 |
| ② | 只擋 `lang:`，`cut:` 照記 | 洩漏沒補起來——`cut:` 的鍵就是整串按鍵，帳號仍在裡面 |
| ~~③~~ | ~~`cut:` 的鍵改成雜湊~~ | **評估過了，不做**——技術可行但解決的問題比想像小，見 2.81.37 |

**傾向 ①**：它跟「誤擋只是沒學到」同一條原則，而且不動檔案格式。

### 2.81.38 實作（2026-09-14）

守門是 `learn::privacy` 一個純函式模組。**兩個掛點的套用對象不同，
那是最容易寫錯的地方**：

| 掛點 | 看什麼 | 為什麼 |
|---|---|---|
| `record`（選字） | **整句送出的文字** | 注音的按鍵串是亂碼，看文字才對 |
| `cutting_records`（切詞） | **接起來的英文段按鍵** | 英文段的按鍵串就是它的字面 |

**兩處都是「整個一起看」而不是逐格／逐段**，理由同一個：
`0912345678` 會被切成 `英:091234｜注音:56｜英:78`（數字鍵是注音鍵），
**分開看每一段都不夠長、每一條都會放行**。

`cutting_records` 照選項①——任一段命中就**整串什麼都不記**，包括最後
那條 `切:整串按鍵`。

**不印 log，改用計數器**（`privacy::skipped()`）：`dlog!` 是平台層的，
`core` 要保持平台無關（CLAUDE.md 那條）。而且**只算次數不記內容**——
記內容等於把守門擋下來的東西又寫到另一個地方，那就白擋了。

**測試五條**，其中 `守門不可以擋掉正常的中文按鍵串` 是 2.81.4 那個
陷阱的守衛：拿真的注音按鍵串（`ru/ 6wu84`、`cl3vu;4y94ru.4`…）確認
一條都不被擋。**那個坑不會有編譯錯誤也不會有測試失敗**，只會讓切詞
學習無聲全滅，所以一定要有這條。

### 2.81.39 第一版就踩進去了：「被判成英文」不等於「真的是英文」

**寫了守衛測試還是踩到**，因為測資不夠真。

使用者實測回報（2026-09-14）：**改了字卻沒有新紀錄**。查下去是守門
把整句合法的中文擋掉了：

```text
up jo42841j4zp4h61j4tl   →  因為大部分詞不超
第一名切法： 英:up ｜ 英:jo42841j4zp4h61j4t ｜ ㄅ:l
                    ^^^^^^^^^^^^^^^^^^^^^^ 被判成英文
```

那一大段其實是**還沒切開的注音**（`jo4`＝為、`284`＝大、`1j4`＝部…），
裡頭的「五位數字」`42841` 是**音節邊界黏出來的假象**——`jo4` 的尾 `4`
＋ `284` ＋ `1j4` 的頭 `1`。**沒有任何一個音節含五位數字。**

> **使用者一句「42841 不是注音合法吧」點破了錯誤前提。** 我把切法標的
> `English` 當成「這真的是英文」，但那常常只是**三個引擎都不認得的
> 預設值**。判斷之前要問引擎（`show_ime` 一跑就看出來了），不是看字面。

**修法兩道**：

| | 做什麼 |
|---|---|
| `privacy` | 加 `looks_like_bopomofo_keys` 豁免——**字母佔比 ≥ 1/3 且散布到後半**。注音的聲母介音韻母全在字母鍵上，純號碼沒有字母、身分證只有開頭一個 |
