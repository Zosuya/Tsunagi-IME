# 詞庫就位後的完整量測：引擎跟 Windows 逐節相同

[[spike 1 在真的 Mac 上重跑：core 原生過，但翻出三個靜默的洞]] 那一輪是**刻意沒裝詞庫**跑的。詞庫從外接碟複製過來之後
（待決 5 選了「從 Windows 那台複製」），把所有計分器重跑一遍。

**最重要的一行**：

```
  總計   1421 │  0  15  42  84 │ 1280  90.1%  +63 │ 1.16  202⚠2  2.9%

=== 跟基準比 ===
  總計    1280 → 1280  持平
  （全部持平）
```

**17 節一節不差**。`testdata/基準.txt` 是在 Windows 上存的，macOS 這邊
逐節對上——不只是「編得過、測試過」，是**同樣的輸入算出同樣的候選、
同樣的排序、同樣的選字**。core 的可攜性到這裡才算真的量完。

| 計分器 | 結果 |
|---|---|
| **漏斗** `check_all` | 1280/1421＝**90.1%**，跟基準全部持平 |
| **語言模型** `check_lm` | ✓ 全部一致 |
| **符號稽核** `check_symbols` | ✓ 2051 名字／5457 符號 |
| **凍結安全** `check_freeze` | D=8 時凍錯 0.89% 步／4.9% 句 |
| `bench_dict` | 注音 133,101 條、日文 745,965 條，合計 672ms |
| `mkkeys` | 2/2 打得出原詞 |

**每鍵耗時（Apple Silicon）**——跟 §2.57.8 在 Windows 上量的並排：

| | p50 | p95 | p99 | 最慢 | 一幀預算 |
|---|---|---|---|---|---|
| macOS（M 系列） | 2.8ms | 6.2ms | **8.6ms** | 15.5ms | 16ms |
| Windows（§2.57.8） | — | — | 7.9ms | — | 16ms |

**同一個量級，都在預算內**，不需要為了 Mac 再調一次熱路徑。最慢那一鍵
15.5ms 出現在「超長（日文 110 鍵）」，離預算只剩 0.5ms——**但 Windows
那邊本來就這樣**，不是 macOS 才有的問題。

**兩個順帶量到的**：

- 詞庫載入 650.5ms，計分器自己就印了「⚠ 超過 0.5 秒——TSF 裡要預載，
  不能等第一次打字」。macOS 這邊反而輕鬆：輸入法是**常駐的獨立行程**，
  開機載一次就好，不像 DLL 每個宿主行程各載一次（[[執行模型的根本差異]]）
- `bench_typing` 的「常駐記憶體」在 Mac 上印**量不到**——那段是
  `#[cfg(windows)]`（`bench_typing.rs:27`、`bench_connection.rs:13`）。
  要在 Mac 上量得補一支，還沒做

**順帶發現一個跟 CLAUDE.md 對不上的地方**：改寫欄是 `202⚠2`，而
CLAUDE.md 寫著「`⚠` 後面是伸到游標 3 格外的次數，那是硬指標、**必須是
0**」。出現在 `japanese_verbs`（20⚠1）與 `long`（21⚠1）。**跟基準比是
持平，所以 Windows 上本來就是 2，不是移植造成的**——但那條規則說它該是
0，兩者對不上，要嘛規則要改、要嘛那兩句要修。列在這裡免得被忘掉。
