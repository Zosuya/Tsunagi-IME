# 設定頁的五處平台缺口：對話框接上了

設定頁移植時有五處是 Windows 專屬、在 macOS 上一律回 `None` 的空殼
（[[macOS 移植的六項待決：四項裁決，不做語言鎖定一天就推翻]] 的待決 2）。這一節結掉其中兩處，並記下另外三處為什麼先擱著。

### 接上的：`NSOpenPanel`（選資料夾、選圖片）

兩種用途共用同一個面板，差別只在 `canChooseDirectories`／`canChooseFiles`
那兩個開關。**不用 rfd**：這個 crate 在 macOS 上要接的東西不只檔案對話框，
而 `platform/macos` 已經在用 objc2，多拉一套等於同時維護兩套呼叫慣例。
版本刻意跟 `platform/macos` 對齊——分岔的話 workspace 會編出兩份 objc2，
型別互不相容。

兩個實作上的點：

- **`runModal` 一定要在主執行緒**（它跑一個巢狀事件迴圈）。egui 的
  `update` 本來就在主執行緒，所以從按鈕回呼裡叫是安全的；用
  `MainThreadMarker::new()?` 當保險，拿不到就回 `None` 而不是崩掉
- 圖片副檔名的過濾用的是**已標為 deprecated 的 `setAllowedFileTypes:`**。
  現行作法 `setAllowedContentTypes:` 的型別是 `UTType`，那要再拉一個
  `objc2-uniform-type-identifiers`——只為三個副檔名多一個依賴不划算，
  而舊的那支在 AppKit 裡仍然活著。objc2 沒生繫結，直接送訊息

### 先擱著的：字型選擇

macOS 沒有跟 `ChooseFontW` 對等的東西。`NSFontPanel` 是**非模態面板**、
靠 target/action 回呼，跟 egui 的即時模式 UI 整合彆扭（面板不擋主視窗，
選了字型要另外接一條通知路徑）。正解大概是用 CoreText 拿字型家族清單、
在 egui 裡自己做一個附預覽的選單——那是跨平台共用的，之後 Windows 也能
換掉 `ChooseFontW`。工程量最大的一處，使用者裁定先擱著。

### 先擱著的：背景圖解碼——**因為 macOS 根本還沒有背景圖**

原本以為只差一個解碼器。查了才發現：**macOS 的候選面板不畫背景圖**。
`candidate_panel::paint` 只有三樣東西——`window_bg` 的圓角底、反白塊、
文字；Windows 那邊還有「先畫圖、再蓋一層半透明漸層」（`strength` 控制
蓋多重，見 `Background::overlay_alpha`）與文字描邊（`text_outline`）。

所以現在把 `image_load` 做出來，設定頁預覽解出來的圖**對不到任何實際
畫面**——輸入法那邊不會長成那樣。正確順序是先在 macOS 面板把背景圖畫
出來，設定頁預覽再共用同一套解碼器；那正是 Windows 刻意用 WIC（而不是
純 Rust 解碼器）的理由：**跟實際繪製同一套解碼，色彩管理與 gamma 才不會
兩邊不一樣**。

順帶量到的一件事：`objc2-core-text` 與 `objc2-core-graphics` 已經是
`objc2-app-kit` 的傳遞依賴、本來就在編。真要做字型清單與圖片解碼，
**不需要新的第三方 crate**，只是把它們從傳遞依賴改成直接宣告。
