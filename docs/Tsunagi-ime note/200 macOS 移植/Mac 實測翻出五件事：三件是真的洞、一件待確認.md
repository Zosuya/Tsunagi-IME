## 共同的教訓：驗收只在 Windows 做過

②③④ 有同一個形狀：**功能在 Windows 上驗過、記為「三宿主實打通過」，
但那三個宿主全在 Windows**。擴充包編輯器的驗收（2026-09-14）就是這樣。

③ 尤其典型——它壞掉的原因**不是任何一邊寫錯**，而是兩邊各自都對：

- Windows 的組字區顯示**原始按鍵**（`cj6wl6`）
- macOS 的組字區顯示**轉換後的國字**（「胡桃」），這是跟隨 Mac 原生輸入法慣例的
  刻意決定，`echo_ime.rs` 的 `composition()` 有長註解說明

而「怎麼打」那個欄位的整個實作前提是「組字區裡裝的是原始按鍵」。
**前提只在一個平台成立，於是功能在另一平台靜默地做錯事。**

> **可推廣的判準**：任何「從組字區／preedit 撈東西」的功能，兩平台的語意
> 不同，一律要兩邊各驗一次。這類 bug 不會編譯錯、不會測試紅，只會在
> 使用者手上壞掉。

## ① 倒退鍵：查過了，但症狀還沒對上

程式碼盤過一遍，**鍵位表兩平台共用同一份**（`core/src/binding.rs`，
`Mode::Typing/SegMenu/Selecting` 底下的 Backspace 綁定完全一致），
core 的處理路徑也沒有分岔。

查到的**唯一實質差異**：

| | Windows | macOS |
|---|---|---|
| 組字刪到空之後 | `end_composition(EndKind::Cancel)`，**明確拆掉 composition** | 只 `refresh()` → `set_marked("")`，靠 IMK「marked text 設成空字串＝取消」的隱含語意 |

位置：`platform/windows/src/text_service/mod.rs` 的 `Action::Backspace`／
`DeleteCell`／`DeleteSeg` 三處都有 `if is_empty()` 收尾；
`platform/macos/src/echo_ime.rs` 對應的三處沒有。

**推測的症狀**是「刪光後組字底線殘留」或「宿主 caret 位置怪異」。

但使用者的描述是「Mac 因為沒有組字區，所以 Shift+刪除的邏輯跟 Windows 不同」
——**這跟程式碼查到的對不上**（Mac 是有組字區的，只是顯示國字）。
所以這條**待使用者確認實際症狀**再判斷，不要憑上表就動手。

### 第二輪：症狀問出來了，但跟程式碼又矛盾（2026-09-19）

問清楚之後，使用者要的是「打『你好』按 `Shift+Backspace` 應該刪掉整個『好』」，
而**鎖定注音下實際是一個一個音退**。

先釐清鍵位——三組設定名字很像但各管各的，很容易記錯：

| 情境 | 設定名 | 綁哪顆鍵 | 預設 |
|---|---|---|---|
| **鎖定語言**（注音／日文） | `backspace_whole_cell` | **倒退鍵**（不可選，不用 Shift） | **開** |
| **段選單**（按過 TAB） | `delete_marked_seg` | 三態可選 | `Backspace` |
| **選字模式**（自動模式逐格） | `delete_marked_cell` | 三態可選 | **`Off`** |

**沒有任何一種預設狀態會讓 `Shift+Backspace` 刪整個字**，所以那個期待本身
就對不上現況。鎖定注音下該按的是**單獨的倒退鍵**。

> **⚠ 2026-09-20 已定位，以下這節保留當追查記錄。**
> 真正的根因**不在退格、也不在反白框，而在送出**：Mac 的 `commit()` 誤用了
> 給組字區顯示用的 `composition()`（含 `pending_symbols`），
> 把沒成字的注音當文字送進宿主。完整經過與三條判準見
> [[Mac 送出時把沒成字的注音也送出去：追了五輪的定位過程]]。

### ★ 卡住的矛盾：程式碼說 Windows 也該壞 ★

查 core 之後發現關鍵——**每打一個音節，反白框就被清掉了**：

```rust
// core/src/session/mod.rs 的 refresh()
self.select_idx = None;
// **又打字了就把標記收掉**：那個標記的意思是「你剛改了這一格」，
// 繼續打字之後它就過期了，留著會在組字區留下一個沒人管的框。
self.last_select = None;
```

而 `backspace()` 刪整格的條件是 `marked_index()` 要找得到框，找不到就
**靜默退回「刪一個音」**（那是設計上的正常退路，不會有任何跡象）。

這件事有測試釘住，不是意外：`assert!(s.marked_index().is_none(), "剛打完不該有框")`，
另一條測試 `沒有框時維持原本的退格` 還明文寫著「**鎖定注音的退格本來就是
刪掉整個音節**…這條路不能被新功能改掉」。

**所以照程式碼推論，「打完字直接按倒退鍵」在兩平台都該是刪一個音。**
但使用者實測回報 **Windows 那邊組字框會正常刪除**。

**兩件事不能同時為真，待使用者在 Windows 上照固定步驟複測**
（鎖定注音 → 打 `su3cl3` → 什麼都不按 → 倒退鍵 → 看組字區變成什麼）。

- 若 Windows 真的刪掉整格 → 調查漏了什麼，回頭查 Windows 為什麼有框
- 若 Windows 也是刪一個音 → **這不是 Mac 的 bug，而是這個功能從來
  沒有在「剛打完字」的情境下生效過**，變成規格問題：要不要讓鎖定注音下
  的框跟著游標走

> **這一條記下來的價值在方法**：使用者的體感描述（「Mac 跟 Windows 不同」）
> 與程式碼推論衝突時，**不要挑一邊相信**。兩邊都可能錯——描述可能是
> 記錯鍵位或記錯平台，推論可能漏看一條路。**要用固定步驟在兩個平台
> 各跑一次**，把體感換成可比對的事實。

### 附帶查出一個真的 Mac 漏接：方向鍵

跟倒退鍵不同件事，但同一輪查出來的。鎖定注音下按 `←` `→`：

| | Windows（`arrow_right`） | macOS（`enter_select_first`） |
|---|---|---|
| 框還留著時按 → | **往右移一格** ✔ | 回到**同一格**，框不動 ✘（要按兩下才動） |
| 會不會彈候選面板 | 不會（框與候選是兩件事） | **會**（多呼叫了 `open_cands()`） |

位置：`platform/macos/src/echo_ime.rs` 的 `EnterSelect`／`EnterSelectLast`
兩處，改用 `arrow_right()`／`arrow_left()` 並拿掉 `open_cands()` 即可對齊。

**這一項曾被平台稽核判定成「等價、沒問題」，判錯了**——完整經過與教訓
見 [[怎麼系統性抓出平台層漏接：解構與 API 反查]]。

> **2026-09-27 已改完，Mac 實機未驗**：兩處分別改成
> `self.session().borrow_mut().arrow_right()` 與 `arrow_left()`，拿掉
> `open_cands()`；`refresh()` 只重畫組字區，候選面板要不要顯示交給
> `visible_candidates()` 問 `cands_open()`，所以拿掉呼叫之後面板不會
> 自己彈出來。這條分派本來就走 core 共用的 `arrow_*`，兩平台差異
> 只在平台層有沒有呼叫對函式，core 不用改。額外在
> `core/src/session/tests.rs` 加了 `arrow不會自己打開候選清單`
> 鎖住「只出框、不開清單」這個契約。**驗收方式**：鎖定注音打一個詞、
> 按 Enter 離開選字（框留著），連按 `←` 或 `→`——應該每按一下就移動
> 一格、且不彈出候選面板；要看候選字仍是按 `↑`／`↓`（手勢那條路，
> 見 `on_gesture`／`enter_select_showing`，沒有動它）。

這個 bug 可能正好解釋使用者的體感：**若在 Windows 習慣先按方向鍵調框再刪**，
到 Mac 上方向鍵不動框，刪掉的自然就不是同一格。

另外兩處是平台慣例差、不是 bug，記著免得日後誤判：

- **攔截的修飾鍵集合不同**：Windows 是 Alt／Win 按著就讓給宿主，
  macOS 是 Control／Option。這是兩邊系統慣例不同造成的
- **Shift 的取得方式不同**：Windows 在 action 分派時重新 `GetKeyState()`，
  macOS 把按下當時讀到的值一路傳下來。理論上 Windows 那條有時差，
  但實務上沒觀察到
