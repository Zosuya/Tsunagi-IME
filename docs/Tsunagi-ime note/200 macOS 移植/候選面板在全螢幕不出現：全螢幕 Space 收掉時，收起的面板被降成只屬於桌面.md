# 候選面板在全螢幕不出現：全螢幕 Space 收掉時，收起的面板被降成只屬於桌面

> **狀態**：**提示條也驗過了（2026-09-27 使用者 Mac 實機驗過），收尾。****根因已在 spike 重現、也在真的輸入法上照步驟重現（2026-09-23 第三輪）。
> 修法已實作（偵測到就重建），候選面板 C29 真機通過，提示條 C29b 待驗**。
>
> - **根因**：任何一個全螢幕 Space 被收掉（退出全螢幕、或全螢幕中的 app
>   結束）的那一刻，**收起中**的面板會被系統從「每個 Space 都在」降成
>   「只屬於一般桌面」。AppKit 那邊讀回來的 `collectionBehavior` 完全沒變，
>   是 window server 那邊掉的
> - **症狀**：之後在**原本就開著**的全螢幕 app 裡打字，面板叫得出來但待在
>   桌面那一格——就是使用者說的「留在上一個畫面」。回到一般桌面又正常，
>   **新開**的全螢幕也正常，所以看起來「時有時無」
> - **修法**：同值重設、清空再設回、`orderFrontRegardless`、收起再開**全部
>   無效**，只有**丟掉重建**有效。偵測用 `isOnActiveSpace`，`orderFront`
>   當下就準
>
> 第一輪（下方前半）追的座標、第二輪追的層級都不是這個病因，但都是真的洞，
> 留著。**第一輪的復原方式「退出全螢幕再進去」會好**，第三輪也解釋了：
> 新建的全螢幕 Space 會把壞掉的面板收進去。

兩個 VS Code 視窗同時開著，一個正常、另一個**打得出字（底線、組字都在），
但候選面板完全不出現**。查完發現兩件事：症狀有**兩個**嫌疑犯而且從外面
分不出來；而定位邏輯確實漏了一條，Windows 那邊早就有。

## 現場

| 事實 | 值 |
|---|---|
| 壞掉的視窗 | VS Code **全螢幕**（獨立 Space），在 Claude Code 擴充的輸入框打字 |
| 正常的視窗 | 同一個 VS Code app、同一個螢幕、一般視窗 |
| 螢幕 | 只有內建一台，**沒有外接**（排除多螢幕座標問題） |
| 輸入法行程 | 只有一個，比壞掉那個視窗的 renderer 晚 23 秒啟動 |
| 按鍵紀錄 | `keyprobe.log` 顯示 VS Code 的按鍵正常「接手／放行」 |

**恢復方式**：使用者退出全螢幕再進去一次就好了。注意**退出全螢幕的當下
還是壞的**——所以不是「全螢幕這個狀態擋住面板」，被重置的是視窗狀態轉換
時重算的東西。

## 排除掉的

- **多螢幕座標**：只有一台內建螢幕
- **全螢幕本身**：退出全螢幕當下仍然壞
- ~~**面板被蓋住**：層級是 `NSPopUpMenuWindowLevel`（101），而且
  `CanJoinAllSpaces | FullScreenAuxiliary | Stationary` 都設了，見 [[spike 3：候選視窗用 NSPanel]]~~
  **這條排除錯了**（2026-09-23 量到）：實際層級是 **3**，不是 101，見文末第二輪
- **按鍵到不了輸入法**：log 裡 VS Code 的方向鍵、Esc 都有正常接手
- **宿主連著被砍掉的舊行程**：那條會整個沒反應，不會有組字

## 兩個嫌疑犯，從外面分不出來

這是這次查起來最花時間的地方——**下面兩條路的症狀一模一樣**，都是
「打得出字、面板不見」：

1. **宿主答不出插入點座標**（`caret_rect` 回 `None`）→ `set_marked` 的
   `else if` 整段跳過，面板**根本沒畫**
2. **宿主答得出，但座標離譜** → 面板畫了，但被擺到**螢幕外**

[[spike 4：插入點座標 7 個宿主都拿得到]] 量過的 7 個宿主都沒發生過第 1 種，
但那次**沒有測全螢幕**——相容性測試清單 M5 的備註本來就寫「編輯器內的
插入點座標最容易錯」，而全螢幕一條都沒列。

## 找到的缺口：定位只夾了一側

`candidate_panel::show` 原本的夾制是**左右兩邊都夾、上下只夾底部**：

- 掉出螢幕底部 → 翻到游標上方 ✓
- **翻上去之後會不會超出螢幕頂端 → 沒檢查** ✗
- **游標座標本身就在螢幕外 → 完全沒防** ✗

`width_panel`（全半形那條 bar）是**鏡像的同一個洞**：預設放上方，翻到
下方之後沒檢查會不會掉出底部。兩處各寫一份定位邏輯，兩份漏掉的是同一
件事。

### Windows 早就做對了

`platform/windows/src/candidate_window.rs` 的 `place()` 三條規則齊全
（放下方 → 放不下翻上方 → 都放不下就貼齊），還附六個邊界測試。**macOS
缺的正是它已經有的東西**——移植時這段是各自重寫的，不是照抄。

## 做了什麼

抽出 `candidate_panel::place()`，純數值運算所以測得起來，兩處共用：

1. 規則照 Windows 的 `place` 翻譯（**那邊左上原點、這邊左下原點，上下的
   加減相反**）
2. **最後無條件把位置夾回可視範圍**——這條才是重點。前面的規則處理的是
   「螢幕放不放得下」，前提是座標合理；座標本身離譜時，算出來的位置照樣
   在螢幕外
3. 十個邊界測試，含「游標座標高到離譜」「游標掉到螢幕下方外」兩條，斷言
   面板必須完全落在螢幕內

## 下次怎麼定案：`[panel]` 診斷紀錄

加了診斷紀錄寫進 `keyprobe.log`（前綴 `[panel]`，`tools/keyprobe.py` 只認
`[key]` 開頭所以不干擾它）。兩種情況各記一筆，**連續重複的不再寫**——
組字中每按一鍵都會問一次座標，不去重會把檔案灌爆。**正常情況一行都不會
產生。**

- 宿主答不出座標 → `宿主回零矩形，問不到插入點座標，面板不顯示`
- 座標落在所有螢幕之外 → `插入點座標落在所有螢幕之外：(x, y) 高 h`

下次再發生，看這兩行就知道是哪一條，不必再靠讀程式碼推理。

## 教訓

**「面板不出現」這種症狀，光讀程式碼分不出病因**——這次兩個嫌疑犯都在
程式碼裡看得到，但無法判斷是哪一個發生了。這跟 CLAUDE.md 那條「按鍵沒
反應先埋 log 看狀態，不要讀程式碼猜」是同一件事：**能靜默失敗的分支都
該留一行紀錄**，不然真的出事時什麼線索都沒有。

## 第二輪（2026-09-23）：面板層級實際是 3，第一輪那條「排除」推錯了

使用者回報：**全螢幕的 app 裡候選面板有時候出得來、有時候不行，不確定
觸發點**。這次不再讀程式碼推理，直接量。

### `[panel]` 紀錄一筆都沒有

`keyprobe.log` 11817 行，`[panel]` 開頭的 **0 筆**。上面那兩條診斷是
2026-09-20 加的，當天裝的版本就有。所以 9/20 之後如果發生過，**兩個
座標嫌疑犯（答不出座標、座標在螢幕外）都可以排除**——座標是好的、
`show()` 也真的呼叫了，面板卻沒被看見。

（待使用者確認：9/20 之後真的發生過嗎？）

### 量到的洞：`setFloatingPanel(true)` 把層級蓋回 3

用 `CGWindowListCopyWindowInfo` 列出輸入法行程的視窗：**面板的 layer 是
3**（`NSFloatingWindowLevel`），不是程式碼裡設的 101。

原因是呼叫順序。兩個面板（`candidate_panel`、`width_panel`）都寫成：

1. `setLevel(NSPopUpMenuWindowLevel)` ——設成 101
2. `setFloatingPanel(true)` ——**這個 setter 的副作用是把層級設成
   `NSFloatingWindowLevel`（3）**，第 1 步白做

第一輪「面板被蓋住」那條排除，根據是「程式碼寫了 101」——**讀程式碼
推出來的，沒量**。跟這篇上面的教訓是同一件事：S_OK 不代表參數是你以為
的值，寫了 `setLevel` 不代表層級就是那個值。

### spike：兩個行程模擬「全螢幕宿主＋輸入法」

`scratchpad` 裡兩支 Swift 小程式：假宿主（一般 app，開視窗進全螢幕）、
假輸入法（accessory、面板旗標跟 `candidate_panel.rs` 完全一樣，只差層級）。
判準是 `CGWindowList` 的「在目前 Space 的畫面上」＋`isOnActiveSpace`。

| 情境 | 層級 3（現行） | 層級 101（修正） |
|---|---|---|
| 輸入法先啟動，宿主後進全螢幕 | 看得到 | 看得到 |
| 宿主先進全螢幕，輸入法後啟動 | 看得到 | 看得到 |
| 面板在一般桌面建好收起，進全螢幕後再開 | 看得到 | 看得到 |
| **宿主在全螢幕裡開一個浮動（3）小視窗疊在同一處** | **被蓋掉** | 看得到 |
| 對照組：拿掉 `FullScreenAuxiliary` | 看不到（`isOnActiveSpace=false`） | 同左 |

結論：

- **全螢幕本身不擋面板**——旗標是對的，層級 3 也進得了全螢幕 Space。
  網路上有人說「floating 層級太低、進不了別人的全螢幕 Space」（見下方
  參考），**在我們這個組合（accessory＋nonactivating）上量不到**
- **層級 3 會被任何「浮動層級、而且比我們晚推到前面」的視窗蓋掉**——
  宿主自己的浮動面板、別的 app 的置頂小工具都算。這種失敗天生就是
  「有時候」：看當下哪個視窗最後被推到前面、疊不疊在同一處
- **但這還不能解釋「為什麼跟全螢幕有關」**——假宿主重現不了真實的
  時有時無。層級修回 101 是修一個量得到的洞，不保證就是使用者看到的那個

### 偵測器 spike：面板「沒被看見」能不能在當下自己發現

要讓下次真的發生時留下線索，先確認輸入法自己查得出來：

- **`isOnActiveSpace` 在 `orderFront` 當下就準**——對照組當下就回 `false`
- **`CGWindowList` 當下不準**：同一輪事件裡問，四個面板全部回「不在畫面上」，
  連帶「上面蓋著什麼」也全錯（把宿主的主視窗都列進去）。**要延後約 0.3 秒
  再問**才對
- 延後再問，「被蓋掉」那個情境查得到是誰蓋的（`spike_host2/layer3`）
- 耗時：四個面板合計 4ms，**不能每按一鍵都問**（排序是熱路徑，一幀 16ms），
  只在面板「從收起變成打開」時問一次

### 提案（尚未實作，等使用者決定）

1. **層級修回 101**：兩個面板都把 `setFloatingPanel` 移到 `setLevel` 前面。
   驗收：重建後用 `CGWindowList` 看 layer 是 101
2. **補兩種診斷**，都寫進 `[panel]`、面板打開時才查：
   - 當下查 `isOnActiveSpace`——不在目前 Space 就記一筆
   - 延後查 `CGWindowList`——不在畫面上、或被別的視窗蓋住，記下是誰蓋的
3. `orderFront` 換 `orderFrontRegardless`：Apple 文件說後者正是給「作用中
   的 app 借另一個 app 顯示資料」用的（就是輸入法的情況），但 **spike 裡
   兩者量不出差別**。先不換，等診斷真的記到「不在目前 Space」再試

### 參考

- speaktype PR #142：聲稱 floating 層級「太低、進不了全螢幕 Space」、要升到
  status 層級——我們的組合量不到這件事，但方向一致（層級不要停在 3）
- antiburn PR #419：用 `orderFrontRegardless`，並在**每次顯示前**重設面板設定
- Thuki 的開發文章：全螢幕上「約三分之一的時候跑到後面」——跟我們的

## 第三輪（2026-09-23）：定案——全螢幕 Space 收掉時，收起的面板被降級

使用者找到觸發條件的線索：**全螢幕狀態下用 Control＋←→ 切畫面，候選框
好像留在上一個畫面**。

### 先排除「Control 切換本身」

假輸入法（旗標跟產品一樣的六種變體）開著，使用者手動 Control 切 10 次、
經過 Safari／Claude／VS Code／Obsidian 四個全螢幕——**六種全部跟過去**。
用「叫別的 app 到前面」觸發的 Space 切換也一樣。所以不是切換本身。

### 關鍵量測：面板「屬於哪幾個 Space」

用 SkyLight 的私有函式 `SLSCopySpacesForWindows` 問視窗屬於哪些 Space
（**只在 scratchpad 的診斷工具裡用，產品不用私有 API**）：

| 視窗 | 所屬 Space |
|---|---|
| 假輸入法的面板（同一組旗標） | `[219, 215, 260, 1, 298]`——全部，收起後也是 |
| **真的輸入法的面板（跑了一小時的那個行程）** | **`[1]`——只有一般桌面** |
| 真的輸入法重啟後的新面板 | 全部，使用者打了三分鐘都沒掉 |

→ 面板**一開始是好的，用著用著掉了**。

### 重現：收掉一個全螢幕 Space

假宿主進全螢幕再結束（它的全螢幕 Space 跟著被收掉）：

| 面板當時的狀態 | 收掉之後屬於 |
|---|---|
| 開著 | 全部（沒事） |
| 在那個全螢幕開過、收掉前已收起 | **`[1]`** |
| 從沒在那個全螢幕開過、一直收著 | **`[1]`** |

`collectionBehavior` 讀回來三個都還是 `273`（`CanJoinAllSpaces |
Stationary | FullScreenAuxiliary`）——**AppKit 以為沒變，是 window server
那邊掉的**。候選面板絕大部分時間是收著的，所以**每次有人退出全螢幕或關掉
全螢幕 app，面板就壞一次**。

### 真機確認（同一天）

照上面的步驟請使用者在真的輸入法上做一次：VS Code 已在全螢幕 → 另開一個
app 進全螢幕 → 沒在組字時把它退出全螢幕 → Control 切回 VS Code 打字——
**面板出不來**。同一個行程、同一個面板（重啟後剛量過屬於全部 5 個 Space
的那個），這時問它的所屬 Space：**`[1]`**。病因在產品上確認。

### 補救：只有重建有效

**測法要注意**：第一次把補救放在一個「面板壞掉**之後**才新建」的全螢幕
Space 上測，六種全過——因為**新建的 Space 會把壞掉的面板收進去**
（所屬 Space 從 1 個變 2 個）。那是測錯地方，不是補救有效。改成回到
**壞掉之前就存在**的全螢幕 Space（跟使用者的 VS Code 全螢幕一樣）再測：

| 補救 | 回到既有全螢幕後看得到？ |
|---|---|
| 不補救（現況） | ✗ |
| 同值重設 `collectionBehavior` | ✗ |
| 先清空再設回 `collectionBehavior` | ✗ |
| `orderFrontRegardless` | ✗ |
| 收起再開 | ✗ |
| **丟掉重建** | **✓**（所屬 6 個 Space，全部） |

偵測：`orderFront` 之後當下問 `isOnActiveSpace`，壞的回 `false`、重建的回
`true`，**不用等**。

### 修法（2026-09-23 使用者同意後實作）

1. **`show()` 裡偵測＋重建**（`candidate_panel::stranded`，兩個面板共用），候選面板與全半形提示條都做：面板**從收起
   變成打開**的那一次，`orderFront` 之後問 `isOnActiveSpace`；`false` 就
   丟掉舊面板、重建、重填內容、再開一次（最多一次，不會無限迴圈）。
   只在「收起 → 打開」時問，因為**開著的面板不會壞**（上面那張表），
   組字中每按一鍵就不必多一次查詢
2. 重建時寫一行 `[panel]`（帶第幾次，避免被去重吃掉）——之後看得出多常發生
3. 順便修第二輪的層級（`setFloatingPanel` 移到 `setLevel` 前面）——跟這個
   病因無關，但是量得到的洞
4. 相容性測試清單補上 **C29／C29b**：關掉一個全螢幕 app 之後，到另一個
   原本就開著的全螢幕 app 組字／切語言鎖定

### 真機驗收（2026-09-23）

- **C29 通過**：用假宿主進全螢幕再結束，把真的輸入法的面板弄壞（所屬 Space
  從 5 個掉成 `[1]`）→ 使用者切回 VS Code 全螢幕打字 → **面板出現**。
  `keyprobe.log` 多一行 `[panel] com.microsoft.VSCode 候選面板不在目前的
  Space（…），丟掉重建（第 1 次）`；新面板屬於全部 5 個 Space、層級 101，
  舊的那個視窗已經消失（沒有漏）
- C29b（全半形／語言鎖定提示條）待驗

**沒有自動測試**：病要靠「全螢幕 Space 被收掉」才觸發，`cargo test` 碰不到
 window server。驗證靠 C29 真機實打，加上 `keyprobe.log` 的 `[panel]` 重建紀錄

### 教訓

- **「時有時無」通常是「壞了之後要特定條件才看得出來」**：壞掉（收掉全螢幕）
  跟看得出來（在既有全螢幕打字）是兩個不同的時間點，使用者只看得到後者，
  所以說不出觸發點
- **補救要在「壞掉之前就存在」的環境上驗**：新環境會自動把壞掉的東西修好，
  在那裡測什麼補救都會過
- **設定讀回來沒變 ≠ 系統那邊沒變**：`collectionBehavior` 一直是 `273`，
  window server 早就不認了。跟第二輪的層級是同一課，這次連讀回來都騙人
