# 段選單與學習存檔：三個狀態機接完

接 [[選字模式：鍵位、候選網格、組字區的逐格反白]]。CLAUDE.md 講的三個狀態機（mod／cutting／select）在 macOS 上
接完了，加上學習層。

### 段選單：跟選字同一組手勢，換一個粒度

`Session` **沒有「選單開著嗎」這個狀態**——它只提供 `seg_*` 那組操作，
開關由平台層自己記（Windows 是 `State::seg_menu`，macOS 是
`Composition::seg_menu`）。

| 鍵 | 段選單 | 選字 |
|---|---|---|
| ←→ | 換一段 | 換一格 |
| ↑↓ | 換這段的解釋 | 換這格的字 |
| Shift+←→ | 推這段的邊界 | 推日文詞界 |
| 1-9 | 直接挑 | 直接挑 |
| Enter | 定案這一段，反白移到下一段 | 選定這個字，移到下一格 |

**反白的單位是「段」不是「格」**——一段可能橫跨好幾格
（`ㄋㄧˇㄏㄠˇ` 是一段兩格），所以組字區的 attributed string 改用
`seg_preview_texts()` 逐段上屬性。那支回的是**「按下 Enter 會變成什麼」**
而不是現況，使用者推邊界時才看得到結果。

**兩層互斥**（Windows 那邊使用者裁定過的規則）：段選單開著就只選段，
不進選字；`Tab` 開選單前先 `exit_select()`。

### `Esc` 的差別：關選單那半一樣，保不保留定案不一樣

一開始我看鍵位表的註解（「**Esc 是「全部重來」**，不是關選單」）就下結論說
Windows 的 Esc 不關選單——**看錯了**。處理端 `Action::SegReset` 除了
`seg_reset()` 還有 `state.seg_menu = false`，所以它也會關。

真正的差別只有一項：

| | Windows | macOS |
|---|---|---|
| `Tab` | 關選單，**保留**已定案的段 | 同左 |
| `Esc` | 關選單，**丟掉**已定案的段（整串重新交給引擎） | 關選單，**保留**（跟 `Tab` 同） |

macOS 兩顆鍵效果相同是使用者裁定的。`seg_reset()` 因此在 macOS 沒有入口。

> **教訓**：鍵位表只說「綁到哪個 Action」，**Action 實際做什麼要看處理端**。
> 我拿註解當結論，還據此寫了一段「刻意分岔」的說明——那段本身是錯的。

### 學習層：載入、記錄、存檔

- **載入**跟詞庫一起，在背景執行緒（`learn::load` 在 `preload` 之前，
  照 Windows `background.rs` 的順序）——它是查詢的第三層
  （學習層→領域包→靜態詞庫）
- **記錄與存檔在送出時**。存檔要寫磁碟，不能放在每一鍵的熱路徑上；
  送出是天然的節點
- **密碼欄一律不學**：macOS 的判準是 `IsSecureEventInputEnabled()`。
  那時系統本來就不太會把按鍵交給輸入法，所以這是**第二層保險**
  （Windows 的 `state.password` 同一個定位）

學習檔在 `config::user_dir()`，也就是
`~/Library/Application Support/tsunagi-ime/learned.txt`——`learn::path()`
會忽略傳進去的 `data_dir`。

### ★ 一個沒有任何錯誤訊息的 bug：先清才學 ★

第一版的 `commit()` 順序是：

```rust
let text = self.composition();
self.session().borrow_mut().clear();   // ← 先清
...insertText...
self.learn_and_save();                 // ← 才學
```

**`learn_on_commit()` 讀的是 `slots`**——清掉之後它永遠回 0，於是
`learned.txt` 從來不會生出來，而且**一句錯誤訊息都沒有**（回 0 是合法的
「沒東西可學」）。

查法是寫一支測試直接問引擎：模擬「打 `su3` → 進選字 → 按兩次下 →
`confirm_cand` → `learn_on_commit()`」，得到 **1 筆**；沒選字的對照組是
**0 筆**。引擎沒問題就代表是接法錯了，回頭看順序一眼就找到。

正確順序是**先學再清**。
