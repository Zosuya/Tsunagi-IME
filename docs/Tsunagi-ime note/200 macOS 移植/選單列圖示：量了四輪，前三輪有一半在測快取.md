# 選單列圖示：量了四輪，前三輪有一半在測快取

把佔位的黑圓點換成「通」，前後花了四輪。第一輪先做量測工具、逐像素對齊
Apple 的 `zhuyin.tiff`，量出 squircle 圓角與 `TISIconIsTemplate`；第二輪
發現 **Apple 自家輸入法的圖根本不會被畫**（AinuIM 的圖檔是倒心形、畫面上
卻是「ア」），於是判定「現在就是天花板」；第三輪查第三方原始碼，
fcitx5-macos 與 vChewing 獨立收斂到長寬比 1.38、圓角 22%——**macOS 26 把
圓角改大了，前兩輪是準確地複製了一張 macOS 15 時代的舊資產**。第四輪收尾
時才發現，前面好幾個「實測有效／無效」的結論**全是在測同一份沒更新的快取**
——選單列以外的地方（Fn HUD）只有**重新登入**才會重讀。

## 試過的路

### 一、規格是量出來的：先做工具再動手（原 2.52.40）

原本的 `menu.tiff` 畫的是**一顆黑圓點**（補圖示那次放的佔位圖）。換成
「通」的過程翻出四件事，每一件都不是看圖看得出來的。

**方法先講**：每改一次都要重裝＋重登入才看得到，太慢也太吵。所以先寫
`tools/iconcmp.swift`——用 TIS API 把**系統手上那份**圖示挖出來
（`kTISPropertyIconImageURL`／`kTISPropertyIconRef`），倒成 PNG 並逐像素
量。規格是量 Apple 的 `zhuyin.tiff`（注）與 `Hiragana.tiff`（あ）得到的，
不是憑印象調。（**那個對照組挑錯了**，見第三節。）

#### `NSImage` 的 size 取自「點」不是「像素」

Apple 的圖是 16px＋32px 兩張，**但兩張都宣告 16 點**（@2x 的正規做法），
所以 `NSImage.size` 是 16×16。我第一版讓 32px 那張宣告 32 點，於是系統拿
一張「32 點的圖」去畫 16 點的位置——大小與邊框當場就不對。

#### 量墨水框與畫字是**兩套座標**

`colorAt(x:y:)` 的原點在左上，`draw(at:)` 的原點在左下。直接把量到的 y
拿去畫，字會沉到下半部。而且字級不能用算的：小尺寸下有 hinting，字級與
墨水框不是線性關係，一次換算會差一成——改成迭代逼近到目標值。

量出來的規格（畫布 32px）：方塊**填滿整個畫布**（Apple 沒有內縮）、字挖空
的墨水框佔 64～65%、`isTemplate=false`、純黑＋alpha。

#### 圓角是**連續曲率**，不是正圓弧

量 Apple 左上角的輪廓，它落在正圓弧半徑 4 與 5 的**中間**（頂列第一個實心
像素在 x=3，但下一列就到 x=1）——那是 squircle 的特徵，macOS 整套 UI 的
圓角都是這種。`NSBezierPath(roundedRect:)` 只畫得出正圓弧，要用
`CALayer.cornerCurve = .continuous` 再 render 進點陣圖。半徑 5.0 之後輪廓
跟 Apple 幾乎逐像素一致（頂列 alpha 74/180/228 對 77/190/243）。

#### 反白時要不要反色，是 **plist 的鍵**在管

使用者回報「內建的圖被反白選到後會顏色反轉，我們的不會」。**`isTemplate`
標在檔案上沒有用**——TIFF 存不下那個旗標，量 Apple 的檔案讀回來也是
`false`。真正的開關是 Info.plist 的頂層鍵 **`TISIconIsTemplate`**，抄自
`AinuIM.app`（Apple 唯一一個跟我們結構相同的 `.app` 型輸入法）。

#### 換了圖卻看不到：快取要用**改名＋跳版本**破

檔案與 plist 都換了、`TextInputMenuAgent` 與 `SystemUIServer` 也重啟了，
選單列還是舊圖。有效的組合是：

1. **圖示改名**（`menu.tiff` → `menuTemplate.tiff`）——新路徑，按路徑做的
   快取必然落空。順便合乎 AppKit「`Template` 結尾自動當樣板圖」的慣例
2. **`CFBundleVersion` 往上跳**——TIS／HIToolbox 對輸入源中繼資料的快取，
   版本是常見的鍵
3. 重新登記＋`killall TextInputMenuAgent SystemUIServer`

**改圖示之後記得跳版本**，不然會以為自己改的沒生效。

#### 剩下的一點差別：用 A／B 證明不是圖檔造成的

改完之後仍有「顏色略深、寬度略窄」。與其繼續調參數，做了一次 A／B：
**把 Apple 的 `zhuyin.tiff` 原封不動當成我們的圖示**裝進去。結果我們那一列
**還是畫得不一樣**。

所以那點殘差跟圖檔無關——是系統對「我們的輸入源」與「它自己的」走了不同
的繪製路徑（最可能是 Retina 下挑了不同的 representation 或不同的縮放）。
**再怎麼修圖都改不到**，就此打住。

> 這一節的教訓比結論有用：**先做一個能量測的工具，再動手改**。前面兩版
> 都是「看起來不對 → 憑感覺調 → 再看一次」，花掉好幾輪重登入；量出規格
> 之後三個差異一次就對上了。而最後那個 A／B 只花一次安裝，就把「還要不要
> 繼續調」這個問題永久結掉。

> **後續更正**：這一節說「移除 `tsInputModeAlternateMenuIconFileKey`
> 是真的有效」——**不是**，那一次也是快取，見第四節。

### 二、Apple 自家輸入法的圖示是系統畫的（原 2.52.41）

上一節的 A／B 證明「同一個 zhuyin.tiff 裝在我們這邊長得不一樣」，但沒解釋
**為什麼**。加上按 Fn 切換輸入源那個大 HUD 裡我們的格子是空的（選中時只剩
一顆紅圈），又追了一輪。

#### 決定性的證據：Ainu.tiff 畫的是倒心形，畫面上卻是「ア」

把 Apple 的 AinuIM 加進來當對照組。它的 `Ainu.tiff` 是黑色圓角方塊裡挖空一個
**倒心形**（阿伊努的符號），`CustomIcon` 那張 PDF 也是倒心形。但選單列、下拉
選單、Fn HUD 三個地方顯示的**全是「ア」**——那個字不存在於它附的任何一個
圖檔裡。

再對照注音：`Primary` 標籤是「注音」兩個字，畫面上是「注」一個字。

結論只有一個：**macOS 26 對 Apple 自家的輸入來源，不畫它們附的圖檔，也不畫
標籤，而是用一張內建的符號表**（注／あ／ア／A…）以系統自己的樣式畫。這一次
把前面所有對不上的東西都解釋掉了：

| 現象 | 原因 |
|---|---|
| 色差（Apple 的是深灰、我們的是純黑） | 它們是系統畫的文字，用的是標籤色；我們是圖檔 |
| 寬度差一點 | 它們的方塊依文字量寬；我們是 16 點正方形 |
| Fn HUD 裡 Apple 是裸字、我們是方塊 | 同上——它們根本不是 TIFF |
| 同一個 zhuyin.tiff 裝到我們這邊就不一樣 | 因為裝在 Apple 那邊時**從來沒被畫過** |
| HUD 裡我們選中後只剩紅圈 | 那是 `tsInputModeAlternateMenuIconFileKey` 指到同一張黑圖，黑圖畫在紅色高亮上（第一節已修） |

#### 試過、證明沒用的兩條路

- **`TISIconLabels → CustomIcon` 給一張裸字 PDF**（照 AinuIM 的規格：28×36 點、
  黑色路徑、字轉路徑不依賴字型）。裝上去之後 HUD 畫的還是 TIFF 的方塊。
  既然 Apple 自己的 Ainu 也不是靠它顯示「ア」，這個鍵在現代系統上大概只剩
  相容用途。工具與檔案已刪，不留下「它有作用」的錯覺
- **完全不給圖檔、只給 `Primary` 標籤**——想看系統會不會退回用自己的樣式畫
  「通」。結果是**通用的鍵盤佔位圖**。第三方沒有這條路

#### 「所以現在的樣子就是天花板」——這個結論下早了

第三方輸入法在 macOS 26 上能做到的，就是一張**規格對齊 Apple 圖檔**的樣板
TIFF（第一節量出來的那套：16 點、滿版、squircle 圓角 5/32、字挖空 65%、
`TISIconIsTemplate`、不設 alternate icon）。選單裡看起來一致，HUD 裡會是方塊
而不是裸字，色階略深一點——**這些不是我們的檔案能改的**。

（**錯在對照組挑錯人**，見下一節：規格本來就不該對齊 Apple 的舊圖。）

> 三個順帶量到的事實，之後改圖示會用到：畫這些 UI 的是三個行程
> （`TextInputMenuAgent` 選單列、`SystemUIServer`、`TextInputSwitcher` Fn HUD），
> 改完要 `killall -9` 三個一起；`TextInputSwitcher` 常常殺不掉，要確認 pid
> 真的變了；輸入源快取在 `/var/folders/…/C/com.apple.IntlDataCache.le.kbdx`，
> 重新登記就會更新，**不必登出**。

### 三、兩個第三方輸入法的圖示規格（原 2.52.42）

上一節結案時說「現在的樣子就是天花板」。**那個結論是錯的**，錯在對照組挑錯人。

使用者問「新酷音有支援 mac 嗎」，順著查下去翻到兩個第三方 IMK 輸入法的
原始碼，答案就在裡面。

#### 新酷音在 macOS 上的現況

引擎（libchewing）本來就跨平台，但**沒有原生的 macOS 輸入法程式**：以前靠
OpenVanilla 的 SpaceChewing 模組，早就停止維護；現在是寄生在
**fcitx5-macos** 裡（裝 fcitx5-macos 再裝 chewing 模組）。

#### 決定性的發現：fcitx5-macos 為 macOS 26 準備了另一張圖

`assets/` 裡有 `penguin-15.svg` 與 `penguin-26.svg`，**兩張的差別只有圓角**
（`a 3 3` 對 `a 7 7`），而 `update.sh` 依系統版本挑：

```sh
major_version=$(sw_vers -productVersion | cut -d. -f1)
if (( major_version >= 26 )); then
  cp "$RESOURCES_DIR/menu_icon_26.pdf" "$RESOURCES_DIR/menu_icon.pdf"
else
  cp "$RESOURCES_DIR/menu_icon_15.pdf" "$RESOURCES_DIR/menu_icon.pdf"
fi
```

**macOS 26 把選單列圖示的圓角改大了**——Apple 沒說，這是社群實測出來的。

#### 兩個專案獨立收斂到同一組數字

用同一支量測工具（`iconcmp` 那套）量下來：

| | 長寬比 | 圓角指標 |
|---|---|---|
| fcitx5-macos（macOS **26** 版，PDF 29×21） | **1.38** | **22%** |
| vChewing（原生 IMK，PNG 22×16＋@2x） | **1.38** | **22%** |
| fcitx5-macos（macOS 15 版） | 1.38 | 9% |
| **Apple `zhuyin.tiff`** | **1.00** | **9%** |
| 我們（第一節調完的） | 1.00 | 9% |

**我拿 Apple 的 `zhuyin.tiff` 當標準逐像素校對，而第二節已經證明那張圖
根本不會被畫**——它是 macOS 15 時代的舊資產，正方形、圓角小。校得再準也
只是準確地複製了一張過時的圖。使用者從第一輪就說「寬度不對」，那是對的：
**它本來就不該是正方形**。

新規格：**22×16 點（比例 1.38）、圓角佔高 30%（量出來是 22%，跟兩個參考
一致）、字挖空約高的 65%**。

#### 順帶對到的三件事

- **`TISIconIsTemplate = true`**：vChewing 也有（頂層），我們的做法是對的
- **不設 `tsInputModeAlternateMenuIconFileKey`**：vChewing 也沒有。fcitx5 有
  設但指向同一張圖，那正是第一節讓 Fn HUD 選中時整格消失的原因
- **fcitx5 用 PDF 向量**當圖示（`tsInputModeMenuIconFileKey` 吃 PDF）。我們
  用多解析度 TIFF，兩條路都通；想讓 Fn HUD 裡放大時銳利一點可以再換

#### 重裝的順序也錯了

vChewing 安裝程式的註解（`InstallerVMProtocol.swift`）：

> 只針對 TextInputMenuAgent：結束 imklaunchagent 會讓正在接收文字輸入的客體
> App 失去與所有輸入法的對接、須重啟該客體 App 才會恢復；**TextInputSwitcher
> 只是純 UI 套件、結束它沒有意義**。呼叫端應於本方法返回後**再延後半秒才執行
> 輸入源啟用（register）**。

我一直是 register 完才去 killall，順序反了——剛登記好的東西會被 agent 手上
那份舊清單蓋掉。`build-app.sh` 已改成**先殺 agent、等一下、再登記**，而且
不再殺 `TextInputSwitcher`（殺了也沒用）。

> 教訓跟第一節那條是一對：那次學到「先做能量測的工具再動手」，這次學到
> **量測工具再好，對照組挑錯就白費**。判斷對照組的標準是「它畫在螢幕上的
> 東西，是不是真的來自我要抄的那個檔案」——Apple 的不是，第三方的才是。

## 根因：Fn HUD 讀的是 MenuIcon，而前面在測快取（原 2.52.43）

上一節把選單列與下拉選單修對了之後，只剩「按 Fn 的 HUD 裡選中我們那格會整個消失」。
這一節把它結掉，同時修正前面兩節裡幾個**被快取污染的錯誤結論**。

### 真正的原因是快取，不是設定

過程中試過四種組態（移除 alternate icon、alternate 給白色裸字、palette 給
裸字、`TISIconIsTemplate` 保留），每一次都「沒改變」。**最後使用者重登入一次，
問題就沒了**——現在裝的組態（0.3.4）既沒有 alternate icon、palette 也跟 menu
指同一張，HUD 選中時照樣正確反色。

也就是說：**那幾輪的實驗全部無效**，它們測到的是同一份沒更新的快取。
`killall TextInputMenuAgent`／`SystemUIServer`／`TextInputSwitcher`、重新登記、
跳 `CFBundleVersion` 都不足以讓 HUD 重讀——**只有重新登入會**。

> 這推翻了第一節的一個推論：那裡說「移除 `tsInputModeAlternateMenuIconFileKey`
> 是真的有效」。**不是**，那一次也是快取。這個鍵設不設都可以，vChewing 沒設。

### HUD 讀的是 `MenuIcon`，不是 `PaletteIcon`

趁使用者願意重登入，把兩個鍵**故意指不同的圖**（menu＝方塊、palette＝裸字）
再登入一次：選單列與 HUD **都是方塊**。所以 `PaletteIcon` 不是 HUD 的來源，
第三方在 HUD 裡只能是自己那張圖。

實機對照也證實了同一件事：把 vChewing 裝起來並排比，**它在 HUD 裡也是方塊**
（「繁唯」），只有 Apple 自家是裸字。第二節的結論成立。

### 附帶學到的：第三方輸入法怎麼裝起來當對照組

想拿別人的輸入法當對照組時會卡在這裡，記一下：

- **`.app` 不能用手拖進 `~/Library/Input Methods/`**。檔案帶著
  `com.apple.quarantine`，macOS 會把它 **translocate** 到唯讀的隨機路徑跑
  （`/private/var/folders/…/AppTranslocation/…`），登記落不了地
- **`xattr -dr` 要對 `~/Downloads` 裡的原始檔下**，對 `~/Library/Input Methods/`
  裡的檔案下會被擋（終端機沒有完整磁碟取用權）
- vChewing 的官方作法是 pkg：
  `installer -pkg ~/Downloads/vChewing-*.pkg -target CurrentUserHomeDirectory`
  ——只裝使用者目錄，不需要 sudo
- **`TISEnableInputSource` 回 `noErr` 但永遠不落地**，這是設計如此：macOS 不讓
  程式自己加輸入法（那等於開側錄鍵盤的後門），一定要使用者在系統設定裡點。
  我們自己的輸入法當初也是這樣（`tisq` 的註解記著）
- 系統設定的清單裡顯示的是 **TIS 回報的 `LocalizedName`**（vChewing 是
  `vChewing-CHT`），不是 `InfoPlist.strings` 裡的 `CFBundleDisplayName`
  （那是「唯音」）。搜不到就是搜錯字

### 定案

圖示一張：`menuTemplate.tiff`（22×16 點、圓角佔高 30%、字挖空 65%、
`TISIconIsTemplate`），三個鍵都指它。選單列與下拉選單跟 Apple 一致；HUD 裡是
方塊而不是裸字——**那是第三方的天花板，vChewing 也一樣**。

> 這四節的方法論教訓，按踩到的順序：
> **① 先做能量測的工具再動手** →
> **② 量測工具再好，對照組挑錯就白費** →
> **③ 驗證環路沒清乾淨，做再多實驗都是在測同一份快取**。
> 第三條最貴：它讓前面好幾個「實測有效／無效」的結論全部作廢。
