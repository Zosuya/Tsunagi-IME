**執行順序**——不是編號順序，是風險與相依順序：

| 順位 | spike | 為什麼排這裡 |
|---|---|---|
| 0 | 讀威注音作者那篇指南 | IMK 官方文件出了名的爛，這篇是少數新的；Windows 這邊讀不到 |
| 1 | **spike 2 Echo 輸入法** | 風險最高，不通則整份規劃作廢，越早知道越好 |
| 2 | **spike 4 插入點座標** | 決定候選視窗畫得出來嗎、畫在哪 |

| 4 | **spike 5 快捷鍵攔截** | 風險最低，也最不影響架構決策 |

**2. IMK 的 Echo 輸入法**（Mac 版 Phase 0 重做）：全案風險最高的一段。
先做一個什麼功能都沒有的假輸入法裝進系統——**不要接 core**，接了出問題
會分不清是 IMK 的錯還是引擎的錯。

要驗證的就三件事：按鍵進得來（IMK 有把按鍵交給我們）、標記文字出得去
（`setMarkedText:` 畫得出帶底線的組字區）、送出文字進得了宿主
（`insertText:`）。極簡到「打 `a` 顯示 `a`，Enter 送出，Esc 取消」即可。

- **驗收**：TextEdit、瀏覽器、終端機**三種都通**才算過。不是 TextEdit
  通了就算——終端機與瀏覽器歷來最會出事，Windows 那邊 §2.38 的
  `TS_E_NOLAYOUT` 就是栽在瀏覽器
- **注意**：unwinding 穿過 `extern "C"` 會 abort，**每個 ObjC 方法覆寫都要
  包 `catch_unwind`**（[[執行模型的根本差異]]）

**4. 插入點座標在各 App 的可靠度**：`attributesForCharacterIndex:
lineHeightRectangle:` 在 Chrome、Electron、終端機各回什麼，等於 macOS 版的
`TS_E_NOLAYOUT` 調查。**排在 spike 3 前面是刻意的**——若多數 App 拿不到
座標，候選視窗的設計會完全不一樣（跟游標走？固定螢幕角落？），先畫會白畫。

- **驗收**：列出每個宿主回傳的矩形，標明哪些是 0 矩形／不可靠，並確認退路
  （對應 Windows 的 `GetScreenExt`）在那些宿主上可用

**3. 候選視窗用哪套畫**：手刻 Cocoa（非啟用式 `NSPanel` ＋ CoreText），或
沿用設定頁的 egui 預覽。

- **未知數**：egui 要做成「不搶焦點的浮動面板」不確定做不做得到——這是這個
  spike 真正要回答的問題，先驗證這一點再決定投哪邊
- **驗收**：面板浮在宿主上方、點它不奪走宿主焦點（對應 Windows 那邊
  `WS_EX_NOACTIVATE` 擋不住滑鼠、要回 `MA_NOACTIVATEANDEAT` 的坑）

**5. 快捷鍵攔截**：§2.14 那套在 Mac 重量一次，要有 Mac 版的 `keyprobe`。
**範圍縮小了**——待決 3 裁決 macOS 不做語言鎖定，所以「單按 `Ctrl` 會不會
跟宿主打架」不用量了。

- **驗收**：量出哪些組合鍵到不了輸入法（被系統或宿主先吃掉），跟 Windows
  的結果並排比較
