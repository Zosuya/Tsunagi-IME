# 系統不再自動拉起輸入法：是工作階段內的累積效應

**症狀**：開發到後期，輸入源登記正常、選單看得到、選得到，但切過去
**打不出字**——輸入法行程根本沒被啟動。自己 `open` 一下就一切正常，
所以整天的驗收都做得下去，這個洞被掩蓋到最後才浮現。

### 結論：原本的假設是對的，我中途否證錯了

[[輸入源註冊不進系統：三個假設都錯，根因是 bundle id]] 引威注音的 `AGENTS.md` 寫著「macOS 限制單次登入工作階段內能砍掉
輸入法行程的次數，安裝多次後會失效，要登出再登入」。**這是對的。**

登出再登入之後，在**乾淨的工作階段**裡量到：

| 情境 | 結果 |
|---|---|
| 登入當下（21:27:55） | `CoreServicesUIAgent: _LSLaunchRB` → `Successfully spawned tsunagi_ime[32556]` ✅ |
| 登入後砍掉一次，切過去（21:30:07） | 同一條路徑 → `Successfully spawned tsunagi_ime[32967]` ✅ |
| 同一個工作階段跑了十幾輪重裝／`pkill` 之後 | `_launch:` 送出、`messageStatus == 0`，**接收端一行都沒有** ✗ |

所以不是「系統一律不肯」，是**同一個工作階段內對同一個 bundle 累積失敗
到某個程度就不再嘗試**。旁證：在已經壞掉的那個工作階段裡，Apple 的
`AinuIM`（同樣是舊式獨立 app）**照樣被拉得起來**——所以退化是**針對特定
bundle**，不是全域的。

### 我推翻自己的那一段，留著當教訓

中途我用「log 顯示系統每次都有嘗試 `_launch:`」否證了原本的假設，
轉而追查別的方向，最後停在一個 Gatekeeper 的推論上：

```
spctl -a -t exec  ~/Library/Input Methods/Tsunagi.app     → rejected（ad-hoc）
spctl -a -t exec  /System/Library/Input Methods/AinuIM.app → accepted
```

**那個推論是錯的。** 登入時**同一個 `CoreServicesUIAgent`** 就把我們這個
ad-hoc 簽章的 app 啟動起來了，用的參數（`0x8000300/dontSwitch`）跟它啟動
Ainu 一模一樣。簽章差異真實存在，但**不是這一關的原因**。

> **錯在哪**：我看到「`_launch:` 有被呼叫」就認定「系統有嘗試」，因此排除
> 了「不再嘗試」的假設。但**送出訊息的是宿主端的 IMKClient，決定要不要
> 動作的是接收端**——兩者是不同的行程。「有人喊了」不等於「有人回應」。

### 實務後果：只是開發時的注意事項

- **登入時系統會拉起它**，所以正式使用不受影響
- **中途被砍也會自己回來**（乾淨工作階段實測）
- 只有**同一個工作階段內反覆重裝**才會退化，**登出再登入就重置**
- `build-app.sh` 每次自己 `open`，開發流程已經繞過去了

連帶：**待決 4（發布範圍）不必因此升級**。ad-hoc 對自己用是夠的——
裝得進去、啟用得了、打得出字、登入會自動拉起。

### 順手查到與修掉的

- **失敗會污染宿主行程**：系統二進位裡有
  `IMKInputSession … not attempting xpc connection due to too many failed
  connection attempts`。實測第一次失敗後，**同一個宿主行程就再也不呼叫
  `_launch:`**。所以**每輪測試都要把宿主整個關掉重開**，否則量到的是
  「客戶端放棄了」而不是「系統不肯啟動」——我為此白測了一輪。
- **同一個 bundle id 有兩份 app**：`build-app.sh` 在 `target/Tsunagi.app`
  組出 bundle 再複製到 `~/Library/Input Methods/`，而 LaunchServices
  **兩份都收**。已改成安裝後 `lsregister -u` 並刪掉建置產出。
  **這是真的 bug，只是不是這一關的根因。**
- **啟動請求走 CFMessagePort `com.apple.inputmethodkit.launcher`**，
  接收端是 `CoreServicesUIAgent`，成功時 17 毫秒內就會出現
  `_LSLaunchRB` → `_LSLaunchThruRunningboard` → `Successfully spawned`。
  **那三行是判斷「系統到底有沒有動作」的判準**，比「打不打得出字」客觀。
- `IMKClientErrorLogging`（`defaults write -g IMKClientErrorLogging -bool true`）
  會讓宿主印出 IMK 客戶端的完整動作，**是這一節所有證據的來源**。
  它在**行程啟動時**才讀，所以要先開開關再重開宿主。看完記得關。
