# 選字模式：鍵位、候選網格、組字區的逐格反白

接 [[接上引擎：詞庫定位、Session 取代自己記的緩衝]]。打字通了之後剩下的是選字——CLAUDE.md 講的三個狀態機
（mod／cutting／select）裡的最後一個。段選單（`Tab`）還沒接，那是另一個。

### 鍵位照 Windows 的 `DEFAULT_BINDINGS` 逐條抄

**兩個平台的手勢要一樣，使用者不該為了換平台重學。**

| 鍵 | 打字中 | 選字（未展開） | 選字（展開） |
|---|---|---|---|
| ← | **從最後一格**進選字 | 換格 | 換欄 |
| → | 從第一格進選字 | 換格 | 換欄 |
| ↑↓ | 進選字 | 換候選字 | 同欄上下 |
| 空白 | 注音的**一聲** | 展開全部 | 收合 |
| 1-9 | 注音鍵 | 直接挑**這一頁**的第 n 個 | 同左 |
| Enter | 送出 | 選定，跳下一格 | 同左 |
| Esc | 取消組字 | 離開選字 | 先收合，再按才離開 |

三個抄過來的判斷，理由都在 Windows 的註解裡：

- **左鍵從最後一格進**——使用者按左鍵的直覺是「從右邊選過來」
- **空白鍵在打字中是一聲**，沒組字時才是空白。同一顆鍵三種狀態三種意思
- **數字在選字時是選字不是輸入**——打字時十個數字全是注音鍵，選字時已經
  在挑字了就空出來了

### 候選面板：直排／多欄網格

原本做成橫排是**我一開始就選錯**。Windows 是「未展開一直排、展開多欄網格」
（`candidate_window.rs` 的 `COLUMNS`），橫排在展開時會攤成一條跨越螢幕的長帶。

改成一欄九個往下數、滿了換欄。兩個細節也照抄：

- **編號只畫在反白所在的那一欄**。數字鍵挑的是「目前選中那一欄」的第幾個，
  每欄都畫 1-9 看起來像每欄都能按，實際只有一欄有用——**那是會讓人按錯的
  假資訊**
- **編號的位置每一欄都預留**，即使那一欄不畫編號。不預留的話反白換欄時
  所有的字會左右跳
- **欄寬只由內容決定，面板貼合內容——刻意不用 `min_width`。** 那是 Windows
  候選視窗的版面常數，套過來會有連鎖後果：內容比它窄時得把欄撐開才點得到、
  才有完整的反白條，而撐開的量又隨欄數變，於是**同一欄在展開前後寬度不一樣**
  （實測回報）。macOS 的浮動面板本來就該貼合內容，拿掉之後兩個狀態一致，
  格子也剛好鋪滿內容區

### ★ 組字區的反白不能用畫的 ★

選字時要看得出正在選哪一格。Windows 在獨立的預覽列上畫一個框；**macOS
沒有那條預覽列**（[[接上引擎：詞庫定位、Session 取代自己記的緩衝]] 的決定），所以反白只能做在組字區本身——而
**組字區是宿主畫的，那塊畫布不是我們的**，畫矩形在這裡沒有用。

正解是把組字區**逐格組成 attributed string**，正在選的那一格加上：

- `NSUnderlineStyle::Thick`（其餘格是 `Single`）
- `NSBackgroundColorAttributeName` = `selectedTextBackgroundColor`

用系統的選取色而不是自己的主題色，是因為它**跟著使用者的強調色走**，
而且那正是系統其他地方「選取的文字」長的樣子。

順帶把 `NSMarkedClauseSegment` **逐格編號**（原本整串固定給 0）——那是
「文節」的正規用法，宿主靠它知道組字區分成幾段。[[spike 3：候選視窗用 NSPanel]] 為了不弄當宿主
才加上這個 attribute，當時只給一段；現在它有了真正的用途。

### 兩個 bug，和一段效率很差的除錯

**bug 1：點候選字完全沒反應。** 根因是 `Composition::client` **從來沒有被
寫入過**——那行「記住宿主」在某個中途 assert 失敗的腳本裡，**在寫檔前就
死了**，於是整批修改都沒落地。`tsunagiSelectCandidate:` 從寫出來的那一刻起
就在讀一個永遠是 `None` 的欄位，一進來就提早 return。

**bug 2：點不到候選字。** 內容比主題的 `min_width` 窄時面板會被拉寬，
**而欄沒有跟著撐開**——格子只有 22pt、面板卻有 96pt，點在中間那一大塊
就落在所有格子外面。同一個 bug 也讓反白條只有一小塊，看起來像沒選中。

> **除錯方法的教訓**：這兩個 bug 我前後猜了五輪（座標換算、訊息沒送到、
> 通知對象是空的、索引換算、方法沒註冊），**每輪只加一點記錄，所以每輪
> 只能排除一個假設**。最後把整條路徑一次記全——含物件位址——才一眼看到
> `client=★None` 跟「`on_key` 零筆記錄」的矛盾。
>
> **應該一開始就那樣做。** 分段加記錄看起來省事，實際上是把一次診斷拆成
> 五次來回。另外：**腳本失敗之後要驗證檔案的實際狀態**——bug 1 能潛伏
> 那麼久，就是因為我看到報錯訊息卻沒回頭確認哪些改動真的落地。
