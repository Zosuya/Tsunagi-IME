## Phase 1 — 合法性判斷（三個單語引擎）


> **2026-08-28 重做**。原本的計畫是「引擎回傳候選 + 信心分數，辨識層合併
> 排序」，實作出來的成績是切點正確率 40.8%。改用「先判合法、再談候選」
> 的設計後，同一份測資（426 句）拿到 95.3%。詳見
> [[新架構：合法性優先]]。

**設計依據是 canvas 規格檔**，不是這份文件的散文描述：

| 規格 | 檔案 |
|---|---|
| 注音合法規則 | `字元規則/通用注音合法規則.canvas` |
| 注音例外規則 | `字元規則/通用注音例外規則.canvas` |
| 注音鍵位對照 | `注音按鍵合法表及對照表.md` |
| 日文合法規則 | `字元規則/通用日文合法規則.canvas` |
| 日文例外規則 | `字元規則/通用日文例外規則.canvas` |
| 日文按鍵合法表 | `字元規則/日文按鍵合法表.md` |
| 日文輸入單位一覽 | `字元規則/日文輸入單位一覽.md`（175 條 mora + 表外 3 種） |

那些 canvas 是**可執行的規格**——每個判斷節點恰好兩條出邊（綠=是、紅=否），
可以當成程式直接跑。驗證方式就是把 canvas 當直譯器執行，比對測資。

**統一介面**（跟舊版的差別：不回傳候選）

```rust
pub enum Validity { Valid, Invalid }   // 沒有 Partial，見下

pub trait LangEngine {
    /// 這串按鍵在本語言下合不合法。
    fn validity(&self, keys: &str) -> Validity;
}
```

**為什麼沒有 `Partial`**：使用者定的規格是「沒打完 = 非法」。打到一半時
往下一條語言問即可，顯示什麼交給之後的「偏好語言」功能決定。少了中間態，
判斷樹只有兩個出口，規則大幅簡化。

**1a. 注音引擎** — **完成**（`core/src/bopomofo/`，2026-08-28）
- [x] 鍵位對照表（`keymap.rs`，依使用者核對過的對照表）
- [x] 音節結構驗證（`syllable.rs`）：聲母(0~1) → 介音(0~1) → 韻母(0~1) → 聲調(1)
- [x] 例外規則：`ㄓㄔㄕㄖㄗㄘㄙ` 這 7 個可單獨成音節
- [x] **注音一律以聲調鍵收尾**——一聲在書寫時不標符號，但在輸入時仍要按空白鍵
- [x] 切音節（`split_syllables`）：**貪婪由長到短**。`su3` 若由短到長會先切出
      `s`，但 `s`（ㄋ）單獨不合法，最長優先才切得對

**1b. 日文羅馬字引擎** — **完成**（`core/src/romaji/`，2026-08-28）

      完全相同的路徑，不必複製整棵子樹
- [x] 例外表（`#特sh/ch`、`#特th/dh`、`#特who`、`#特tsu`、`#特w`）
- [x] 例外規則的兩條過濾：`c` 開頭接母音、`wu`/`yi`/`yyyi`
- [x] **撥音一律打 `nn`**——多語言輸入法的取捨，撥音邊界才不依賴後文
- [x] 外來語補上 `f`（規格表原本只列 `v`）：ふぁ ふぃ ふ ふぇ ふぉ ふゅ

## Phase 2 — 切點引擎（語言辨識）


依 `語言辨識演算法(新).canvas` 與 `通用語言輸入法 篩選規則.canvas`。

**第一層：合法性瀑布**

```
注音範圍? ─是→ 注音合法 ─合法→ 注音例外 ─合法→ Valid(注音)
   │否           │非法          │非法
   └─────────────┴──────────────┴→ Invalid → 日文範圍? → ... → Invalid → Passthrough(英文)
```

實測驗證過的性質：**注音與日文零重疊**——注音必須以聲調鍵收尾（`3467` 或
空白），日文只用字母和 `-`，兩者的按鍵集合天然不相交。所以「注音優先」
這個順序不會搶走任何日文。

**第二層：切點引擎**——**已完成（2026-08-29）**

實作與這裡原本的計畫**不一樣**，因為累加式架構讓好幾條規則變得不必要。
完整說明見 [[Phase 2 完成：累加式切法與排序]]，這裡只記結果。

- [x] **累加式切法**（`cutpoint/incremental.rs`）：切法一旦成立就留著，
      新字元接在後面延續。**不是**對最終按鍵串窮舉——沒辦法知道使用者
      什麼時候要把字打完。
- [x] **候選丟棄規則**（`cutpoint/prune.rs`）：單字母段要在邊界上、
      英文段須是詞。候選數中位從 4480 砍到 13，正解零損失。
- [x] **輸出等價正規化**（`cutpoint::normalize`）：相鄰同語言的段合併。
      同一個語言內部切不切不影響輸出，比對前要先正規化。
- [x] **排序**（`cutpoint/rank.rs`）：九個判準依序比較，見 [[Phase 2 完成：累加式切法與排序]]。

**這三條規則實作後證明不需要**：

| 原計畫的規則 | 為什麼不需要 |
|---|---|
| 空白鍵的兩階段判斷 | `rup` 非法、`rup␣` 合法，引擎自己認得。累加式沒有「先切區塊」這一步，雞蛋問題不存在 |
| 標點前後為切點 | `g;4` 注音認得，`hello,` 的逗號注音不認、自動落到英文 |
| 三條特殊規則（單字母併入／英日英夾心／查詞典補候選） | 前者由 `prune` 取代，後兩者在累加式下沒有貢獻 |

**後來加的規則**（都是實測發現的問題，不在原計畫裡）：

- 相鄰同語言不切（最後一組例外——那可能是還在打的半成品）
- 英文段不該偷走注音音節的開頭（`filed|9␣` vs `file|d9␣`）
- 英文詞不該被切成兩半（`日:fi | 英:led` 合起來是 `filed`）
- 兩字母英文詞要夠常用才算命中（`cl`、`vu` 是雜訊，`go`、`ok` 不是）
- 常用英文詞不讓給日文（日文詞典 74 萬條，`you`→よう、`the`→てぇ）

**退出條件**：達成。使用者定的兩個標準——

| 標準 | 要求 | 現況（570 句） |
|---|---|---|
| 切點涵蓋 | 100%——正解一定要在候選裡 | **570/570 ✓** |
| 前 3 名 | 正解要排進前三 | **561/570（98.4%）** |

```powershell
cargo run --release -p ime-core --bin check_incremental   # 主計分器
cargo run --release -p ime-core --bin cutpool             # 切點閘門
```

      - 衝突偵測要做得可靠，工程量比功能本身大——要知道每個模式下

      本來就是為了「改鍵位只動一個地方」而集中的。（原本在 Windows 平台層的
      `keymap.rs`，2026-09-13 上搬 core、兩平台共用；`keymap.rs` 只剩 `VK_*` → `Key` 的翻譯）

      > 上面列舉的鍵位是 2026-08-31 當時的：語言鎖定後來從單按 `Ctrl` 換成
      > `Shift+空白`，全半形搬到 `主修飾鍵+Shift+空白`（2026-09-09）。

## Phase 4 — 智慧化與個人化（估 4 週+，可迭代）


> **Phase 2 的排序是「預訓練」的基準**（2026-08-29 決定）。
> 它只靠三本靜態詞典，而詞典必然收不全——實測「詞庫沒有的英文詞
> ＋ 注音」時，正解中位排第 6、最差第 35。試過四種排序改法都失敗
> （見 [[Phase 2 完成：累加式切法與排序]] 的已知限制），根本原因是 `covered` 這個主判準對詞庫
> 沒有的詞恆為 0，而任何想繞過它的結構訊號要嘛沒鑑別力、要嘛強到
> 破壞其他句子。
>
> **這是資料問題不是演算法問題**，正解是這個階段的個人化：使用者
> 打過的詞自動加權，越用越準。

- [x] **選字學習**（第一刀，2026-09-01）：使用者方向鍵改過的字加權。
      **存純文字不是 SQLite**——學習檔要能被肉眼審查、手動刪一行、
      跨電腦用任何工具合併，跟領域包同一套哲學。見 [[選字學習：純文字儲存、k^n 指數權重、記 2～4 字子段]]
- [x] **切詞學習**（第二刀，2026-09-02）：使用者按 Tab 換過的切法。
      段落層級＋整串層級兩種粒度，720 句 650 → 664。見 [[切詞學習（第二刀）：段落層級＋整串層級]]
      —— 這一項就是原本寫的「誤判修正回饋」，只是訊號來源改成
      切法選單（我們有格子模型，不必另外設快捷鍵）
- [x] **學習曲線的底數 `k`**：**維持 8**（使用者裁決，2026-09-02）。
      原本規劃要 spike 掃，實際用起來體感是對的，不再花一輪。見 [[選字學習：純文字儲存、k^n 指數權重、記 2～4 字子段]]
