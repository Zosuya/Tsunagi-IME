# 按鍵延遲：p99 從 47.9ms 到 11.9ms

Phase 5 訂的效能目標是「按鍵到候選更新 < 16ms（p99）」，實測 47.9ms，
差了三倍。這一節記的是怎麼找到原因的——**過程比結論有用，因為我
前兩次都改錯地方**。

### 2.11.1 先看形狀，不要急著改

```
p50   7.6ms      ← 大部分按鍵很快
p99  47.9ms      ← 少數特別慢
```

這個形狀本身就是線索：**不是整體偏慢，是有特定情境把工作量放大**。
那種問題通常一找到就很好修。

分案例看，超標的三個全是日文長句，而且延遲隨長度成長：

| 案例 | 最慢一鍵 |
|---|---|
| 長句（純日文 47 鍵） | 25.8 ms |
| 極長（日文 71 鍵） | 37.7 ms |
| 超長（日文 110 鍵） | 52.1 ms |

但「極長（三語 70 鍵）」只要 5.7ms——**不是單純的長度問題**，是日文
的切法特別多（羅馬字沒有聲調鍵當天然斷點）。

再拆階段：切法 1.7 秒、排序 1.4 秒、去重 25 毫秒。去重不是問題，
另外兩個各佔一半。

### 2.11.2 兩次改錯地方

看程式碼時很容易找到「明顯的浪費」，而它們**都不是瓶頸**：

1. `score()` 只要 `normalize()` 的長度，卻讓它複製了整份段落
   （含字串）。改成不配置的 `normalize_len` ——**效能沒有可見變化**。
2. 切點引擎每段都 `collect::<String>()` 取出文字。改成能借就借
   （純 ASCII 時位元組位移等於字元位移）——**同樣沒有可見變化**。

兩個改動本身都是對的，留著；但它們證明了一件事：**成本不在配置，
在詞典查詢**。憑「看起來很浪費」去改，會把時間花在錯的地方。

### 2.11.3 真正的原因：同一件事查了九次

埋計數器量候選之間的重複程度：

```
59 鍵的日文長句：候選 400、段落總數 1472、相異段落 159
```

**重複九倍**。而每次段落驗證要把羅馬字轉成假名（配置字串）再查詞典，
實測一次 8 微秒。1472 × 8µs ≈ 12ms，剛好對得上排序那一段的耗時。

### 2.11.4 兩個快取

**切點引擎**用 `(起點, 終點)` 當快取鍵，不是段落文字。這樣有兩個好處：
省掉取字串的配置，而且——**按鍵串只會往後追加，驗過的範圍內容永遠
不會變**，所以快取跨按鍵也一直有效，不必每鍵清空。

這一項讓產生切法從 1.6 秒掉到 65 毫秒（25 倍）。

**排序**那幾個段落判斷（在不在詞典、是不是乾淨的詞、是不是常見英文詞）
全是 `(按鍵, 語言)` 的純函式，快取到 thread-local 跨按鍵共用。設了
20000 筆的上限，滿了整份丟掉——**丟掉的代價很低**（重算幾百筆），
而 LRU 那套的簿記成本可能比省下來的還多。

### 2.11.5 快取踩到的坑：詞庫是背景載入的

新寫的守門測試**單獨跑會過、跟其他測試一起跑會失敗**。

原因：`prune::keep` 用得到英文詞庫，而詞庫是背景載入的（見
[[詞庫載入：切換輸入法那一秒是怎麼來的]]）。
在詞庫載好之前算出來的答案被快取起來，載好之後就不對了。測試平行
執行時，別的測試會在中途把詞庫載進來，這個時序才現形。

修法是加一個**詞庫版本號**：每載完一本就加一，快取拿它當有效期，
版本一變整份丟掉。

> **這個 bug 只在特定時序下現形**。要是當初只單獨跑那個測試就放行，
> 它會活到使用者手上，症狀會是「剛切過去打的前幾個字切得怪怪的，
> 重打一次又正常」——那種問題極難重現，更難查。

（正式環境其實碰不到：第一次按鍵那條路會擋著等詞庫載完。但快取的
正確性不該建立在「呼叫順序剛好對」上面。）

### 2.11.6 結果

| | 之前 | 現在 | 目標 |
|---|---|---|---|
| p50 | 7.6 ms | **2.4 ms** | — |
| **p99** | **47.9 ms** | **11.9 ms** | < 16 ms ✓ |
| 最慢一鍵 | 55 ms | 13.8 ms | — |

十個案例全部在一幀預算內（原本三個超標）。切點正確率完全不變：
570 句涵蓋 570/570、前三名 561/570。

守門員是 `逐鍵與整串重建結果相同`：那份快取假設「按鍵串只會往後長」，
哪天有人加了會縮短或改寫按鍵串的方法，逐鍵那條路會拿到過期答案，
測試就會紅。

**使用者感覺不到這次改動**——p50 本來就遠低於察覺門檻。會有感的只有
「連續打一百多鍵的日文羅馬字、中間不打空格」，那時原本是 18fps 的
黏滯感。這是補驗收目標，不是修抱怨。
