# 二進位詞庫與 mmap：常駐 232MB → 23MB

[[詞庫載入：切換輸入法那一秒是怎麼來的]] 當初擋住這件事的三個
理由——選詞模組還在動、格式可能要改一次、時程不急——在 Phase 4 結案
之後全部解除。

### 2.29.1 病灶：包在文字外面的結構是文字的五倍

| | 讀音／鍵 | 候選／值 | 文字本身 | 常駐 |
|---|---|---|---|---|
| 日文 | 74.6 萬 | 112.9 萬 | 27.5 MB | 約 200 MB |
| 注音 | 13.2 萬 | 13.2 萬 | 2.3 MB | 23 MB |

**每一個字串都是一次獨立的堆配置**，各帶 24 位元組標頭：日文光是候選
陣列本體就 43.1 MB（112.9 萬 × 40 bytes）、雜湊表條目 34.1 MB，字串的
堆配置**共 187.5 萬次**。

注音還多一筆：建表峰值比常駐高 21 MB，那是 `word_freq`（19 萬詞）、
`char_freq`、`reading_share`——**只有決定順序時要用**，讀 `.bin` 之後
執行期根本不會碰。

### 2.29.2 兩個跟 §2.10.5 雛形不同的決定

**一、成本值必須存。** 雛形只存表記，把 mozc 的 `lid`／`rid`／`cost`
丟掉了。但**日文整句轉換（§2.23）
是那個 spike 之後才做出來的**，它靠 `連接矩陣[rid][lid]` 決定分詞。
[[詞庫載入：切換輸入法那一秒是怎麼來的]] 寫著「等 Phase 4 做完，『要不要存成本值』這題會自己有答案」
——答案是必須存。

**二、雜湊索引，不是二分搜尋。** 雛形量到單次 690ns，換算每鍵 +0.87ms
（平均每次按鍵查詞庫 1267 次）。而動手前最慢一鍵已經 12.4ms、預算
16ms——**餘裕只剩 3.6ms，不夠賭**。雜湊表多 4MB 換回 O(1)。

`total`（詞成本＋句首＋句尾接續）**不存**：只有排序與「有把握」的門檻
用得到，兩件都在產生版面時做完，省 4.5MB。`KANA_BEST` 那張小表變成版面
裡的一個位圖。

### 2.29.3 量到的（本機 i7-14700KF、完整詞庫）

| | 改前 | 改後 |
|---|---|---|
| **常駐記憶體** | **232 MB** | **69 MB** |
| 英文載入 | 10 ms | 10 ms |
| 注音載入 | 156 ms | **1 ms** |
| 日文載入 | 703 ms | **16 ms** |
| 按鍵 p50 | 2.4 ms | 2.2 ms |
| 按鍵 p99 | 11.0 ms | 11.2 ms |
| 按鍵最大 | 12.4 ms | 11.6 ms |

**延遲沒有變差是意外**——文件預測二進位會讓每鍵多 0.8ms。雜湊索引擋掉
了二分搜尋的成本，而**連續版面的快取局部性是淨賺**：迭代一個讀音的候選
只碰一兩條快取線，不必追指標到 N 個散落的堆配置。

`bench_typing` 原本會印的「⚠ 超過 0.5 秒——TSF 裡要預載」那行消失了。

**三支計分器一個數字沒動**（720 列 0 錯、570/570・560/570・551/570、
677/720 切法錯 20 選字錯 23），`cargo test` 兩邊全綠。

### 2.29.4 踩到的一個坑：Rust 一樣會漏記憶體

`cands_for_kana` 對學習／領域包的詞直接 `Box::leak`——那是 safe 函式，
編譯器不會有意見，因為**漏正是我叫它做的事**。但那個函式在 Viterbi 的
O(n²) 迴圈裡每按一鍵被呼叫上千次，只要使用者學過任何日文詞就每鍵漏一
份，**無上限**。

改成駐留（同一個字串只漏一次，上限是「學過幾個不同的日文詞」）。

留下的教訓：**Rust 保證的是記憶體安全，不是不漏。**漏掉的那塊還是合法
記憶體、沒有指標懸空，所以不違反安全承諾。`cargo clippy --all-targets`
跑過是乾淨的（沒有「熱路徑上不要 leak」這種 lint），單元測試也不會失敗
——功能完全正確，只是記憶體一直增加。釘住它的測試只能釘**行為**：
「同一個字串重複要，必須拿到同一塊記憶體」。

順帶一提借用檢查器在這裡幫了忙：直接把領域包索引裡的字串借出去會被拒編
（`index()` 回傳暫時值）。換成 C++ 那就是懸空指標——**Rust 把「用到已
釋放的記憶體」換成「漏記憶體」**，最危險的錯誤變成最無聊的錯誤。

### 2.29.5 mmap：單行程 69MB → 23MB，多行程每個只多 6MB

二進位版面把常駐降到 69MB 之後，剩下的全是「檔案整份讀進 `Vec`」
（`dict_ja.bin` 40MB、`connection.bin` 13.6MB、英文 8MB、
`dict_zh.bin` 3.7MB）。

**這在輸入法上特別貴**：DLL 載在**每一個宿主行程**裡——檔案總管永遠
挖著它（見 CLAUDE.md 的已知陷阱），再加瀏覽器、編輯器、Word。五個行程
就是五份。

`memmap2` 是 `core/` 的第一個非 std 依賴，照既有慣例掛成 `optional` ＋
feature、預設開啟；關掉退回 `fs::read`，行為完全一樣、只是不共用。

#### 本機實測（i7-14700KF、完整詞庫）

單行程：

| | mmap 關 | mmap 開 |
|---|---|---|
| **常駐** | 69 MB ✗ | **23 MB ✓ 達標** |
| p99 | 10.5 ms | 10.5 ms |

三個行程同時活著：

| | mmap 關 | mmap 開 |
|---|---|---|
| 每個行程 WorkingSet | 68.3 / 67.8 / 67.8 MB | 10.5 / 11.1 / 10.5 MB |
| **每個行程私有工作集** | **64.1 / 63.5 / 63.5 MB** | **6.1 / 6.7 / 6.1 MB** |
| **私有總和** | **191.1 MB** | **19.0 MB** |

**私有工作集才是每個行程真正的成本**——`WorkingSet64` 把共用頁重複算進
每個行程，拿它加總會低估 mmap 的價值。

**每多一個宿主行程只多 6MB**（不開 mmap 是 64MB）。真實情境是檔案總管
＋瀏覽器＋編輯器＋Word 四個，開 mmap 約 25MB、關約 255MB，差距隨行程數
線性拉開。**延遲一分錢都沒付**（p99 兩邊都 10.5ms）。

#### 真實宿主實測：Notepad +6.6MB（2026-09-02）

上面那些是 `bench_dict --hold` 量的**獨立行程**。真實宿主第一次量是
做相容性測試清單時（`tools/mem.ps1`），量法必須換成**差值**——
explorer 本身三百多 MB、Brave 一百多，輸入法那幾 MB 埋在裡面看不出來。

切輸入法前記基準，每個宿主都打過字之後量私有工作集的增量：

| 宿主 | 私有增量 | WS 增量 |
|---|---|---|
| Notepad | **+6.6 MB** | +11.7 |
| WINWORD | +15.7 MB | +42.6 |
| Brave | −2.9 MB | +11.1 |
| explorer | −2.7 MB | −2.7 |

**Notepad 那列跟獨立行程的 6.1MB 吻合**，它最安靜所以最可信。

**Brave 那列是共用頁最漂亮的證據**：私有**減少**而 WorkingSet **增加
11.1MB**——詞庫的頁確實映射進工作集了，卻沒有算進私有，因為它跟別的
行程共用同一份。這個組合只有 mmap 生效時才會出現。

判讀規則因此是**兩欄一起看**，不是只看私有：

| 私有增量 | WS 增量 | 意思 |
|---|---|---|
| 小或負 | 明顯為正 | mmap 生效 |
| 跟 WS 差不多大 | 正 | 沒共用，這個行程自己扛了一份 |
| 負 | 負 | 純噪音，跟輸入法無關 |

**量錯過一次**：第一版腳本直接印宿主行程的私有工作集總量，拿去跟
「6MB」比——那個比法不成立，量到 explorer 300MB 得不出任何結論。
**獨立行程的數字不能拿去當真實宿主的判準。**

#### 配套：產生器改成原子寫入

`map_file` 的 SAFETY 依據就是這一條。mmap 的風險是「映射期間檔案被外部
改掉」——已經借出去的位元組在腳下變動是 UB。三支產生器
（`gen_dict_ja`／`gen_dict_zh`／`gen_connection`）一律**先寫暫存檔再原子
改名**：改名換新 inode，舊映射原封不動活到那些行程結束。**重新產生詞庫
不會動到正在打字的行程看到的位元組。**

寫了對策就要真的做，不然 SAFETY 註解是空話。

#### 量測踩到的坑：一個指標會騙人

第一次量 mmap 關的時候，`Get-Process` 回報 WorkingSet 只有 **2.6MB**，
同一時間私有工作集卻是 64MB——**工作集不可能小於它的私有部分**，這組
數字自相矛盾。原因是抓到行程還沒穩定的快照。

重量之後三個指標才自洽（WS 68 ／ 私有 64 ／ Private Bytes 64），也跟
`bench_typing` 的 69MB 對得上。

**教訓：多行程量測要同時抓 WorkingSet、私有工作集、Private Bytes 三個值
互相驗證**，只看一個會被瞬間值騙。`bench_dict --hold` 就是為了讓行程停
住、量到穩定值才加的。

#### 為什麼 libchewing 沒做，我們卻要做

查過它的 Rust 重寫版：系統詞庫是唯讀 Trie（8 位元組節點、u16 音節、
DER 容器），載入是 `read_to_end` 進 `Vec<u8>`，**依賴只有 `der`、`log`、
選用的 `rusqlite`，沒有任何 mmap crate**。

但規模不能直接比——**它沒有日文那一套**：我們 69MB 裡有 54MB 是
`dict_ja.bin` 加接續矩陣，那是 libchewing 完全沒有的東西。它的每行程
佔用大概十來 MB，mmap 省不到什麼。**「它沒做所以我們不用做」在規模上
不成立。**

（C 版 0.3.2（2008）的釋出說明講的正是 mmap，Rust 重寫時沒有繼承
——查不到理由，不做推測。）
