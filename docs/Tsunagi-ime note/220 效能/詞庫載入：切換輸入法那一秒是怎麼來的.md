# 詞庫載入：切換輸入法那一秒是怎麼來的

使用者長期抱怨「切到這個輸入法要等大約一秒才能打字」。查出來的原因
跟直覺完全相反，過程本身比結論更值得留著。

### 2.10.1 先量，不要猜

在 `Activate` 的八個步驟都埋計時，結果非常乾脆：

```
[啟用] 載入詞庫前     @0ms
[啟用] 詞庫載入完成   @1202ms   ← 全部時間在這
其餘七個步驟          合計 1ms
```

再拆開三本詞庫：

| 詞庫 | 時間 |
|---|---|
| 英文 | 8 ms |
| 注音 | 122 ms |
| **日文** | **1086 ms**（89%）|

**直覺會往「檔案太大、讀太慢」猜，那是死路**——後來量到讀 60MB 只花
58ms，成本全在建雜湊表（逐行切欄位、逐條配字串、逐條插入）。

### 2.10.2 第一刀：關掉的引擎不該載

`preload` 從來沒看過引擎設定，一律三本全載。而日文引擎關掉的使用者，
每次切輸入法都在等一本**永遠不會被查**的詞庫。

順帶挖出一個埋著的順序錯誤：兩個呼叫點都是**先載詞庫、才讀設定**，
那樣根本不可能知道哪些引擎有開。改成先 `refresh_config` 再
`ensure_dict_loaded`。

實測 1203ms → 137ms。

### 2.10.3 第二刀：同一份資料的雜湊做了兩次

日文載入時建了兩張表：`JAPANESE`（假名的集合，回答「是不是日文詞」）
與 `KANA_WORDS`（假名 → 漢字寫法）。但**前者的內容就是後者的鍵**——
實測兩邊都是 745965 條，逐條比對完全相同。

像是有電話簿還另外抄一份姓名名單：要問「這個人在不在」，翻電話簿就
知道了。

注音那邊一模一樣：`BOPOMOFO` 與 `WORDS` 在同一個迴圈的同一個分支裡
各插入一次同樣的鍵（還為此多做一次 `clone`），132050 條全部相同。
（`CHARS` 是單字讀音，另一個鍵空間，那個不重複。）

**為什麼會變成這樣**：兩張表是不同時期為不同目的加的——一個給 Phase 1
判合法性，一個給後來的選詞模組。各自都合理，只是沒人發現它們的鍵長成
了同一份。這種重複用讀的不容易看出來，是量測時「兩個數字一模一樣」才
露出馬腳的。

日文 1086ms → 722ms，注音 132ms → 103ms。

### 2.10.4 第三刀：背景載入

`Activate` 不再等詞庫，丟一條執行緒去載。**實測啟用完成 @0ms**。

動手前先查清楚兩件事，這是它能這麼簡單的原因：

1. **DLL 不會在行程活著時被卸載**——`DllCanUnloadNow` 一律回 `S_FALSE`
   （Phase 0 就刻意留的保守做法），背景執行緒不會做到一半踩空。
2. **載到一半使用者就打字也安全**——詞庫是 `OnceLock`，第二個呼叫者會
   擋在那裡等載完，不會看到半成品；而按鍵那條路本來就有一次
   `ensure_dict_loaded`，剛好接住。使用者只等剩下的時間，不是從頭等。

擋重複開執行緒的判準是「**現在需要的那幾本在不在**」而不是「載過一次
沒」——這樣使用者事後在設定裡打開日文，下次啟用才補得了。

| | 切換時要等 |
|---|---|
| 一開始 | 1203 ms |
| 只載有開的引擎 | 137 ms |
| 改背景載入 | **0 ms** |

### 2.10.5 二進位詞庫：驗證過了，但決定先不做

> **2026-09-02 已經做了**，見 [[二進位詞庫與 mmap：常駐 232MB → 23MB]]。
> 下面留的是當初「決定先不做」的判斷與理由——那些理由後來被記憶體目標
> 推翻，過程本身有價值，所以不刪。
>
> **標題不要再改**：有五處連結指著它，改標題等於一次弄斷五個錨點。

> **這一節記的是 2026-08-31 的雛形驗證與當時「先不做」的三個理由。**
> 那三個理由在 Phase 4 結案後全部解除，實作與實測見
> [[二進位詞庫與 mmap：常駐 232MB → 23MB]]
> ——結果是常駐 232MB → 69MB。下面兩個當時的預測**都沒有成真**：
> 「查詢慢 10 倍」被雜湊索引擋掉了，格式也確實如預期改了一次
> （成本值必須存，因為整句轉換是雛形之後才做的）。

延遲解決了，記憶體沒有。量到的數字：

| 設定 | 每個行程佔用 |
|---|---|
| 日文關 | 約 8 MB |
| 日文開 | **約 290 MB** |

而且**每個行程各一份**——記事本一份、瀏覽器一份。`bench_typing` 的
驗收目標是常駐 < 50MB，現況 221MB 未達標。

根源是 `HashMap<String, Vec<String>>`：74 萬個 `String` 各自帶指標與
長度標頭，雜湊表還要留空槽，結構開銷遠超過資料本身（原始檔才 60MB）。

做了雛形驗證（`core/src/bin/spike_dict_bin.rs`，**未接進輸入法**），
格式設計成「載入時零解析、零配置」：字串連續排在一起、用位移量索引，
讀進來就是能查的樣子。

| | 文字版 | 二進位版 | |
|---|---|---|---|
| 載入 | 705 ms | **12 ms** | 快 59 倍 |
| 記憶體 | 290 MB | **43 MB** | 剩 1/7 |
| 檔案 | 60 MB | 41 MB | |
| 查詢「在不在」 | 70 ns | 690 ns | 慢 10 倍 |
| 正確性 | — | 745965 條逐條比對，零不一致 | |

查詢變慢是唯一代價。埋計數器量到**平均每次按鍵查詞庫 1267 次**，換算
多花 0.8ms，而按鍵延遲 p50 本來就 7.6ms——影響約 10%，而且可以靠把
排序索引換成雜湊索引消掉。

**決定：先不做**。理由不是技術，是時機：

- **選詞模組還在動**。二進位版會把 `words_for_kana` 從回傳 `Vec<String>`
  改成回傳借用的 `&str`，呼叫端是 `compose.rs`——那正是 Phase 3、
  Phase 4 還在演進的區域。現在換掉它的資料來源，等於在會移動的地板上
  鋪磁磚。
- **格式很可能要改一次**。雛形把 mozc 的成本值丟掉了，而 Phase 4 的
  個人化若要把使用者權重跟基礎分數混合就會需要它。等 Phase 4 做完，
  「要不要存成本值」這題會自己有答案。
- **時程上不急**。「常駐 < 50MB」本來就排在 Phase 5（發佈前），現在是
  Phase 3。而且延遲已經被背景載入吸收掉了，就算開日文也感覺不到。

**選型已定（2026-09-01）：系統表直接編譯成二進位，不要走 SQL。**
決定性的理由是本節上面那個數字——**平均每次按鍵查詞庫 1267 次**。
二進位單次 690ns（實測）換算 0.87ms；SQLite 一次查詢約 2–10µs（估計，
未實測）換算 2.5–12ms，而按鍵預算只有 16ms、現況 p99 已經 11.5ms。
另外兩個理由：我們對詞庫只有「給鍵拿詞」這一種操作，SQL 的查詢規劃／
交易／關聯全都用不到卻要付錢；而 mmap 讓多個宿主行程**共用同一份實體
記憶體**，正好對上「每個行程各背一份」這個病灶。

旁證是新酷音走過這條路而且往回走了：它的系統詞庫是 Trie 二進位
（`word.dat`／`tsi.dat`），**連使用者詞庫也是 `.dat`**，SQLite 現在是
可選功能，初始化時發現舊的 `chewing.sqlite3` 會自動匯入新格式。

不衝突的部分先記著，日後不必重查：Phase 4 的個人化是獨立的**可變層**，
跟不可變的基礎詞庫剛好互補（分層的形狀見
§2.17）。但要注意
**個人層也在熱路徑上**，一按鍵同樣查上千次，所以它該是「記憶體裡的
可寫小表，落地時才寫檔」，而不是每次查詢都去問資料庫；Phase 6 跨平台也沒問題，
格式是 little-endian，三個目標平台都是 LE，`core` 仍保持平台無關
（只有 mmap 那層要放進 `platform/`）。mmap 還有一個現在拿不到的好處：
多個行程**共用同一份實體記憶體**，而不是各背一份。
