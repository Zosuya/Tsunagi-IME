# 標點也能選寫法

> **狀態**：平台層「有候選才進組字區」那條沒辦法單元測試，要真機驗。
> **macOS 實打通過**（2026-09-15：`[` 進組字區、`!` 進組字區選全半形、鎖注音的 `,` 出標點，
> [[驗收清單：已實作未驗收]] 的 B 節）。**Windows 也過了**（D 節：`[`、`!` 進組字區，`@` 直接送出）。
> macOS 的 `@` 直接送出也補驗通過（2026-09-15），**兩平台全過**

使用者提的：「標點符號可以增加選擇功能嗎？例如 `[` 可以選不同個樣式」。

## 2.47.1 基礎結構本來就在

查現況時發現這件事比預期便宜——**標點早就自成一格**了：

```text
su3cl3[  →  #1 su3 你   #2 cl3 好   #3 [ [   （不選字：英文段）
```

只差那一格標成不可選。格子模型、選字介面、學習層全都不必動，跟改一個
字走同一條路。

而 `width.rs` 的註解本來就記著為什麼引號沒收：

> 引號沒收：`「」` 要分開頭與結尾，**得記狀態**，不是這一層的事。

**這次的做法正好繞掉那個問題**——`[` 和 `]` 是兩個不同的鍵，各自有各自
的候選清單，根本不必記「現在是開還是閉」。

## 2.47.2 一鍵兩用不是問題（我一開始想岔了）

第一版評估時我說「`, . ; / -` 是注音鍵（ㄝㄡㄤㄥㄦ），給候選會打架」。
**那個判斷是錯的。**

那個歧義在**切點階段就解決完了**——`punct::is_punct` 會往後看聲調，
`5;4` 的 `;` 要看到 `4` 才知道是ㄤ。等到它變成一個標點格的時候，引擎
已經確定它是標點。那時再給候選完全不衝突。

使用者的直覺對，我的推論錯。

## 2.47.3 範圍：只給不用 Shift 的鍵

使用者裁決：Shift 系列的符號是明確按出來的，意圖很清楚（打 `!` 就是要
驚嘆號），不需要再選。

最後是八個鍵：

| 鍵 | 候選（第一個是目前顯示的字） |
|---|---|
| `[` `]` | 「」『』【】〔〕［］《》〈〉 |
| `'` | ‘ ’ 『 』 |
| `,` | ，、；（日文旁邊第一個是讀點） |
| `.` | 。 … ． ‧ |
| `;` | ； ： |
| `/` | / ／ ？ ・ |
| `-` | - － — ～ ‧ |

`/` 那列放 `？` 是刻意的——**不按 Shift 也選得到問號**。`.` 那列的 `…`
同理，刪節號很常用但很難打。

## 2.47.4 學習層免費接上

`learn` 記的是「按鍵 → 文字」，標點格的鍵是 `[`、值是 `「`——跟選字
完全同一條路。**「記住你慣用的括號樣式」沒有寫任何新機制**，選過兩次
就變預設。

兩個收窄：

- **只接受候選表裡的值**。學習檔是使用者可以手改的，而這一格會直接進
  文件——收窄成「表裡有的那幾個」比信任檔案內容安全。
- **標點在 `learn::record` 裡自成一段**。標點的 `lang` 是英文，不分開的
  話 `check[` 會被當成同一段，學到「check「」這種沒有意義的子段。

## 2.47.5 `...` 合併：在 compose 做，不動切點引擎

切點引擎的標點格**一格就是一個字元**（`to_segments` 寫死
`end == begin + 1`）。要讓 `...` 成為一格，改切點引擎是一種做法，但那會
動到三支計分器量的東西；在 `compose` 合併則完全碰不到切點。

合併後 `keys` 仍然接得回原字串（`...` 三個字元變成一格的 `keys`）——那是
`check_rewrite`、倒退鍵刪格、學習都靠的性質，有測試釘住。

**第一版漏了語言條件**，`hello...` 也被合併成 `hello…`。那跟「打程式碼時
不會突然冒出全形符號」牴觸，而且測資的 `hello|.|.|.` 期望的正是三個點
——**是計分器把它抓出來的**（679→677）。加上「只在中日文脈絡下合併」
之後分數回到原位。

## 2.47.6 括號成對連動

把 `[` 選成 `「` 之後，後面那個 `]` 還是 `]`——使用者得再選一次，而且
要記得自己剛才選了哪一種。成對的東西該一起變。

- 往後找**第一個沒被巢狀吃掉的收括號**（中間再遇到 `[` 就加一層深度），
  所以 `[a[b]c]` 的外層配得到外層
- **用按鍵認配對，不是用文字**——那一格顯示什麼還沒定，但使用者按的是
  哪個鍵是確定的
- **手動選過的不覆蓋**，跟 `apply_word_context` 同一條原則
- **只做方括號**。`'` 的開與收是同一個鍵配不出來；引號那類要記狀態才
  分得出開閉，那正是 §2.47.1 引用的那條註解說的事，不重蹈覆轍

## 2.47.7 順帶修掉的兩個 bug

**一、全形模式的句點是 `．` 不是 `。`。** `Width::Full` 直接走 `to_full`，
而那是 ASCII+0xFEE0 的固定偏移，給的是「全形的**英文**標點」。`width.rs`
自己的註解就寫著這件事，但 `Full` 那一支自己踩了進去。改成先查
`to_cjk_punct`，查不到才退回 `to_full`。

**二、鎖定日文時標點會整個消失。** `RomajiInput::push` 把湊不成假名的
字元堆在 `pending` 裡等後續，而標點永遠湊不成——它卡在那裡切不出段落，
送出時整個不見：

```text
鎖定日文打 sushi,  →  すし        ← 逗號沒了
```

**那是資料遺失，不是顯示問題。** [[鎖定注音時打不出標點：一鍵兩用怎麼解]] 修過「鎖定注音打得出標點」，
但只修了注音那條路，日文這條漏著。

## 2.47.8 鎖定語言時標點跟著鎖走

自動模式下標點看**前面那一段**的語言，但句首沒有前一段，原本一律給半形
（「打程式碼時不會突然冒出全形符號」，那個預設是對的）。

鎖定之後就有依據了：鎖注音／日文時句首打句點該是 `。`。鎖英文維持半形
——那個模式的語意本來就是「等同關掉輸入法」。**沒鎖時行為完全不變。**

## 2.47.9 平台層：「直接送出」的前提沒了

`text_service` 有一條「開頭就打符號的話直接送出去，不進組字區」，理由是
「只想打一個驚嘆號卻要按 Enter，多兩道手續換不到任何好處」。

**那個理由在標點沒有候選的前提下成立。** 現在 `[` 能選寫法，前提沒了，
判準改成「有沒有候選」：有的進組字區，沒有的（`@` `#` `$` `!`）維持直送。

> **2026-09-15 更正**：`!` 不在「沒有候選」那一邊了——[[標點選不到半形：一個裁決漏了反向，補了兩輪]]
> （2026-09-08，`e2957b1`）讓 `：？！（）` 也給半形候選，所以 `!` 會進組字區。
> 維持直送的是 `@ # $ % & *` 這批。

這條**沒辦法單元測試**，要真機驗。

## 2.47.10 一個測試的教訓

第一版把日文標點的期望寫成 `すし、`，**單獨跑會過、跑全套會掛**——
`sushi` 轉成 `すし` 還是 `寿司` 要看詞庫載了沒，而詞庫載不載取決於同一輪
跑了哪些測試。

改成只驗標點本身（`ends_with('、')`、不含半形逗號）。**測什麼就斷言
什麼，不要順手綁上無關的東西。**
