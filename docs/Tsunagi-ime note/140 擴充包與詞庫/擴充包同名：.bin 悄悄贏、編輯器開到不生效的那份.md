# 擴充包同名：.bin 悄悄贏、編輯器開到不生效的那份

> **狀態**：2026-09-20 修完（三項裁決都有答案了，見文末）。
> **這個洞後來真的毀掉了一次官方包**，經過見最後一節。

**使用者遇到的**：自己建了一個包也叫「台語」，按儲存，**可能蓋過官方台語包**，
之後那個包**刪不掉，顯示「刪除失敗」**。

**先講結論**：官方台語包**沒有被毀損**。設定頁存檔只寫 `.txt`，
永遠不碰 `.bin`。但也正因為這樣，才產生一連串使用者看不出來的怪現象。

## 一個規則，三個後果

載入時的找檔規則（`core/src/pack.rs` 的 `find_pack`）：

```rust
for d in dirs {
    if {name}.bin 存在 { return Bin }   // .bin 先問
    if {name}.txt 存在 { return Txt }
}
```

**同一個資料夾裡 `.bin` 永遠優先，而且是整份取代不是逐條合併**。
這個規則本身沒錯——官方包的正常流程就是維護 `.txt`、跑 `gen_pack_bin`
產 `.bin`，兩者同名並存是**必要的**。

問題是**使用者自建的包撞上這個名字時，三件事同時靜默出錯**：

| # | 現象 | 位置 |
|---|---|---|
| 1 | 使用者的 `台語.txt` **從來沒生效過**，生效的一直是官方 `.bin` | `find_pack` |
| 2 | **編輯器開的是那份不生效的 `.txt`** ——看到、改到的跟實際在用的是兩份 | `read_editable` 不走 `find_pack`，自己只找 `.txt` |
| 3 | 刪除**只刪 `.txt`**，刪完包照樣完整生效，UI 卻回報「已刪除」 | `delete()` 只組 `{file}.txt` 的路徑 |

`is_bundled_only` 也只看 `.txt`，同樣對 `.bin` 盲。

**三個都沒有任何提示**。使用者唯一能察覺的方式是「改了怎麼沒反應」。

## 為什麼不能用資料夾分辨官方與自製

直覺的修法是「官方包放一個資料夾、使用者包放另一個」，但
**這條路已經被 [[台語包退出安裝程式：簽好的 bundle 塞不得東西]] 堵死了**
——2026-09-11 決定台語包不進安裝程式（往簽好的 bundle 塞檔案會破壞簽章封印），
改成從獨立 repo 下載、使用者自己丟進擴充包資料夾。

**所以官方包跟自製包現在躺在同一個地方**，位置分辨不出來。

使用者提的另一個方向是「用作者欄判斷」或「加一個隱藏欄位」。
**不建議**，理由是它判斷的東西不對：檔頭欄位是**資料**，可以複製貼上；
要判斷的是「這個檔案是不是官方包的一部分」，那是**事實**。

**現成的答案其實是 `.bin` 本身**：`gen_pack_bin` 是專案內部工具，
一般使用者不會有、設定頁也不會產生 `.bin`。所以

> 資料夾裡有 `X.bin` ＝ `X` 這個名字被官方包佔用了

不需要新欄位、不需要信任任何人寫的檔頭。而且程式裡**已經有這個認知**
——`meta_from_bin` 無條件把 `.bin` 標成唯讀，註解明寫「不看檔頭裡寫什麼」。

**前提**：所有官方包都會做成 `.bin`。若以後會出現只有 `.txt` 的官方包，
這個判準就會漏掉它們。待確認。

## 刪除為什麼會失敗

`delete()` 做的事很單純：`std::fs::remove_file` 刪掉 `{name}.txt`，
**沒有備份、不進資源回收筒**（對比 `write_editable` 覆寫前會存 `.txt.bak`），
失敗只印原始的 io error 字串，**沒有退路**。

先排除一個猜測：**mmap 映射中不會造成刪除失敗**。專案自己量過（§2.34.1）：

| 操作 | 詞庫（mmap 映射中） |
|---|---|
| 就地覆寫 | ❌「檔案的使用者對應區段在開啟狀態」 |
| **刪掉** | ✅ **可以立刻刪** |

Rust 的 `File::open` 在 Windows 是全共享，且 mmap 的是 data section
不是 image section，Windows 允許刪除、刪完映射仍有效。macOS 是 POSIX
`unlink` 語意，更不會失敗。**兩邊都是「刪得掉、舊映射繼續有效」。**

所以症狀不是「刪不掉」而是「**刪了還在用**」——直到宿主行程重開。

> **順帶記一筆**：設定頁光是列清單就會對每個 `.bin` 呼叫 `map_pack_bin`，
> 而它 `Box::leak` **永久洩漏**映射到行程結束。`*cache = None` 只清 UI 快取，
> 映射不會釋放。

真正會刪失敗的是別的：檔案被其他程式開著、唯讀屬性、權限不足。
**Mac 上那次實際是哪一種，要看資料夾現況才知道**（待使用者提供）。

## ⑤ 同讀音多輸出：規格缺口，不是 bug

使用者說「編輯器會一直覆蓋掉舊的，沒辦法同時有兩筆一樣打法的」。
**那是刻意的**，而且理由正當。

各層的支援度**天差地別**：

| 層 | 同讀音多輸出 | 怎麼做到的 |
|---|---|---|
| `zh`／`zh_long`／`ja` | ❌ **只能一個** | `push_first`，第一個贏、後面的整條丟棄 |
| `sym` 符號 | ✅ **原生支援** | 一個名字對一整排候選，同一列用空白分隔，**不同包的同名還會合併** |
| `tw` 台語 | ✅ **原生支援** | 一個國字詞 → 多種說法，雙向 |

編輯器在新增列時就**主動砍掉同按鍵的舊筆**，理由正是實測回報：
留兩筆的話後面那筆**永遠不會生效，卻靜靜躺在檔案裡騙人**。
所以編輯器乾脆在輸入當下就處理掉。

**中文／日文查詞主路徑刻意只回一個**，因為 `zh` 那層的詞是逐格填字的。
要「一個讀音多個候選」，目前唯一的通用做法是**走 `sym` 那條**
（`\名字\` 叫出候選列），或台語的段選單。

### 判重的兩個真漏洞（這兩個是 bug）

- **就地編輯既有列時完全不判重**：點格子直接改按鍵，沒有任何 dup 檢查。
  把第 5 列的按鍵改成跟第 2 列一樣，兩筆都會留在檔案裡、第 5 列變死資料
  ——**正是新增路徑刻意要避免的那個症狀**，從側門繞回來了
- **`invalid_rows` 不檢查重複**，所以存檔前的「有無效資料就不給存」閘門
  也攔不到；`render` 存檔本身照單全收

## 附帶查清的：同名時誰贏（這些是對的，記著免得誤判）

- **跨包同讀音**：`Config::behavior.packs` 的**清單順序在前的贏**，有文件
- **使用者的六張表 vs 官方 `.bin`**：一律「使用者先問、`.bin` 後問」
- **`sym` 與 `tw` 是合併不是覆蓋**：兩個包都有 `\音樂\` 時 ♪♫ 與 🎵🎶 會接起來
- **同一檔案內重複讀音**：跟跨包**完全相同**（同一條程式路徑），
  `parse` 不去重、去重全發生在 `build_index`

## 待裁決（三項）

1. **中文／日文要不要支援同讀音多候選？** 動引擎層（目前 `push_first`），
   影響排序與選字，工程量不小。替代方案是**引導使用者走 `sym`**，零改動
2. **`.bin` 與 `.txt` 同名時怎麼辦？** 傾向「存檔時偵測同名 `.bin` 就擋下來、
   要求改名」。但「誰該贏」是規格決定
3. **官方包以後會不會有純 `.txt` 的？** 決定「`.bin` 當官方標記」這個判準夠不夠用

另外**需要使用者提供**：Mac 擴充包資料夾的實際檔案清單
（`~/Library/Application Support/tsunagi-ime/`，`.txt` 與 `.bin` 都要）。
刪除失敗的真正原因、以及現在那個檔案怎麼救，都取決於它。


## 裁決與修法（2026-09-20）

三項待裁決的答案：

| | 問題 | 裁決 |
|---|---|---|
| ① | 中日文要不要支援同讀音多候選 | **做了**，見 [[擴充包編輯器的實作與收尾]] 之後那批 commit（`zh_all`／`zh_long_all`） |
| ② | `.bin` 與 `.txt` 同名時怎麼辦 | **擋下來，並提一個名字讓使用者一鍵改** |
| ③ | 官方包以後會不會有純 `.txt` 的 | **可能會有** ——所以「有 `.bin` ＝官方」那個判準當場作廢 |

### ★ 判準換掉了：不問身分，只問名字有沒有被佔 ★

③ 的答案直接否掉了原本傾向的做法。改成：

> **同一個資料夾裡不准有兩個同名的包。**

誰是官方變成不相干的事，也不必新增任何檔頭欄位（檔頭是**資料**、可以
複製貼上，判斷不了**事實**——這一點前一版就想對了，只是找錯替代品）。

`core` 新增 `name_taken_by` / `suggest_free_name`，四處接上：

- **存檔**：撞名擋下來，狀態列旁給一個「改名為『台語-2』並儲存」的按鈕。
  編輯既有的那份 `.txt` 再存檔不算撞名（`ignore_txt`）——那就是他自己
- **開啟**：同名 `.bin` 在的話直接說「你在這裡改的東西不會生效」
- **刪除**：`.txt` 刪掉但同名 `.bin` 還在時**老實講**，不再回報「已刪除」
  了事。不偷偷刪 `.bin`——那多半是官方包，使用者按的是「刪掉我這一份」
- **`is_bundled_only`**：本來只看 `.txt`，官方包做成 `.bin` 之後唯讀提醒
  整個消失，現在兩種都看

## ★ 2026-09-20：這個洞真的毀掉了官方台語包 ★

前一版寫著「官方台語包**沒有被毀損**，設定頁存檔只寫 `.txt`，永遠不碰
`.bin`」。**那句話在「有 `.bin` 擋著」的前提下才成立**，而使用者的開發機
上沒有。

經過：使用者在設定頁新建一個叫「台語」的包按存檔，**官方台語包 91013 行
被覆寫成 5 行**——連 CC BY-SA 4.0 的姓名標示檔頭一起沒了。那是**授權
問題**，不只是資料問題（那個檔頭自己寫著「不可以拿掉」）。

### 三件事湊在一起

1. **`packs_dir` 指向專案目錄**（`$ROOT/packs`，官方包的原始檔就在那）
2. **唯讀檢查擋不到「新增」那條路**：`state.readonly` 是畫面狀態，新建的
   包那個值是 `false`，根本不會經過檢查
3. **`.bak` 救不了**：它存的是**上一次覆寫後**的版本。使用者存了兩次，
   備份裡已經是壞的

救回來靠的是 `packs/` 在版控裡（`git checkout HEAD -- packs/台語.txt`）
——**那個設定同時是兇手和救命繩**。

### 別人也會中，而且沒有 git 可以救

`Tsunagi-packs` 的 README 寫的是「下載 `.txt`，丟進
`~/Library/Application Support/tsunagi-ime/packs/`」——**那就是設定頁存檔
的同一個資料夾**。官方包跟自建包從第一天起就躺在一起。

（repo 裡 `台語.bin` 與 `台語.txt` 兩份都有，但 README 只叫人下載 `.txt`。
兩份都放的人 `.bin` 會擋著、功能不受影響，只毀掉授權檔頭；只拿 `.txt`
的人功能直接壞掉。）

**救回的方式是重新下載**，資料沒有永久損失。

### 修法：閘門下沉到 core

`write_editable` 覆寫前**去讀磁碟上那份檔案的檔頭**，寫著 `readonly: true`
就拒絕。

> 判準要讀**磁碟上那份檔案**怎麼寫，不是呼叫端說什麼。

設定頁那道（`state.readonly`）保留，它是第一道；真正會毀掉檔案的是
`fs::write` 那一行，閘門就該擺在那裡。加上同名偵測，現在兩道門擋著。

使用者裁定（2026-09-20）：**兩道門夠了**，不再加「覆寫前丟資源回收筒」
那類保險（要多一個套件、兩平台各一個 API）。

### 教訓

- **「某某不會被毀損」這種結論要寫清楚前提**。前一版的結論沒錯，但它靠的
  是「有 `.bin` 擋著」，而那個前提在開發機上不成立——一句話少了前提，
  下一個讀的人就會據此安心
- **畫面狀態不是閘門**。`state.readonly` 是 UI 的判斷，繞一條路（新增而非
  編輯）就完全不經過它
- **備份要能對抗「連續存檔」**。單一 `.bak` 被第二次存檔一蓋就沒了
