# 擴充包要放哪：獨立 repo，與兩個量出來的洞

> **狀態**：決策記錄；兩個編碼洞已於 2026-09-08 修好，下載功能刻意不做

使用者問的：「未來可能還需要地方放擴充包，要怎麼處理？新 repo？」
**決定先討論不實作**，這一節是記錄，日後真的要開 repo 時照著做。

### 2.49.1 結論：獨立 repo，下載功能先不做

建議開 `tsunagi-packs`，第一階段只放純文字檔加一份 README——使用者
下載 `.txt` 丟進 `%APPDATA%\tsunagi-ime\packs\`，設定頁按重新整理。
**這條路今天就通了，不必寫任何程式。**

不放主 repo 的三個理由，第一個是硬的：

- **授權會打結**。程式是 GPL-3，包是第三方資料，可能各有來源。
  `CREDITS.md` 已經在處理「程式的授權 vs 資料的授權」，收進同一個
  repo 等於把那件事再複雜化一次
- **節奏對不上**。程式一個月一版，包可能一週三次。放一起的話改一個
  詞表要動到有 CI、有版本號、有安裝程式的那個 repo
- **投稿門檻**。想貢獻遊戲名詞表的人不該需要面對一個 Rust 專案

### 2.49.2 授權：可以指定預設，但不能「一律」

使用者問「一律走 GPL-3 不行嗎」。**當預設可以，當一律不行**——詞表
最常見的來源不是自己打的，而**有些授權在法律上就是不能改成 GPL-3**。
本專案自己就有現成的例子：教育部字頻是 CC BY-**ND**（不得改作），
libchewing 的資料是 LGPL（§2.31 標過需隔離）。

「一律 GPL-3」的實際結果不會是大家照做，而是**有人照填了但那句話是
假的**，等於多背一個聲明。

規則寫成三條：

1. 沒特別註明的視為 GPL-3.0-or-later（跟程式一致，投稿的人不用想）
2. 要用別的授權就在檔頭 `# license:` 寫清楚——**這個欄位已經存在**，
   設定頁也已經會顯示，不必新增任何東西
3. ND 與 NC 的資料不收。理由不是意識形態，是那兩種會讓「這個包能不能
   被別人再散布」變成逐案判斷，而包的價值就在流通

**真正要問投稿者的是來源不是授權。** 來源清楚了授權自然就定了；
只問授權的話多數人會憑感覺勾一個。

（另一個沒選的方向：GPL-3 是寫給軟體的條款，套在純文字詞表上不會壞
但不合身，FSF 自己建議非軟體用 CC 系列。如果目標是「包能到處流通」，
CC0 當預設更合身。兩個都合理，看要哪一個，還沒定。）

### 2.49.3 兩個量出來的洞：都只在「從網路下載回來」才踩得到

問「獨立 repo 撐不撐得住」時實測的。做三個內容一樣的包，只差編碼：

| 存檔方式 | 結果 |
|---|---|
| UTF-8 | 名稱、版本、詞都對 ✓ |
| **UTF-8 帶 BOM** | 詞還在，**檔頭整個消失**（name／version／description／license 全 `None`） |
| **Big5（記事本的「ANSI」）** | **0 條**，設定頁的勾選框被停用 |

BOM 那個壞在**它半動**：包能用，但設定頁顯示的是檔名、沒有版本作者
授權——看起來像作者偷懶沒填，實際上他填了。而 BOM 正是從網頁「另存
新檔」或用舊工具編輯最容易長出來的東西。

根因在 `parse_meta`：`t.strip_prefix('#')` 對 `\u{feff}#…` 失敗，
而它的語意是「遇到第一行資料就停」，於是**整段檔頭在第一行就被判定
結束**。`U+FEFF` 不屬於 Unicode 的 White_Space，`trim()` 清不掉它。

Big5 那個更誤導：`read_to_string` 對非 UTF-8 直接回 `Err`，被當成
「沒有內容」，清單上顯示「還沒有詞（沒填，或格式不對）」——但格式
完全正確，錯的是編碼。使用者照那句話去檢查格式永遠查不出來。

**兩個都只在「包從別處來」時才會遇到**，自己寫的包踩不到——這正是
開 repo 之前要先修的理由。修法都很小：讀檔時吃掉 BOM；讀檔失敗要
講真正的原因，不要跟「沒有詞」共用一句話。

#### 2026-09-08 修好了

台語包接上段選單之後，「包從別處來」從假設變成現實（台語資料要從
ChhoeTaigi 下載），所以先把這兩個補起來。

**一支 `read_pack` 收兩件事**：

```rust
match std::fs::read_to_string(path) {
    // BOM 在這裡吃掉——`parse` 與 `parse_meta` 兩處都受惠
    Ok(s) => Ok(s.strip_prefix('\u{feff}').unwrap_or(&s).to_string()),
    // **編碼錯要分得出來**，不能跟「檔案不在」共用一個 Err
    Err(e) if e.kind() == InvalidData => Err(PackReadError::NotUtf8),
    Err(_) => Err(PackReadError::Missing),
}
```

`Info` 多一個 `error: Option<PackReadError>`，設定頁看到 `NotUtf8`
就顯示**「編碼不是 UTF-8（用記事本另存為 UTF-8）」**——直接講原因，
還講怎麼修。

順手修掉的第三件：`info()` 原本只找 `dir()`（使用者的目錄），**預載
包的檔頭永遠讀不到**。改成走 `dirs()`，跟載入時同一條路。

測試用兩個真的問題檔案守著（`core/testdata/packs/bom_pack.txt` 帶
BOM、`big5_pack.txt` 是 Big5）——不是模擬，是實際的位元組。

### 2.49.4 兩件還沒有機制的（不是 bug）

**更新通知**：`# version:` 這個欄位存在、設定頁也顯示，但沒有任何
東西拿它跟上游比對。以現在的量沒差，包多了會有人抱怨。

**投稿的格式驗證**：包的解析是「錯的那一行靜默跳過」——這對使用者
是對的（一行打錯不該毀掉整包），但對**審 PR** 是壞的：貢獻者少打
一個 Tab，肉眼看不出來，合併之後那一行就是不存在。

解法現成：解析器已經在 `core` 裡，加一支 `check_pack`（吃一個檔案，
印出收了幾條、第幾行被跳過、為什麼），packs repo 的 CI 抓 release
的執行檔跑一次。**等真的有人投稿再做。**

### 2.49.5 下載功能為什麼現在做是錯的時機

這是 CLAUDE.md 待決定裡「領域包的來源與信任」那條。兩個理由：

- **還沒有量**。包只有自己寫的幾個，做設定頁內的瀏覽／一鍵安裝是為
  不存在的使用者建設施
- **它會開一個新的攻擊面**。輸入法看得到使用者打的每一個字，而包能
  改變送進文件的內容。現在的防線是 `sanitize` 加上**純文字肉眼可審**
  ——「肉眼可審」在手動下載時是真的成立，變成自動下載之後就名存實亡。
  真要做的話該一起決定的是「只信任這一個 repo 還是任何網址」、要不要
  簽章、更新是不是靜默的。那是一整套設計，不是加一個按鈕

### 2.49.6 順帶定的

**內建那 40 組符號留在程式裡**，不要搬進包——內建的價值是開箱即用，
repo 放的是擴充的。**`index.json` 現在不要建**，那是給下載功能用的，
沒有下載功能就是一份會過期的檔案。
