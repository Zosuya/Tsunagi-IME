# Mac 設定頁的按鍵欄拿到國字：兩平台刻意不一致，撞在一起

> **狀態**：2026-09-20 修完，三宿主未走（設定頁本身就是宿主，實打過）。
> 原本傾向的修法 1 被 spike 否決，最後走的是第四條路（舉旗）。

**症狀**：在 macOS 的設定頁編擴充包，「怎麼打」那一欄打字進去，
**存進去的是國字而不是按鍵字面**。Windows 沒有這個問題。

## 不是欄位寫錯，是前提只在一個平台成立

「怎麼打」欄（`settings/src/pack_editor.rs` 的 `keys_field`）的做法很特別
——**不是普通的文字框，而是「唯讀框＋自己攔事件」**：

1. 給 `TextEdit` 一份 `keys.clone()` 的複本，使用者打進去的東西**寫不回**
   真正的 `keys`（複本純粹拿來顯示游標與選取）
2. 自己掃 `ui.input` 的事件，兩條來源：
   - `Event::Key` → 只收 26 字母、10 數字、`;,./-`、空白（輸入法關著時走這條）
   - `Event::Ime(Preedit(s))` → **把組字區的內容整個當成按鍵**
3. `ImeEvent::Commit(_)` **刻意空實作**——註解寫「我們要的是按鍵，
   不理會送出的內容」

第 2 點第二條的那一行（`if let Some(p) = preedit { *keys = p; }`）
就是出事的地方。**它無條件把組字區內容當成原始按鍵蓋掉整欄。**

設計依據是 [[擴充包編輯器：設計與四個量測]] 的 spike 實測：

```
Key(C) Ime(Enabled) Ime(Preedit("c"))
Key(J) Ime(Preedit("cj"))
Key(Num6) Ime(Preedit("cj6"))
```

→ 當時的結論是「按鍵欄讀 `Ime(Preedit)` 的內容，不管輸入法最後 commit 出什麼」。

**這個結論在 Windows 完全正確，在 macOS 完全錯誤。**

## 兩邊的組字區裝的是不同的東西

| | 組字區內容 | 來源 |
|---|---|---|
| **Windows** | `cj6wl6`（**原始按鍵**） | `session.composition_text()`，自動模式下回 `input.keys()` |
| **macOS** | `胡桃`（**轉換後的國字**） | `echo_ime.rs` 的 `composition()`，回 `s.text()` |

macOS 那邊**是刻意的**。`composition()` 的 doc comment 原文：

> **為什麼不是 `composition_text()`**：那支在自動模式下回的是原始按鍵
> （`su3cl3`）⋯⋯ **macOS 不這樣做**：每個原生輸入法都是組字區直接顯示
> 轉換後的結果⋯⋯`su3cl3 → 你好`⋯⋯**這是兩個平台刻意不一致的一處**。

註解甚至**已經寫明這是刻意不一致的一處**——只是寫的時候沒有人想到
「按鍵欄靠組字區撈原始按鍵」這個用途會被它打死。

## 為什麼測試與驗收都沒抓到

三層都漏了：

- **驗收在 Windows 做的**：擴充包編輯器記為「2026-09-14 三宿主實打通過」，
  那三個宿主全在 Windows
- **spike 只在 Windows 跑過**：`settings/src/bin/spike_keyfield.rs` 的
  `install_cjk` 只找 `C:\Windows\Fonts\`
- **文件沒記**：[[設定頁裡打字：Tab 與方向鍵被 egui 搶走]] 與
  [[擴充包編輯器：設計與四個量測]] 兩篇 grep 全文**沒有任何 mac／macOS 字樣**

另外，設定頁**確實會被自家輸入法接管**（它是輸入法 spawn 起來的獨立執行檔，
`echo_ime.rs` 裡沒有任何 bundle id 白名單或自家 app 排除邏輯）——
整個 `keys_field` 的設計本來就建立在「使用者的系統輸入法就是通譯自己」
這個前提上，那部分沒問題。

## 順帶釐清：`lock_ime_keys_while_composing` 跟這件事無關

容易混淆，記一下免得日後找錯地方。那支處理的是**焦點問題**
（Tab 跳欄、方向鍵移焦點打斷組字，見 [[設定頁裡打字：Tab 與方向鍵被 egui 搶走]]），
只套在三個會組字的**普通** `TextEdit` 上，**沒有套在 `keys_field`**。
跟「送進來的是不是國字」是兩回事。

## 修法三選一（未定）

| | 做法 | 風險／未知 |
|---|---|---|
| **1** ★ | macOS 上不信任 `Preedit`，只走 `Event::Key` 那條 | **要先 spike**：macOS 的 IME 吃掉按鍵後，egui 還收不收得到 `Event::Key`？Windows 實測是**一個都收不到**，Mac 未知 |
| 2 | 改 `echo_ime.rs` 的 `composition()`，讓自家設定頁的 preedit 回原始按鍵 | 破壞 doc comment 明文記錄的 macOS 慣例決定；且需要「認出宿主是不是自家設定頁」的機制，**目前沒有** |
| 3 | 欄位聚焦時要求關閉 IME | 兩平台都沒有任何這類機制（全 repo 搜不到 `set_ime_allowed` 之類），要從零做 |

**傾向第 1 條**，但那個「Mac 收不收得到 `Event::Key`」必須先做最小測試
——它是整條路成立與否的前提，猜不得。

## spike 實測（2026-09-20）：修法 1 出局

`settings/src/bin/spike_keyfield.rs` 在 Mac 上跑兩輪，打 `su3cl3`。
（順手把 `install_cjk` 的字型候選補上 macOS 兩支——原本只找
`C:\Windows\Fonts\`，在 Mac 上開起來注音全是豆腐塊。**那正是這篇的
教訓本身**：spike 只在一個平台跑過，結論就只在那個平台成立。）

### 一、系統輸入法＝通譯（開著）

```
Ime(Preedit("s")) → Preedit("す") → Preedit("你") → Preedit("你c")
→ Preedit("你cl") → Preedit("你好") → Commit("你好")
```

**一個 `Key(...)` 都沒有，一個 `Text(...)` 都沒有。** 跟 Windows 一樣，
輸入法吃掉按鍵之後 egui 這層什麼都收不到。

→ **修法 1 死了**：不是讀到錯的東西，是什麼都讀不到，那一欄會變成
完全打不進字。

另外看 preedit 的中間態：`你c`、`你cl`——**已成字的變國字、未成字的
留字母**。所以也別想「從組字區反推回原始按鍵」，資訊在中途就丟了。

### 二、系統輸入法＝ABC

```
Key(S) Text("s")  Key(U) Text("u")  Key(Num3) Text("3")  ...
```

每個鍵都收得到，按鍵欄正確填出 `su3cl3`，語言辨識認成
`Bopomofo:su3cl3`。**「切成英文再填這一欄」這條繞法成立。**

## 問題範圍比原本寫的小：自動填其實會先接住

重讀 `pack_editor.rs` 的「新增一條」：**輸出欄打完詞之後會自動反查填
按鍵**（`guess_keys(&word)`，走 `ime_core::reverse`），只有**反查失敗**
才退回用 `typed_keys`——而 `typed_keys` 正是從 preedit 記下來的那份，
在 Mac 上是國字。

所以 macOS 上真正會拿到國字的只有兩種情況：

1. **詞庫反查不到的詞**（註解裡的例子就是「英雄聯盟」）→ 退路填進國字
2. **手動點進「怎麼打」欄自己打** → `keys_field` 無條件吃 preedit

常見的「你好／今天天氣好」那種反查得到的詞，Mac 上其實是**填對的**。

## 剩下的三條路（重新評估後）

| | 做法 | 代價／未知 |
|---|---|---|
| **A** | macOS 上**不信任 preedit**：`keys_field` 不吃、退路也不用 `typed_keys`，欄位旁提示「請切英文輸入法填這欄」 | 零風險、改動最小。體驗是「要切輸入法」，但**至少不會寫進髒資料** |
| **B** | 讓自家輸入法認出設定頁，preedit 送原始按鍵（體驗跟 Windows 一致） | 機制**已經存在**（`candidate_panel::diag`／`keyprobe::host` 都在問 `sender` 的 `bundleIdentifier`），但 **`keyprobe.log` 實測：設定頁報的是 `?`**——它是 `.app` 裡的裸執行檔，沒有自己的 bundle id。拿 `?` 當判準會誤傷所有問不出 bundle 的宿主（log 裡有 53 筆），那些宿主會變成打不出中文。要做可靠得先給設定頁自己的 bundle |
| **C** | 反查填不到時，讓使用者打國字、由編輯器列出候選按鍵讓他挑 | 多音字有歧義，要做選擇 UI；但**不必切輸入法**，而且只在反查失敗那條路上出現 |

**前一版寫的「目前沒有認出宿主的機制」是錯的**——機制有，卡的是設定頁
自己沒有 bundle id。


## 最後的修法：設定頁舉旗（2026-09-20）

三條路都不好走（改讀實體按鍵＝什麼都讀不到、認出宿主＝設定頁沒有
bundle id、關掉 IME＝機制要從零做），使用者裁定改成第四條：

> **設定頁主動舉旗，輸入法看到旗子就在送出時改送原始按鍵。**

規格是使用者定的：**組字中照舊看得到自己在打什麼，按下送出才變成
按鍵串**。所以只改送出那一下，`composition()` 一個字沒動。

```
設定頁                              輸入法（另一個行程）
  │ 點進「怎麼打」欄                    │
  │ ──── 舉旗（user_dir 裡一個小檔）──▶ │ 看到旗子
  │ 打 su3cl3                          │ 組字區照舊送「你好」
  │ 按 Enter                           │ 送出時改送「su3cl3」
  │ ◀──── 收到 "su3cl3" ───────────────│
  │ ──── 離開欄位就收旗 ───────────────▶ │
```

實作在 `ime_core::keycapture`（兩平台共用的門面）＋ `echo_ime::commit`
＋ `pack_editor::keys_field`。

### 為什麼舉旗比「認出宿主」好

**它繞過了整個識別問題**。設定頁沒有自己的 bundle id、報的是 `?`，而
別的宿主也有報 `?` 的——拿那個當判準會讓那些宿主打不出中文。舉旗把
「誰要按鍵」交給要的人自己說。

### 三個刻意的設計

- **旗子會過期**（5 秒），設定頁每幀重舉、整幀畫完沒人舉就收掉。設定頁
  當掉沒收旗時，別的 app 最多被影響幾秒
- **擷取那一下不進學習層**：送出去的是按鍵串、目的地是欄位，不是真的在
  寫字（同台語包不進學習層的理由）
- **欄位收資料看內容不看平台**：`pick_keys` 只收「像按鍵」的（送出優先、
  其次組字中），一份程式碼在 Windows 收組字區的按鍵、在 macOS 收送出的
  按鍵。拿 `cfg` 分的話，哪天某一邊改了組字區內容就會再靜默壞一次

## 修完之後又掉出四個坑（同一個根）

全都是**「那一欄不是普通文字框」**的後果——框裡放的是 `keys` 的複本，
於是每一件「普通文字框本來會幫你做的事」都得自己補。按回報順序：

### 一、組字中看不到自己在打什麼

擋掉國字是對的，但畫面上因此空白一片，變成盲打。修法是**先掃事件再
畫框**，組字中框裡顯示輸入法給的那串。

### 二、★ 顯示只閃一幀 ★

修完第一版，使用者回報「打字體驗沒有改善」——**`Ime` 事件只在「組字
內容變了」那一幀送來，而 egui 每秒重繪幾十幀**。拿本幀的 `preedit` 來
畫的話，只有那一幀看得到、下一幀就變回 `keys`。

**這類 bug 靜態的判斷測不出來**（每個判斷單獨看都對），測試必須連著跑
好幾幀比對每一幀畫了什麼。修法是把組字內容存進 egui 的暫存。

### 三、送出那一幀閃一格空白

寫上面那組測試時掉出來的，不是猜的。框的內容在 `ui.add` 那一行就定案，
而 `keys` 是畫完才更新的。修法是**把所有事件處理移到畫框之前**，順帶
讓輸入法關著時的打字也不再慢一拍。

### 四、全選刪不掉

`Cmd+A` 之後按退格沒反應——egui 把複本選起來、刪掉都改不到真正的
`keys`，下一幀原樣回來。所以全選要自己記、刪除要自己動手，而且它跟
第二點一樣是**跨幀**的（`Cmd+A` 一幀、刪除鍵是下一幀）。

## 教訓

- **「宿主收不到鍵盤」是輸入法架構的本質**，兩個平台都一樣。Windows 之所以
  沒事不是因為它攔得到，而是它的輸入法**主動把按鍵當組字區內容送出去**。
  問題從來不是「攔不攔得到」，而是「輸入法願不願意交出來」
- **跨幀狀態要測跨幀**：`Ime` 事件、選取狀態都只在某一幀出現，靜態的
  單點判斷全都會綠著騙人
