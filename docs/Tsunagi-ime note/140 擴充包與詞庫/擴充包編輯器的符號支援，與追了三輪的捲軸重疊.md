# 擴充包編輯器的符號支援，與追了三輪的捲軸重疊

### 2.80.1 先驗一件事：符號包不是 `zh` 長輸出的替身

[[擴充包編輯器的實作與收尾]] 2.75.13 的選項三寫「使用者要的其實是符號那種行為」。動手前先量
`pack::split_symbols`：

```text
       ★ ☆ ✦ → ["★", "☆", "✦"]        ← 空白分隔
         ★☆✦ → ["★", "☆", "✦"]        ← 舊格式逐字元
  我請你喝一杯 → ["我","請","你","喝","一","杯"]   ← 一樣逐字元
      👨+👩+👧 → ["👨‍👩‍👧"]              ← `+` 展開成 ZWJ，一個圖
```

**一個沒有空白的長字串會被逐字元拆成一排候選**，不是一格長輸出。
所以符號支援跟 `zh` 一對多是兩件事，後者仍然等裁決。

### 2.80.2 設計：列的類別可選，包的類別仍然推導

使用者問「包類別要不要可以選」。**不要用宣告的**——`kind_tag()` 的
註解早就寫死理由：檔頭是手寫的，會跟內容不一致；推導出來的事實不會
說謊。而且包本來就可以是混的（清單上就有「詞＋符號」）。

但**新增一列時必須讓使用者明講是詞還是符號**，因為那是唯一算不出來
的東西：名字 `星` 跟注音按鍵、`sekibun` 跟英文詞，字面上分不開。
所以「內容」那一行多了一組「新增：詞｜符號」切換，其餘一切照舊——
語言欄仍然是算的。

符號列跟詞列**同一張表**，欄位語意剛好對得上：輸出＝符號串、
怎麼打＝名字（你確實是打 `\星\`）、語言＝符號。不另開一張表的理由
是**不要再多一個捲動區**（兩支捲軸的坑，見下面）。

三件跟詞不同的事：

- **「怎麼打」對符號是名字，不攔實體按鍵**。`keys_field` 是為了繞開
  輸入法（按鍵要原樣進來），而名字 `星` 非得用輸入法打不可。改完也
  不重算語言——拿名字去 `detect` 只會判成別的東西
- **拆解預覽**：打的當下表格下面一行顯示「會拆成 3 個：★ ☆ ✦」，每
  一列的語言欄滑過去也看得到。**數字問 `pack::split_symbols`**（為此
  開放成 `pub`），不自己拆——那套規則複製到 UI 兩邊一定漂掉
- **四條擋法**：沒有符號、還沒填名字、名字裡有反斜線（`merge_symbols`
  靠一對 `\` 找名字，裡面再有一個就永遠配不起來）、拆不出任何符號

順手修一個潛在的：重複判斷原本只比 `keys`，符號名字 `star` 會跟英文
詞 `star` 互相蓋掉。現在同類別才算重複。

### 2.80.3 捲軸重疊：追了三輪，根因在另一張表

做完符號支援，使用者回報「捲軸會重疊」。**前兩輪都猜錯**，記下來是
因為錯的方式有教訓。

**第一輪（猜）**：以為是我把「詞｜符號」塞進刪除欄、語言欄寫成
「符號 3」，撐爆了 `fixed` 裡手估的 60／90。移出去——沒好。

**第二輪（量，但量錯了情境）**：在無視窗的 egui 裡把整頁排一次版
印座標，量到**表頭比資料列多凸出一個捲軸寬**（878 vs 892）——表頭
刻意放在捲動區外面，但 `fill()` 拿的是沒退讓過的寬度。這是真的 bug，
修了（`set_max_width(inner_w)`），釘了測試——**但使用者說還是疊**。

**第三輪（量真的 app）**：無視窗怎麼跑都對，那就在真的設定頁裡每一
幀印座標到 log，一開就停在擴充包分頁載台語：

```text
面板              8 .. 844.2   可用 836.2
外層捲動區 視窗    8 .. 844.2   內容寬 873.7   ← 比視窗寬 37px
內容表  父可用寬 873.7  inner_w 859.7  視窗 8 .. 867.7  ← 超出外層視窗
```

**整頁被撐得比視窗寬**。逐段印 `min_rect` 找是誰：

```text
資料夾列  844.2
清單      881.7   ← 就是它
操作列    881.7
…
```

上面的**擴充包清單**：「內容」欄放 `description`，用的是 `ui.label`，
**在 Grid 裡不換行、有多長就多寬**。台語包那句「用注音打華語詞、候選
出台語漢字。資料：台文華文線頂辭典」一放進去整張 Grid 就超過視窗。
接下來是連鎖：清單的捲動區橫向不能捲，只好長大配合；整頁那支也一樣；
下一幀所有東西拿到的「可用寬度」都是灌水的，內容表的退讓就退在一個
比視窗還寬的父容器裡。畫面上：兩支捲軸疊在一起。

**為什麼無視窗重現不了**：測試的包資料夾是不存在的，清單是空的。

**為什麼跟符號支援同時出現**：不是。它一直在，只是這天剛好在台語包
上被看到。

使用者接著問「上面那張（清單）有同樣問題嗎」。用真的包量三種寬度：

```text
視窗 852（現在的）：清單捲動區右緣 830、整頁視窗右緣 844 → 退了 14px ✓
視窗 713（最小 820px ÷ zoom 1.15）：清單 683 ＝ 683 ✓
縮小視窗：第 0、1 幀內容還是舊寬度，第 2 幀回到視窗寬 → 過渡，不是洞
```

清單的表頭在捲動區**裡面**，沒有內容表那個表頭凸出的問題。

修法：清單裡**自由文字的欄一律有上限**——名稱 200、作者 120、說明吃
剩下的（其餘各欄上限加總扣掉）。用 `set_max_width` ＋ `Label::truncate`，
短的仍然只占它需要的寬，長的截斷。不丟資料：整列滑過去本來就有
`details(info)`。修完用真的包量：內容寬 836 ＝ 視窗寬。

### 2.80.35 為什麼 Windows 上沒發生：不是平台差異

使用者問「原本 Windows 那邊不是好了，怎麼換 Mac 就壞了」。查完三件事，
**跟平台無關**——記下來免得日後被誤記成「macOS 特有」。

**一、第二支捲軸是新分頁才有的。** 舊的 `packs_page` **一個內層捲動區
都沒有**（`git show 225bb62^` 裡搜 `ScrollArea` 是空的）；新版把清單改成
固定 10 列、自己會捲，第二支捲軸這時才出現。而「說明欄用 `ui.label`
不換行」**新舊一模一樣**——所以舊版在 Windows 上其實也會太寬，只是那時
只有一支捲軸，症狀是「右邊被切掉一點」，沒人注意。欄位還從 5 欄變 8 欄
（多了類別、作者、版本），基準寬度本來就更寬。

**二、預設視窗大小就會疊。** 拿修正前的程式碼掃視窗寬度
（`with_inner_size` 980px ÷ `enlarge_ui` 的 zoom 1.15 ＝ egui 852 點）：

```text
視窗  980px（預設）→ 內容 885 vs 視窗 836 → 溢出 49px ★會疊
視窗 1100px        → 941 ＝ 941  沒事
視窗 1200px 以上   → 沒事
```

**Windows 用同一份程式碼、同一個 zoom、同一個預設視窗，重建後照樣會疊。**
字型不同（微軟正黑體 vs 蘋方）只會讓臨界值移動幾十像素，救不了 49px。

**三、Mac 這邊還多一個「今天才看得到」的巧合。** 在 `packs_dir` 指到
repo 之前，這台 Mac 的清單是**空的**——`.app` 沒帶 `packs/`
（`build-app.sh` 的缺口，見 §2.79 旁邊那段），使用者資料夾也沒有。
所以這天才第一次在 Mac 上看到「有內容的新清單」。

**教訓**：兩個平台跑同一份 UI 程式碼時，「另一邊沒發生」**通常是還沒
測到，不是不會發生**。判準是去看那條路徑有沒有平台分支——這次
`pack_list.rs` 一個 `cfg` 都沒有。

### 2.80.4 兩條測試，都先看過紅燈

| 測試 | 守什麼 | 拿掉修正時 |
|---|---|---|
| `排版::表頭與資料列的右緣要對齊` | 內容表的表頭不比捲動區寬（700／900／1200 三種寬度） | 差 14px，紅 |
| `排版::清單有長說明時整頁不會比視窗寬` | 真的做一個說明很長的包給清單讀，整頁內容寬 ≤ 視窗 | 1456 vs 836，紅 |

兩條都在無視窗的 egui 裡把**整個分頁**排版，巢狀跟 `main.rs` 一樣
（中央面板 → 整頁捲動區 → 這一頁），連鎖反應跨幀所以各跑三幀。

第二條的紅燈檢查還順帶回答了一個問題：只拿掉 `set_max_width` 留著
`truncate` 不會紅——`truncate` 自己就截到可用寬度。留 `set_max_width`
是為了不讓說明欄吃光整列、把作者與版本擠出去。

### 2.80.5 教訓

- **「無視窗重現不了」不等於「沒有 bug」**，等於「測試的情境跟使用者
  的不一樣」。這次差在「清單是空的」。下一步不是再猜，是去真的 app
  埋 log——CLAUDE.md 那條「按鍵沒反應先埋 log」對排版一樣成立
- **兩支捲軸疊在一起的根因可能在另一張表**。退讓是相對於父容器的，
  父容器被撐寬就全部作廢。egui 的 Grid 裡 `ui.label` 不換行，**自由
  文字的欄一定要有上限**
- 猜錯一次就該停手改量。第一輪的猜測不是全錯（那兩個常數確實是估的、
  確實會被撐），但它不是這次的原因——修了沒好就該立刻換方法
