# 擴充包吃掉 30MB：字串池與官方包二進位化

> **狀態**：三步都完成並驗收（2026-09-15）。M1 從 36.2MB 降到 **9.0MB**。

## 怎麼發現的

2026-09-15 跑相容性測試 M1（記事本的記憶體增量），量到**私有增量
36.2MB**——而清單寫的預期是「十幾 MB 以內」，2026-09-02 首測是
**6.6MB**。

差了 5.5 倍，但**獨立行程仍然只有 6.1MB**（`bench_dict --hold`，
跟當年一模一樣）。詞庫的 mmap 共用沒壞。

### 排除法走過的三個彎路

值得記下來，因為前兩個推論都很合理但都是錯的：

1. **「是 Win11 記事本自己肥」**——它確實肥（空白 102MB），但對照組
   打臉：同一個行程裡切微軟注音只漲 **2.5MB**，通譯漲 **32.8MB**。
   而且那輪對照是使用者指定的順序（通譯先吃乾淨起點），對通譯最有利
2. **「是 bigram 或字頻表」**——2026-09-02 之後才加的，嫌疑最大。
   實測 `char_freq_map` 只有 0.6MB，`lm::load` 的 `.gram` 本體是 mmap
   **0.0MB**
3. **對照組本身第一次也做錯了**：記基準時記事本已經載著微軟輸入法
   （英文模式也會載 DLL），量到的 2.8MB 是「英文模式→中文模式」的差，
   不是「未載入→載入」。**使用者當場指出順序不對**，重做才拿到可比的
   數字。教訓：**對照組的基準要跟受測組同一個起點**，不然兩邊口徑不同

### 真正的根因

寫了 `spike_mem_layers` 逐層量 `preload`，一行就現形：

```
english::load                +    5.8 MB
dict::load_bopomofo          +    0.0 MB
dict::char_freq_map          +    0.6 MB
lm::load（.gram 本體）        +    0.0 MB
dict::load_japanese          +    0.1 MB
dict::load_connection        +    0.0 MB
learn::load（2911 條）        +    0.4 MB
  + 包「內建emoji」            +    0.7 MB
  + 包「內建符號」              +    0.2 MB
  + 包「台語」                 +   30.8 MB   ← 這裡
```

**台語包一包 30.8MB**，而檔案只有 1.65MB。

## 45 倍膨脹是怎麼來的

| 項目 | 數字 |
|---|---|
| 唯一詞數 | 82,373 |
| **這些詞的純文字總量** | **695 KB** |
| **實際佔用** | **30.8 MB** |
| 膨脹倍數 | **45 倍** |
| 華語詞（分組數） | 49,726 |
| 總詞次 | 181,990（每個詞平均被存 3.7 次） |

兩個原因疊加：

**一、每個 `String` 的固定成本遠大於內容。** 平均詞長 8.4 bytes，
而 `String` 的 header 就 24 bytes，加上堆配置的 overhead——**內容只佔
不到兩成**。

**二、雙向索引讓同一個詞被獨立配置好幾次。** 以「沙發／膨椅／胖椅」
為例：三個詞各當一次 key，**每個 key 各存一份完整的 group 複本**
→ 9 個 `String` 配置，內容重複。

結構在 `pack.rs` 的 `build_index`：

```rust
pub tw: HashMap<String, Vec<String>>,
```

**注意**：`Index` 的六層（`en`／`ja`／`zh`／`zh_long`／`tw`／`sym`）
**全都是這個模式**，只是其他層的資料量小所以沒被看見。修法要做在
`Index` 這一層，一次解決六層。

## 第二個問題：重建留碎片，而且不會回來

`pack::load` 是**整批重建**（`read` 全部 → `build_index` → `set_index`
換掉），不是增量更新。舊索引的配置還給配置器，但配置器留著不還 OS。

實測用**完全相同的包清單**重載五次（內容一模一樣，理論上不該多用一個
byte）：

| 重載次數 | 增量 | 累計 |
|---|---|---|
| 第 1 次 | +1.4 MB | 49.8 |
| 第 2 次 | 0.0 MB | 48.4 |
| 第 3 次 | **+3.2 MB** | 51.6 |
| 第 4 次 | +0.3 MB | 51.9 |
| 第 5 次 | **+5.2 MB** | **57.1** |

**五次什麼都沒改的重載多吃 8.6MB**，數字忽大忽小是配置器碎片的典型
特徵——不是穩定的洩漏，是重用失敗。

**使用者在設定頁每勾一次／取消一次包就觸發一次重建。** 勾來勾去試幾次，
記憶體就一路往上。

## 放大效應：每個宿主各一份

這 30.8MB **不是 mmap，不跨行程共用**。開了記事本、瀏覽器、VSCode、
Word 就是四份 = 123MB。

## 決定的方向（2026-09-15 與使用者確認）

**用「誰發布」切，不是用「多大」切**——界線清楚且穩定：

| 類型 | 走哪條 | 為什麼 |
|---|---|---|
| **官方發布的包**（含符號、emoji） | **mmap 二進位** | 我們打包、使用者不改，性質跟詞庫同一類 |
| **使用者自己寫的包** | 文字檔 ＋ **字串池** | 隨時要改，這是擴充包編輯器的前提 |

兩件事都要做：

### 一、字串池（先做，收益最大）

所有詞存進一個連續的 `String`（或 `Box<str>`），索引改存
`(offset, len)` 或直接用 `&'static str` 指進池子。

- **配置次數從 18 萬降到個位數**——同時解決膨脹與碎片
- 預估 30.8MB → **3～4MB**
- **不動 `Index::tw` 的雙向語意**。CLAUDE.md 警告過那五個 bug 是同一個
  根因（斷詞、反白位置、選不回中文），語意一動就全垮
- 六層通吃，使用者手寫的大包也自動受惠
- **是二進位化的前置**：池子的版面本身就接近檔案格式，之後要 mmap
  只是把池子換成映射的位元組，不會白做

### 二、官方包二進位化

- **原始文字檔留著當素材**（進版控或放 `tools/`），用 `gen_` 產出
  `.bin` 才放進發布——跟現在詞庫的做法一致
- 載入時優先找 `.bin`，沒有就讀文字檔（使用者包走這條）
- 跨行程共用：五個宿主從 5×N 變成 1×N

**已知代價**：官方包的發布流程多一道打包步驟。符號包內容常微調
（2026-09-07 才裁定過「同名符號要接起來」），文字檔改一行就好，
二進位要重跑 `gen_`。

## 三個實作決定（2026-09-15 使用者裁決）

### 1. 字串池用 `(offset, len)` 索引，不用 `&'static str`

```rust
struct Str { off: u32, len: u32 }
pub tw: HashMap<Str, Vec<Str>>,
```

**理由：一步到位。** `&'static str` 的好處是查詢端完全不用改，但
**之後換 mmap 時還要再改一次**——二進位檔裡存的本來就是 `(off, len)`。
既然已經決定官方包要二進位化，直接用整數對，池子換成映射的位元組時
查詢端不必再動。

代價是查詢端每個用到的地方都要透過池子切出 `&str`，這次要一併改。

### 2. `pack::load` 一併加上「內容沒變就不重建」

比對檔案的 mtime／雜湊，一樣就跳過整個 `build_index`。

**為什麼不等字串池做完再看**：字串池把配置次數降到個位數之後，碎片
**大概**會消失，但那是推測。而「設定頁勾來勾去累積 8.6MB」是使用者
真的會遇到的路徑，兩件事各自獨立、各自有價值——**不重建**連帶把
「勾一下卡 100ms」也解決了（實測每次重建 83～107ms）。

### 3. 二進位格式用簡單排序表，不用 darts

詞排序存好，查詢用二分搜尋。

**理由：擴充包只需要「精確查一個詞」**，不需要前綴搜尋——那是詞庫
（累加式切法要一路問前綴）才有的需求。darts 是為前綴搜尋設計的，
對這個用途是殺雞用牛刀，而且格式複雜、`gen_` 難寫難除錯。

排序表的另一個好處：**版面幾乎就是字串池本身**（一段排序好的詞 ＋
一張 `(off, len)` 表），跟決定 1 天然對齊。

## 第一步（字串池）已完成 2026-09-15

**台語包 30.8MB → 4.8MB（−84%）**，三層疊加，每層都實測過：

| 步驟 | 台語包 | 做了什麼 |
|---|---|---|
| 原本 | 30.8 MB | `HashMap<String, Vec<String>>` |
| ① value 進池子 | 18.1 MB | 每個詞只配置一次，value 存 `(off,len)` |
| ② key 也進池子 | 9.7 MB | 改**排序表＋二分搜尋**，key 不再各自配置 |
| ③ group 攤平 | **4.8 MB** | 82373 個 `Vec` 的 header 就 8MB，攤平成一條 |

連帶的改善：

- **重載五次的碎片從 +8.6MB 降到 +1.9MB**（第二步的「不重建」還沒做）
- 「常用符號 +4.2MB」「資訊技術 +5.7MB」那種碎片假象消失（現在是 +0.7／+0.0）
- 合計私有 38.8MB → 13.4MB

**②的取捨**：查詢從雜湊 O(1) 變成二分搜尋 O(log n)，9 萬筆約 17 次
比較。段選單斷詞才會查（不是打字熱路徑），漏斗 1322 通過無退步。

**現在整層只剩三塊連續記憶體**——字串池、排序表、攤平的說法表。
這正是二進位檔的版面，第三步 dump 出去就是檔案。

### 踩到的兩件事

- **key 不能直接換成指標**：第一版想把 `HashMap` 的 key 也換成 `Str`，
  但查詢要 `.get(word)` 拿 `&str` 比對，而指標要先知道位置——雞生蛋。
  **排序表繞開了這個問題**：二分搜尋時才把指標還原成 `&str` 比字面
- **`Vec<Str>` 本身也是成本**：②做完剩 9.7MB 時以為是雜湊表 overhead，
  實際是 82373 個各自獨立的 `Vec`（每個 24 bytes header ＋ 堆配置）。
  攤平之後又省 5MB

## 第二步（不重建）已完成 2026-09-15

**重載五次：+1.9MB／每次 90ms → +0.0MB／每次 0ms。**

`load` 開頭比對指紋，一樣就整個跳過（不讀檔、不建索引、不換表）。

**指紋是 `(路徑, 大小, mtime)` 不是內容雜湊**：台語包 1.65MB，每次
勾選都重讀重算是白費；而要防的是「使用者改了包卻沒生效」，編輯器
存檔一定會動到 mtime，這對那件事夠靈敏。

**已知的漏判**：同一秒內把檔案改成完全相同的大小。代價是「改了沒
生效，重開設定頁才看到」——比起每次都重建 90ms＋漏記憶體，這個取捨
划算。

**跳過比重建更安全**：不換表就沒有「換的瞬間別人正在查、查到半套」
的問題（那是 `session::segmenu` 測試裡 `OnceLock` 在防的事）。

測試 `改了包要重新載入` 守著最危險的失敗模式——判錯的話**不會報錯、
沒有任何跡象**，使用者只覺得「改了沒反應」。

## 第三步（官方包二進位化）：spike 過了 2026-09-15

**要驗的只有一件事**：mmap 的位元組上**直接查得動嗎**。載入時若要再
轉一份到堆上（`String`／`Vec`／`HashMap`），共用就白做了——共用的頁
沒人碰，私有那份照樣每個宿主一份。

`spike_pack_bin` 拿台語包產一份 `.bin`、映射、逐筆比對：

| | 單一行程私有 | 五個行程私有總計 |
|---|---|---|
| 文字檔（現在） | 5.29 MB | **27.7 MB** |
| **mmap `.bin`** | **0.05 MB** | **3.5 MB** |

- **82373 個詞逐筆比對全部一致**（不抽樣，21ms 查完一輪）
- 檔案 4.39MB，dump 54ms
- 查完一輪之後私有**再 +0.00MB**——頁進了工作集但不是私有配置

**工作集看不出差別**（46.0 vs 42.6MB），因為 mmap 的頁被哪個行程碰過
就計入哪個行程的工作集，五個行程重複計同一批實體頁。**要看私有**，
那才是真正各自佔掉的實體記憶體。

### 版面（spike 驗過的）

```
魔術字 "TSNGPACK" 8 ＋ 版本 4 ＋ 詞數 4 ＋ 攤平數 4 ＋ 池子長度 4
排序表  n × 16 bytes   (key_off, key_len, span_at, span_len)
說法表  m × 8  bytes   (off, len)
池子    UTF-8，連續一塊
```

全部是小端 `u32`，**直接在映射的位元組上切出來讀**，不反序列化成任何
結構。這正是 `Index` 現在那三塊連續記憶體的樣子——第一步的「一步到位」
兌現了。

### spike 踩到的兩件事（正式實作要避開）

- **長度檢查要求相等，不能只擋「太小」**。第一版 table 實際每項寫了
  16 bytes 而讀取端算 12，檔案大了 329KB 才現形；若當初只擋太小，
  會安靜地讀到錯位的資料
- **不能「清掉索引再重載」來取比對基準**：第二步的指紋機制看到
  「路徑／大小／mtime 沒變」會整個跳過，重載回來的是空索引。要在
  清掉之前先把答案抄一份

## 第三步（官方包二進位化）實作 2026-09-15

spike 驗過方向之後正式做。**四件事**，前兩件是前置：

### 1. 六層全部改成排序表

原本只有 `tw` 是「字串池＋排序表」，其他五層還是 `HashMap<String,…>`
——而 **`HashMap` 沒辦法在映射的位元組上直接查**，這是 mmap 的硬前提。

六層統一成一個 `Table`（`Vec<(Str, Span)>`），值一律是「指進共用
`flat` 的一段範圍」：`en` 長度 0（只有鍵）、`ja`／`zh`／`zh_long`
長度 1、`sym`／`tw` 是一組。**一種形狀通吃**，省掉六套版面。

記憶體沒退步（台語 4.6MB，改造前 4.8MB），重載五次仍是 +0.0MB。

**意外的收穫**：符號稽核的 `max_by_key` 原本走 `HashMap`，平手時挑
哪個是隨機的；排序表讓它變成**穩定的**。

### 2. `core/src/pack_bin.rs`：格式模組

版面見該檔的 doc。要點：

- **檔頭也進檔案**。`# name:` / `# license:` 那幾行**不是說明文字，
  是授權的一部分**——台語包的檔頭載明 CC BY-SA 4.0 要求的姓名標示，
  拿掉就違反授權。不存的話設定頁會顯示成「沒有名稱、沒有授權」，
  看起來像作者偷懶沒填，跟 BOM 那個洞（§2.49.3）同樣的症狀
- 檔頭存成**「名稱 → 值」的清單**不是固定欄位，之後 `Meta` 加欄位
  時舊的 `.bin` 仍然讀得動，跟 `parse_meta` 的處理方式一致

### 3. 載入路徑：`.bin` 優先於同名 `.txt`

**官方包不併進 `Index` 的六張表，另外掛一層**（`Index::bins`）。

併進去就得把映射的內容抄一份到池子裡——那正是 mmap 要避免的事。
分開放，查詢時兩邊各問一次，官方包的位元組從頭到尾沒被複製過。

**順序**：使用者的包先問，官方包後問——跟同名檔案「使用者的優先」
一致。所有呼叫端完全不必改，合併發生在 `Index` 內部。

### 4. 三個「只認 `.txt`」的洞

改完載入才發現的，每一個都會讓官方包**在設定頁完全看不到**：

- `available()`（列清單）只掃 `.txt` → 使用者無從勾選
- `info()`（顯示名稱／版本／授權／條數）只讀 `.txt`
- `stamp()`（判斷「包被改過了要重載」）只看 `.txt` 的 mtime

**找檔規則抽成一支 `find_pack`**，`read`／`fingerprint`／`info`／
`stamp` 全部共用——兩邊的規則一漂掉，指紋就會對不上實際載入的檔案，
症狀是「改了包沒生效」而且完全沒有跡象。

### 5. `gen_pack_bin`：產檔工具

`cargo run --release -p ime-core --bin gen_pack_bin -- 台語`

**收路徑不收包名**——`find_pack` 的規則是「`.bin` 優先」，產檔端拿
包名去找會**找到上一次自己產的 `.bin`**，變成拿產物當原料。

**走原路產**（`read_pack` ＋ `parse` ＋ `build_index` ＋ 倒出來），
不在工具端重寫一份建表邏輯。注音符號轉按鍵、字數與音節數的分流、
台語雙向索引、符號同名合併全在 `build_index` 裡，重寫一定會漂掉，
而**漂掉的症狀是「`.bin` 跟 `.txt` 查出不一樣的東西」，不會有任何
編譯錯誤或測試失敗**。

|---|---|---|
| 台語包私有 | 4.8 MB | **0.0 MB** |
| 載入耗時 | 104 ms | **2 ms** |

- 端對端測試 `二進位包跟文字包查出一樣的東西` 釘住六層 ＋ 檔頭 ＋ 清單

## 實打抓到的：TAB 完全沒反應（熱路徑旗標沒看到官方包）

**`cargo test` 全過、漏斗零退步，但使用者按 TAB 開不出段選單。**

`set_index` 設三個熱路徑旗標時用的是：

```rust
let has_tw = !new.tw.is_empty();   // ← 只看使用者文字包那張表
```

而官方包在 `Index::bins` 裡，**直接摸欄位看不到它們**。結果是
`tw_says` 查得到資料（它會問 `bins`），但 `HAS_TW` 是 false，
而平台層靠這個旗標決定要不要開段選單。

修法是一律走查詢方法（`tw_is_empty()`／`sym_is_empty()`，它們問兩邊）。

### 為什麼測試與漏斗都抓不到

**它們都不經過旗標**。測試直接呼叫 `index().tw_says(…)`，漏斗走的是
切點與選字——`any_tw()` 只有平台層在問。這正是 CLAUDE.md 那條
「錯在平台層時測資鎖不到」的實例。

### 怎麼找到的

**埋 log 五分鐘，不要讀程式碼猜。** 在那個守門判斷前後各印一行：

```
[段選單] TAB：lock=Some(Bopomofo) any_tw=false taigi_ready=false → 擋掉
```

一行就指出是 `any_tw` 而不是 `lock`。查表、分派、鎖定模式全對，錯在
旗標——讀程式碼很難看出來。

### 釘住它

端對端測試加了三行斷言（`any()`／`any_tw()`／`any_sym()`）。**驗證過
它真的抓得到**：把修正還原成舊寫法，測試就紅在「有台語就要亮
`any_tw()`——段選單靠它」。

**教訓**：`Index` 的欄位是私有的有理由——`bins` 是後來加的一層，
任何「直接摸欄位」的地方都會漏掉官方包。同一個模組裡摸得到不代表
該摸。

## 順手抓到的一個既有 bug

`gen_pack_bin` 產台語包時警告「檔頭沒有 `license` 欄」——查下去發現
**台語包的授權聲明從來沒被程式讀到過**。

檔頭寫的是 `# 授權：CC BY-SA 4.0`（**全形冒號＋中文欄名**），而
`parse_meta` 是 `split_once(':')` 配固定的英文鍵名。那三行整個被忽略，
設定頁一直顯示「沒有授權」。

**CC BY-SA 的姓名標示是授權條件不是說明文字**，掉了就不能散布。
已補成正式欄位（`# license:`／`# author:`／`# homepage:`），中文說明
保留在下面給人看。

**二進位化只是讓它現形**——這個洞在文字檔時代就存在，只是沒人發現。
