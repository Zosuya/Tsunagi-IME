# 台語怎麼接進引擎：包層覆蓋、tw 層被 revert，最後段選單＋國字雙向詞表

「台語能不能當第四種語言接進主輸入法」試了三條路。第一條**直接用現成的
領域包層**——管線是通的，但包是**覆蓋不是新增**，打「謝謝」會得到「感恩」，
而且 `build_index` 的「字數要等於音節數」砍掉 35.5% 的詞。第二條做了
**獨立的 `tw` 層**（補充而非取代），躲開了包層那條路，卻漏了**學習層這個
後門**——選兩次台語詞就永久取代華語，整批 revert。第三條走**段選單**：
台語只是「注音那一段的另一份詞庫」，不動 `compose`、不進學習層；再把詞表
的鍵從注音改成**國字**、登記改成**雙向**，一口氣刪掉四個補丁。

## 試過的路

### 一、當第四種語言：包是覆蓋不是新增（原 2.64.10）

使用者問待決事項 1 的 (c) 選項。**答案：架構上接得上，一行引擎程式碼都不用改
就能載進去；但直接用領域包那一層的結果是錯的，得先解一個設計衝突。**

工具：`core/src/bin/spike_taigi_pack.rs`。把 [[台語三個 spike：覆蓋率 72%，一對多比預期嚴重]] 產的資料做成一個
真正的領域包（[[領域包：從「合併進詞庫」改成「獨立的一層」]] 那一層），載進引擎、送真的按鍵進去看候選。

**好消息：管線是通的**

領域包本來就是為「使用者自己加詞」設計的獨立一層，中文那條路
（`is_bopomofo_word` → `rank.rs` 的 `claimed`）連切點都吃得到。台語詞掛在
華語詞的注音下面，結構上完全吻合——**不需要第四個語言引擎，不需要動
`language.rs`，不需要新的狀態機**。

**壞消息：包是「覆蓋」不是「新增」**

實測結果，載入 5,336 條之後：

```
謝謝（vu,4vu,4）→ 感恩   ★候選變了   新增: 感
小氣（vul3fu4）→ 凍霜   ★候選變了   新增: 凍
```

**想打「謝謝」會得到「感恩」。**這不是 bug，正是 [[領域包：從「合併進詞庫」改成「獨立的一層」]] 2.17.5 的設計：層順序是
學習 → 領域包 → 靜態詞庫，包排在靜態詞庫前面，`word_for` 找到就回傳。
對「我要加 hololive 這個詞」那個用途完全正確，對台語卻是災難——
**台語詞應該是「多一個選擇」，不是「取代原本的詞」**。

所以 (c) 不是零成本。要嘛給包層加一個「補充而非覆蓋」的模式，要嘛台語走
自己的一層。這是實作前必須先決定的事，**待決事項 1 選 (c) 的話要一併決定它**。

**另外兩個卡關的地方（都在 `build_index`）**

| 關卡 | 為什麼卡 | 損失 |
|---|---|---|
| 注音符號**不能有空白** | `symbols_to_keys` 逐字元掃描，靠「角色沒往後走」判音節邊界，空白直接查表失敗 | 第一版全滅（0 條），改成 `ㄗㄌㄧㄠˋㄎㄨˋ` 這種連寫就好 |
| **字數要等於音節數** | 選詞層一格填一個字（`apply_word_context`），對不上就丟掉 | **35.5%**——台語詞跟華語詞字數本來就不一樣（「以後」2 音節 vs「落尾手」3 字） |

兩關過完，11,449 行只有 **5,336 條（46.6%）**進得了索引。字數那一關是
**結構性的**，不是資料清洗能解的——台語跟華語不是一字對一字的關係。

**這件事把待決事項 1 的三個選項重新排了序**

- (c) 只當第四種語言：**接得上但要先解覆蓋問題**，而且字數限制會砍掉三分之一
  的詞。原本看起來最省事的選項，實際上要動到選詞層
- (b) 編譯開關切出獨立產品：**沒有被這次的發現削弱**——獨立產品可以自己決定
  選詞層怎麼填，不必遷就通譯的「一格一字」
- (a) 分開 repo：不變，仍然要維護兩份平台層

### 二、(b) 編譯開關：查證下來比原本估的樂觀（原 2.64.11）

使用者接著問 (b)。**結論：比原本估的省事——三個「要先付的成本」有兩個
其實已經付過了，而「精簡版」的開關執行期就能用，不必等編譯期。**

工具：`core/src/bin/spike_taigi_slim.rs`。

**一、語言開關是現成的，不用做**

`config::Engines`（`core/src/config.rs`）本來就是「啟用哪些語言引擎」的
設定，`Input::with_engines` 吃它。實測三種組態打同一批按鍵：

```
按鍵         全開          關日文        鎖注音
su3cl3       注:su3cl3     注:su3cl3     注:su3cl3      （你好）
sushi        日:sushi      英:sushi      （空）          ← 關鍵
```

`sushi` 在全開時被判成日文，**關掉日文之後自動退成英文 passthrough**——
正是精簡版該有的行為，一行程式碼都沒改。

所以「編譯開關切出獨立變體」**功能面已經到位**；編譯開關
要處理的只剩「不要把日文資料打包進去」，那是安裝腳本的事，不是引擎的事。

**二、單注音本來就繞過切點引擎**

`Input::for_lock(Some(Bopomofo))` 走的是 `BopomofoInput`，切段用
`single_language_segments`——只把標點切出來，**完全不進 `cutpoint/`**。
「鎖定注音是獨立的輸入路徑」這次確認它在執行期真的是獨立的。

`cutpoint/`＋`romaji/`＋`english`＋`language` 實測 7,180 行（先前記
7,099，差在期間的改動），精簡版確實走不到。

**三、品牌收攏：比想像中集中**

原本說「名字／GUID／圖示／安裝路徑散在各處要先收攏」。實地查了：

| 東西 | 在哪 | 要動幾處 |
|---|---|---|
| CLSID／Profile GUID／顯示名 | `platform/windows/src/guids.rs` | **一個檔、四個常數** |
| 顯示名（重複寫死） | `lang_bar.rs` 2 處、`settings/main.rs` 1 處 | 3 處，該改成引用 `guids.rs` |
| 資料夾名 | `config.rs` 的 `APP_DIR` 一個常數 | 1 處（其餘都是註解） |
| 安裝程式品牌 | `installer/tsunagi.iss` | **已經用 `#define` 集中**（`AppName`／`Publisher`／`AppUrl`） |

`AppId`（`{01BC8BB0-…}`）那行的註解已經寫明「一旦發布就不能改」——
兩個產品同機共存需要兩組，**現在還沒發布，是最便宜的時機**。

**四、所以 (b) 剩下的真正工作**

1. 三處寫死的顯示名改成引用 `guids.rs`（小事，但不做就會漏改）
2. 第二組 GUID／`AppId`／`APP_DIR`（新的常數，不是重構）
3. 安裝腳本吃參數決定帶不帶日文資料——**這是唯一有份量的一項**
4. 測試矩陣變兩倍（對策是把開關數壓到最少）

**資料大小的帳**（安裝包實際帶的 `.bin`，不含原始 txt）：

| | 大小 |
|---|---|
| `dict_zh.bin`＋`zh_bigram.gram` | 13.6 MB |
| `connection.bin`（日文） | 13.6 MB |
| `dict_ja.bin`（日文，建置時產） | 未量，mozc 原始 40 MB 文字 |
| `en_50k.txt` | 0.6 MB |

精簡版省掉的是日文那兩個檔，**至少一半的安裝包體積**。

**跟 (c) 比**：(c) 卡在選詞層的「一格一字」，要動核心；(b) 卡在安裝腳本，
**不動核心**。這次查證讓兩者的差距更明顯。

### 三、`tw` 層：補充而非取代（原 2.64.12）

使用者裁定：**先做 (c)**、一對多**全收排在華語候選之後**、標示方式先做
能跑的。(a) 分開 repo 排除。

**做法：領域包多一張表**

`zh` 與 `tw` 的鍵是同一種東西（華語詞的注音），語意相反：

| | 語意 | 打「謝謝」的結果 |
|---|---|---|
| `zh` | **取代**——查到就是那個詞 | 「感恩」（使用者失去打華語的能力） |
| `tw` | **補充**——多一個選擇 | 「謝謝」，「感恩」在候選裡等人選 |

**走的是 `\星\` 那條路**（`compose::merge_taigi`）：把連續的注音格併成
一格，候選算好放進 `Slot::cands`。這是既有機制，符號格早就在用。

**關鍵：不套用 `zh` 的字數限制**——`tw` 整段換掉、不逐格填，字數自然不必
相等，所以第一節量到的那 35.5% 不再是損失。

**實測**（7,402 條載入後）

```
謝謝 → 候選: 謝謝 seh-seh 感恩
以後 → 候選: 以後 而後 尾手 落尾 後來 落尾手 將來 路尾
小氣 → 候選: 小氣 雞仔腸 鳥仔肚 凍霜 菝仔屎 㾀屎 譴相 鄙厘 貓𡳞
漂亮 → 候選: 漂亮 媠噹噹 媠氣 鑠奅 飄撇
```

**每一行第一個都是華語詞**，送出的文字全部維持原樣。

**回歸**：漏斗 1280 → 1280 持平（沒有台語包時完全不影響既有行為）、
`bench_typing` p99 8.4ms（改動前 8.5ms，誤差內）。

**踩到的坑：測試被平行跑洗掉**

`pack::INDEX` 是行程全域的，靠「載包」來測會被同時跑的其他測試換掉，
症狀是單獨跑會過、全部跑會掛。測資檔第一行就寫了這件事，還是踩到。
修法是把台語表當參數傳（`merge_taigi_with`），測試不碰全域狀態。

**當時還沒做的**

- **候選視窗不標示哪個是台語詞**（使用者裁定先做能跑的）
- **設定頁沒有台語包的入口**，要自己把檔案放進 `packs\`
- **`tw` 不影響切點**（`zh` 會，透過 `claimed`）。台語詞的注音就是華語詞的
  注音，切點本來就切得對
- 產包工具 `spike_taigi_cover --pack` 仍是 spike，不是正式的 `gen_*`

### 四、`tw` 層被 revert：台語詞從學習層繞回來取代華語詞（原 2.64.13／2.64.14）

**CLAUDE.md 的規矩救了一次。**「新功能至少要與既有功能同時存在的情境下
測試一次」——上一節只測了「打一個詞，候選對不對」，那是功能單獨存在
的樣子。補測互動之後找到一個嚴重的洞。

工具：`core/src/bin/spike_taigi_mix.rs`。

**洞：選兩次台語詞，華語就永久打不出來了**

```
選兩次台語的「感恩」（LEARNED = 2）
  → word_for("vu,4vu,4") 變成「感恩」
  → 打「謝謝」的注音永遠出「感恩」
  → 關掉台語包也救不回來（污染已經寫進 learned.txt）
```

原因：`learn::record` 拿 `(keys, text)` 去記，而台語格的 `keys` 是**華語詞
的注音**、`text` 是**台語詞**。學習層排在領域包前面，一旦記進去就凌駕一切。

**這正是 `tw` 那一層費工避開的「取代」，從後門繞回來了。** 第一節擋住
了包層那條路，卻沒想到學習層是同一件事的另一個入口。

**當時的修法：`Slot` 多一個 `alt_lang`**

標記「這一格是另一種語言的說法，不是這串注音的正解」。`record` 分段時
讓它自成一段並整段跳過。

**為什麼不能用 `cands.is_some()` 代替**：符號格也有 `cands`，而符號的學習
是**刻意要的**（選過 `LEARNED` 次的符號變預設，見 `merge_symbols`）。兩者
的差別是語意不是結構。

**分段邊界不是多餘的**：不隔開的話「你好今天」會被當成同一段，整段被丟掉
——連累「今天」的選字也學不到。測試鎖住這條。

**其餘互動情境實測都正常**

| 情境 | 結果 |
|---|---|
| 台語段＋英文（`你好hello`） | 2 格，正常 |
| 台語段＋日文（`你好sushi`） | 2 格，`sushi` 照樣是「寿司」 |
| 台語段＋標點 | 標點自成一格，正常 |
| 長句夾台語（`你好今天`） | 3 格，後面的注音照常逐格選字 |
| 先選字再併格 | `picked` 的格子跳過，不併 |
| 兩個台語詞相連 | 各自成格 |

**還沒解的：格數變少**——`merge_taigi` 把「你 好」兩格併成「你好」一格，
而游標移動、倒退鍵是**按格**走的，使用者的體感會變成「按一次倒退鍵刪掉
兩個字」。

**整批 revert（commit 518289f）**：`tw` 層與上面的學習層修法在 2026-09-08
被整批撤掉，理由是**互動模型不對**——[[台語輸入法：三種解讀、資料盤點與產品形態]]
待決事項 2 在「鎖定模式」與「混進候選」之間沒定案，而實作走了後者，
候選變擠。**段選單是第三條路**，使用者裁定只走它。

#### 為什麼段選單不必那 209 行

`tw` 層是給**選字候選**用的：`Slot` 多一個欄位、`compose` 多一段合併
邏輯，都是為了「打字打到一半、選字時多一個台語選項」。

段選單的候選是**自己窮舉的**（起點 × 長度 × 語言），台語只是「注音
那一段的另一份詞庫」——查一次 `pack::index().tw` 就好，不動 `compose`。

#### 資料重建（原本的不見了）

台語資料**從來沒進過版控**（只在 `%APPDATA%`），而那份已經不在。
重新從 ChhoeTaigi 下載跑一次，數字跟分支上記的完全一致：

| | 條數 | 比例 |
|---|---|---|
| 純漢字華語詞 | 19042 | — |
| **可靠（引擎打得回原詞）** | **9126** | **72.0%** |
| 產出的包 | 11919 行 | 2297 個鍵對多個詞 |

取得方式寫進 `tools/取台語資料.md`——**資料不進版控**（2.5MB 外部檔
而且上游會更新，跟 `en_50k` 同一條規矩）。

#### 三道防線

| 防線 | 為什麼 |
|---|---|
| **獨立的 `Packs::tw` / `Index::tw`** | 併進 `zh` 會直接取代華語（第一節量過） |
| **獨立的 `any_tw()` 旗標** | 台語不走查詞熱路徑，只裝台語包的人不該白付雜湊（理由同 `any_sym`） |
| **不進學習層** | 上面那個洞。`learn::record` 只記 `picked` 的格，而台語那格不設 `picked`——**結構上就不會被記** |

第三道跟先前的修法不同：那時要在 `Slot` 加欄位再讓學習層跳過，
現在是「本來就不會走到那條路」。段選單的選擇存在 `Session::seg_taigi`
（`(段的按鍵, 台語詞)`），套用時**整段換掉**——台語詞與華語詞 35.5%
字數不同，逐格填不進去。

## 根因：詞表做成單向的——五個 bug 同一件事（原 2.64.15）

> **這一節的重點是最後那個教訓**：我連續修了五個實測回報的 bug，每個
> 都修對了症狀，但根因是同一個設計錯誤——而且是使用者一句話點破的。

### 一、資料源：iTaigi → 台文華文線頂辭典

上一節那份包來自 **iTaigi 華台對照典**（19046 筆，CC0），問題是
**收得太少**：使用者實測「沙發」——台語講「膨椅」——那份**根本沒收**。
而且眾包資料有錯條目：第 427 筆把「出頭天」的華語詞欄填成「你好」，
所以打 `su3cl3` 第一個台語候選就是「出頭天」。

同一個 ChhoeTaigi repo 底下換成 **台文華文線頂辭典**（91339 筆，
鄭良偉／楊允言兩位教授）：

| | iTaigi | 台華線頂 |
|---|---|---|
| 原始筆數 | 19046 | **91339** |
| 授權 | CC0 | **CC BY-SA 4.0** |
| 「沙發→膨椅」 | ✗ | ✓ |

**教育部台語辭典不能用**：它的用字最準（官方審訂，「跤踏車」而非
「腳踏車」、「媠」而非 `suí`），但授權是 **CC BY-ND（禁止改作）**
——建包要拆欄、拆頓號、重排，每一項都是改作。量過的差異記在
`tools/取台語資料.md`：教育部獨有 6999 個詞（多是地名、機構名、
專門詞），但**兩份都收的 16840 個裡有 10641 個說法不同**，教育部
有 7063 個台華線頂給不出的說法。**真要用時先查原始網站現在標什麼
授權**——公務機關的資料常另有政府開放授權，跟 ChhoeTaigi 轉載時
標的未必相同。

### 二、鍵從注音改成國字

舊版包是 `tw <TAB> ㄕㄚㄈㄚ <TAB> 膨椅`，段選單拿**按鍵**去查。
按鍵有歧義：`z8 vu,4` 同時是「發謝」與「發洩」，所以
「這才是我們要的沙發謝謝」會冒出**六個跨詞邊界的誤配**（出氣／發洩／
解氣／消解／消敁／敁氣）——「發」跟「謝」跨在「沙發」和「謝謝」中間，
畫面上根本沒相鄰過。16 個候選裡 6 個是垃圾。

**組字區已經有國字了**，歧義在選字階段就解掉了。改成拿國字查、走
**最大匹配斷詞**：從左往右掃，切過的不重複用，「沙發」佔掉兩格之後
不會回頭試「發謝」。同一句現在切出 5 個詞，誤配 0 個。

附帶好處：不必轉注音就不會被多音字卡住。舊版要「整詞查得到注音」
才收，那道關卡丟掉 20%——**條目 33149 → 49726**。

反白單位也跟著從「段」改成「詞」（使用者裁定）：`←→` 跳詞（跳過
沒有台語說法的位置）、`Shift+←→` 調寬度（「我們」↔「我」，**起點
固定只調長度**——要選「們」用 `←→` 跳過去，不必再加一組推左邊界的鍵）。

### 三、五個 bug，同一個根因

換成國字之後，使用者連續回報五個問題。**每一個我都修對了症狀，
但每一個都是同一件事的不同面向**：

| 回報 | 當時的修法 |
|---|---|
| 選字設定在台語 TAB 沒生效 | 改 `seg_done` 的判準 |
| 台語選不回中文 | 定案過的位置拿按鍵重算華語 |
| 按 TAB 選不回去 | 斷詞認出定案過的位置 |
| 最後選完沒跳出去又回到第一個 | 加旗標記「走完了」 |
| 選回中文沒觸發自動跳下一個 | 位置要在改紀錄前先問 |

根因是**詞表做成單向的**：拿畫面上的字查華語那一邊。畫面變成
「膨椅」就查不到，所以才需要「記住原本是什麼」——而那份紀錄又讓
斷詞、往下跳、走完判斷全部失準。

使用者的原話點破了它：

> 照理說他不是互相對應的嗎，你選的詞可以用同樣的方式選回原本的
> 那不是詞表在做的是嗎

**「沙發」跟「膨椅」是同一個東西的兩種說法，地位相等**——就像選字裡
「好」跟「郝」是同一個音的兩個字。選字從來不記「你原本選的是哪個」，
它只知道「這個音對應這些字」。

改成建索引時**雙向登記**：

```text
沙發 → [沙發, 膨椅, 胖椅]
膨椅 → [沙發, 膨椅, 胖椅]   ← 同一組
胖椅 → [沙發, 膨椅, 胖椅]
```

第一個元素固定是華語詞。四個補丁直接刪掉（`tw_cursor_zh`、斷詞裡
認定案位置那段、候選分兩批組裝、位置提前算的特殊處理），`TwWord`
的 `zh`／`tw` 兩欄併成 `says`——不分「原本的」跟「換過的」。

**教訓**：五輪都在補症狀，我應該在第二次就停下來重新看設計。判準
很簡單——**同一塊地方連續冒出性質相似的 bug，那是設計在說話，不是
巧合**。

### 四、重寫時發現的（跟雙向無關）

`apply_taigi` 是**整段換掉**的（「沙發」兩格併成「膨椅」一格，台語詞
與華語詞 35.5% 字數不同，逐格填不進去），但**按鍵留在原本的格子裡**。
所以斷詞遇到「一格裝著一整個詞」要把後面被清空的格也涵蓋進範圍，
否則定案時只拿到半截按鍵，換不回去。

### 五、選字的三個 Enter 設定要接上

段選單跟選字**共用同一個設定**（使用者裁定），但三個都沒接對：

- **`seg_done` 算的是「段」**——鎖定注音時整串就是一段，第一次 Enter
  就讓 `seg_locked` 追上 `seg_count()`（都是 1），選單立刻關掉
- **「選完離開選字」沒退出**——只設反白位置，從來不標「走完了」。
  選字那層的語意很明確：`confirm_cand_with(false)` 直接 `exit_select`
- **「最後一字選完直接送出」完全沒接**
