# 準確率：文字命中從 49% 到 89%

### 起點：錯字率根本沒有被量過

`check_incremental` 量的是**切點**——「哪一段是什麼語言」對不對。
但切對了不代表顯示的字對：`u10` 切成注音之後「一班」還是「一般」是
選詞層的事，而那一層此前沒有任何工具在量。

新增的工具，這一節的所有數字都出自它們：

| 工具 | 量什麼 |
|---|---|
| `check_compose` | 文字正確率：切法第一名 → `compose` → 跟文字期望比。失分拆成切法錯／空白差／選字錯，另報字元級錯字率與**依語言拆的錯字率** |
| `check_testdata` | 測資稽核：文字期望與按鍵期望對不對得上 |
| `bopomofo_words`／`bopomofo_sentences` | 新測資，見下方「測資的兩個盲點」 |

### 走過的路

| 改動 | 文字命中 |
|---|---|
| 起點（570 句） | 49% |
| 空白在 `Auto` 下一律半形 | 76% |
| 中日文標點改查表（`。` 不再是 `．`） | 77% |
| 修 47 列文字與按鍵對不上的測資 | 81% |
| 同音詞改用詞頻（`word_freq.txt`） | 84% |
| 接上偏好表 `priority.txt` | 86% |
| 切點：組合式 `covered` ＋ 短假名碎片懲罰 | 86%（測資擴到 720 句） |
| 寬容-列舉 | **88%**（632/720） |

依語言的錯字率：**注音 2.2%、日文 9.4%、英文 0%**。

### 一、`claimed` 對注音問錯了問題

```rust
Bopomofo => is_bopomofo_word(keys)          // 整段必須是「一個詞」
Romaji   => n >= 2 && validity == Valid     // 合法就算
```

但切點引擎切的是**語言不是詞**（§2.7），
一個注音段可以是一整句中文——那當然不是單一詞條，`covered` 就是 0。
於是中文越長越必輸，任何兩個字母的合法假名都能贏：

```text
注:ji3rup␣wu0␣…（我今天早上去公司開會）  covered=0
注:ji3 | 日:ru | 注:p␣wu0␣…              covered=2  ← 勝出
```

實測純中文長句有 **42% 被切壞**（50 句裡 21 句），而且正解都排第 2 名
（15/21）——典型的「差一個判準」而不是候選生不出來。

改成**組合式**：最長匹配拆成詞再加總，跟選詞層同一套做法。
實作要注意**切原字串不要接字串**——`concat()` 版本 p99 從 12.4 衝到
17.9ms（預算 16ms），改成切片後回到 13.7ms。

同時補一條**短假名碎片**懲罰，補上日文缺的對稱性（英文有三條懲罰、
日文原本一條都沒有）。門檻 12 字元把碎片（2～3）與活用形句子
（28～34）分開。**不能用「不在詞典裡」當判準**——`ru`／`au`／`su`
這些單假名 mozc 都收了。

結果：切法錯 75 → 40，長句組 19/50 → 32/50、錯字率 16.4% → 5.0%，
切點第一名 516 → 531，沒有任何一組測資退步。

### 二、同音詞：字頻不是詞頻

`BPMFMappings.txt` 沒有詞頻欄位，同音詞誰勝出原本用「組成字的最低
**字**頻」當代理。那個代理會錯——「班」字頻 841 比「般」751 高，
於是 `u 10 ` 給「一班」；「策士」的最低字頻比「測試」高，於是
`hk4g4` 給「策士」。

改查 `word_freq.txt`（19 萬詞）。兩張表**單位不同不能混算**，所以分層：
詞頻表收錄的一律贏過沒收錄的，同層之內才比數值。

**執行期成本為零**——同音詞的勝負本來就是載入時決定的，查詢路徑一行
沒動。詞條數 132236 不變（常駐記憶體不增加），注音詞庫載入
216→300ms 且是背景做的。

接著把 `priority.txt`（91 條人工排序）接回來——那個檔一直在版控裡，
但重寫 Phase 1/2 時沒接，`core/src/` 完全沒有引用它。它**凌駕詞頻**，
而且**可以指定詞庫沒收的詞**：「這部」「這不」兩個都不在
`BPMFMappings` 裡，打 `5k41j4` 的「這不」是逐字選出來的，不補進來
怎麼調排序都出不來。

### 三、被實測否決：維特比 DP ＋ 長度先驗

照 libchewing 的做法把選詞層的貪婪最長匹配改成維特比 DP（各段 log
機率相加＋長度先驗）。**沒有比較好**：

| 版本 | 注音段正確 | 長句組錯字率 |
|---|---|---|
| 貪婪最長匹配（原版） | 522/540 | **16.4%** |
| DP ＋ 我們的長度先驗 | 521/540 | 18.1% |
| DP ＋ libchewing 先驗 | 522/540 | 18.1% |
| DP 不加長度先驗 | 521/540 | 18.1% |

根因是**兩份資料的性質不同**。從各自的資料算出來的長度先驗：

```text
單字 -0.73   雙字 -0.79   ← 我們的 word_freq（語料詞頻）
單字 -1.52   雙字 -0.42   ← libchewing 的 tsi.src（為輸入法調過的詞典）
```

我們的單字累積量太大（「的」55500015），算出來的先驗**根本沒有分詞
壓力**——單字反而比雙字便宜。套 libchewing 的常數只能追平貪婪版。

**這不代表 DP 的方向錯**，而是缺了 mozc 那種「詞成本＋接續成本」的
完整模型，見下方第六點。DP 的實作已撤。

### 四、測資的兩個盲點

**盲點一：注音段太短。** 前十組的注音段有 **93.3% 只有 1～2 個音節**
——混合語言輸入天然把中文切碎，那種長度沒有分詞歧異，量不出選詞
演算法的差別。補了 `bopomofo_sentences`（50 句純中文，7～15 音節）。

**盲點二：只稽核注音。** `check_testdata` 原本只查注音段，日文與英文
完全沒查。擴充成三種語言：

| 語言 | 查什麼 |
|---|---|
| 注音 | 逐音節問詞庫「這個音有哪些字」 |
| 日文 | 按鍵是否合法羅馬字；期望裡的假名片段要依序出現在轉出的假名裡；整段假名要完全相同；漢字詞的讀音（mozc 反查，多讀音全部對不上才算錯）要出現 |
| 英文 | passthrough，文字要跟按鍵一模一樣 |

日文**不能嚴格比對漢字**——讀音是多對多，mozc 只收辭書形，硬比會
製造大量假警報。

工具做過**負向對照**：故意注入三種錯（非法按鍵、假名對不上、英文
文字與按鍵不符）都抓得到，所以「0 列」是有意義的 0。

累計修掉的測資錯誤：47 列（`e93` 是 ㄍㄞˇ 不是「修」那批）＋ 1 列
（`minnani` 違反「撥音一律打 nn」的規格）。

**產生新測資一律程式產生按鍵**——從詞庫的詞層讀音推導，多音字要標註
否則產生器直接報錯。50 句裡有 16 句因此被擋下來過。

### 五、寬容-列舉補上了，剩下的才是引擎的鍋

`期望基準審核.md` §0 定義了四種標記，但**寬容-列舉在這個分支的計分器
從來沒實作**，全部測資出現 0 次。

後果是同一份測資對同一個詞有兩種期望：

```text
trilingual:33   gannbatte  →  期望 gannbatte    （羅馬字）
trilingual:54   gannbatte  →  期望 頑張って      （漢字）
```

`sushi` 判成英文原樣送出、或判成日文寫作 `すし`，兩者都對。實作之後
標記 14 列，日文錯字率 16.0% → **9.4%**，引擎一行沒改。

剩下 3 列**故意留著失敗**：`anime`／`karaoke` 是外來語，正確寫法是
片假名（`アニメ`／`カラオケ`），而引擎預設給平假名。那是真缺陷，
標成通過等於把它藏起來。

### 六、日文的下一步是接續成本，不是另一張詞頻表

`すし` 的第一候選是「酸し」不是「寿司」。單看詞成本，**「酸し」(4451)
反而比「寿司」(4520) 便宜**，所以另做一張日文詞頻表救不了。

真正的差距在 mozc 的**接續成本矩陣**（`connection_single_column.txt`，
2672×2672，`表[前詞右id][後詞左id]`）：

```text
BOS → 名詞(1851)        1066
BOS → 文語形容詞(2391)  5748    ← 「酸し」是文語形容詞
```

句首接名詞 1066、接文語形容詞 5748，差 4682，遠大於兩詞本身 69 的
差距。實測 8 個單詞案例：只看詞成本 6/8，加上接續成本 **8/8**，
而且修好了 `すし→寿司`、`さくら→桜`，一個都沒弄壞。

**單詞轉換只需要矩陣的兩條線**——`BOS→各id` 與 `各id→EOS`，共 5344
個數字（約 21KB）；整句 Viterbi 才需要完整的 714 萬格（14～28MB）。
以常駐記憶體現況 222MB／目標 50MB 來說，這個差別決定第二步值不值得做。

#### 實作之後（2026-09-01 當天完成）

接上兩條線之後日文錯字率 9.4% → **8.1%**，整體 632 → **640/720（89%）**。
三個實作上的坑：

**一、信心門檻要有，但實作方式決定生死。** 整段查詞典對「詞」有效，
對「詞組」會出事——`どうしよう` 是「どう＋しよう」兩個詞，詞典沒有
這個條目，但「同仕様」剛好有。那種假命中的總成本明顯偏高（8447，
正確的單詞轉換都在 4588～5740），拿總成本當門檻擋得掉，值 12 句。

但**第一版的實作把延遲從 14.0ms 打到 24.4ms**：原本想「沒通過門檻的
就把假名塞進候選第一名」，而 74.6 萬個讀音有 **98% 沒通過**——等於為
73 萬筆各配一個字串。反過來做（通過的 1.5 萬筆另存一張小表）之後
p99 回到 12.9ms。

門檻嚴到只有 2% 過得了，那正是意圖：**只有夠常用的詞才敢不問使用者
就寫成漢字**。

**二、`words_for_kana()` 會 clone 整份候選清單。** 選詞層每一鍵要對
幾百個候選跑一次 `compose`，用它取第一名會讓 p99 衝到 26.9ms。加了
`best_kana_word()` 只借用不複製。

**三、平假名該贏的時候會自己贏。** `ありがとう`、`おはよう` 查出來的
第一名就是平假名——A6 裡「おはよう 為平假名優先」那條例外**不必另外
維護偏好表**，接續成本模型自然給出正確答案。

同時把 171 列測資的日文期望重新定基準（使用者裁決「以日常使用為準，
大部分時候以漢字為主，平假名作為可選」）。那些列原本記錄的是引擎
當時的行為（`でんわ`），不是正確的日文（`電話`）。33 種相異轉換逐一
檢視過，全部是標準寫法，外來語一律片假名（`アニメ`／`ソフト`／
`ファイル`／`コーヒー`）。
