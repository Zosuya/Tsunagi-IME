# 二進位詞庫改版面的部署缺口：舊 .bin 照包，安裝版就沒有日文詞典

> **狀態**：Mac 的 `build-app.sh` 自動重產 2026-09-27 使用者 Mac 實機驗過；只剩 GitHub CI 沒實跑。程式與 Windows 端的腳本實測過（分支 `trial/deploy`）：
> `build-ime.ps1`、完整跑一次 `build-installer.ps1` 產出安裝程式、
> `release.yml` 新加的那段抽出來在本機跑。**沒測到的**：macOS 兩支腳本
> （這台沒有 Mac，只做 `bash -n` 與把那一段抽到 Git Bash 跑）、`release.yml`
> 沒在 GitHub 上跑過、產出的安裝程式沒有真的裝起來打字（要提權）。

B 群（[[漏斗 1335 之後：六群失敗的診斷與 spike]]）為了保留「同表記不同詞性」，
把 `dict_bin.rs` 的 `VERSION` 從 2 跳到 3——建檔以來第一次跳。程式從此拒收
舊的 `dict_ja.bin`，而**沒有任何一道關卡會提醒「該重產了」**。

## 缺口：兩種下場，都不會報錯

`KanaDict::new` 認不得檔頭 → `load_japanese` 退回 `build_kana_layout`
從文字詞典重建：

| 在哪裡 | 手上有文字詞典嗎 | 下場 |
|---|---|---|
| 開發機 | 有 | 每個行程多花約 1.1 秒重建（反方實測 1127ms），版面改放在各行程私有的 heap、不再共用映射。**症狀只是「變慢」** |
| 安裝版 | **沒有**（只帶 `.bin`） | 重建也失敗 → **日文詞典整個消失**，查詞全空，沒有任何訊息 |

後者上一輪的反方已經模擬重現（只放 v2 的 `.bin`：`load_japanese` 回 `None`；
換成重產的 v3：0ms 載入）。

**四條路沒有一條會重產**：

| 路徑 | 原本的關卡 | 為什麼擋不住 |
|---|---|---|
| `installer/build-installer.ps1` | `Test-Path` | 檔在就過 |
| `platform/macos/build-release.sh` | 「缺的才產」 | 檔在就不產 |
| `.github/workflows/release.yml` | 快取 key 只看 `download.ps1` | 命中就連產生器都不跑，快取裡是舊的 `.bin` |
| `build-ime.ps1`／`build-app.sh` | 不碰詞庫 | 開發機永遠是舊的，只是變慢 |

`release.yml` 的註解寫著「產出的二進位詞庫只跟原始檔有關」——**版面號碼一跳，
這個前提就不成立了**，它也跟程式有關。

還有一個小洞：`build_kana_layout` 讀 `id.def` 用的是 `if let Ok`，讀不到就
默默當成「沒有詞類會活用」。執行期這樣退是對的（總比沒有好），但
`gen_dict_ja` 產的是**要被包出去**的檔——少了詞性、檔頭卻是對的，之後沒有
任何關卡看得出來。

## 修法

**判準放在 core，跟執行期認檔同一套**，腳本只問、不自己讀檔頭：

- `dict_bin::is_current`、`dict_bin_zh::is_current`、`dict::connection_is_current`。
  前兩個跟 `KanaDict::new`／`ZhDict::new` 共用同一支解析（`IndexRef` 為此加了
  生命週期參數，借來的 bytes 也能驗）；接續矩陣的格式從 `gen_connection` 搬進
  core（`encode_connection`），產檔與載入只看同一組常數
- **不只比檔頭**：各區塊塞不塞得進檔案也驗。截斷的檔檔頭完全正確，只看檔頭會
  被當成「最新」，包出去一樣認不得
- 三支產生器加兩個旗標（`core/src/bin/common/gen_flags.rs`）：
  `--if-stale` 認得就跳過（`gen_dict_ja` 33ms）、認不得或不存在才重產；
  `--check` 只檢查，不是這一版的版面回 1。認不得的參數直接結束（打錯字默默
  照「一律重產」跑，比失敗更難發現）
- `gen_dict_ja` 產檔前檢查原料（`dict::missing_kana_sources`）：缺 `id.def`、
  `connection_single_column.txt` 或十份詞典任一份就失敗
- 腳本：

| 腳本 | 做什麼 | 失敗時 |
|---|---|---|
| `build-ime.ps1` | DLL 建完跑三支 `--if-stale`；沒下載過詞庫（沒有 `data/japanese`）時日文兩支跳過並提示 | 回非零，講明「DLL 已建好、詞庫沒跟上」 |
| `build-app.sh` | 同上，接在編譯之後 | `pipefail` 讓整支停下 |
| `build-installer.ps1` | 新的第 2 步：`--if-stale` 再 `--check`，`-SkipBuild` 也照跑 | `Fail` |
| `build-release.sh` | 取代「缺的才產」：`--if-stale` 再 `--check` | `exit 1` |
| `release.yml` | 兩個 job 還原快取後一律 `--if-stale` | pwsh 那段每支都檢查結束碼（run 區塊只看最後一行） |

`release.yml` 選「一律跑 `--if-stale`」而不是「把程式版本塞進快取 key」：
key 要列哪些原始碼檔，改版面的人不會記得來改那裡；`--if-stale` 問的就是
程式自己。

**規則**：改了建表邏輯（格式沒變、內容變了也算）就要把 `VERSION` 加一——
上面所有關卡只比這個號碼。`dict_bin.rs` 的 `MAGIC` 註解原本寫「改版面就換
尾巴那兩碼」，跟這次實際的做法（動 `VERSION`）對不上，已經改成講清楚分工。

## 踩坑：Windows 上「映射中寫不進去」要看檔案系統

自動重產的前提是「輸入法用著也寫得進去」。而輸入法用著的時候，**每個宿主
行程都映射著詞庫**——連認不得的舊版面也是（`map_file` 映射完才驗檔頭，驗不過
的那份映射照樣留到行程結束）。

`write_data_file` 原本是「寫暫存檔 → `remove_file(舊)`（失敗吞掉）→ `rename`」，
註解說 Windows 的 `rename` 遇到目標存在會失敗。預期它在映射中會壞，實測
（Win11 25H2、Rust 1.97.1，另一個行程用 `map_file` 映射著目標）：

| 目標所在 | 舊版 `write_data_file` | 新版 |
|---|---|---|
| NTFS（C:、D:） | ✅ | ✅（直接蓋過去） |
| exFAT（F:） | ❌ 存取被拒（os error 5），`.tmp` 還留著 | ✅（舊檔改名讓開） |
| 網路路徑 `\\localhost\D$`（SMB） | ❌ 存取被拒 | ✅ |

**NTFS 上根本沒壞**。同一個被映射的檔，換不同的 API 結果不同：

| 操作（NTFS，目標被映射） | 結果 |
|---|---|
| Rust `std::fs::rename` 蓋過去 | ✅ |
| Rust `std::fs::remove_file` | ✅ |
| .NET `File.Delete`（`DeleteFileW`） | ✅ |
| .NET `File.Move(…, overwrite)`（`MoveFileExW` + `REPLACE_EXISTING`） | ❌ 存取被拒 |
| `SetFileInformationByHandle` 舊式刪除（`FileDispositionInfo`） | ❌ 5 |
| 舊式改名、蓋過去（`FileRenameInfo`、`ReplaceIfExists`） | ❌ 5 |
| 舊式改名、讓開（不蓋） | ✅ |
| 讓開後刪那個舊檔：還在映射／映射結束後 | ❌ 5／✅ |

分界是 **POSIX 語意**：std 的 `rename`／`remove_file` 與 Win11 的 `DeleteFileW`
都用它，被映射的檔照刪照蓋；舊式語意（`MoveFileExW`、明講舊式的呼叫）**不准刪、
也不准蓋掉被映射的檔，但准改名**。exFAT 與 SMB 不支援 POSIX 語意，std 只能退回
舊式——所以才壞。

**所以症狀是「看檔案系統」，不是「Windows 一律不行」**：開發機的 repo 在 NTFS
上，原本的寫法一直是好的；repo 放在外接碟（exFAT）或網路磁碟上才會踩到。
[[spike：升級安裝時檔案被鎖住]] 那張表的「刪掉改名後的殘骸 ✅ 可以立刻刪」也是
同一件事——那次用 .NET 量，走的是 `DeleteFileW` 的 POSIX 語意。

修法（只動 Windows，POSIX 平台維持直接 `rename`）：

1. 先照常 `rename` 蓋過去——NTFS 走這條，原子、沒有「檔案不在」的空窗
2. 被拒才把舊檔改名成 `<名字>.old-<序號>` 讓出路徑，再放新檔；新檔放不進去就
   把舊的放回去。**序號不能固定**：上一輪讓開的還被映射著時同名改名會失敗
   （`build-ime.ps1` 對付 DLL 時踩過同一個坑）
3. 成功後盡力清掉以前讓開、已經沒人映射的 `.old`（刪不掉留到下次）
4. 失敗時不留 `.tmp`

清 `.old` 那步第一版漏了一個：只給檔名的相對路徑，`parent()` 是空字串，
`read_dir("")` 會失敗——實測才發現。

## 驗證

測試（**每一條都真的把修正還原跑過，會紅**）：

| 測試 | 還原什麼會紅 |
|---|---|
| `dict_bin`／`dict_bin_zh` 的 `目前版面才算最新_跟執行期同一套` | 拿掉 `VERSION` 的比對 |
| `接續矩陣_產出來的自己認得_舊的認不得` | 拿掉接續矩陣的版本比對 |
| `日文原料缺哪份要點名` | 原料清單拿掉 `id.def` |
| `資料檔狀態_不存在_舊的_目前的` | （三種狀態的分流） |
| `映射中的資料檔也換得掉`（`#[cfg(windows)]`） | 還原成舊版寫法：紅在網路路徑那半；拿掉清 `.old`：也紅 |

最後一條走兩條路：本機的暫存資料夾（NTFS），加上**同一個資料夾的
`\\localhost\C$\…` 回送路徑**——SMB 沒有 POSIX 語意，跟 exFAT 同一種，不必
接隨身碟就重現得出舊版的失敗。拿不到系統管理共用時只測本機那半，會印出來。

腳本（worktree，Windows）：

- `build-ime.ps1`：另一個行程映射著舊的 v2 `dict_ja.bin` 時跑——建完 DLL、
  重產成 v3、exit 0（「舊映射看到的位元組不變」由上面那條測試與 exFAT／SMB
  的探針驗過）；再跑一次三份都「已是最新」，
  整支 **1.2 秒**；舊版面＋拿掉 `id.def`：停在 `gen_dict_ja`、exit 1、舊檔原封不動
- `build-installer.ps1`：放回 v2 完整跑一次——建置 43.7 秒、第 2 步重產成 v3
  （42,661,280 bytes）、三份 `--check` 通過、ISCC 產出 26.7MB，exit 0
- `build-release.sh`：用假的 cargo（`--if-stale` 什麼都不做）確認 `--check` 會
  擋下舊版面
- 漏斗逐句 0 差異（`dict_ja.bin` 換成產生器產的 v3，跟從文字重建是同一支
  `build_kana_layout`）

## 刻意沒做的

- **`--if-stale` 只比版面號碼，不比原料內容**。原料更新走 `download.ps1`，那支
  本來就一律重產（沒帶旗標）；改建表邏輯卻忘了加 `VERSION` 的話仍然抓不到——
  這條只能靠 `VERSION` 註解裡的規則
- **`gen_pack_bin` 沒加旗標**：官方擴充包的 `.bin` 不進安裝程式
- **`release.yml` 的快取可能蓋掉進版控的檔**：快取的 `path` 是整個
  `data/bopomofo`，裡面有進版控的 `dict_zh.bin`、`priority.txt`……還原快取是
  解 tar，預期會蓋過 checkout 下來的版本（**推斷，沒在 GitHub 上驗**）。那樣的話
  版面號碼一樣、內容較舊的 `dict_zh.bin` 會被包出去，`--if-stale` 看不出來。
  這次沒動，待裁決（例如還原後 `git checkout -- data`）
