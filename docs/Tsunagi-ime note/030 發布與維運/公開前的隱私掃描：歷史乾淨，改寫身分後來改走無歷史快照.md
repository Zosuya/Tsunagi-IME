# 公開前的隱私掃描：歷史乾淨，改寫身分後來改走無歷史快照

> **後來的變化（2026-09-04）**：§2.36.3 的「用 `git filter-repo` 改寫全部
> commit 身分、維持單一 repo」**沒有執行，被取代了**。使用者改選
> §2.36.4 結尾就列著的保守路線——**開發歷史留在原本的 repo，公開那邊只放
> 一份沒有歷史的快照**，不改寫歷史、不改 hash。做法是
> `tools/publish-snapshot.ps1`（macOS 版 `publish-snapshot.sh`，2026-09-09）：
> 匯出追蹤中的檔案、拿掉不公開的（`CLAUDE.md`、開發文件、兩份相容性測試清單、
> 發布腳本自己、設計原始檔）、檢查死連結與舊身分字串、以發布帳號建**接在
> 公開 repo 最後一個 commit 之上**的單一 commit，最後印出 push 指令由使用者自己推。
> 建議只在發版時同步一次。
>
> **仍然有效的**：§2.36.1 的掃描結果與 §2.36.2 的重跑指令；§2.36.3.1 裡
> 「committer 那欄容易漏」「檔案內容裡的舊字串也要清」「憑證要用
> `useHttpPath` 按 repo 路徑分開」三條教訓都已寫進快照腳本（憑證那條 macOS 的
> osxkeychain 實測踩了同一個坑，commit `a6fbc2c`）。**§2.36.3.1 的改寫手冊
> 本身不必再做**。發布流程另見 [[macOS 的建置與發布流程]] §七。
>
> **原狀態**：改寫歷史的操作手冊已完整演練並還原，發布時再重做一次

**起因**：擔心 commit 歷史裡有本機的私人資訊，考慮把開發與發布分成兩個
repo。掃過之後結論是**不必分**——要防的東西這裡不存在。

### 2.36.1 掃描結果

| 項目 | 結果 |
|---|---|
| 絕對路徑（使用者目錄、專案磁碟機） | **從來沒有進過任何 commit** |
| 電腦名稱 | 沒有 |
| 現存檔案裡的個人路徑 | 零 |
| 測資內容 | 為測試設計的組合句，不是日常輸入紀錄 |

專案本來就在這件事上寫得小心：`.iss` 用 `{#Root}` 相對路徑、腳本用
`$PSScriptRoot` 與 `$PWD`。CLAUDE.md 的「不要寫死絕對路徑」一直有被遵守
——那條原本是為了跨電腦開發，順便擋掉了這個問題。

### 2.36.2 怎麼重跑

```powershell
# 作者資訊
git log --format='%an <%ae>' | Sort-Object -Unique

# 歷史裡有沒有引入過使用者路徑
git log -p --all -S 'C:\Users' --oneline

# 現存檔案
Select-String -Path *.md,*.ps1,*.rs,*.iss -Pattern 'C:\\Users|AppData'
```

**`git log -S` 才是重點**——它搜的是「哪個 commit 增刪過這段字串」。
現在的檔案乾淨不代表歷史乾淨，而歷史是刪不掉的。

### 2.36.3 決定：把歷史的作者統一成發布帳號（2026-09-03）

真正的動機不是「歷史髒」，是**身分分離**——開發用的是私人帳號，發布要用
另一個公開的創作帳號。這比原本設想的需求硬得多：

**光是轉移 repo 擁有者不夠。** commit 歷史裡每一筆的 author email 就是
GitHub 用來比對帳號的鍵——repo 搬過去了，那幾百筆還是會顯示私人帳號的
頭像與連結。

決定：**用 `git filter-repo` 把全部 commit 的 author 與 committer 改成
發布帳號**，之後也用那個身分開發，維持單一 repo。

- 所有 commit hash 會變。現在還沒有人 clone 或 fork，代價是零
- **公開之後就做不了**——別人已經 clone、fork，或在 issue 裡引用了 hash
- AI 協作的那幾十筆（author 是 Claude）一併統一
- git 設定只設 local，不動 global：其他專案仍用原本的身分

同時清掉**歷史檔案內容**裡出現過的舊 email 與舊帳號名——只改 author 而
留著文件裡的字串等於白做。這一節原本就寫了那個地址，是自己製造的漏洞。

### 2.36.3.1 操作手冊（2026-09-03 完整演練過並還原）

**整套走過一遍了**，指令都是驗證過的。演練後還原回舊身分繼續開發，
發布時照這個順序重做一次。

#### 步驟 0：備份（不可省）

```powershell
git bundle create doc/backup/before-rewrite-<日期>.bundle --all
git bundle verify doc/backup/before-rewrite-<日期>.bundle
```

`doc/backup/` 已在 `.gitignore`。**那個 bundle 絕對不能進版控**——它含著
改寫前的完整歷史，推上去等於前功盡棄。

還原方式（演練後就是這樣退回來的）：

```powershell
git fetch <bundle> master:restored --force
git reset --hard restored
git branch -D restored
```

> `git fetch` 不能直接寫進正在 checkout 的分支，所以要繞一個暫時的 ref。

#### 步驟 1：準備兩個設定檔

**mailmap**（改 author／committer）。格式是
`新名字 <新email> <舊email>`，每個舊 email 一行：

```text
發布帳號 <發布email> <舊的私人 email>
發布帳號 <發布email> <noreply@anthropic.com>
```

**replacements**（清檔案內容裡的字串）。**長的規則放前面**，否則短的會
先吃掉長的前半：

```text
舊email==>新email
舊帳號名==>發布帳號名
舊帳號名小寫==>去識別化的替代字
```

舊 email 與舊帳號名用 `git log --format='%an <%ae>' | sort -u` 查，
**不要寫進文件裡**——那正是上次製造漏洞的方式。

#### 步驟 2：改寫

```powershell
git filter-repo --mailmap <mailmap> --replace-text <replacements> --force
```

要順便從歷史移除誤入版控的檔案，加 `--invert-paths --path <檔案>`
（這次就順手清掉了兩個合併時的暫存檔）。

`--force` 是因為這個 repo 有 remote；filter-repo 的防呆機制會擋。
**它跑完會自動移除 `origin`**，那是刻意的——防止你把改寫後的歷史推回
原本的地方。

#### 步驟 3：驗證（四項都要過）

```powershell
git log --format='%an <%ae>' | Sort-Object -Unique     # 只剩發布帳號
git log --format='%cn <%ce>' | Sort-Object -Unique     # committer 也要換掉
git log --all -S '<舊字串>' --oneline                   # 每個都要 0 筆
git log --all --oneline -- <被移除的檔案>               # 0 筆
```

**committer 那欄容易漏**——只看 author 會以為好了。

#### 步驟 4：新身分與 remote

```powershell
git config user.name  "<發布帳號>"      # 不加 --global
git config user.email "<發布email>"
git remote add origin https://<發布帳號>@github.com/<發布帳號>/<repo>.git
```

網址裡帶帳號名是為了下一步。

#### 步驟 5：憑證要分開（這次卡最久的地方）

Windows 的 Git Credential Manager **預設把憑證存成「一個 host 一把鑰匙」**，
只看主機名。所以不管網址寫誰，它查到舊帳號那把就直接用——push 回
「Repository not found」（private repo 用錯身分時 GitHub 回 404，不是 403，
避免洩漏 repo 是否存在），而且**連問都不問**。

```powershell
git config credential.https://github.com.useHttpPath true
git config credential.guiPrompt true
git config credential.gitHubAuthModes browser
```

`useHttpPath` 改成「每個 repo 路徑各存一把」，於是新 repo 查不到快取、
會重新問，後兩條讓它走瀏覽器授權而不是在終端機問密碼。

> **GitHub 從 2021 年起不收密碼**，終端機問的 password 欄位要填 Personal
> Access Token。走瀏覽器授權可以完全避開這件事。

診斷用：

```powershell
git-credential-manager github list                     # 存了哪些帳號
printf 'protocol=https\nhost=github.com\n\n' | git credential fill   # 現在會拿到誰
```

#### 步驟 6：推上去，然後處理舊 repo

```powershell
git push -u origin master
```

推完**點開任一個 commit 看頭像與作者連結**——那才是真正的驗收，本機的
`git log` 顯示對不代表 GitHub 認得。

**舊 repo 裡還是改寫前的歷史**，那才是舊身分真正存在的地方。改名不會清掉
它，要設成 private 或直接刪除。

### 2.36.4 為什麼還是單一 repo

> **後來的變化**：最後走的正是本節結尾那條「有需要再壓一份乾淨的出去」——
> 開發 repo 照舊，公開 repo 只收快照（見開頭引言框）。issue 與程式碼分兩邊
> 的對照成本因此是真的要付的，腳本註解建議只在發版時同步。

分開的長期成本是真的：issue 在公開那邊、程式碼在私有這邊，每次回報都要
對照；外部 PR 要手動搬；版本對不上時很難查。

而它要防的東西這裡不存在。真正需要分的情況通常是「歷史裡有金鑰或私人
資料」或「有不能公開的內部工具」，兩者都沒有。

**如果動機是「不想讓人看到亂七八糟的過程」——開源專案的開發歷史雜是
常態**，寫得清楚的 commit 訊息反而顯示專案真的在被維護。

先不分。反向操作（先分了想合併）比較麻煩，所以保守的順序是先合著、
有需要再壓一份乾淨的出去。
